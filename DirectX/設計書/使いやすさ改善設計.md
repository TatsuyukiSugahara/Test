## 0. 調査で分かった「当初想定との差」

2026-09-14 の実測([使いやすさ課題.md](使いやすさ課題.md) §1-1 に反映済み)で、
作業量の見積りが 2 方向に動いた。

**安くなった点:**

- `Game/Assets/Shader/` に **AquaDash 固有シェーダは 0 本**。41 本の `.fx` は全部エンジン資産か
  旧世代の残置(`shader_entries.txt` 自身が `# [未参照]` と明記)。**取捨選択が要らず、
  フォルダごと移せる。**
- エンジンが実行時に要求する実体は **44 個、うち 43 個がシェーダ**。残り 1 個は `SkyCube.dds`。
  「アセット分離」の実質は**シェーダ 1 種類の移設**。
- コンテンツルート配下に `aqEngine/` を置く**前例が UWP に既にある**
  ([GameUWP.vcxproj:155-159](../Game/GameUWP.vcxproj#L155-L159) が `install/aqEngine/Graphics/MaterialDef.h` を同梱)。
- 現行のパス解決規則の「その他 → `<root>/<path>`」分岐に `"aqEngine/Assets/..."` が**そのまま乗る**。
  リゾルバに新しい規則を足す必要がない(§1.1)。

**高くなった点:**

- 課題メモが挙げていない依存先が 2 つあった。
  シェーダのクロスコンパイル基盤([compile_spv.cmake](../Tools/ShaderCompile/compile_spv.cmake) /

## 1. 方式決定

### 1.1 コンテンツルート配下を 2 系統にする(新しい規則は足さない)

```
<コンテンツルート>/
  ├─ aqEngine/Assets/     ← エンジン所有。ゲーム作者は触らない
  │    ├─ Shader/         ← .fx / *CB.h / shader_entries.txt / spv/ msl/ msl-ios/
  │    └─ Sky/            ← 既定キューブマップ
  └─ Game/Assets/         ← ゲーム所有(現状のまま)
```

エンジン側のコードは `"aqEngine/Assets/Shader/Model.fx"` と書く。

**新しいプレフィクス規則を導入しないのが要点。** 現行の解決規則は 2 分岐で、

| 入力 | 解決先 |
| --- | --- |
| `Assets/...` | `<root>/<ゲームルート名>/Assets/...`(既定 `Game`。P3-A で可変化) |
| それ以外 | `<root>/...` |

後者の分岐が `"aqEngine/Assets/..."` をそのまま `<root>/aqEngine/Assets/...` に組む。
**リゾルバの規則は 1 行も増えない。** 実装の根拠は
[AssetPath.cpp:177-185](../aqEngine/Resource/AssetPath.cpp#L177-L185)。

当初は `Game/Assets/...` 専用の分岐を含む 3 分岐だったが、その分岐は `<root>/<path>` を組む
「それ以外」分岐と結果がまったく同じだったため、P3-A で削除した(挙動は不変)。

採らなかった案:

| 案 | 却下理由 |
| --- | --- |
| `"EngineAssets/..."` という新プレフィクス | 覚える規則が 1 つ増える。§1-2 の「学生が読んで分かる」に逆行する |
| 仮想マウント(`engine://` / `game://`) | 対象が 44 ファイルしかない規模に対して過剰。全プラットフォームの IO 経路に手が入る |
| エンジンアセットをビルド時に `Game/Assets/` へコピー | ゲーム作者の資産とエンジンの資産が同じ場所で混ざり、**どれを触っていいか分からない**という §1-1 の症状が残る |

### 1.2 パス解決を 1 モジュールへ集約する

新規 `aqEngine/Resource/AssetPath.{h,cpp}` に 12 個の重複実装を畳む。

```cpp
// 名前空間はネスト形式(規約)。実物は aqEngine/Resource/AssetPath.h が正。
namespace aq { namespace res {

    // コンテンツ基点。Engine::GetContentRoot() を最優先で見て、
    // 返らなければ CWD から親へ番兵ディレクトリを探す。
    const std::string& FindContentRoot();

    // 入力 1 つに対する探索候補を全部組む(拡張子の大小バリアントを含む)。
    void BuildAssetPathCandidates(const std::string& path, std::vector<std::string>& candidates);

    // 最初に実在した候補を返す。無ければ入力をそのまま返し、候補一覧をログへ出す。
    std::string ResolveExistingAssetPath(const std::string& path);

    // シェーダ用(5 バックエンドの ResolveShaderPath の置き換え先)。
    // 引数が const char* なのは各バックエンドの既存シグネチャに合わせたため。
    // 全滅時の戻り値が「/ へ正規化した入力」になる点だけ上と違う。
    std::string ResolveShaderPath(const char* filePath);

    // 候補を自前で回す呼び出し側(OpenBinaryReadWithFallback 等)が
    // 全滅したときに呼ぶ診断ログ。
    void LogUnresolvedAssetPath(const std::string& path);

} }
```

守るべき制約が 3 つある。

1. **`.mm` から include できるヘッダにする。** `aq.h` を include してはいけない。
   非 Windows の DirectXTex がスタブ `basetsd.h` 経由で `BOOL` を再定義し、Cocoa の
   `typedef bool BOOL` と衝突して `@interface` が全滅する
   ([Mac移植設計.md](Mac移植設計.md) §6 の `aq.h` の行)。
   依存は `<string>` / `<vector>` と `Engine::GetContentRoot()` の前方宣言に留める。
2. **スレッドセーフな遅延初期化。** ワーカースレッドから並列に呼ばれる
   ([07_リソース管理設計.md](07_リソース管理設計.md) §5)。C++11 のマジックスタティック
   (`static const` + ラムダ)で組む。現行 6 個のうち `Resource.cpp` と `D3D11Shader.cpp` の
   2 個は `if (empty())` 方式でレースがあり、これも同時に直る。
3. **`ScopedPersistentAlloc` で囲む。** 関数ローカル static の確保は終了時のリーク報告に乗るため、
   `ScopedPersistentAlloc` で囲んで報告対象から外す。現行実装 4 個が既にそうしている。

**同時に直る既存バグ**: [D3D11Shader.cpp:21](../aqEngine/Graphics/D3D11/D3D11Shader.cpp#L21) の
`FindProjectRoot` だけが `Engine::GetContentRoot()` を見ておらず、パッケージ配置では
D3D11 経路がシェーダを見つけられない(現状 Windows デスクトップ専用なので表面化していない)。

**探索順を 1 本に統一する(意図した挙動変更)。** 現行は 2 系統に分かれている:

| 系統 | 探索順 |
| --- | --- |
| `Resource.cpp`(リソース / JSON / 画像) | 入力そのまま → 基点からの解決 → 拡張子の大小バリアント |
| シェーダ 4 本(D3D12 / Vulkan / Metal x2) | **基点からの解決のみ** → 全滅なら正規化した入力を返す |

統一先は前者。後者は「入力そのままの候補を先に試していない」ので、統一すると順序が変わる。
標準の作業ディレクトリ(`Game/`)では入力 `"Assets/Shader/X.fx"` は
`Game/Assets/Shader/X.fx` に解決され、基点からの `<root>/Game/Assets/Shader/X.fx` と
**同じ実ファイルを指す**ため実害はない、という判断で統一する。
パッケージ配置では `GetContentRoot()` が基点を返し CWD 相対の候補は実在しないので、
こちらも結果は変わらない。

`D3D11Shader.cpp` だけは拡張子の大小バリアントを持っていなかったので、こちらは純粋な上位互換
(先の候補が実在する限り到達しない)。

### 1.3 番兵ディレクトリを `aqEngine/Assets` に変える

現行 6 個すべてが `<dir>/Game/Assets` の存在でコンテンツルートを判定している。
これを `<dir>/aqEngine/Assets` に変える。

理由: **ゲーム側 `Assets/` が空でも成立させたい。** 最小サンプル(P3)は
アセットを 1 個も持たない構成になるため、`Game/Assets` を番兵にすると
サンプルがコンテンツルートを見つけられない。エンジンアセットは必ず存在する。

### 1.4 エンジン既定値は「注入可能 + 既定はエンジン所有」に揃える

[HardShadowRenderer.h](../aqEngine/Rendering/Shadow/HardShadowRenderer.h) の
`Create(settings, const char* shadowVSPath)` が既に注入型で、これが先行事例。
同じ形へ揃える対象:

| 対象 | 現在 | 変更後 |
| --- | --- | --- |
| `ShadowDepth.fx` | ゲームが `"Assets/Shader/ShadowDepth.fx"` を渡す | 既定引数 `"aqEngine/Assets/Shader/ShadowDepth.fx"` |
| `SkyCube.dds` | `SkyRenderer::Create()` が `"Assets/Sky/SkyCube.dds"` を直書き | `Create(const char* cubemapPath = "aqEngine/Assets/Sky/DefaultSkyCube.dds")` |
| 白テクスチャ / UI フォント | エンジン既定が無く、ゲームが先読み([GameFlow.cpp:466-481](../Game/Application/GameFlow.cpp#L466-L481)) | **P3 で入れないと決定**(最小サンプルは UI を出さない。課題メモ §1-1b は持ち越し。§6) |

31 本のシェーダは注入可能にしない。差し替える理由が無く、引数が 31 個増えるだけになる。

##### P4-B の確認中に見つかった既存バグ: シェーダのソースバッファがスレッド間で共有されていた

**症状**: D3D11 構成でステージへ入ると `シェーダーコンパイルエラー` のアサートが 3 つ出る
(`TerrainPBRGBuffer.fx` PS / `SkeletalModelLit.fx` VS・PS)。エラー本文は
`error X3000: Illegal character in shader file` や `error X3018: invalid subscript 'gbuffer'` で、
**そのシェーダには存在しない記述**を指している。

**原因**: `Shader::Load` がソースを `static char shaderBuffer[5 * 1024 * 1024]` へ読んでいた。
シェーダのロードはワーカースレッドから並列に走るので、A がコンパイル中に B が同じバッファへ
別のソースを読み込み、**A のソースが途中から B のものに化ける**。エラーが
「識別子の頭が欠ける」形(`layer0` → `ayer0`)になるのはそのため。

**P4-B の変更由来ではない**。HEAD(CWD 差し替え版)に戻して同じ並列プローブを走らせても
同じ壊れ方をすることを確認した。D3D12 側は読み込み先が呼び出しごとなのでこの穴は無い。

**切り分けで効いた手**: 4 スレッドから include を含むシェーダを同時にロードするプローブを
起動時に仮組みする。ただし **全スレッドに同じ順で同じシェーダを読ませても再現しない**
(踏み合っても中身が同一なので無害)。**スレッドごとに開始位置をずらして別のシェーダを
読ませる**と再現する。

**対処**: 読み込み先を `std::vector<char>` の呼び出しローカルにした。あわせて
エラー本文を `OutputDebugStringA` だけでなく起動ログにも出すようにした(デバッガを
繋いでいないと誰にも見えず、今回の切り分けで最初に詰まった箇所)。失敗時の
`static char text[5 * 1024]` も呼び出しローカルに変えた(同じ理由で混ざる)。

- [x] 並列プローブ(4 スレッド x 8 本 x 3 周)で FAIL=0。4 回連続で 0
- [x] ステージが描画される(**目視で確認**。D3D11 / 271 FPS / `COMPILE FAIL` 0 件 / 終了コード 0)
