# 設計 → 実装 → 評価 サイクル

AI 駆動開発の基本サイクル。まとまった機能は必ずこの 3 フェーズで進める。
1 サイクル = 1 フェーズ(半日〜1日で終わる粒度)に分割し、大きな機能は複数サイクルに割る。

```
┌─▶ ① 設計 ──承認──▶ ② 実装 ──ビルドOK──▶ ③ 評価 ──┐
│   (Fable本体)      (Opusサブエージェント)  (Fable本体) │
│      ▲                                              │
│      └────── 設計に問題が見つかったら差し戻し ──────┘
└──────────────── 次のフェーズへ ──────────────────────┘
```

## モデルの役割分担

| 役割 | 担当 | 方法 |
|---|---|---|
| 設計・判断(案を考える / レビュー / 評価 / コミット) | **Fable(メイン会話)** | 本体で直接行う。サブエージェントに委譲しない |
| 実装(設計済みコードを書く) | **Opus サブエージェント** | Agent ツールで `model: "opus"` を指定して起動 |
| 調査(既存資産の探索・読み取り) | Explore サブエージェント | 独立した調査は複数を**並列**起動してよい |

- 実装モデルは本来 Sonnet が適任(コスト面)。現状は Opus を使い、
  切替の指示があったら `model: "sonnet"` に変えるだけでよい。
- 独立した実装タスク(別ファイル・別サブシステム)は **1 メッセージで複数の
  Agent 呼び出しを並列に**出す。依存があるものは直列にする。

## ① 設計フェーズ(Fable 本体)

1. **既存資産を先に読む。** 関連する `DirectX/設計書/*.md`、ゲーム側設計書
   (`Game/Design/**/*.md`)、および対象の実コード(ヘッダ中心)を確認する。
   推測で設計しない。再利用できる既存機構(Prefab / Level / ThreadPool /
   UIScreen 等)を必ず洗い出す。調査範囲が広い場合は Explore サブエージェントを
   複数並列で出してよい(結論だけ受け取る)。設計判断そのものは本体で行う。
2. **設計書を書く。** 運用規約は `cpp-gamedev` スキルの
   `references/architecture.md` §6 に従う:
   - タイトル直下に `> 対象コミット: <hash> / 最終更新: <日付>`
   - 責務表(クラス/ファイル別)+ 末尾チェックポイント(`- [ ]`)
   - 同じ内容を 2 つの設計書に書かない(一次資料を決めてリンク参照)
   - 置き場所: エンジン機能は `DirectX/設計書/`、ゲーム固有は `Game/Design/<プロジェクト>/`
3. **フェーズ分割を明記する。** 各フェーズに「実装内容 + 評価チェックリスト」を付ける
   (例: `Game/Design/AquaDash/05_実装フェーズ計画.md`)。
4. **ユーザーの承認を得てから実装に入る。** 設計の要点(方式の選択理由・エンジン側変更の
   有無・フェーズ分割)を要約して提示する。

## ② 実装フェーズ(Opus サブエージェントへ委譲)

1. 対象は**現在のフェーズ 1 つだけ**。先のフェーズの実装を先取りしない。
2. **実装は Agent ツール(`model: "opus"`)へ委譲する。** タスク分割の指針:
   - 独立したファイル群・サブシステム単位で分け、**並列**に起動する
     (例: 「走行 System 一式」と「UI 画面一式」は並列可)。
   - **共有ファイル(GameSources.props / *.filters / GameFlow.* /
     Application.cpp 等)は 1 つのエージェントに集約するか本体で編集**し、
     複数エージェントに同じファイルを触らせない(競合防止)。
   - ごく小さな修正(数行のパラメータ調整など)は委譲せず本体で直してよい。
3. **サブエージェントへのプロンプトに必ず含めるもの**:
   - 該当フェーズの設計書パスと「設計書どおりに実装せよ。設計変更は行わず、
     食い違いは報告せよ」という指示
   - 最初に `cpp-gamedev` スキル(規約)を読むこと。新規ファイル追加時は
     `vs-project-files` スキルに従うこと(共有ファイルを担当させる場合のみ)
   - スレッド境界(architecture.md §5)と ECS 遅延コマンド規約の遵守
   - 対象ファイルの明確なリスト(書いてよいファイル / 触ってはいけないファイル)
   - ビルドはエージェント側では行わない(本体が③でまとめて行う)こと
4. **完了後、本体(Fable)が全差分をレビューする。** 規約逸脱・設計との食い違い・
   統合ミスは本体で修正するか、指摘を付けて同じエージェントへ SendMessage で差し戻す。
5. 実装中に設計と食い違いが出たら、勝手に設計を変えず、①へ戻して設計書を
   直してから続ける(小さな命名変更などは実装後に設計書へ反映でよい)。

## ③ 評価フェーズ(Fable 本体)

1. **ビルドを通す。** ビルド方法・落とし穴は memory(`project-d3d12-backend.md` 等)と
   README を参照する。警告の増加も確認する。
2. **実機確認。** 該当フェーズの評価チェックリストを 1 項目ずつ実際に確認する。
   自動で確認できない項目(見た目・操作感)はユーザーに確認ポイントを箇条書きで
   提示し、結果を聞く。
3. **設計書へ反映。** チェックボックスを埋め、実装で変わった点・発見した課題を
   設計書(または README の既知の課題)に追記する。`対象コミット` を更新する。
4. **コミット。** `git-commit` スキルの規約(タグ + 内容)に従う。
   コミット前に改行/BOM の混在に注意(memory: `repo-line-endings-bom.md`)。
5. **memory 更新。** フェーズ完了状態・次のフェーズ・非自明な落とし穴を
   プロジェクト memory に記録する。
6. 全チェックが埋まったら次のフェーズの①へ。埋まらない項目が残る場合は
   その旨をユーザーに報告し、対応方針(修正 / 保留)を確認する。

## 禁止事項

- 設計書なし・承認なしでまとまった機能の実装を始めること。
- 複数フェーズをまとめて 1 コミットにすること。
- 評価チェックリストを実際に確認せずチェックを埋めること。
- 設計・評価・コミットの判断をサブエージェントへ委譲すること(実装と調査のみ委譲可)。
- 複数のサブエージェントに同じファイルを並行編集させること。
