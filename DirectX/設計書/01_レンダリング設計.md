## 0. 設計の全体像

レンダリングは **2 つのレイヤー**に分かれる。

| レイヤー | 名前空間 | フォルダ | 役割 |
|---|---|---|---|
| **グラフィックス抽象 (低レベル)** | `aq::graphics` | `Graphics/` | GPU API(D3D11/D3D12/Vulkan/Metal)を **Bridge パターン**で抽象化。リソース生成・ステート設定・ドローの発行だけを担う。API 固有型を上位に漏らさない。 |
| **レンダリング (高レベル)** | `aq::rendering` | `Rendering/` | 「1 フレームに何を描くか」を組み立てる。`RenderFrame`(スナップショット)→ `RenderPipeline`(パス列)が `RenderCommandList` へ記録 → 専用スレッドで再生。シャドウ/ディファード/空/フォワード/ポストプロセス/オクリュージョン等は**パス**として列に並ぶ。 |

ハイブリッド(DX11/DX12/Vulkan/Metal/Xbox/UWP)の要は **この 2 層の境界**にある。上位の `aq::rendering` は API を一切知らず、切り替えは `Graphics/` 内の実装差し替えだけで済む。

```
[ゲームスレッド]
  ECS(RenderSystem::BuildRenderFrame) → RenderFrame（描画スナップショット）
        │  フラスタムカリング済み
        ▼
  Renderer::BuildCommandList() → RenderPipeline::Build()（パス列を順に記録）
        │                         → RenderCommandList（API 非依存コマンド列）
        │  Submit()
        ▼
[レンダースレッド]  RenderThread
  RenderCommandList::Execute(RenderContext&)
        └─ RenderContext → impl_ : IRenderContextImpl
              ├─ D3D11RenderContextImpl
              ├─ D3D12RenderContextImpl
              ├─ VulkanRenderContextImpl
              └─ MetalRenderContextImpl
```

## 1. グラフィックス抽象レイヤー(`aqEngine/Graphics/`)

### 1.1 Bridge パターンの中核

| ファイル | 責務 |
|---|---|
| `GraphicsDevice.h/.cpp` | **抽象デバイス(シングルトン)**。`Create<TImpl>()` テンプレートでバックエンド実装を注入する。`Initialize`/`Finalize`/`Present`、リソースファクトリ(`CreateVertexBuffer` 等)、オフスクリーン RT 生成(`GetRenderTargetSRVShared` で RT の SRV を非所有 `shared_ptr` として取得可)、`OnSuspend/OnResume`(UWP PLM)、`RecreateSurface`/`GetSurfaceSize`(Android 等のサーフェス差し替え)、`WaitIdle`(提出済み GPU 作業の完了待ち。終了処理や実行時のリソース破棄前に呼ぶ。`AppHost` が使う)、`Begin/EndBatchedTextureUploads` を公開。内部に `IGraphicsDeviceImpl` を 1 つ持ち、全呼び出しを委譲する。上位コードはこのクラスしか触らない。同ヘッダに機能ゲートのフリー関数 `SetComputeSupported/IsComputeSupported`(compute/UAV/GPU 駆動の可否)と `SetBlockCompressionSupported/IsBlockCompressionSupported`(BC テクスチャを直接渡せるか。iOS シミュレータは false → DDS を RGBA8 へ展開。[iOS移植設計](iOS移植設計.md) §4.3)を持つ。 |
| `IGraphicsDeviceImpl.h` | **デバイス実装インターフェース**(Bridge の Implementor)。D3D11/D3D12/Vulkan/Metal の各実装が継承。デバイス/スワップチェーン初期化、リソースファクトリ、`ReadbackOffscreenR32`(GPU→CPU リードバック)、GPU 駆動バッファ生成(`CreateStructuredBuffer`/`CreateRawBuffer`)を宣言。未対応バックエンド用に安全な既定実装(no-op/nullptr/false)を持つ(`OnSuspend`/`RecreateSurface`/`GetSurfaceSize`/`WaitIdle`/`BeginBatchedTextureUploads`/`ReadbackOffscreenR32` 等)。 |
| `RenderContext.h` | **抽象コンテキスト**(コマンド発行の窓口)。`OMSet*`/`RSSet*`/`IASet*`/`VS/PS/CSSet*`/`Draw`/`Dispatch`/`DrawIndexedIndirect`/`DrawIndexedInstanced`/`RSSetScissor*` 等の描画コマンドを、すべて**抽象インターフェース型引数**で受ける。`IRenderContextImpl` に委譲するだけの薄いラッパ。 |
| `IRenderContextImpl.h` | **コンテキスト実装インターフェース**。`DepthMode`/`BlendMode` 列挙もここで定義。GPU 駆動間接描画(`IASetIndexBufferGpu`/`DrawIndexedIndirect`/`UavBarrier`)・インスタンシング(`IASetVertexBufferSlot`/`DrawIndexedInstanced`)・スライス指定シャドウ(`OMSetDepthOnlyTargetSlice`/`ClearDepthMapSlice`)は既定 no-op(スライス系は非スライス版へ委譲)で、対応バックエンドのみ override する。 |
| `RenderContext.cpp` | `ENGINE_GRAPHICS_D3D11` のときだけコンパイルされる D3D11 具象リソース(`SamplerState`/SRV/UAV/RT)の実装。`RenderContext` 本体はヘッダ内インラインのみ。名前と中身が合っていない(命名の澱み。README「既知の課題」への追記は本更新の範囲外) |

**レビュー観点**: `RenderContext` は全メソッドがインラインで `impl_->` に流すだけ。API 追加時は「抽象 IF(no-op 既定)→ 各実装 override」の順で足す規約になっているか(間接描画がこの流儀)。

### 1.3 バックエンド実装(D3D11 / D3D12 / Vulkan / Metal)

4 API が **同じファイル構成で概ね 1:1 に並ぶ**。ビルド構成 `ENGINE_GRAPHICS_D3D11 / _D3D12 / _VULKAN / _METAL`
(MSBuild は `AqGraphicsApi`、CMake は `AQ_GRAPHICS_API`)で 1 つだけコンパイルされる。
CMake では Windows 以外は Vulkan / Metal のみ、Metal は Apple(macOS / iOS)専用、Android は Vulkan のみ、iOS は Metal のみ。

| D3D11 (`Graphics/D3D11/`) | D3D12 (`Graphics/D3D12/`) | Vulkan (`Graphics/Vulkan/`) | Metal (`Graphics/Metal/`、`.mm`) | 役割 |
|---|---|---|---|---|
| `D3D11GraphicsDeviceImpl` | `D3D12GraphicsDeviceImpl` | `VulkanGraphicsDeviceImpl` | `MetalGraphicsDeviceImpl` | `IGraphicsDeviceImpl` 実装。デバイス/スワップチェーン(Metal は `CAMetalLayer`)/キュー初期化、リソースファクトリ、Present、`WaitIdle`、リードバック。 |
| `D3D11RenderContextImpl` | `D3D12RenderContextImpl` | `VulkanRenderContextImpl` | `MetalRenderContextImpl` | `IRenderContextImpl` 実装。DX11=immediate context、DX12/Vulkan/Metal=コマンド記録。 |
| `D3D11Buffers` | `D3D12Buffers` | `VulkanBuffers` | `MetalBuffers` | 頂点/インデックス/定数バッファ具象。 |
| `D3D11Shader` | `D3D12Shader` | `VulkanShader` | `MetalShader` | シェーダコンパイル/ロード(Vulkan は `.spv`、Metal は `.metal`(MSL)を実行時コンパイル)。 |
| `D3D11Resources` / `D3D11RenderResources.h` | `D3D12Resources` / `D3D12RenderTarget` | `VulkanResources` / `VulkanRenderTarget` | `MetalResources` / `MetalRenderTarget` | SRV/サンプラー/UAV/RT の具象。 |
| `D3D11DepthMap` | `D3D12DepthMap` | `VulkanDepthMap` | `MetalDepthMap` | シャドウ深度マップ具象。 |
| — | `D3D12RootSignature` | `VulkanPipelineLayout` | — | ルートシグネチャ/ディスクリプタレイアウト。DX11 には概念が無く、Metal は index で直接束ねるため不要。 |
| — | `D3D12PipelineStateCache` | `VulkanPipelineCache` | `MetalPipelineCache` + `MetalDepthStencilCache` | PSO キャッシュ(DX12/Vulkan/Metal は PSO 明示のためキャッシュ必須。DX11 は動的ステートで不要)。Metal は深度ステンシルステートが PSO と別オブジェクトなので専用キャッシュを持つ。 |
| — | `D3D12GpuBuffer` | — | (`MetalGraphicsDeviceImpl.mm` 内で `CreateStructuredBuffer`/`CreateRawBuffer` を実装) | GPU 駆動クラスタカリング用バッファ(構造化/RAW/間接引数)。Vulkan は `Graphics/Vulkan/` 内に該当 override が見当たらない(既定の nullptr。TODO: Vulkan での GPU 駆動カリングの可否は未確認)。 |
| `imgui_impl_dx11`(ThirdParty) | `D3D12ImGui` | `VulkanImGui` | `MetalImGui` | ImGui バックエンド接続。 |
| — | `D3D12Common.h` | `VulkanCommon.h` / `VulkanVMAImpl.cpp` | `MetalCommon.h` | 共通ヘルパ(DX12=ヘルパ、Vulkan=VMA アロケータ)。 |

**ハイブリッドの肝**:
- **DX11** … immediate context・動的ステート中心で最も単純。Xbox One UWP(FL11_0 未満 = App 分類の FL10_0 経路)フォールバックの主経路。compute/UAV/間接描画は FL によって非対応 → `SetComputeSupported(false)` で機能を落とす(`D3D11GraphicsDeviceImpl` が FL11_0 以上かで設定)。具体的な FL 値の根拠は [Xbox移植設計](Xbox移植設計.md) に一元化。`IRenderContextImpl` のインスタンシング(`DrawIndexedInstanced`)・間接描画は `D3D11RenderContextImpl.h` に override が見当たらない(既定 no-op。TODO: インスタンス描画の D3D11 での挙動は未確認)。
- **DX12** … 明示的な PSO/ルートシグネチャ/フェンス/リードバックヒープ。GPU 駆動カリング・Hi-Z リードバックが完全動作する主戦力。実機 Xbox のフル描画経路。
- **Vulkan** … 同一構造の先行事例(抽象 IF 追加 0 本で移植した実績)。SDK 未導入時は `#ifdef` ガードで実コンパイル対象外。Android の描画 API でもある([Android移植設計](Android移植設計.md))。
- **Metal** … macOS / iOS。抽象 IF の追加 0 本を方針とし、差分は `MetalRenderContextImpl` に閉じる。HLSL(`.fx`)は無改変で、ビルド時に `.spv` → `.metal`(MSL)を生成し、実行時に `newLibraryWithSource:` でコンパイルする。compute・間接描画(`IASetIndexBufferGpu`/`DrawIndexedIndirect`/`UavBarrier`)・インスタンシング・スライス指定シャドウを実装している。`MetalGraphicsDeviceImpl.h` だけは素の C++(ObjC 型を出さない)。詳細は [MetalBackend設計](MetalBackend設計.md)、iOS 差分は [iOS移植設計](iOS移植設計.md)。

## 2. レンダリングレイヤー(`aqEngine/Rendering/`)

### 2.1 フレームデータとコマンド基盤

| ファイル | 責務 |
|---|---|
| `RenderFrame.h` | **1 フレームの描画スナップショット**。ゲームスレッドが構築しレンダースレッドが消費。`CameraData`/`RenderItem`(1 ドロー分。GPU リソースは全て `shared_ptr` で 1 フレーム遅延消費に耐える)/`OceanRenderItem`/`DecalRenderItem`/`InstancedRenderItem`/`ParticleRenderItem` を保持。`items`(deferred)/`forwardItems`(透明)/`oceanItems`/`decalItems`/`instancedItems`(インスタンス描画。forward)/`particleItems`(半透明ビルボード)に分類。カリング用ローカル AABB・GPU 駆動カリングバッファもここ。 |
| `IRenderCommand.h` | **描画コマンド基底 IF**。`Execute(RenderContext&, FrameContext&)` の 1 メソッドのみ。 |
| `RenderCommandList.h/.cpp` | **コマンドを 64KB ページのリニアアリーナに placement-new して記録・再生**。`Enqueue<T>()` で積み、`Execute()` で順に再生、`Reset()` でデストラクタを呼びカーソルだけ戻す(次フレーム再利用)。ページは再確保しないので保持ポインタが常に有効。
| `FrameContext.h/.cpp` | **フレーム単位のリソースプール**。`ConstantBufferPool`(per-draw b0/material b2/bones b4/ocean b5 を draw ごとに Allocate、フレーム跨ぎで再利用)。`FrameContext` は全コマンドの `Execute` に渡され、CB プール(b0/b2/b4/b5)・lighting(b1)/shadow(b3) の CB・確定 displayRT を供給。 |
| `RenderTargetHandle.h` | RT を指す軽量ハンドル(メイン RT / オフスクリーン RT を統一的に参照)。 |
| `aqEngine/RenderConfig.h`(`Rendering/` 直下ではない) | `AQ_RENDER_PIPELINED`(直列/非同期切替。既定はコメントアウト = 直列)のビルド設定。 |

### 2.2 レンダラー本体とスレッド

| ファイル | 責務 |
|---|---|
| `Renderer.h/.cpp` | **`RenderPipeline` の持ち主**。`BuildCommandList(frame, outList, ...)` は `RenderPipeline::Build()` への委譲だけで、パスも順序も持たない(一次資料は [レンダーパイプライン設計](レンダーパイプライン設計.md))。`SetPipeline()` で確定済みパイプラインを受け取り、`GetPipeline()` がゲームの入口(`Find<T>()` でパスへアクセス)、`GetOutputRT()` が表示 RT の決定。`RenderDebugSync`(_DEBUG 専用の同期実行)も持つ。 |
| `RenderThread.h/.cpp` | 専用スレッドでコマンドリストを実行するリングバッファ。同期モード・リング構成・累計カウンタによるフレーム同期の詳細は [マルチスレッド設計 §2](05_マルチスレッド設計.md) を一次資料とする。 |
| `RenderFrame.h`(前掲) | — |

**レビュー観点(スレッド)**: DX11 immediate context は単一スレッド専有。ゲームスレッドは絶対に描画 API を触らず、`Submit` 経由でレンダースレッドに渡す規約。`RenderDebugSync` は「レンダースレッドから呼べ」とコメントで縛っている。非同期パイプライン時は「フレーム N と N+1 で別メイン RT を使う」(Engine 側トグル)が前提。

**標準構成(`PipelinePresets::Standard`)**: Shadow → ClusterCull → GBuffer → Hi-Z → Decal → DeferredLighting → Sky → Forward → Ocean → Particle → MotionBlur → Bloom → Tonemap → UI。
`enableShadow` / `enableDeferred` / `enableHiZ` / `enableSky` / `enablePostProcess` で各部分を外せる。

**Mobile 構成(`PipelinePresets::Mobile`)**: GBuffer を持たないフォワードのみ。Shadow → Forward → Sky → Particle → Tonemap(Bloom / MotionBlur 無し)→ UI。
`preset.pipeline = Auto` のときだけプラットフォームで選ぶ(AQ_PLATFORM_ANDROID / AQ_PLATFORM_IOS → Mobile)。既定は `Standard`。

**機能ゲート**: compute が要るパス(`ClusterCullPass` / `HiZPass` / `OceanPass` / `MotionBlurPass` / `BloomPass` / `TonemapPass` / `OutlinePass`)は
`IsSupported()` が `IsComputeSupported()` を返し、非対応環境では `Build()` が列から除外する(旧 `IsComputeSupported()==false` の「ポスト全スキップ + sceneRT 直表示」は、Tonemap も除外される結果として同じ)。

**ポストプロセスのパス分割**: 旧 `BloomRenderer` / `PostProcessChain` は解体され、`MotionBlurPass` / `BloomPass` / `TonemapPass` に分かれた
(効果の実体は `Rendering/PostProcess/Effects/`。§2.6・§7)。MotionBlur → Bloom → Tonemap は掲示板の `PostInput` / `BloomTexture` / `Output` で繋ぐ。

**輪郭線(`OutlinePass`)**: G-Buffer の法線(GBuffer1)を隣り合う画素と比べてシルエットと折り目を線色で塗る compute パス(Frame scope)。
直前の `Output`(無ければ `Scene`)を読んで自前 RT へ書き、それを新しい `Output` にする。深度(worldPos)は half float の刻みで縞が出るため使わない。
**`Standard()` には入らず**、使うゲームが `InsertBefore<UIPass>` 等で自分で挿す。GBuffer を持たない列では何もせず素通し。シェーダは `Outline.fx`。

**オフスクリーン専用パス**: メインの列とは別に、ゲームが `PipelineBuilder` で 2 本目の `RenderPipeline` を組む(§8)。掲示板はパイプラインごとに独立。

## 3. フレームの流れ(`AppHost::Render` 実体)

**一次資料は [レンダーパイプライン設計](レンダーパイプライン設計.md)**。描く順序は `Renderer` ではなく
`PipelineBuilder` が組んだパス列(`RenderPipeline`)が持ち、`Renderer::BuildCommandList` はそこへ委譲するだけになった。
機能ゲート(`IsComputeSupported()` 等)も各パスの `IsSupported()` に移り、起動時に列から除外される形になっている。

`Core/AppHost.cpp` の `AppHost::Render()`(旧 `Application::Render`。`Application` は `AppHost` と `IAppModule` に分割済み)が毎フレーム行う手順:

1. メインカメラ位置を `LightManager` に反映。
2. **ImGui**(`AQ_IMGUI` 時): プラットフォーム別 `NewFrame`(Win32 / Mac / Android・iOS / UWP は自前で DisplaySize・DeltaTime)+ バックエンド別 `NewFrame`(DX11/DX12/Vulkan/Metal を `#ifdef` 分岐)→ `ImGui::NewFrame`。FPS/バックエンド名/VSync(DX12)のオーバーレイ、`module_->OnImGuiRender()`、デバッグ UI(F1 / 中クリック / モバイルは 4 本指ダブルタップで表示切替)を経て `ImGui::Render` で `ImDrawData` を確保。
3. `module_->OnPreRender()`(ゲーム固有のオフスクリーン Submit。ミニマップは 2 本目の `RenderPipeline`。§8)。
4. メイン `RenderCommandList` を確保し、SetRenderTarget/Clear/ClearDepth/SetViewport を Enqueue。
5. `RenderSystem::BuildRenderFrame(mainFrame)` … ECS 走査+**フラスタムカリング**で `RenderFrame` を構築(分割画面時はビュー毎に構築。§5)。
6. `Renderer::BuildCommandList(...)` → `RenderPipeline::Build(...)`(分割時は `RenderPipeline::BuildViews`)… 確定した列の順にコマンド記録。
7. ImGui があれば `ImGuiRenderCommand` を末尾に Enqueue。
8. `RenderThread::Submit(...)` … レンダースレッドへ。表示 RT は列の最終出力(`Renderer::GetOutputRT`)。

終了時・`FlushRender()` では `GraphicsDevice::WaitIdle()` で提出済みの GPU 作業を待ってからリソースを破棄する(`AppHost.cpp`)。

## 5. 分割画面ビュー(マルチビュー)設計

> 追加: 2026-09-06(AquaDash P5)。ゲーム側要件は
> [AquaDash 04_描画_分割画面_UI設計](../Game/Design/AquaDash/04_描画_分割画面_UI設計.md) が一次資料。

1 フレームに最大 4 ビュー(カメラ + ビューポート矩形)を同一バックバッファへ直接描く。
**ビュー数 1 のときは従来経路をそのまま通し、コスト増ゼロを保証する。**

### 方式(調査で確定した前提)

- カメラ定数 (b0) は **per-draw**(各コマンドが CameraData を値持ち)→ 1 リスト内でビュー毎にカメラを差し替え可能。
- ディファードライティングは SV_POSITION 基準の GBuffer Load → **サブビューポート設定だけで正しく領域制限**される。
- lighting(b1)/shadow(b3) は per-frame かつカメラ非依存 → 全ビュー共有。シャドウパスは先頭 1 回。
- Clear 系コマンドはビューポートを無視して全面クリア → **クリアはフレーム先頭/最初のビューのみ**。
- Bloom/トーンマップは compute 全画面 → ビューループ外で 1 回(ビュー境界のにじみは仕様上の妥協)。
- UI は NDC 固定頂点 → 全画面 1 回(ビュー毎 HUD は将来、ビューポート切替+バッチ分割で対応)。

### 実装(パス列での実行)

> 2026-09-16(レンダーパイプライン P3)で、旧 `Renderer::BuildCommandListViews` は `RenderPipeline::BuildViews` へ移った。
> ビュー数・ビュー毎の扱いは各パスの `GetScope()` と `PassViewInfo` で決まる(一次資料は [レンダーパイプライン設計](レンダーパイプライン設計.md))。

```
Clear(メインRT+depth)           … 1回(AppHost::Render が積む)
Frame scope(先頭側)            … 1回 (ShadowPass は frames[0] で確定)
for view in views:  View scope
    SetViewport(view.rect)
    GBuffer(クリアは view0 のみ) → デカール → ディファードライティング → 空 → フォワード → 海
    ClusterCull / Hi-Z … 単一ビューのときだけ(IsSingleView)
    パーティクル … view0 のみ(IsFirstView。エミッタ共有動的VBへの多重書込み回避。既知の制限)
SetViewport(全画面)
Frame scope(末尾側)            … MotionBlur(単一ビューのみ有効)/ Bloom / Tonemap / UI を 1 回
ImGui / CopyToBackBuffer+Present(Submit は 1 フレーム 1 回のまま)
```

### ファイル別変更(現行)

| ファイル | 内容 |
|---|---|
| `Rendering/Pipeline/RenderPipeline.h/.cpp` | `ViewRect` と `BuildViews(frames, rects, count, ...)`。`Renderer.h` 側は `ViewRect` を互換 using で保つ。`Build`(1 ビュー)は従来経路でコスト増なし |
| `Rendering/Pipeline/IRenderPass.h` | `PassScope` / `PassViewInfo`(`IsFirstView` / `IsSingleView`) |
| `Rendering/Deferred/IDeferredRenderer.h` / `Deferred/DeferredRenderer.*` | `BuildGBufferCommandList` に `clearTargets`(既定 true)。`GBufferPass` が先頭ビューだけ true を渡す |
| `Component/BodyComponentSystem.*` | `BuildRenderFrame(frame, camera, フラスタム有効, オクリュージョン有効, 統計更新, gather)` のカメラ直指定版 |
| `Core/AppHost.h/.cpp` | `SplitView{camera, rect}` / `SetSplitViews` / `ClearSplitViews`。`Render()` はビュー数 >= 2 のときだけマルチビュー経路へ分岐(上限 4。1 ビューは従来の単一経路) |
| `HID/IKeyboardBackend.h` | `KeyBoardType::Num1..Num4`(分割の擬似人数切替テスト用) |

### 制限(分割時のみ。1 ビュー時は無関係)

- Hi-Z オクリュージョン / GPU クラスタカリングは複数カメラ前提が崩れるため**分割時は無効**(パス側が `IsSingleView()` で何もしない。フラスタムカリングはビュー毎に有効)。
- パーティクルは view0 にのみ描画(共有動的 VB の多重書込み対策。必要になれば VB 連結+offset 描画で解消)。
- シャドウは全ビュー共有 1 枚(注視点は player0)。
- HUD は全画面 1 枚(player0 の値)。ビュー毎 HUD は AquaDash P7 以降で検討。

## 6. インスタンス草の描画(手続きメッシュ + 風揺れ)

大量の草をインスタンス描画するための、メッシュ生成と専用シェーダ。

> 2026-11 注: エンジン共通シェーダは `aqEngine/Assets/Shader/` へ移設済み(コミット `883ea1d`)。本節のパスはその後の位置に直してある。

カリング側(静的インスタンスのベイク + セル単位カリング)は
[カリング設計.md §15](カリング設計.md) が一次資料。本節は**描画**のみを書く。

### 6.1 メッシュ(`Graphics/MeshPrimitives.{h,cpp}`・新規)

手続き生成の再利用可能なプリミティブを置く新ファイル。第一弾が草の房。

- 中心で交差する 3 枚のクアッド(房)。12 頂点。
- ラスタライザは `CULL_MODE_BACK` 固定のため、**巻き順を反転したインデックスも足して両面化**する
  (頂点は共有するので 12 頂点 / 12 三角形)。
- 法線は面法線ではなく**上向き寄り**にする。両面から見て明暗が反転せず、陰影が柔らかくなる。
- `uv.y` を「根元 0 / 先端 1」として持たせる。風の振幅と色グラデーションの両方がこれを使う。
- アルファテストは既存シェーダに無いため、抜きテクスチャではなく**実体形状**で表現する。

### 6.2 シェーダ(`aqEngine/Assets/Shader/InstancedGrass.fx`・新規)

入力レイアウトは `InstancedSimple.fx` と同じ(slot0 = 位置/法線/UV、slot1 = `I_WORLD0..3` + `I_COLOR`)。
違いは 2 点。

- **VS で風の変位**: `uv.y` を重みに、根元を動かさず先端ほど大きく揺らす。
  位相はインスタンスのワールド位置(`I_WORLD` の平行移動成分)から作るため、
  **per-instance データを増やさずに**株ごとに揺れがずれる。
- **PS で縦グラデーション**: `uv.y` で根元を暗く、先端を明るくする。ライティングは
  `InstancedSimple.fx` と同じランバート。

### 6.3 風の定数バッファ(b2 `WindCB`)

- 中身: 時刻・強さ・周波数・風向。192 バイトに揃え、`perDrawCBPool` を借りる
  (`ClusterCullCBData` が同じ理由で 192B に揃えている前例に倣う)。
- **b2 は本来 `MaterialCB` / `PBRMaterialCB` だが、インスタンス描画経路はマテリアル CB を
  bind しない**ため衝突しない。将来インスタンス経路にマテリアルを持たせるときは要再配置。
- **時刻はゲームスレッドで `Engine::GetTotalTime()` を読み、`InstancedRenderItem` に載せて運ぶ**。
  レンダースレッドからエンジンのシングルトンを読まない(スレッド境界規約)。

## 7. ポストプロセスのパス分割(P15 → レンダーパイプライン P2)

> 設計 2026-09-09(P15)でチェーン構成へ分割し、2026-09-16(レンダーパイプライン P2)でチェーン
> (`PostProcessChain` / `IPostProcessRenderer`)を解体して 3 つの**パス**へ置き換えた。
> 現行のコードに `PostProcessChain` / `IPostProcessRenderer` のクラスは無い(grep で確認。コメント中の言及のみ)。
> 効果の実体のファイル構成は §2.6、パス列の一次資料は [レンダーパイプライン設計](レンダーパイプライン設計.md)。

### 7.1 現行の契約(コード確認済み)

- **入力**: `PostProcessContext { sceneRT, width, height, hasCamera, worldPosRT }`。
  各パスが `PassViewInfo` と掲示板から毎フレーム作る(寸法は `view.fullWidth/fullHeight`。RT 自体は `Setup(w, h)` 時の固定寸法。リサイズ対応は将来課題)。
- **パスの直列実行**: `MotionBlurPass → BloomPass → TonemapPass` の順(いずれも Frame scope)。
  中継は掲示板で行う: `MotionBlurPass` が `PostInput` を書き(実行しなければ `Scene` をそのまま `PostInput` に流す)、
  `BloomPass` が `PostInput`(無ければ Scene)から `BloomTexture` を書き、`TonemapPass` が `PostInput` + `BloomTexture` を読んで `Output` を書く。
  各エフェクトは「1 入力 RT → 1 出力 RT + 自前の中間 RT」に閉じる。
- **有効判定**: `IsSupported()`(compute 必須。非対応環境では列から除外)と、エフェクトの `IsEnabled(context)`(毎フレーム。無効なら積まず入力を素通し)の 2 段。
  **Tonemap は常時 ON**(HDR→LDR 変換が無いと表示できないため。`IsSupported()` の範囲でのみ除外)。
  モーションブラーの有効条件(強度 > 0 かつ当該フレームのカメラあり)は `context.hasCamera` で明示する
  (`hasCamera = view.IsSingleView()`。分割画面経路は false でブラー無効: §5 の暗黙仕様の明文化)。
- **最終 RT と RTV 復元**: `TonemapPass` が出力(LDR finalRT)を `Output` に登録し、
  **`Build` の最後に `SetRenderTargetCommand(Output)` で RTV として復元して終える**(後続の UI / ImGui がそこへ描く契約)。
  旧設計の「チェーン側が 1 箇所で行う」は、パス列では最終パス(Tonemap)の責務になった。
- **RT の所有**: 各エフェクトが自分の中間 RT を `Initialize(w, h)` で生成・所有する。プール化・リサイズは将来(既知の課題④の寸法契約と合わせて)。
- **値の受け渡し**: ブルーム強度などは `TonemapPass::SetBloomIntensitySource(BloomPass*)` で参照する。パラメータの調整はゲーム/デバッグパネルが `Find<T>()` で各パス(`GetEffect()`)へ触る。

### 7.2 互換性の要点(P15 時点で変えなかったもの)

- CB レイアウト(`BloomCBData`)は 4 シェーダ共有のまま(分割はシェーダ側 cbuffer と同時でないと壊れるため触らない)。シェーダ(.fx)も P15 では無変更。
- `IsComputeSupported()==false` 経路は、各パスが `IsSupported()` で列から外れる形になり、結果として「ポストプロセス全スキップ + シーン RT 直表示」。
- 削除: 参照ゼロの `BloomBlur.fx`(Dual Blur 移行の残骸。旧 `Game/Assets/Shader/`)。
- TODO: `PostProcessCB.h`(`Commands/`)の現行 CB 構成と、P15 以降のシェーダ変更の有無は未確認。

## 8. オフスクリーンシーンパス(P17 → レンダーパイプライン P4)

> 設計 2026-09-09(P17)。2026-09-16 に **2 本目の `RenderPipeline`** へ置き換えた
> (レンダーパイプライン設計 P4)。既知の課題「オフスクリーンパス(512²)がディファード経路で
> シーンを描けない」(README 2026-09-06 発見)の解消。発端はゲーム(AquaDash)の俯瞰 RT ミニマップ
> ([AquaDash 04 §4](../Game/Design/AquaDash/04_描画_分割画面_UI設計.md))。
> パス列の一次資料は [レンダーパイプライン設計](レンダーパイプライン設計.md)。

### 8.1 問題と方針

- 症状: ライティング/フォワードが `OMSetRenderTargetWithDepth(オフスクリーンRT, GBuffer0)` で
  512² RTV と 1920×1080 DSV を同時バインドし、D3D の制約違反で静かに失敗する。
  原因は「GBuffer(=深度の持ち主)が描画構成に 1 組しか無く、メイン解像度固定」なこと。
- 方針: **縮小 GBuffer を自前で持つ 2 本目の `RenderPipeline` をゲームが組む**。
  列は `GBufferPass` → `DeferredLightingPass` → `ForwardPass` の 3 本だけで、
  影 / Hi-Z / デカール / 海 / パーティクル / ポストプロセス / UI は積まない。
  `DeferredRenderer` は `GBufferPass::Setup` が `PipelineBuilder::Build(512, 512)` の寸法で作るので、
  RTV と DSV の寸法が食い違わない(追加 VRAM は RGBA8×1 + RGBA16F×3 ≒ 3.1MB)。
- **パイプラインは掲示板(`PassResources`)を各自 1 枚持つ**ので、同じキー(`Scene` / `GBuffer0` …)を
  使ってもメインの列と混ざらない。専用クラス(旧 `OffscreenScenePass`)を持つ必要が無くなった
  (P4 で削除。「UI の焼き込み」「シャドウマップ二重描画」といった流用時の事故は、
  積まないパスは存在しないという形で最初から起きない)。

### 8.2 責務表

| ファイル | 責務 |
|---|---|
| `Game/Application/GameModule.h/.cpp`(`Application` 分割後) | 2 本目の `RenderPipeline`(`minimapPipeline_`、512×512)とカラー RT(`hasDepth=false`)を `OnInitialize` で作って所有する。`OnPreRender` で `SetRenderTarget` / `Clear` / `SetViewport` を積んでから `Build()` を呼び、`displayRT = INVALID` で `AppHost::GetRenderThread().Submit` する。ベイク要求(`minimapBakeRequested_`)が立ったフレームだけ描く |
| `Graphics/Camera.h/.cpp` | **正射影モード**(`SetOrthographic(width, height)`。設定時は viewAngle/aspect 経路の代わりに `Matrix4x4::MakeOrthographic` で射影を作る。既存カメラは無影響) |
| `Component/BodyComponentSystem.h/.cpp` | **同一フレーム 2 回目の gather 要求を再利用するガード**。「登録インスタンスの Flush は毎フレーム必ず 1 回」の不変条件を保ったまま、オフスクリーン側の gather を先行実行できるようにする(後述 8.3) |
| `Graphics/GraphicsDevice.h/.cpp` | `GetRenderTargetSRVShared(handle)`(RT の SRV を**非所有 deleter の shared_ptr** で返す。`UIImageComponent::texture` が `shared_ptr<IShaderResourceView>` のため) |
| `Rendering/Shadow/ShadowData.h` | `MakeNeutralShadowCBData()`(影を無効化する b3 の値。旧 `OffscreenScenePass` の static から移設) |

### 8.3 契約

- **Submit**: `displayRT = RenderTargetHandle{}(INVALID)` で Submit し、Present しない(カメラは `CameraType::Offscreen` の正射影)。
  `RenderThread` はリング 4 スロットで 2 Submit/フレームを想定済み(マルチスレッド設計 §2)。
  リングは FIFO なので `OnPreRender` の Submit はメインパスより先に実行される。
- **RenderFrame 構築**: カメラ直指定版 `BuildRenderFrame(frame, camera, false, false, false, gather)`
  で呼ぶ。フラスタムカリング無効(俯瞰は全景が入る)、オクリュージョン無効(Hi-Z は 1080p
  メインカメラ由来で誤判定する)、統計更新無効。
- **gather の順序**: インスタンスの gather(セルカリング+Flush)はフレームに 1 回の制約が
  ある。描画するフレームだけオフスクリーン側が `gather=true` で**先行して**行い(フラスタム
  無効なので全セルが積まれる)、同フレームのメインパスはガードにより再利用する
  (そのフレームだけ全インスタンス描画になるが、用途がロード時 1 回のベイクなので許容)。
  草など `maxDrawDistance` 持ちのセルは俯瞰カメラとの距離で自然に落ちる。
- **ライティング**: メインと同じ `LightManager` の `LightingData` を Submit に渡す。
  シャドウ CB は `MakeNeutralShadowCBData()`(オフスクリーンは影なしの素朴なライティング)。
- **頻度は呼び出し側が決める**: 毎フレーム呼べばシーン約 1 回分のコストが素直に増える。
  AquaDash はロード完了時に 1 回だけベイクする(dirty フラグ)。旧実装の停止理由だった
  「未使用なのに毎フレーム二重描画」はこの契約で解消。
