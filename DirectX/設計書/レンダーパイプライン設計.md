## 0. 目的と非目標

**目的**

- パスの順序変更、ゲーム独自パスの挿入 / 置換、プラットフォーム別の構成を、エンジンを改修せずに行えるようにする
- [Renderer.cpp](../aqEngine/Rendering/Renderer.cpp) の `BuildCommandList` と `BuildCommandListViews`、
  Game 側の `OffscreenScenePass` に分かれている「同じ順序の写し 3 つ」を 1 つにする
- 散らばった `IsComputeSupported()` の分岐と、`dynamic_cast` で黙って機能が落ちる配線を、起動時の検証に置き換える

**非目標**

- RT の自動確保・寿命解決・バリア自動挿入(フレームグラフ)。RT は今どおり初期化時に所有者が作る
- `Graphics/` の Bridge と `RenderThread` / `RenderCommandList` の変更。コマンドの記録と実行の境界は今のまま
- 描画結果の変更。P1 は画素比較で今と同じ絵を出すことを合格条件にする

## 1. 概念モデル

```
初期化                                            毎フレーム
ゲーム / PipelinePresets                          RenderFrame(s)
  │ Add<Pass>() / InsertAfter<T>() / Replace<T>()   │
  ▼                                                ▼
PipelineBuilder ──Build()──▶ RenderPipeline ──Build(frames, list)──▶ RenderCommandList ──▶ RenderThread
  1. IsSupported() で除外        passes[] 順序確定       各パスが PassResources を
  2. Reads が前段の Writes に     resources キー→RT       読み書きしながら積む
     在るか検証(名指しで失敗)     outputRT
```

### 1.1 `IRenderPass`

パスは ECS の System と同じ位置づけの公開インターフェース。エンジンの標準パスもゲームのパスも同じ型。

```cpp
namespace aq { namespace rendering {

	enum class PassScope : uint8_t
	{
		Frame,   // フレームに 1 回(影・ポスト・UI)
		View,    // ビューごと(分割画面ではビュー数だけ回る)
	};

	// 掲示板のキー。エンジン定義は PassResourceKeys に、ゲーム独自は aqHash32("Game.Xxx") で作る
	using PassResourceKey = uint32_t;

	class PassDeclaration
	{
	public:
		void Reads(PassResourceKey key);
		void Writes(PassResourceKey key);
		void ReadsOptional(PassResourceKey key);   // 無くても動く(例: Sky は Depth が無ければ深度なしで描く)
	};

	class IRenderPass
	{
	public:
		virtual ~IRenderPass() = default;
		virtual const char* GetName() const = 0;
		virtual PassScope   GetScope() const { return PassScope::View; }
		/** 機能要件。false のパスは Build() が除外してログに出す */
		virtual bool        IsSupported() const { return true; }
		/** 読む / 書くキーの宣言。Build() の検証に使う */
		virtual void        DeclareResources(PassDeclaration& decl) const = 0;
		/** RT の生成と掲示板への登録。失敗したら false(パイプライン全体が失敗) */
		virtual bool        Setup(PassResources& res, uint32_t width, uint32_t height) { return true; }
		/** コマンドの記録(ゲームスレッド)。frame は非 const(ClusterCullPass がアイテムの useGpuCull を確定させる) */
		virtual void        Build(RenderFrame& frame, const PassViewInfo& view,
		                          PassResources& res, RenderCommandList& outList) = 0;
	};
} }
```

実物は [IRenderPass.h](../aqEngine/Rendering/Pipeline/IRenderPass.h) が正。

`PassViewInfo` は `viewIndex` / `viewCount` / `rect`(ビューポート)/ `isFirstView` を持つ。
今の「GBuffer のクリアは先頭ビューだけ」「パーティクルは先頭ビューだけ」は各パスが `isFirstView` を見て判断する。

**契約(パスを書く側が守るもの)**

1. 読むキーは `DeclareResources` で宣言する。宣言していないキーを `Build` で読んだら assert
2. 入った状態に戻して終わる。`BlendMode` は Opaque、`DepthMode` は ReadWrite。RT のバインドは次のパスが自分で行う
3. `Scene` に描くパスは、自分で `SetRenderTargetWithDepthCommand(Scene, Depth)` を積む(`Depth` が無ければ `SetRenderTargetCommand(Scene)`)。前のパスが何をバインドして終えたかに依存しない
4. `Setup` で作った RT は自分が所有し、デストラクタで解放する
5. `Build` はゲームスレッド、積んだコマンドの `Execute` はレンダースレッド(既存の規約どおり)

### 1.2 `PassResources`(掲示板)

`PassResourceKey → RenderTargetHandle` の表。RT ハンドルだけを扱う(シャドウマップの `IDepthMap` は
今どおり `FrameContext` 経由で `DrawItemCommand` に届くので載せない)。

| キー | 意味 | 書く側 |
| --- | --- | --- |
| `Scene` | シーン RT(メイン RT かオフスクリーン RT) | パイプライン生成時に外から与える |
| `Depth` | シーンの深度を持つ RT(= GBuffer0) | `GBufferPass` |
| `GBuffer0` 〜 `GBuffer3` | G-Buffer 各面 | `GBufferPass` |
| `WorldPos` | `GBuffer2` の別名(ポストプロセスとゲームパスが読む) | `GBufferPass` |
| `HiZ` | Hi-Z ピラミッドの読み戻し面 | `HiZPass` |
| `PostInput` / `PostOutput` | ポストプロセスの入出力(ピンポン) | 各ポストパス |
| `BloomTexture` | Bloom の結果(Tonemap の第 2 入力) | `BloomPass` |
| `Output` | 最終出力。`RenderThread::Submit` の displayRT に渡す | 最後に `Output` を書いたパス |

ゲームは `MakePassKey("Game.Outline")` のように自前キーを作って `Setup` で登録できる(`aqHash32` ではなく
[PassResources.h](../aqEngine/Rendering/Pipeline/PassResources.h) の constexpr FNV-1a。掲示板のキー同士で一致すればよいので独立させた)。
エンジンのキーとの衝突は `PassResourceKeys` を `MakePassKey("aq.Scene")` のように接頭辞付きで定義して避ける。
`Scene` は毎フレーム `RenderPipeline::Build` が差し替える(パイプライン化時はメイン RT が交互に変わるため)。

### 1.3 `PipelineBuilder` と `RenderPipeline`

```cpp
class PipelineBuilder
{
public:
	template <typename TPass, typename... Args> PipelineBuilder& Add(Args&&... args);
	template <typename TAnchor> PipelineBuilder& InsertAfter (std::unique_ptr<IRenderPass> pass);
	template <typename TAnchor> PipelineBuilder& InsertBefore(std::unique_ptr<IRenderPass> pass);
	template <typename TAnchor> PipelineBuilder& Replace     (std::unique_ptr<IRenderPass> pass);
	template <typename TAnchor> PipelineBuilder& Remove();
	/** 検証して確定する。失敗は理由付きで [pipeline] ログに出し nullptr */
	std::unique_ptr<RenderPipeline> Build(uint32_t width, uint32_t height);
};

class RenderPipeline
{
public:
	/** 1 ビュー。sceneRT は毎フレーム差し替える */
	void Build(RenderFrame& frame, RenderCommandList& outList, RenderTargetHandle sceneRT, float viewportW, float viewportH);
	/** 複数ビュー。Frame scope → (View scope × ビュー数) → Frame scope の順。P1 で実装済み */
	void BuildViews(RenderFrame* frames, const ViewRect* rects, uint32_t viewCount,
	                RenderCommandList& outList, RenderTargetHandle sceneRT, float viewportW, float viewportH);
	RenderTargetHandle GetOutputRT() const;
	template <typename TPass> TPass* Find();   // ゲームが影の中心やブラー強度を触るための入口
};
```

`Build()` の検証順:

1. `IsSupported()` が false のパスを列から外し、`[pipeline] 除外: BloomPass (compute 非対応)` を出す
2. 先頭から順に `DeclareResources` を集め、`Reads` のキーが「初期状態(Scene)+ それまでの `Writes`」に
   無ければ `[pipeline] MotionBlurPass は WorldPos を読むが、それを書くパスが前に無い` を出して失敗
3. 各パスの `Setup` を順に呼ぶ。失敗したパスの名前を出して失敗
4. `Output` を最後に書いたパスの RT を `GetOutputRT()` に、無ければ `Scene`

Frame scope のパスは View scope のパスより前か後にしか置けない(`Frame → View… → Frame`)。
間に挟まっていたら「View scope の列の途中に Frame scope の X がある」で失敗させる。

### 1.4 プラットフォームでの選択

2 段構え。ゲームコードに `#if AQ_PLATFORM_*` は書かせない([architecture.md](../../.claude/skills/cpp-gamedev/references/architecture.md) §2)。

| 段 | 誰が | 何を |
| --- | --- | --- |
| 自動縮退 | `PipelineBuilder::Build` | `IsSupported()` で動かないパスを外す。同じ `Standard()` を渡しても compute の無い端末では Bloom / MotionBlur / Hi-Z / Ocean が外れる |
| 明示 | ゲーム | `PipelinePresets::Mobile()` を使う、または自分のリストを書く。`ForCurrentPlatform()` は `PlatformBudget` と機能フラグで `Standard` / `Mobile` を選ぶ |

`Application::SetupStandardRenderers(preset)` は残し、中身を `PipelinePresets::ForCurrentPlatform(preset)` →
`SetRenderPipeline()` に置き換える。AquaDash と Sample は無改修で動く。

## 2. 既存クラスとの対応

既存のレンダラーは捨てず、パスが薄く包む。内部の描画コードは 1 行も動かさない。

| パス | Scope | 包む既存クラス | Reads | Writes |
| --- | --- | --- | --- | --- |
| `ShadowPass` | Frame | `HardShadowRenderer`(`IShadowRenderer`) | — | —(シャドウマップは `FrameContext` 経由) |
| `ClusterCullPass` | View | `Renderer::BuildCommandList` の Pass 1.5 を移す | — | — |
| `GBufferPass` | View | `DeferredRenderer::BuildGBufferCommandList` | Scene | Depth, GBuffer0-3, WorldPos |
| `HiZPass` | View | `HiZRenderer`(今はコールバック) | WorldPos | HiZ |
| `DecalPass` | View | `DeferredRenderer::BuildDecalCommandList` | GBuffer0-3 | GBuffer0 |
| `DeferredLightingPass` | View | `DeferredRenderer::BuildLightingCommandList` | GBuffer0-3 | Scene |
| `SkyPass` | View | `SkyRenderer` | Scene, Depth(optional) | Scene |
| `ForwardPass` | View | `Renderer::RecordDrawItem` + `recordForwardItems` + `InstancedDrawItemCommand` | Scene, Depth(optional) | Scene |
| `OceanPass` | View | `OceanDrawCommand`(compute 必須) | Scene | Scene |
| `ParticlePass` | View(先頭ビューのみ) | `ParticleDrawCommand` | Scene | Scene |
| `PostProcessPass`(P1 のみ) | Frame | `PostProcessChain` をそのまま | Scene, WorldPos(optional) | Output |
| `MotionBlurPass` / `BloomPass` / `TonemapPass`(P2 で分割) | Frame | 既存の `IPostProcessPass` 3 つ | Scene / PostInput 等 | PostOutput / BloomTexture / Output |
| `UIPass` | Frame | `UIBatchRenderer::BuildCommandList`(今はコールバック) | Output(または Scene) | Output |
| `ImGuiPass`(P2) | Frame | `ImGuiRenderCommand` | Output | Output |

`GBufferPass` / `DecalPass` / `DeferredLightingPass` は 1 つの `DeferredRenderer` を `shared_ptr` で共有する。
3 つに割るのは HiZ や SSAO を GBuffer とライティングの間に挟むため。
`DeferredRenderer` の所有者は `GBufferPass` とし、他の 2 つは `Find<GBufferPass>()` で辿らず、
`PipelinePresets` が生成時に同じ `shared_ptr` を渡す(ゲームが `Add<GBufferPass>()` だけ書いた場合に備え、
`DecalPass` / `DeferredLightingPass` は `Setup` 時に掲示板から `GBuffer0` を読めなければ検証で落ちる)。

`Renderer` の `GetShadowRenderer()` / `GetPostProcessRenderer()` は AquaDash が使っている
([Game/Application/Application.cpp:118-126](../Game/Application/Application.cpp#L118-L126))ので、
P1〜P2 の間は `pipeline->Find<ShadowPass>()` へ転送する形で残し、P5 で削除する。

## 4. フェーズ計画

### P1: 挙動不変の置き換え

`Rendering/Pipeline/` を新設し、§2 のパス(ポストプロセスは `PostProcessChain` 丸ごとの `PostProcessPass`)で
`Standard()` を組む。`Renderer::BuildCommandList` / `BuildCommandListViews` は内部で `RenderPipeline` を呼ぶだけにする。
検証(`Reads` / `Writes`)は宣言だけ入れて、この段では失敗させない(ログのみ)。

- [x] `Standard()` で AquaDash のタイトルとステージが従来どおり描画される(2026-09-16。Mac / Metal と Vulkan、解決失敗 0 件、Vulkan 検証レイヤ報告 0 件)
- [x] 同じ場面の画素比較で平均差が 2/255 以下。変更前後を同じ手順(起動 9 秒でタイトル、Space 後 12 秒でステージ)で撮って比較:
      Metal タイトル 0.015 / ステージ 0.457、Vulkan タイトル 0.016 / ステージ 0.129(いずれも /255。ステージの差は草の揺れとタイマー表示)
- [x] Sample の箱 1 個が描画される(Metal で目視)
- [x] `[pipeline]` ログに確定した列が 1 回出る: `ShadowPass > ClusterCullPass > GBufferPass > HiZPass > DecalPass > DeferredLightingPass > SkyPass > ForwardPass > OceanPass > ParticlePass > PostProcessPass > UIPass`
- [x] `IsComputeSupported()` の分岐が `Renderer.cpp` から消え、各パスの `IsSupported()` に移っている(grep で 0 件。`Renderer.cpp` は 345 行 → 106 行)
- [x] Hi-Z と UI のコールバックが消え、`HiZPass` / `UIPass` になっている。Hi-Z のオクリュージョン登録(`RenderSystem::SetOcclusionTester` / `GpuClusterCuller::SetHiZSource`)は `Find<HiZPass>()` 経由で維持
- [ ] Windows(D3D11 / D3D12 / Vulkan)でビルドが通る(Windows 機で確認。`Engine.vcxproj` / `.filters` には登録済み)

##### 発見と教訓

- **`BuildViews` は P1 で実装した。** `Renderer` のメンバをパスへ移した時点で、分割画面の写しを残すと所有権が二重になるため。
  `Renderer::BuildCommandListViews` は委譲だけの薄い関数として残っており、P3 は「分割画面の目視確認とこの関数の削除」になる
- **RT のバインドはパスごとに積む(契約 3)。** 旧実装はライティング直後に 1 回だけ `SetRenderTargetWithDepth` を積んで Sky と Forward が共有していたが、
  Sky / Forward / Ocean / Particle がそれぞれ積む形にした。コマンドが最大 3 つ増えるが画素は変わらない(上の比較)。
  パス間の暗黙の状態依存を無くすほうを取った
- **Hi-Z の `Setup` 失敗はパイプライン全体の失敗になる。** 旧実装は Hi-Z だけ無効にして続行していた。
  「`Setup` 失敗 = パイプライン失敗」の契約を優先した結果で、Hi-Z のシェーダが読めない環境が出たら
  `HiZPass::IsSupported` 側で先に弾く形にする
- **UI のパスは `SetupStandardRenderers` 経由でだけ入る。** `SetRenderPipeline()` で自前の列を渡すゲームは `UIPass` を自分で `Add` する
  (P2 で `PipelinePresets` の各プリセットに含める形にし、入門ドキュメントにも書く)
- `ClusterCullCommand` / `GpuClusterCuller` は `Occlusion/GpuClusterCuller.h`、`IsClusterCullEnabled` は `Occlusion/ClusterCull.h` にある(設計時の記述と違った)

### P2: 宣言と検証、プリセット、ゲームパスの部品

`Reads` / `Writes` の検証を有効にし、`PostProcessChain` を 3 パスに割る。`InsertAfter` / `InsertBefore` / `Replace` / `Remove`、
`FullscreenComputeCommand`、`Mobile()` / `ForCurrentPlatform()` を追加する。

#### P2 の方式決定(2026-09-16、着手前)

- **ポストプロセスの分割**: 既存の `IPostProcessPass` 実装(`MotionBlurPass` / `BloomPass` / `TonemapPass`)は
  compute の実体を持つので捨てず、**`MotionBlurEffect` / `BloomEffect` / `TonemapEffect`(基底 `IPostProcessEffect`)に改名**して
  `Rendering/PostProcess/Effects/` に置く。パイプライン側の `Pipeline/Passes/MotionBlurPass` / `BloomPass` / `TonemapPass` が
  それぞれの Effect を所有する(名前の衝突を避けつつ、ゲームが `Add<BloomPass>()` と書ける)。
  `PostProcessChain` / `IPostProcessRenderer` / P1 の `PostProcessPass` は削除。`PostProcessContext` は Effect の内部引数として残す
  (設計時は掲示板へ置き換える予定だったが、Effect 内部の引数束ねに過ぎないので改名だけに留める)
- **ポストの受け渡し**: 「現在の色」は `PostInput` キーで運ぶ。`MotionBlurPass::Build` は実行したときだけ自分の出力を
  `PostInput` に書き、しなかったら `Scene` を書く(実行時に決まるので `Build` 内で掲示板を更新する)。
  `BloomPass` は `PostInput` があればそれ、無ければ `Scene` を読んで `BloomTexture` を書く。
  `TonemapPass` は同様に読んで `Output` を書き、最後に `SetRenderTargetCommand(Output)` を積む(UI が描けるように)。
  宣言は `ReadsOptional(PostInput)` / `ReadsOptional(BloomTexture)` にする(MotionBlur や Bloom が無い列でも組めるように)
- **モーションブラー強度の入口**: `IPostProcessRenderer::SetMotionBlurStrength` は無くなるので、AquaDash は
  `renderer_.GetPipeline()->Find<MotionBlurPass>()->SetStrength()` に変える(Game 側の変更 1 箇所)。
  `Renderer::GetPostProcessRenderer()` は削除
- **デバッグパネル**: `PostProcessDebugPanel` は 3 つの Effect のポインタを受ける形にし、Application は `Find<...>()` で集めて生成する
- **汎用フルスクリーンコマンド**は compute 版とし、名前を `FullscreenComputeCommand` にする。
  引数: CS(`IShader*`)、入力 RT ハンドル最大 4 つ(t0〜)、出力 RT ハンドル(u0)、定数バッファ(`IConstantBuffer*` + 最大 256 バイトのブロブ)、幅・高さ。
  `Execute` は `TonemapPassCommand` と同じ手順(RTV を外す → CB 更新 → SRV/UAV バインド → 8×8 の Dispatch → 全部外す)
- **プリセットの選択**: `RendererPreset::pipeline`(`Standard` / `Mobile` / `Auto`。既定 `Standard`)を足す。
  `SetupStandardRenderers` は既定のまま `Standard` を組むので AquaDash の iOS / Android の絵は変わらない。
  `Auto` は `ForCurrentPlatform()`(`AQ_PLATFORM_ANDROID` / `AQ_PLATFORM_IOS` なら `Mobile`)。
  `Mobile()` = Shadow(任意)→ Forward → Sky → Particle → Tonemap → UI(GBuffer を持たない)
- **ゲームが列を組む入口**: `Application::BuildStandardPipeline(preset)` が UI パス込みの `PipelineBuilder` を返す(protected)。
  ゲームはそれに `InsertBefore<UIPass>(...)` などしてから `SetRenderPipeline(builder.Build(w, h))` する。
  `SetupStandardRenderers(preset)` はこの 2 行の包み
- **Sample の 4 歩目「描画パスを足す」**: エンジン所有の `aqEngine/Assets/Shader/Vignette.fx`(compute。画面の縁を暗くする)を足し、
  Sample 側に `VignettePass`(`Reads Output` / `Writes Output`、自前 RT を `Setup` で作り `FullscreenComputeCommand` で描く)を書いて
  `InsertBefore<UIPass>` で挟む。シェーダをエンジン側に置くのは、ゲーム側シェーダのクロスコンパイル経路が
  まだ無いため(Apple / Android は事前コンパイルが要る。別課題)

##### 発見と教訓

- `aq.h` が供給するパスのヘッダはポスト 3 パスだけ。ゲームが `InsertBefore<UIPass>` のように目印に使うパスは自分で include する
