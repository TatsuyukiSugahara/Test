# AQ-DLC(aqEngine Development Life Cycle)

AWS の AI-DLC(AI-Driven Development Life Cycle)を、1 人 + Claude の個人開発向けに縮めたもの。
設計 → 設計レビュー → 承認 → 実装 → テスト → コミット の順で進める。

AI 駆動開発の基本サイクル。まとまった機能は必ずこの流れで進める。
1 サイクル = 1 フェーズ(半日〜1日で終わる粒度)に分割し、大きな機能は複数サイクルに割る。

```
① 設計書を書く ─▶ ② 設計レビュー(Codex CLI) ─指摘ありなら直して再レビュー─┐
                         │ 指摘なし                                              │
                         ▼                                                       │
              ★ ユーザー承認(必須。ここで止まる) ◀──────────────────────────────┘
                         │
   ┌─────────────────────▼──────────────────────────────────────────┐
   │ フェーズごとに繰り返す                                          │
   │ ③ 実装(サブエージェント) ─▶ ④ テスト・評価 ─▶ ⑤ コミット ─┐   │
   │        ▲   設計の食い違い → ①へ戻して再承認                  │   │
   │        └──────────────── 次のフェーズへ ◀───────────────────┘   │
   └────────────────────────────────────────────────────────────────┘
```

**止まってよいのは次の場合だけ**: ★ユーザー承認 / 設計との食い違い(設計変更が要る) /
ビルドやテストが直せない / 自動で確認できない項目(見た目・操作感)のユーザー確認。
それ以外は承認後、コミットまで止まらずに進める。

## モデルの役割分担

| 役割 | 担当 | 方法 |
|---|---|---|
| 設計・判断(案を考える / 指摘の採否 / 評価 / コミット) | **メイン会話** | 本体で直接行う。サブエージェントに委譲しない |
| 設計レビュー(設計書を実コードと突き合わせて指摘する) | **Codex**(Claude の外) | 本体が `codex exec` を読み取り専用で実行して指摘を受け取る。採否と修正は本体 |
| 実装(設計済みコードを書く) | サブエージェント | Agent ツールで起動。`model` は下記の方針で Claude が選ぶ |
| 調査(既存資産の探索・読み取り) | Explore サブエージェント | 独立した調査は複数を**並列**起動してよい |

### サブエージェントのモデル選択

- **モデルはタスクの難しさに応じて Claude が判断する。** 固定しない。
  - 設計書が詳細で、機械的に書ける実装(定型コンポーネント / System、既存パターンの横展開、
    登録作業、リネーム等)→ `sonnet`。軽い調査・単純な編集は `haiku` でもよい。
  - 設計の解釈を要する実装、スレッド境界・GPU 同期・ライフタイムなど罠の多い箇所、
    既存コードの深い理解が要る変更 → `opus` を選んでよい。
  - 迷ったら `sonnet`。失敗や差し戻しが続くときだけ上位へ切り替える。
- **`fable` は指定しない。** `model` に `fable` を渡さない(`subagent_type: "fork"` も
  使わない。fork は本体のモデルを引き継ぐため)。
- 独立した実装タスク(別ファイル・別サブシステム)は **1 メッセージで複数の
  Agent 呼び出しを並列に**出す。依存があるものは直列にする。

## ① 設計(メイン会話)

1. **既存資産を先に読む。** 関連する `DirectX/設計書/*.md`、ゲーム側設計書
   (`Game/Design/**/*.md`)、および対象の実コード(ヘッダ中心)を確認する。
   推測で設計しない。再利用できる既存機構(Prefab / Level / ThreadPool /
   UIScreen 等)を必ず洗い出す。調査範囲が広い場合は Explore サブエージェントを
   複数並列で出してよい(結論だけ受け取る)。設計判断そのものは本体で行う。
2. **設計書を書く。** 運用規約は CLAUDE.md の「設計書の運用規約」に従う:
   - タイトル直下に `> 対象コミット: <hash> / 最終更新: <日付>`
   - 責務表(クラス/ファイル別)+ 末尾チェックポイント(`- [ ]`)
   - 同じ内容を 2 つの設計書に書かない(一次資料を決めてリンク参照)
   - 置き場所: エンジン機能は `DirectX/設計書/`、ゲーム固有は `Game/Design/<プロジェクト>/`
3. **フェーズ分割を明記する。** 各フェーズに「実装内容 + 評価チェックリスト」を付ける
   (例: `Game/Design/AquaDash/05_実装フェーズ計画.md`)。
4. 設計書は**テスト方針**も含める: 各フェーズで何を自動確認し(ビルド・既存テスト・起動と撮影など)、
   何をユーザー確認に残すかを評価チェックリストに分ける。

## ② 設計レビュー(Codex CLI)

レビューは **Codex** が行う。Claude(サブエージェント含む)はレビューしない
(書いた側と別の目で見るため)。

### 実行方法

本体が Bash で `codex exec` を実行する(`~/.local/bin/codex`。実体は
`/Applications/ChatGPT.app/Contents/Resources/codex-cli/bin/codex`。ChatGPT ログインで動く。
**Plus の利用枠を消費する**ので、1 回の依頼で設計書 1 本に絞る)。

```bash
source ~/.local/aq-mac-env.sh   # PATH に codex を通す
codex exec -s read-only -C <repo> --ephemeral \
  -o <scratchpad>/review-<設計書名>.md \
  "<設計書パス> を実コードと突き合わせてレビューしてください。設計書は編集せず、
   指摘の一覧(重大/中/軽、設計書の該当箇所、根拠となるコードのパス)だけ返してください。
   観点: ... 指摘が無ければ「指摘なし」と返してください。"
```

- `-s read-only` で Codex にファイルを書き換えさせない。`-o` に最終メッセージが保存されるので、それを読む。
- 所要は設計書 1 本で 1〜2 分程度。タイムアウトは長め(10 分)に取る。
- 結果ファイルはスクラッチパッドに置く(リポジトリに入れない)。

### 点検してもらう観点(依頼文に含める)

- 実コードとの食い違い(存在しない API・クラス、誤った前提)、既存機構の見落とし・二重実装
- スレッド境界・ECS 遅延コマンド・Bridge 抽象(`cpp-gamedev` の architecture.md)への違反
- フェーズ分割の妥当性(1 フェーズが大きすぎないか、依存順が正しいか)
- 評価チェックリストが検証可能か(確認方法・条件・許容差が書かれているか)
- 運用規約(CLAUDE.md「設計書の運用規約」)の遵守

### 手順

1. 設計書を書き終えたら、上記コマンドでレビューを実行する。
2. 返ってきた指摘を、本体が**1 件ずつ実コードで事実を確かめてから**採否を判断し、設計書を直す。
   不採用の指摘は理由を添えて記録する(承認時に報告する)。
3. 直したら再レビューする。**再レビューは「前回の指摘が直ったか + 新たな重大・中が無いか」に絞る**
   (枠の節約)。重大・中の指摘が無くなるまで繰り返す。同じ指摘が 3 回続くなど収束しないときは
   ユーザーに判断を仰ぐ。
4. **★ユーザーの承認を得てから実装に入る(必須)。** 設計の要点(方式の選択理由・エンジン側変更の
   有無・フェーズ分割・テスト方針)と、Codex の指摘と対応(不採用の理由を含む)の要約を提示して止まる。
   承認はフェーズ分割を含む設計書全体に対して 1 回。承認後に設計を変えたときだけ再承認を取る。
   **Codex のレビュー通過は承認の代わりにならない。**

### Codex を呼べないとき

`codex` が無い・ログイン切れ・利用枠切れで実行できないときは、手渡しにする。設計書のパス・観点・
依頼文をユーザーへ提示して止まり、ユーザーが Codex(アプリ等)で実行した指摘を受け取って
手順 2 以降へ進む。ユーザーが「Claude でやって」と明示したときだけ、別のサブエージェントで代行してよい。

## ③ 実装(サブエージェントへ委譲)

1. 対象は**現在のフェーズ 1 つだけ**。先のフェーズの実装を先取りしない。
2. **実装は Agent ツールへ委譲する(`model` は上記の方針で選ぶ)。** タスク分割の指針:
   - 独立したファイル群・サブシステム単位で分け、**並列**に起動する
     (例: 「走行 System 一式」と「UI 画面一式」は並列可)。
   - **共有ファイル(GameSources.props / *.filters / GameFlow.* /
     Application.cpp 等)は 1 つのエージェントに集約するか本体で編集**し、
     複数エージェントに同じファイルを触らせない(競合防止)。
   - ごく小さな修正(数行のパラメータ調整など)は委譲せず本体で直してよい。
3. **サブエージェントへのプロンプトに必ず含めるもの**:
   - 該当フェーズの設計書パスと「設計書どおりに実装せよ。設計変更は行わず、
     食い違いは報告せよ」という指示
   - 最初に `cpp-gamedev` スキル(規約)を読むこと。新規ファイル追加時は
     `vs-project-files` スキルに従うこと(共有ファイルを担当させる場合のみ)
   - スレッド境界(architecture.md §5)と ECS 遅延コマンド規約の遵守
   - 対象ファイルの明確なリスト(書いてよいファイル / 触ってはいけないファイル)
   - ビルドはエージェント側では行わない(本体が③でまとめて行う)こと
4. **完了後、本体(メイン会話)が全差分をレビューする。** 規約逸脱・設計との食い違い・
   統合ミスは本体で修正するか、指摘を付けて同じエージェントへ SendMessage で差し戻す。
5. 実装中に設計と食い違いが出たら、勝手に設計を変えず、①へ戻して設計書を
   直してから続ける(設計変更は再レビュー → 再承認。小さな命名変更などは実装後に設計書へ反映でよい)。

## ④ テスト・評価(メイン会話)

1. **ビルドを通す。** ビルド方法・落とし穴は該当プラットフォームの移植設計書
   (`DirectX/設計書/`)と README、CLAUDE.md を参照する。警告の増加も確認する。
2. **テスト。** 既存のテストがあれば回し、設計書のテスト方針で自動確認とした項目を実行する。
   該当フェーズの評価チェックリストを 1 項目ずつ実際に確認する(起動・撮影・ログなど。
   Mac の手順は memory と移植設計書)。
   自動で確認できない項目(見た目・操作感)だけ、ユーザーに確認ポイントを箇条書きで
   提示し、結果を聞く。
3. **設計書へ反映。** チェックボックスを埋め、実装で変わった点・発見した課題を
   設計書(または README の既知の課題)に追記する。`対象コミット` を更新する。
## ⑤ コミット(メイン会話)

1. **コミット。** `git-commit` スキルの規約(タグ + 内容)に従う。
   コミット前に改行/BOM の混在に注意(既存ファイルの改行コード・BOM は保持する。CLAUDE.md 参照)。
2. **到達点の記録。** フェーズ完了状態・次のフェーズ・非自明な落とし穴は
   **設計書の「到達点」「発見と教訓」節が正本**(memory はリポジトリに入れない)。
   memory には「どの設計書のどこを読むか」とこの PC 固有の手順だけを残す。
3. 全チェックが埋まったら次のフェーズの③へ(承認済みの設計の範囲内)。埋まらない項目が残る場合は
   その旨をユーザーに報告し、対応方針(修正 / 保留)を確認する。

## 禁止事項

- 設計書なし・設計レビューなし・ユーザー承認なしでまとまった機能の実装を始めること。
- 複数フェーズをまとめて 1 コミットにすること。
- 評価チェックリストを実際に確認せずチェックを埋めること。
- 設計・評価・コミットの判断をサブエージェントへ委譲すること(実装と調査のみ委譲可)。
- 設計レビューを Claude 自身(サブエージェント含む)で済ませること(レビューは Codex。
  ユーザーが「Claude でやって」と明示したときだけ別エージェントで代行してよい)。
- Codex に設計書やコードを編集させること(必ず `-s read-only`)。
- Codex の指摘を実コードで確かめずに設計へ反映すること。
- 複数のサブエージェントに同じファイルを並行編集させること。
