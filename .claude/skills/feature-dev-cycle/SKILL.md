# 設計 → 実装 → 評価 サイクル

AI 駆動開発の基本サイクル。まとまった機能は必ずこの 3 フェーズで進める。
1 サイクル = 1 フェーズ(半日〜1日で終わる粒度)に分割し、大きな機能は複数サイクルに割る。

```
┌─▶ ① 設計 ──承認──▶ ② 実装 ──ビルドOK──▶ ③ 評価 ──┐
│      ▲                                              │
│      └────── 設計に問題が見つかったら差し戻し ──────┘
└──────────────── 次のフェーズへ ──────────────────────┘
```

## ① 設計フェーズ

1. **既存資産を先に読む。** 関連する `DirectX/設計書/*.md`、ゲーム側設計書
   (`Game/Design/**/*.md`)、および対象の実コード(ヘッダ中心)を確認する。
   推測で設計しない。再利用できる既存機構(Prefab / Level / ThreadPool /
   UIScreen 等)を必ず洗い出す。
2. **設計書を書く。** 運用規約は `cpp-gamedev` スキルの
   `references/architecture.md` §6 に従う:
   - タイトル直下に `> 対象コミット: <hash> / 最終更新: <日付>`
   - 責務表(クラス/ファイル別)+ 末尾チェックポイント(`- [ ]`)
   - 同じ内容を 2 つの設計書に書かない(一次資料を決めてリンク参照)
   - 置き場所: エンジン機能は `DirectX/設計書/`、ゲーム固有は `Game/Design/<プロジェクト>/`
3. **フェーズ分割を明記する。** 各フェーズに「実装内容 + 評価チェックリスト」を付ける
   (例: `Game/Design/AquaDash/05_実装フェーズ計画.md`)。
4. **ユーザーの承認を得てから実装に入る。** 設計の要点(方式の選択理由・エンジン側変更の
   有無・フェーズ分割)を要約して提示する。

## ② 実装フェーズ

1. 対象は**現在のフェーズ 1 つだけ**。先のフェーズの実装を先取りしない。
2. コーディング規約は `cpp-gamedev` スキルに従う(設計に関わるコードは
   architecture.md 必読)。
3. 新規 .cpp/.h の追加・リネーム・削除は `vs-project-files` スキルに従い
   vcxproj / filters へ登録する。
4. スレッド境界(architecture.md §5)と ECS 遅延コマンド規約を守る。
   非同期化できるロード・重い処理は ThreadPool / 既存非同期経路に載せる。
5. 実装中に設計と食い違いが出たら、勝手に設計を変えず、①へ戻して設計書を
   直してから続ける(小さな命名変更などは実装後に設計書へ反映でよい)。

## ③ 評価フェーズ

1. **ビルドを通す。** ビルド方法・落とし穴は memory(`project-d3d12-backend.md` 等)と
   README を参照する。警告の増加も確認する。
2. **実機確認。** 該当フェーズの評価チェックリストを 1 項目ずつ実際に確認する。
   自動で確認できない項目(見た目・操作感)はユーザーに確認ポイントを箇条書きで
   提示し、結果を聞く。
3. **設計書へ反映。** チェックボックスを埋め、実装で変わった点・発見した課題を
   設計書(または README の既知の課題)に追記する。`対象コミット` を更新する。
4. **コミット。** `git-commit` スキルの規約(タグ + 内容)に従う。
   コミット前に改行/BOM の混在に注意(memory: `repo-line-endings-bom.md`)。
5. **memory 更新。** フェーズ完了状態・次のフェーズ・非自明な落とし穴を
   プロジェクト memory に記録する。
6. 全チェックが埋まったら次のフェーズの①へ。埋まらない項目が残る場合は
   その旨をユーザーに報告し、対応方針(修正 / 保留)を確認する。

## 禁止事項

- 設計書なし・承認なしでまとまった機能の実装を始めること。
- 複数フェーズをまとめて 1 コミットにすること。
- 評価チェックリストを実際に確認せずチェックを埋めること。
