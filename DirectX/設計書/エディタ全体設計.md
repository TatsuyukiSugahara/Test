2. 実装の分担の目安: (A) ImGui 本体の差し替え・`imgui.vcxproj`・CMake・`AQ_RENDER_PIPELINED` との排他・シャドウ深度マップの表示停止 → (B) D3D12 の置換と (C) Vulkan の置換を並行。`D3D12ImGui.cpp` / `VulkanImGui.cpp` はファイル名を残して公式バックエンドを呼ぶ接続層に書き換えると、vcxproj を触らずに済む。

**この PC 固有の手順**(別 PC では読み替える):

- msbuild: `C:\Program Files\Microsoft Visual Studio\18\Community\MSBuild\Current\Bin\MSBuild.exe`。例: `Game\DirectX.vcxproj /p:Configuration=Debug /p:Platform=x64 "/p:SolutionDir=<repo>\DirectX\\" /p:AqGraphicsApi=D3D12`。Editor は `Editor\Editor.vcxproj` を `Configuration=Editor_Debug`。
- 起動確認: 作業ディレクトリを `DirectX/Game` にして exe を起動し、数秒後に `CloseMainWindow()` で閉じて終了コードと `Game/startup_timing.log` の `[crash]` を見る。
- 設計レビュー: Codex CLI を `codex exec -s read-only -C <repo> --ephemeral -o <出力> "<依頼文>"` で使う(Windows では Codex アプリの `app\resources\codex.exe`)。
- GameUWP(DebugXbox)はこの PC にストア向けツールセットが無くビルドできない。vcxproj の差分で確認する。

## 1. 目的とスコープ

aqEngine に、Unity に近い操作感のエディタを追加する。現状はランタイム上に ImGui を重ねており、ゲーム画面が狭く見づらい。これを「エディタ用ビルド」と「ランタイム用ビルド」に分けて解決する。

### 作るもの

- エディタ用 exe(Editor)とランタイム用 exe(Game)の 2 系統のビルド
- ゲームビュー、ヒエラルキー、インスペクター、コンテンツブラウザ、コンソールのパネル(Docking / Multi-Viewport)
- 既存リフレクションの拡張(フィールド属性、文字列、フィールド単位の編集イベント)
- Level の編集・保存・読み込み(既存の `.level.json`)
- Play モード(再生、一時停止、停止)と Undo/Redo
- ゲーム内デバッグ UI は、従来どおりゲーム画面の中に表示する

### 初版では作らないもの

- アセットの GUID・.meta・マニフェスト(パス参照のまま進める。14 章に将来案として残す)
- エディタスクリプト(Python)。12 章に構想を残し、着手時に別の設計書に起こす
- Prefab 参照ノードの override 編集 UI(既存 override の**無変更保存**だけは保証する)
- プレハブのバリアント、スクリプトのホットリロード
- WPF 外部エディタ([アプリケーション構成とエディタ連携設計](アプリケーション構成とエディタ連携設計.md))との統合
- Xbox/UWP、Android、iOS でのエディタ動作(ランタイムのみ対象)
- 複数人での同時編集

### 一次資料の分担

同じ内容を 2 つの設計書に書かないため、次のように分担する。本書は「エディタとしての全体接続」と「エディタのために足す差分」だけを書く。

| Reflect / ComponentRegistry / JSON 形式 / 型消去 / Prefab の形式・生成・override | [Prefab設計](Prefab設計.md) |
| Level の形式・ロード・アンロード・LevelEditorPanel | [Level設計](Level設計.md) |
| AppHost / IAppModule / 起動引数 / LinkService | [アプリケーション構成とエディタ連携設計](アプリケーション構成とエディタ連携設計.md) |

## 3. プロジェクト構成とビルド構成

### 3.1 方針

- **既存構成への追加にとどめる。** 既存の Debug / Release / Profile / DebugXbox / ReleaseXbox の意味と出力は変えない。
- エディタ構成は **Windows デスクトップ(x64)の VS ソリューションだけ**に足す。CMake(Mac)への追加は E10 で行う。
- 静的ライブラリ内の `#if` は、そのライブラリをビルドした構成で決まる。exe だけにマクロを付けても切り替わらないので、エディタ構成では aqEngine と GameLogic も別にビルドする。

### 3.2 プロジェクト

| プロジェクト | 種類 | 現状 | 変更 |
|---|---|---|---|
| imgui | 静的ライブラリ | 既存 | E1 で docking 版 + 公式バックエンドへ更新 |
| aqEngine | 静的ライブラリ | 既存 | エディタ構成を追加。エディタ支援コードを `aqEngine/Editor/` に置く |
| Bullet(3 プロジェクト) | 静的ライブラリ | 既存 | エディタ構成は Debug / Release の成果物を使う(`AQ_EDITOR` に依存しないため別ビルドしない) |
| **GameLogic** | 静的ライブラリ | **新規** | `Game/Application/` のうちエントリ以外を収める。デスクトップ VS 構成のみ |
| Game | exe | 既存 | エントリ(`Main.cpp`)だけを持ち、GameLogic をリンクする |
| GameUWP | exe | 既存 | 従来どおりゲームのソースを直接コンパイルする(エントリを props から自分の vcxproj へ移すだけ) |
| **Editor** | exe | **新規** | エディタのエントリ、パネル、コマンド、`EditorContext` |

`GameSources.props` は「ゲームロジックのソース一覧」に限定し、エントリ(`Main.cpp`、`UWPMain.cpp`)は各 exe の vcxproj へ移す。GameLogic.vcxproj と GameUWP.vcxproj が同じ props を読むので、ソースの追加は今までどおり 1 か所で済む。CMake(Mac / iOS / Android)は E10 まで現状のまま(`Application` 以下の再帰収集)。

### 3.3 依存のルール

- aqEngine と GameLogic は、Editor プロジェクトのヘッダーをインクルードしない。
- エンジン内部に触れるエディタ支援コード(GraphicsDevice への ImGui テクスチャ登録、エディタ用フック)は `aqEngine/Editor/` に置き、ファイル全体を `#if AQ_EDITOR` で囲む。
- 編集モデル(`LevelEditModel`、7 章)は既存の Level エディタも使うので、`aqEngine/Level/` に置き `AQ_DEBUG_IMGUI` で囲む。
- パネル、コマンド、Undo/Redo など、エンジンの公開 API で書けるものは Editor プロジェクトに置く。
- 両 exe は既存の `app::RegisterAppModules()` を呼んで GameModule を登録する。これがリンクの入口になり、GameLogic.lib の .obj が落ちない。

### 3.4 ビルド構成とマクロ

| 構成 | AQ_EDITOR | AQ_IMGUI | AQ_DEBUG_IMGUI | 最適化 | ビルド対象の exe |
|---|---|---|---|---|---|
| Debug(既存) | 0 | 定義 | 定義 | なし | Game |
| Release(既存) | 0 | 定義 | 未定義 | あり | Game |
| Profile / DebugXbox / ReleaseXbox(既存) | 0 | 既存のまま | 既存のまま | 既存のまま | 既存のまま |
| **Editor_Debug**(新規) | 1 | 定義 | 定義 | なし | Editor |
| **Editor_Release**(新規) | 1 | 定義 | 定義 | あり | Editor |

- **`AQ_EDITOR=1` のときは `AQ_DEBUG_IMGUI` も必ず定義する。** 既存のインスペクター、Prefab / Level エディタ、`EntityDebugTag` が `AQ_DEBUG_IMGUI` でコンパイルされるため。逆(`AQ_DEBUG_IMGUI` だけ)は従来のランタイムのデバッグ UI。
- マクロはプロパティシート `Editor.props`(新規)に 1 か所だけ書き、エディタ構成の全プロジェクトが取り込む。
- `AQ_EDITOR` の既定値は `aq.h`(PCH)の先頭付近で `#ifndef AQ_EDITOR` / `#define AQ_EDITOR 0` とする。`aq.h` は CRLF・BOM なし(E0a で確認)なので、それを保って編集する。
- `#if AQ_EDITOR` と書く(値は 0 か 1)。既存の `AQ_IMGUI` などは `#ifdef` のまま変えない。
- 中間ファイルと出力は構成ごとに分ける(`x64\Editor_Debug\` など)。混ざると、エディタ用の lib をランタイムの exe がリンクしてしまう。

### 3.5 ifdef の運用

| 書いてよい場所 | 例 | 書き方 |
|---|---|---|
| エディタ支援コード | ImGui テクスチャ登録、エディタ用フック | `aqEngine/Editor/` のファイル全体を囲む |
| エンジンの入口 | AppHost のフック呼び出し、エディタ支援の初期化と終了 | 呼び出し数か所のみ |

- 既存のコンポーネントやクラスのメンバ変数を ifdef で増減させない。構成間でレイアウトが変わり、保存データの互換も崩れる。
- 関数の途中に細かい ifdef を散らさない。関数ごと分けて、ランタイム側は空実装にする。
- グローバル変数のコンストラクタによる自動登録は使わない(静的ライブラリでは参照されない .obj が落ちる)。

## 5. フレームの流れと ImGui の 2 コンテキスト

### 5.1 コンテキスト

| コンテキスト | 所有者 | 描画先 | Docking / Multi-Viewport | 入力 |
|---|---|---|---|---|
| ゲーム用 | AppHost(既存のもの) | ランタイム: バックバッファ(現行どおり)<br>エディタ: `displayRT` | 無効 | ランタイム: 現行どおり<br>エディタ: エディタが毎フレーム転送する |
| エディタ用 | Editor(AQ_EDITOR=1 のみ) | バックバッファと、外に出した各ウィンドウ | 有効 | プラットフォームバックエンド(win32)から |

- **コンテキストは常に明示的に切り替える。** `ImGui::SetCurrentContext()` を挟まずに `ImGui::GetIO()` 等を呼ぶ既存箇所(AppHost の入力抑制など)は、ゲーム用コンテキストを明示して呼ぶように直す。
- フォントアトラスは 2 つのコンテキストで共有する(`ImGui::CreateContext(sharedAtlas)`)。アトラスは AppHost が所有し、両コンテキストの破棄後に解放する。
- プラットフォームバックエンド(win32)はエディタ用コンテキストにだけ接続する。ゲーム用コンテキストには、エディタが `io.AddMousePosEvent` などで入力を転送する。座標はゲームビュー上の位置を `displayRT` の座標へ換算したもの(縮小表示の倍率を含む)。`io.DisplaySize` は `displayRT` のサイズにする。
- ゲームビューにフォーカスがない間は、既存の `InputManager::SetFocusBlocked()` でゲーム入力(キーボード・マウス・パッド)を止める。

### 5.2 エディタ用フック

ループは従来どおり `IPlatform::RunFrameLoop` → `AppHost::Update` のままにする。AppHost は Editor のヘッダーを知らないので、エンジン側にインターフェースを置き、Editor が実装して起動時に登録する(`AppModuleRegistry` と同じ考え方)。

実行モードの型は ECS とランタイムも使うので、常にコンパイルされる共通ヘッダーに置く。`IEditorLayer` だけをエディタ限定にする。

```cpp
// aqEngine/Core/RunMode.h(常にコンパイル)
namespace aq
{
	/** 実行モード。ランタイムは常に Play */
	enum class RunMode : uint8_t
	{
		Edit,
		Play,
		Pause,
	};

	/** System がどのモードで動くかの宣言(Play は常に動く) */
	enum class RunModeMask : uint8_t
	{
		PlayOnly	= 0,
		Edit		= 1 << 0,
		Pause		= 1 << 1,
	};
}
```

```cpp
// aqEngine/Editor/IEditorLayer.h(#if AQ_EDITOR)
namespace aq
{
	/** AppHost がフレームの決まった位置で呼ぶエディタ側の処理 */
	class IEditorLayer
	{
	public:
		virtual ~IEditorLayer() = default;

		/** フレーム先頭。前フレームに要求されたモード遷移を確定し、入力の行き先を決める */
		virtual void OnBeginFrame() = 0;
		/** このフレームのモード。OnBeginFrame で確定し、フレームの途中では変えない */
		virtual RunMode GetMode() const = 0;
		/** エディタ用コンテキストでパネルを構築し、発行されたコマンドを適用する */
		virtual void OnBuildUI() = 0;
		/** エディタ用コンテキストの描画データを確定する(ImGui::Render と UpdatePlatformWindows) */
		virtual void OnEndFrame() = 0;
	};
}
```

### 5.3 エディタビルドの 1 フレーム

**既存の `AppHost::Update` の順序は変えない。** フックを挟む位置と、モードによって飛ばす処理だけを決める。担当は「メイン」= メインスレッド、「レンダー」= RenderThread。エディタ構成は直列(`AQ_RENDER_PIPELINED` 無効)に固定するので、レンダーの実行中はメインが `FlushRender()` で止まっている。

| 順 | 担当 | 処理(既存は太字なし、追加は **太字**) | Edit | Play | Pause |
|---|---|---|---|---|---|
| 1 | メイン | **`OnBeginFrame`**: 前フレームに要求されたモード遷移を確定する(8.1)。ゲームビューのホバーとフォーカスから入力の行き先を決め、`SetFocusBlocked` を設定する | ○ | ○ | ○ |
| 2 | メイン | ImGui の入力抑制(ゲーム用コンテキストを明示)と `InputManager::Update` | ○ | ○ | ○ |

- ランタイムビルドでは 1・7・12・15・16 がなく、3・8・9 は常に Play の列で動く。14 のゲーム用 ImGui は現行どおりバックバッファへのコピーの後に描く。

### 5.4 描画抽象に足すもの

Editor プロジェクトは DX12 や Vulkan の型を扱わない。API ごとの差は GraphicsDevice の Bridge(`IGraphicsDeviceImpl`)に閉じ込める。具象クラス `Renderer` には置かない。

| 追加する API | 内容 |
|---|---|
| `ImTextureID GraphicsDevice::GetImGuiTextureId(RenderTargetHandle rt)` | RT を `ImGui::Image` に渡せる ID に変換する。DX11 は SRV、DX12 は ImGui 用ヒープ区画の GPU ハンドル、Vulkan は `ImGui_ImplVulkan_AddTexture` の DescriptorSet、Metal は `id<MTLTexture>`。未対応のバックエンドは無効 ID を返す |
| ImGui 描画先の指定 | ゲーム用の描画データを任意の RT(`displayRT`)へ描く経路と、エディタ用の描画データをバックバッファへ描く経路を分ける。現行の Vulkan / Metal は「描画データを 1 つ保存し、`CopyToBackBuffer` の末尾でスワップチェーンに描く」契約なので、2 つの描画先を表せる形に変える |

テクスチャ ID の寿命:

- ID は**毎フレーム取得し直す**。パネルがフレームをまたいで保持しない。
- RT の作り直し(E3b のリサイズ)で ID は無効になる。作り直しは完了待ちの中で行うので、使用中の ID が消えることはない。
- 登録の解除(Vulkan の DescriptorSet など)は RT の破棄と同じ箇所で行う。

### 5.5 ゲームビューのサイズ

- **E2 ではレンダー解像度を変えない。** `displayRT` はウィンドウのクライアントサイズに追従する既存の挙動のまま(D3D12 は固定寸法)。ゲームビューにはアスペクト比を保って縮小表示し、余白は黒にする。入力の座標換算(5.1)もこの倍率を使う。
- **E3b でゲームビューにレンダー解像度を追従させる。** 既存の `HandleRenderResize` は提示面(スワップチェーン)と RT を一緒に作り直すので、エディタでは「提示面はウィンドウに追従」「RT とパイプラインはゲームビューに追従」と分ける。D3D12 の `SupportsRenderResize` / `ResizeMainTargets` / `ReleaseOffscreenRenderTarget` の実装を E3b の前提作業にする。
- E3b では、ゲームビューのサイズ変更はドラッグ中は要求を上書きするだけにし、サイズが 2 フレーム続けて変わらなかったときに確定する。完了待ちを伴うリサイズを毎フレーム走らせないため。

### 5.6 注意点

- **エディタ構成は直列に固定する。** `ImGuiRenderCommand` は `ImDrawData*` しか持たないので、PIPELINED ではメインの次の `NewFrame` とレンダーの読み取りが重なりうる(コード構造からの推測、未再現)。エディタで PIPELINED を許すには、描画データをフレーム所有のコピーにする必要がある。解除条件として 15 章に残す。
- ゲームのカメラのアスペクト比は `displayRT` のサイズ(`GetRenderWidth/Height`)から計算されている(5.8 節で確認済み)。

→ 詳細は [E2_ゲームビューと入力](エディタ/E2_ゲームビューと入力.md) に分けた(旧 5.7、5.8 節)。


→ 詳細は [E3_解像度とMultiViewport](エディタ/E3_解像度とMultiViewport.md) に分けた(旧 5.9、5.10 節)。

## 6. リフレクションの拡張

### 6.1 既存の仕組み(一次資料は [Prefab設計](Prefab設計.md) 5 章)

- コンポーネントは `IComponent` を継承し、`ecsComponent(型名)` で型情報を持つ。
- 永続フィールドは、メンバテンプレート `Reflect(V& visitor)` の中で `visitor.Field("キー", 値, "ラベル")` と列挙する。JSON 保存・読込(`JsonFieldVisitor`)と ImGui 編集(`ImGuiFieldVisitor`)が同じ列挙を共有する。
- `ComponentRegistry` が型ごとの `ComponentMeta`(`serialize` / `deserialize`、型消去版の `serializePtr` / `deserializePtr` / `drawInspectorPtr`、`requiredWith`、`add` / `remove`)を持つ。JSON のキーは `typeName`(名前)。
- 型の識別は `TYPE_INFO` の `size_t` ハッシュ。初版の `aqHash32` による型 ID は採らない。永続化はすべて名前(`typeName` とフィールドのキー)で行う。

### 6.2 足すもの

| 追加 | 内容 | 使う所 |
|---|---|---|
| フィールド属性 | `Field()` に省略可能な属性を足す(最小・最大、ツールチップ、読み取り専用、非公開、アセットの種類)。属性は小さな値型で、ランタイムでもコンパイルされる(ifdef で消さない) | インスペクター、将来のスクリプト |
| 文字列フィールド | `std::string` 用の `Field()` を各 Visitor に足す。パス参照(モデル、Prefab、テクスチャ)はこれで扱う | インスペクター、コンテンツブラウザのドロップ先 |
| 編集イベント Visitor | 編集用のコピーに対してウィジェットを描き、フィールドごとに「編集開始(変更前の値)」「変更中(現在の値)」「確定(変更後の値)」を、キーと JSON 値の組で返す。対象を直接書き換えない | インスペクター(7.4) |
| コンポーネントの公開情報 | `ComponentMeta` に「インスペクターから追加・削除してよいか」「カテゴリ」を足す | Add Component パレット |

```cpp
// 例: TransformComponent の Reflect(既存の形に属性を足すだけ)
template <typename V>
void Reflect(V& visitor)
{
	visitor.Field("position", position, "position (local)");
	visitor.Field("scale",    scale,    "scale    (local)", FieldAttr{}.Min(0.001f).Tooltip("0以下にしない"));
	visitor.Field("rotation", rotation, "rotation (local)");
}
```

属性の具体的な型名と、既存の Visitor の `Field()` オーバーロードへの足し方は 6.4 節で決めた。既存の `drawInspectorPtr`(直接書き換え)は Prefab エディタのために残し、エディタのインスペクターは編集イベント Visitor を使う。

### 6.3 値の保存と復元

- **バイトコピーはしない。** Undo の値の控え、コピー&ペーストは、すべて JSON で行う。文字列・配列・リソース参照を持つ型も同じ経路で扱え、`deserialize` が持つ復元後処理(モデルの再読込など)もそのまま効く。
- フィールド単位の値は `{ "キー": 値 }` の疎な JSON として扱う。`deserialize` に疎な JSON を渡したとき、書かれていないキーを変えないことを E6 で確認する(TODO)。
- Reflect 化されていないコンポーネント(`serialize` が nullptr)は、インスペクターで読み取り専用表示にし、保存・Undo の対象にしない。対象外の型を E6 で一覧にする。

`ecsComponent` を持つ全型の分類(2026-11-19、E6b 時点。`grep ecsComponent(` と `ComponentRegistry` の登録で確認):

| 分類 | 型 |
|---|---|
| (a) Reflect と型消去(`FillReflectPtrFns`)の両方を持つ。インスペクターで編集できる | Transform、BoxStaticMesh、InstancedStaticMesh、InstancedPointList、StaticMesh、ParticleEmitter、SkeletalMesh、Terrain、Ocean、Decal、Spawner、AudioSource、AudioListener(13 型) |
| (b) 専用の保存(Reflect なし。`drawEditPtr` なし) | Animation |
| (c) Reflect はあるが型消去の関数が無い | LevelStream(Level 設計の L7 で足す) |
| (d) 登録はあるが保存しない | HierarchicalTransform(親子は Prefab のツリーが表す) |
| (e) 登録が無い(エディタの対象外) | エンジン: EntityDebugTag、LevelMember、AudioEventEmitter。Game: AutoCamera、CameraEffect、CameraSteering、CharacterSteering、Coin、PlayerInput、PlayerScore、Session、SpeedCharacter、StateMachine |

→ 詳細は [E6_リフレクション](エディタ/E6_リフレクション.md) に分けた(旧 6.4 節)。

## 7. 編集モデルとエディタパネル

### 7.1 編集モデル

エディタが編集する正本は**ワールド(ECS)ではなく、Level の編集モデル**にする。既存の `LevelEditorPanel` と同じく、`PrefabEditNode`(名前 + 型消去コンポーネント + 子)のツリーで `.level.json` を表す。ワールドは編集モデルから作るプレビューである。

| 理由 | 内容 |
|---|---|
| 既存資産 | ノード編集の共有関数と Level の保存・読み込みを直して使える |
| ID の安定 | ECS の ID は再利用される。編集モデルのノードはエディタが ID を振るので、Undo の履歴が壊れない |
| 構造変更の安全 | ノードの追加・削除はただのツリー操作で、ECS の反復中かどうかを気にしなくてよい |
| Play の復元 | 停止時はワールドを破棄して編集モデルから作り直せばよい。ECS 全体のスナップショットが要らない |

`LevelEditorPanel` の private な編集状態を、`LevelEditModel`(新規、`aqEngine/Level/`)へ切り出す。`LevelEditorPanel` と Editor の両方がこれを使う。

| `LevelEditModel` が持つもの | 内容 |
|---|---|
| ノードのツリー | `PrefabEditNode` のフォレストとサブ Level |
| ノード ID | 各ノードに振る `uint32_t`(保存しない)。モデルの中で一意で、読み込みのたびに振り直す |
| 参照ノードの override | 参照ノード(`prefabRef` あり)は、読み込んだ `overrides` の**生 JSON をそのまま保持**する。`overrides.children` / `removedChildren` も含む。保存時は生 JSON を書き戻す。表示用には参照先を解決した値を別に作る |
| 保存先パス | 開いている `.level.json` |
| プレビューの状態 | 現在のプレビューの LevelId と in-memory 登録キー |

### 7.2 参照ノードの扱い(既存 override の保持)

- **未編集の参照ノードは、override の生 JSON を一字一句変えずに書き戻す。** 既存の `PrefabNodeToJson` がコンポーネント全体を書き出す挙動は、`LevelEditModel` の保存経路では使わない。
- 参照ノードのフィールドを編集したときは、生 JSON の `overrides.components.<typeName>` にそのキーだけを書き足す(既存の deep-merge の意味に合わせる)。
- 参照ノードへのコンポーネントの追加と削除、子の追加と削除は、初版ではできないようにする(override 編集 UI は E12)。
- **数値の精度**: 既存の SimpleJson は数値を `AsFloat()` で float に狭め、`%g`(6 桁)で書き出すので、7 桁以上の小数は保存し直すと変わる。E4 で次のように直す。
  - `JsonValue` に `AsDouble()` を足し(アプリ連携設計 8 章の持ち越し項目と同じ)、書き出しは double を往復できる最短表現(`std::to_chars`)にする。生 JSON の数値は double のまま往復する。
  - `JsonFieldVisitor` の float フィールドは、float の最短表現(`std::to_chars(float)`)を書き出す。`0.1f` が `0.10000000149011612` のような表記にならないようにするため。
  - `std::to_chars` の浮動小数点版が Mac / Android の標準ライブラリで使えるかを E4 で確認する。Mac と iOS 16.4 は使えた(7.8 節)。Android は未確認。使えなければ `%.9g`(float)/ `%.17g`(double)で代える。
- 既存の `LevelEditorPanel` の保存も同じ経路に寄せ、同じ不具合(往復で override が増える)を直す。直す前の挙動は README の「既知の課題」に記録する。

### 7.3 プレビューの置換

初版は**全再生成に固定**する。編集ノードと実エンティティの対応表は作らない(生成コールバックが解決済みのデータしか受け取らないため)。値の編集も、確定時にワールドを作り直す。ドラッグ中の途中経過はゲームビューに出ない(後で対応表を作るときの課題として 15 章に残す)。

置換は手順 7(5.3、System の反復外)で、次の順にその場で行う。既存の `LevelManager::ReloadAll` と同じく、**GPU の完了を待ってから破棄を確定する**。直列構成でも `FlushRender()` が待つのはレンダースレッドの完了だけで、D3D12 / Vulkan の GPU はまだ前フレームのバッファを使っていることがあるため。

1. **最初に** `Engine::WaitForRenderIdle()` で CPU と GPU の完了を待つ。次の Flush は生成だけでなく予約済みの破棄(同じフレームの `LevelManager::Tick` の自動リロードが予約したものなど)も実行するので、その前に GPU を止めておく。
2. `EntityContext::FlushPendingCommands()` で、予約済みのコマンドをすべて実行する。前回のプレビューの同期 `Load` の生成もここで実体化する。生成前にアンロードすると、まだ存在しないエンティティを拾えず、予約済みの生成が後から走ってしまうため。
3. 前回のプレビューの Level と、Play 中にゲームがロードした Level をアンロードする(`LevelManager::Unload`。破棄は予約される)。非同期ロード(`LoadAsync`)が進行中なら取り消す。**非同期ロードの取り消し API は既存にないので E4 で足す**(TODO)。
4. もう一度 `FlushPendingCommands()` で破棄を確定する。1 から描画を挟んでいないので、GPU の完了待ちは要らない。
5. 前回の in-memory 登録キーを `LevelRegistry` から外す。**キー単位の登録解除 API は既存にない(`Register` と全消去の `Clear` だけ)ので E4 で足す。**
6. 現在の編集モデルから `LevelData` を作り、新しいキーで in-memory 登録して `LevelManager::Load` する。生成は次フレームの手順 3(5.3)の Flush で行われる。
7. 新しい LevelId とキーを `LevelEditModel` に記録する。

生成の完了は `LevelManager::IsLoaded()` では判定できない(スロットを確保した時点で true になり、生成は遅延される)。**E4 で「予約した生成が実行された」ことを返す API(例: `IsSpawned(id)`)を LevelManager に足す。**

- 完了待ちを伴うので、同じフレームに置換を何回要求しても、実行は 1 回にまとめる(最後の要求だけを使う)。値の確定のたびに完了待ちが入るのは初版では許容する(ドラッグ中は置換しない)。

### 7.4 パネル

パネルは `EditorContext` を共有し、編集モデルへの変更はすべてコマンド経由で行う。パネル同士は直接呼び合わない。

| パネル | 役割 | 再利用する既存資産 |
|---|---|---|
| ツールバー | 再生、一時停止、停止。Level の新規・開く・保存 | `LevelEditModel` |
| ゲームビュー | `displayRT` の表示。ゲームへの入力の窓口 | `displayRT`、`SetFocusBlocked` |
| ヒエラルキー | Edit 中: 編集モデルのツリー。Play 中: 実行中ワールドのエンティティ(読み取り中心) | ツリー描画(操作要求を返す形に直す)、`SceneHierarchySystem` |
| インスペクター | Edit 中: ノードのコンポーネントを編集。Play 中: 実エンティティの値を表示・直接編集(履歴に残さない) | 編集イベント Visitor(6.2)、Play 中は `ImGuiFieldVisitor` |
| コンテンツブラウザ | アセットのフォルダ表示。パスのドラッグアンドドロップ | 新規(13 章) |
| コンソール | ログの表示 | `EnginePrintf` / `StartupLog` を通知の口で受け取る(9.1 節 6.) |
| 既存のデバッグパネル | Prefab Editor、プロファイラなど、DebugUI のメニューに登録済みのもの | ゲーム用とエディタ用のどちらのコンテキストに置くかは E3a で決める(TODO) |

- ツリー描画の共有関数(`PrefabNodeDrawTree` など)は、子の追加・削除・並べ替えを直接行っている。E7 で「操作要求を返す」形に直し、適用はコマンドに任せる。既存の Prefab / Level エディタは、返った要求をその場で適用して挙動を保つ。

シーンビュー(編集用カメラ、ギズモ、クリック選択)は E11 で追加する。それまではゲームビューだけで進める。

### 7.5 EditorContext が持つもの

- 編集モデル(`LevelEditModel`)
- 選択中のノード(ノード ID の配列)
- コマンドスタック(Undo/Redo)
- 現在のモード(`RunMode`)と、次フレームで確定する遷移要求、再生の開始待ちの状態

### 7.6 インスペクターの動作

1. 選択中ノードのコンポーネントごとに、編集用のコピーを作って編集イベント Visitor で描く。参照ノードは解決済みの表示用の値を描く。
2. 「編集開始」で変更前の値(キーと JSON 値)を控え、「確定」で変更後の値と組にして 1 つのフィールド変更コマンドを発行する。ドラッグ中の途中経過は Undo 履歴に溜まらない。
3. 特定の型に専用の見た目が必要なら、型ごとにカスタム描画関数を登録できるようにする。カスタム描画関数も編集イベントを返す契約にする。

### 7.7 ファイルへの書き込み

編集の途中ではディスクに書かない。SSD の書き込み量を増やさないことと、保存していない変更を勝手にファイルへ反映しないことのため。

| 操作 | 書き込み先 | ディスクへの書き込み |
|---|---|---|
| 値の編集、ノードの作成と削除、Undo / Redo | 編集モデル(メモリ) | なし |
| プレビューの置換、Play / Stop | `LevelRegistry` の in-memory 登録 | なし |
| 保存(ツールバー / Ctrl+S) | `.level.json` | **ここだけ**。変更がなければ書かない |
| Prefab の作成(E9) | `.prefab.json` | 操作 1 回につき 1 回 |
| ドックの配置 | `imgui.ini` | ImGui の既定どおり、配置が変わったときだけ数秒おきにまとめて書く(`IniSavingRate`) |

- 保存は一時ファイルに書いてから置き換える(書き込み中に落ちても元のファイルが壊れないように)。
- 自動保存(13 章の候補)を入れるときは、変更があるときだけ、数分以上の間隔で書く。
- 目安: Level 1 本は数十 KB なので、1 日に 1,000 回保存しても数十 MB。一般的な SSD の書き込み耐性(数百 TBW)に対して無視できる量である。注意すべきは毎フレームの書き込みで、これは上の表のとおり行わない。

## 8. Play モード

アプリ連携設計 8 章の「P4 Edit/Play の実行時切り替え」の一次資料は本書とする。

### 8.1 モードの遷移

遷移は手順 7(5.3)で要求として記録し、次フレームの手順 1 で確定する。

| 操作 | 遷移 | 処理 |
|---|---|---|
| 再生 | Edit → (開始待ち) → Play | 要求を受けたフレームの手順 7 でプレビューを置換する(7.3)。次フレームから「開始待ち」になり、更新は Edit と同じに扱う。生成は開始待ちの最初のフレームの手順 3 の Flush で行われるが、そのフレームの System は生成前に走っている。そこで、手順 1 で `IsSpawned`(7.3)が true だったフレームはもう 1 フレーム開始待ちのまま進め、手順 3 で新しいエンティティの階層変換と描画データを更新する。その次のフレームの手順 1 で `IAppModule::OnPlayBegin()` を呼び、そのフレームから Play にする |
| 一時停止 | Play → Pause | 次フレームの手順 1 から Pause。ゲームの更新を止める。描画とインスペクターは動く |
| 再開 | Pause → Play | 次フレームの手順 1 から Play |
| 停止 | Play / Pause → Edit | 次フレームの手順 1 で `IAppModule::OnPlayEnd()` を呼んで Edit にし、同じフレームの手順 7 で 8.3 の表に従って状態を戻してプレビューを置換する(7.3) |

- 編集モデルは Play 中に変更しない(Play 中のインスペクターは実エンティティを直接書き、履歴に残さない)ので、停止で自然に再生前へ戻る。初版の「ワールドのバイナリスナップショット」は作らない。
- 再生中にゲームがロードした Level(ステージの切り替えなど)も、停止時のアンロードの対象にする(8.3)。

### 8.2 更新の制御

`SystemBase` に「どのモードで動かすか」の宣言(`RunModeMask`。Play は常に動く)を足す。`EntityContext::Update(RunMode mode = RunMode::Play)` は、宣言のない System を飛ばして wave を実行し、**System の後の `FlushCommands` はモードに関係なく必ず行う**。飛ばした System に依存する System は、順序の制約が消えるだけなので、wave の順序はそのまま使える。

| 対象 | Edit | Play | Pause | 理由 |
|---|---|---|---|---|
| 階層変換(`HierarcicalTransformSystem`) | ○ | ○ | ○ | 編集結果と描画の位置を合わせる |
| 描画データの収集(`RenderSystem`) | ○ | ○ | ○ | 描画を続ける |
| アニメーション | × | ○ | × | 時間で進む |
| パーティクル | ○(プレビュー) | ○ | × | Edit では見た目の確認のために流す。Pause では止める(実デルタ時間で進むため) |
| `SpawnSystem`、`LevelStreamSystem` | × | ○ | × | ゲームの進行 |
| ゲームの System | × | ○ | × | ゲームの進行 |
| `module_->OnUpdate()` | × | ○ | × | 5.3 の 8 |
| UI(Screen 更新) | × | ○ | 収集のみ | 5.3 の 9 |
| `LevelManager::Tick` | ○ | ○ | ○ | ロードの進行はゲームの時間ではない。Pause 中に始まったロードも進める |
| カメラ | ゲームのメインカメラをそのまま使う(E11 でエディタ用カメラ) | ゲームのカメラ | ゲームのカメラ | 停止時に再生前の状態へ戻す(8.5) |

ランタイムは常に Play で動く。System の宣言の既定値は「Play のみ」なので、既存のゲームの System は変更しなくてよい。

### 8.3 停止時にワールドの外を戻す

| 対象 | 停止時の処理 | 担当 |
|---|---|---|
| GameFlow の状態機械と保持ハンドル | 破棄して初期状態に戻す | `GameModule::OnPlayEnd` |
| BGM などのサウンド | 再生中のものをすべて止める | `GameModule::OnPlayEnd` とエンジン |
| UI Screen | ゲームが開いた Screen をすべて閉じる | `GameModule::OnPlayEnd` |
| LevelManager のロード中のハンドルと生成待ち | ロードを取り消し、プレビュー以外にロードされた Level をすべてアンロードしてから、プレビューを置換する | エンジン |
| PrefabRegistry のキャッシュ | 残す(Prefab ファイルが変わっていなければ有効) | — |
| ワールド全体 | Level をすべてアンロードし、残りのエンティティ(ゲームが Level を使わずに作ったものを含む)をすべて破棄してから、再生前に記録した Level とプレビューを読み直す | エンジン(Editor の `PlayModeController`。8.5) |
| メイン / オフスクリーンのカメラ | 再生前の状態へ戻す | 同上 |
| パッドのトリガー抵抗と振動 | 外す | `GameModule::OnPlayEnd` |
| 静的変数・シングルトン | 可変なのは `GameModule` / `GameFlow` / `GameInput` の instance だけ(3898d87 で洗い出し)。`GameFlow` は作り直し、他の 2 つは起動時の資産なので残す | — |
| `InstancedStaticMesh` の名前付き登録 | 残す(同名は既存を返す。ステージが増えたときの課題として README の既知の課題へ) | — |

### 8.4 IAppModule に足すもの

```cpp
/** エディタの再生開始。ゲームの状態機械を開始状態にする(ランタイムでは OnInitialize の後に 1 回呼ぶ) */
virtual void OnPlayBegin() {}
/** エディタの再生停止。ワールドの外に持つ状態を初期状態へ戻す */
virtual void OnPlayEnd() {}
```

ランタイムでの呼び方と、`OnInitialize` から `OnPlayBegin` へ移す範囲は 8.5 節で決めた。ランタイムの挙動は変えない。

→ 詳細は [E5_Playモード](エディタ/E5_Playモード.md) に分けた(旧 8.5 節)。

## 9. Undo/Redo とコマンド

編集操作を Command パターンで記録する。コマンドは**編集モデル**に対して実行・取り消しをする。

```cpp
class IEditorCommand
{
public:
	virtual ~IEditorCommand() = default;
	virtual bool Execute(aq::level::LevelEditModel& model) = 0;   // E7 で決定: 受け取るのは編集モデル(7.9 節 4.)
	virtual void Undo(aq::level::LevelEditModel& model) = 0;
	/** 履歴に出す名前 */
	virtual const char* GetName() const = 0;
};
```

| コマンド | 保持するデータ | 適用後 |
|---|---|---|
| フィールドの変更 | ノード ID、`typeName`、フィールドのキー、変更前と変更後の JSON 値(変更前は実行時にモデルから取る。参照ノードでも「override にあったか」は持たない。9.1 節 2.) | プレビューを置換 |
| コンポーネントの追加と削除 | ノード ID、`typeName`、コンポーネント JSON | プレビューを置換 |
| ノードの作成と削除 | 親のノード ID、兄弟内の位置、**取り外したサブツリーそのもの**(`std::unique_ptr<PrefabEditNode>`) | プレビューを置換 |
| 親の付け替え | ノード ID、変更前と変更後の親 ID と位置 | プレビューを置換 |
| 複合 | コマンドの列 | まとめて 1 回置換 |

- 削除コマンドは、ツリーから外したサブツリーをコマンドの中に所有して保持する。Undo ではそれをそのまま元の位置へ戻すので、**子孫のノード ID も含めて**元に戻る。削除前に子孫を対象にしていた履歴も有効なまま使える。作成コマンドの Undo も同様にサブツリーをコマンドへ移す。
- コマンドは手順 7(5.3)でまとめて適用する。プレビューの置換は 1 フレームに 1 回にまとめる(7.3)。
- Play 中の編集は履歴に記録しない。
- 実装の順序: E7 ではコマンドの形だけで編集し(Undo なし)、E8 で Undo/Redo を足す。E7 から変更の経路はコマンドに統一し、「直接書き換え」の段階を作らない。

→ 詳細は [E8_UndoRedoとコンソール](エディタ/E8_UndoRedoとコンソール.md) に分けた(旧 9.1 節)。

### 11.4 往復テストの比較規則

「読み込んで保存し直したファイル」と「元のファイル」を、文字列ではなく意味で比べる。

| 対象 | 比較の仕方 |
|---|---|
| 実体ノード(参照でないノード) | 両方のファイルからコンポーネントを既定値で構築して `deserialize` し、`serialize` した JSON どうしを比べる(キーの順序は無視、数値は double で完全一致)。元のファイルで省略されていたフィールドが既定値で書き足されるのは同値とみなす |
| 参照ノード | `prefab` のパスと、`overrides` の生 JSON を構造で比べる(キーの順序は無視、数値は double で完全一致)。**キーの有無も一致すること**(既定値の書き足しは不合格) |
| ノードの構造 | ノード名、子の順序と数、サブ Level(パス、`loadOnStart`、インライン定義)が一致する |

比較は Editor_Debug 構成で動くテスト用のコマンドライン(または Editor の隠しメニュー)で行い、結果をログに出す。実装方法は E4 で決める(TODO)。

## 12. エディタスクリプト(Python)の構想

エディタに Python を内包し、エディタ内コンソールから編集モデルの操作を自動化できるようにする。設計は E12 で別の設計書に起こす。ここには初版の構想の要点だけを残す。

- リフレクション(6 章)を使い、コンポーネントごとのバインディングは書かない。コンポーネントのクラスは `ComponentRegistry` から起動時に自動生成する。
- 変更はすべて `IEditorCommand`(9 章)を経由し、スクリプト 1 回の実行を 1 つの複合コマンドにする。例外が出たら全体を巻き戻す。
- スクリプトは編集モデルを操作する(ECS を直接触らない)。実行は Edit 中のみ、メインスレッドで手順 7(5.3)の中で行う。
- Windows は公式の embeddable package を同梱し、`PyConfig` で検索パスを同梱フォルダに固定する。Mac は自前ビルドか再配布用ビルドを同梱する。エディタ構成だけでリンクする。
- 補完は「`dir()` で実行中のオブジェクトを調べる方式」から始め、後で jedi と型スタブ(.pyi)へ進める。
- 未決: Python の版と Mac 向け配布物、以前のスクリプトエンジンの流用範囲、Debug 構成でリンクするライブラリ、jedi と ImGuiColorTextEdit のライセンス、無限ループの中断手段。

## 14. アセット GUID(将来案)

初版の 9 章の構想(.meta、アセットデータベース、マニフェスト、`AssetRef`)は E12 で別の設計書に起こす。そのとき扱うこと:

- 既存のモデル・Prefab・Spawner・`.particle` 内のテクスチャがパス文字列を永続化しているので、GUID を入れるだけでは改名に強くならない。パスから GUID への移行と、複合アセットの内部参照の扱いを決める。
- `PrefabRegistry` の `pathOrGuid` は、実装では文字列をそのままファイル読込へ渡している。GUID の解決経路とキャッシュの無効化を決める。

## 16. 採用しなかった案

| 初版の案 | 不採用の理由 | 代わり |
|---|---|---|
| 新しい `TypeInfo` / `FieldInfo` と `AQ_REFLECT_BEGIN` マクロ | 既存の `Reflect<V>` と `ComponentRegistry` が同じ責務を持ち、二重管理になる | 既存の拡張(6 章) |
| `aqHash32` による型 ID とフィールド ID | 既存 ECS の型 ID は `TYPE_INFO` の `size_t`。永続化は名前で足りる | 名前で永続化 |
| フィールド変更のバイトコピー、ワールドのバイナリスナップショット | 文字列・配列・`unique_ptr`・リソース参照を持つコンポーネントがあり、成立しない | JSON での保存と復元、編集モデルからの作り直し |
| 新しいシーンファイル形式 | Level と生成・保存・所属管理が二重になる | シーン = Level |
| `.prefab`、ファイル内 ID、フィールドハッシュの上書き | 既存の `.prefab.json` と名前ベースの override と互換がない | 既存形式を正本に |
| メインループを exe 側へ移す | iOS は OS がループを持つ。ループは IPlatform にある | AppHost にエディタ用フック(5.2) |
| `IRenderer::GetImGuiTextureId` | 既存の Bridge の接続先は GraphicsDevice / IGraphicsDeviceImpl で、IRenderer はない | `GraphicsDevice::GetImGuiTextureId` |
| ECS のワールドを直接編集し、ID 指定生成で Undo する | ECS の ID は再利用され、ID 指定生成もない。構造変更は反復中に行えない | 編集モデルを正本にする(7.1) |
| 既存インスペクター(`drawInspectorPtr`)をそのまま使う | 対象を直接書き換えるので、変更前の値の控えとコマンド化ができない | 編集イベント Visitor(6.2) |
| 既存の `PrefabNodeToJson` で参照ノードを保存する | override をコンポーネント全体で書き出し、往復で override が増える | override の生 JSON を保持(7.2) |
| 初版からゲームビューにレンダー解像度を追従させる | 既存のリサイズは提示面と RT を一緒に作り直し、D3D12 は未対応 | 縮小表示から始め、E3b で追従 |
| 初版からアセット GUID を入れる | 既存のアセットがパス文字列を永続化しており、GUID だけでは改名耐性が得られない。移行設計が大きい | パス参照のまま進め、E12 で別設計 |
| Mac の入力に SDL3 | 依存が増える。公式の osx バックエンドがある | imgui_impl_osx |
| GameUWP と CMake も GameLogic.lib に切り替える | 初期のエディタは Windows デスクトップのみで、他のビルドを巻き込む理由がない | デスクトップ VS だけ切り出す |
