# カリング 設計ドキュメント

> 対象コミット: `9e5a9fe`(+§15 草の大量配置) / 最終更新: 2026-09-08

対象: `aqEngine/Rendering/`, `aqEngine/Graphics/`, `aqEngine/Component/`, `aqEngine/Resource/`
前提: 既存の抽象レイヤ（`RenderContext` / `IRenderContextImpl`）を変更せず、**DX11 / DX12 の両方**でカリングを有効化する。
本書は **設計のみ**。実装コードは含まない。

対象カリング:
1. **トライアングルカリング**（クラスタ／メッシュレット単位）
2. **フラスタムカリング**
3. **オクリュージョンカリング**（Hi-Z 方式）

採用方針（確定事項）:
- **CPU 駆動から段階的に**実装し、後から GPU 駆動（Indirect Draw）へ拡張する。
- トライアングルカリングの粒度は **クラスタ（メッシュレット）単位**。
- DX11 / DX12 で**コードを二重化しない**。差分は最終フェーズの間接描画 API にのみ閉じ込める。

---

## 0. 設計の指針

- **抽象レイヤ（`RenderContext` / `IRenderContextImpl`）はできる限り変更しない。** フラスタム／オクリュージョン（CPU リードバック方式）は抽象レイヤを触らずに導入できる。間接描画が必要になる最終フェーズでのみ `RenderContext` に API を追加する。
- カリングロジックは可能な限り **API 非依存の層**（`BuildRenderFrame` 〜 `BuildCommandList`、および compute シェーダ）に置く。これにより DX11 / DX12 が自動的に共有する。
- 各フェーズは単独で効果が出て、後戻りせず積み上がる構成とする（§7 フェーズ計画）。
- メインカメラのカリングと**シャドウ（ライト視錐台）のカリングを混同しない**。画面外でも影は落ちるため、判定基準を分ける（§3.3）。

---

## 1. 現状アーキテクチャと挿入ポイント

```
[ゲームスレッド]
  RenderSystem::BuildRenderFrame()      ... ECS を走査し RenderItem を frame へ push
        ↓  frame.items (deferred) / frame.forwardItems
  Renderer::BuildCommandList()          ... RenderItem → RenderCommandList
        ↓
[レンダースレッド]
  RenderCommandList::Execute(RenderContext&)   ... DX11/DX12 共通の高レベル API
        └─ impl_ : IRenderContextImpl
              ├─ D3D11RenderContextImpl
              └─ D3D12RenderContextImpl
```

| 層 | 場所 | カリングでの役割 |
|---|---|---|
| バウンディング生成 | `Resource::MeshResource`（`Resource.h`） | ロード時にローカル AABB / 境界球 / クラスタを計算・保持 |
| アイテム構築 | `RenderItem`（`Rendering/RenderFrame.h`） | ワールド変換前のバウンディングを保持 |
| **フラスタムカリング** | `RenderSystem::BuildRenderFrame()`（`Component/BodyComponentSystem.cpp`） | push 直前に視錐台内外判定（CPU・共通） |
| HZB 生成 / オクリュージョンテスト | `Renderer::BuildCommandList()` + 新規 compute コマンド | GBuffer 深度から Hi-Z を作り、AABB をテスト |
| オクリュージョン結果反映 | 次フレームの `BuildRenderFrame()`（CPU リードバック） | 前フレームの可視フラグで除外 |
| **トライアングル（クラスタ）カリング** | 新規 compute パス + 間接描画 | クラスタ単位で可視判定し compact、Indirect Draw |

**最重要**: `RenderItem` は `worldMatrix` を持つがバウンディング情報を持たない。`MeshResource` は頂点／インデックスを持つが AABB を計算していない。よって §2 の共通基盤がすべての前提となる。

## 2. 共通基盤: バウンディングデータ

### 2.1 メッシュ側（ロード時に一度だけ計算）

`MeshResource`（および `SkeletalMesh` / `Terrain` / `HeightmapChunk` の各メッシュ供給元）に、ロード完了時に以下を計算・キャッシュする:

| データ | 内容 | 用途 |
|---|---|---|
| ローカル AABB | `center`, `extent`（半サイズ） | フラスタム／オクリュージョン |
| 境界球 | `center`, `radius` | 高速な早期判定（任意） |

- `FbxLoader` / `MeshLoader` の `FinalizeLoading()` 内、または頂点配列確定後に min/max を走査して算出する。
- スケルタルメッシュは**バインドポーズ AABB を少し膨らませる**（アニメで頂点が境界を超える分のマージン）。厳密にやるならボーン OBB の合成だが、初期はマージン付き AABB で十分。

### 2.2 RenderItem 側

`RenderItem` に以下を追加し、各 `FillRenderItem()` で埋める:

```
math::Vector3 boundsCenter;   // ローカル AABB 中心
math::Vector3 boundsExtent;   // ローカル AABB 半サイズ
// 境界球を使うなら float boundsRadius;
```

`worldMatrix` は既存。カリング時にワールド AABB を導出する（§3.1）。

### 2.3 ワールド AABB 導出（共通ヘルパ）

ローカル AABB（center, extent）にワールド行列 `M` を適用する標準式（回転を吸収して軸並行 AABB を再構成）:

```
worldCenter = M * localCenter
worldExtent.x = |M00|*ext.x + |M01|*ext.y + |M02|*ext.z
worldExtent.y = |M10|*ext.x + |M11|*ext.y + |M12|*ext.z
worldExtent.z = |M20|*ext.x + |M21|*ext.y + |M22|*ext.z
```

`Math` に `AABB` 構造体と上記変換ヘルパを新規追加する（`Vector.h` に `Dot`/`Cross` 等は既存）。

## 3. フラスタムカリング（Phase 1・CPU・DX11/DX12 共通）

### 3.1 フラスタム抽出

`Math` に `Frustum`（6 平面）を新規追加。`Camera::GetViewProjectionMatrix()` から Gribb–Hartmann 法で 6 平面（left/right/bottom/top/near/far）を抽出する。各平面は `(nx, ny, nz, d)` で正規化保持。

### 3.2 判定と挿入

`RenderSystem::BuildRenderFrame()` の各 `Foreach<...>` 内、`FillRenderItem()` 成功後・`push_back` 直前に:

1. ローカル AABB → ワールド AABB（§2.3）
2. ワールド AABB × 6 平面の内外判定（球で早期 reject → AABB で確定、の二段が高速）
3. 完全に外なら **push しない**

これだけで `frame.items` / `forwardItems` が視錐台内に絞られ、GBuffer・forward・後続オクリュージョン処理すべてが軽くなる。

### 3.3 シャドウとの分離（必須）

- メインカメラのフラスタムで切ってよいのは「画面に直接映る描画」のみ。
- `castShadow == true` のアイテムは、メインカメラで外でも**ライト視錐台に入れば影として必要**。
- よって `ShadowPass`（`Rendering/Shadow/`）は**ライトの視錐台**で別途フラスタムカリングする。`BuildRenderFrame` で main 用に弾いたアイテムをシャドウから誤って除外しないよう、シャドウ用の収集は別経路 or 別フラグで管理する。

### 3.4 DX11/DX12 差

なし。完全に CPU・API 非依存。

## 4. オクリュージョンカリング（Phase 2・Hi-Z・CPU リードバック）

ハードウェアオクルージョンクエリ方式は GPU ストール・API 差・1 フレーム遅延が大きく**非採用**。
既に `RenderContext` に `Dispatch` / CS UAV・SRV があるため **Hi-Z（HZB）方式**を採る。

### 4.1 データフロー（フレーム N）

```
フレーム N-1 の深度（GBuffer0 の depth）
        │
        ▼ (compute) ミップ連鎖生成: 各レベル = 親 2x2 の "最遠（max）" 深度
   Hi-Z バッファ（HZB, mip chain）
        │
        ▼ (compute) 各オブジェクトのワールド AABB をスクリーン投影し、
        │            覆う矩形に対応する HZB ミップで深度比較
   可視フラグ配列（UAV, オブジェクトごとに 0/1）
        │
        ▼ CPU へリードバック（1 フレーム遅延）
   フレーム N+1 の BuildRenderFrame で不可視オブジェクトを除外
```

### 4.2 HZB 生成

- 入力: deferred の GBuffer 深度（`DeferredRenderer::GetGBuffer0Handle()` 近傍、`Renderer::BuildCommandList()` Pass 2 の後）。
- compute で max-reduction のミップ連鎖を生成。新規 RT/UAV テクスチャ（R32_Float）を確保。
- DX11/DX12 とも `Dispatch` + CSUAV で共通実装。

### 4.3 オクリュージョンテスト

- 入力: フラスタム通過済みオブジェクトのワールド AABB 配列（structured buffer）+ HZB + view-proj。
- 各 AABB をクリップ空間に投影 → スクリーン矩形と最近接深度を算出 → 矩形サイズに応じた HZB ミップをサンプルし、AABB 最近接深度 ≤ HZB 値なら可視。
- 出力: 可視フラグ UAV。

### 4.4 結果反映（CPU リードバック方式・本フェーズ）

- 可視フラグを CPU にリードバックし、**オブジェクト ID と対応付けて**保持。
- 次フレームの `BuildRenderFrame` で、前フレーム不可視だったオブジェクトを push しない。
- **1 フレーム遅延**するため、カメラ急変時の「一瞬の抜け」を許容するか、保守的判定（迷ったら可視扱い）でポップを防ぐ。
- オブジェクトと結果を対応付ける安定 ID が必要（ECS Entity ID を使う）。

### 4.5 DX11/DX12 差

- HZB 生成・テストの compute は共通。
- リードバック（GPU→CPU コピー）は `IRenderContextImpl` 経由。DX11 は staging、DX12 は readback ヒープ + フェンスだが、**いずれも既存の抽象に薄く追加**で済む（新規描画 API は不要）。

## 5. トライアングル（クラスタ）カリング（Phase 4・GPU 駆動）

CPU で全三角形を毎フレーム回すのは非現実的。ラスタライザのバックフェースカリングは GPU が常時実施済み。よって**クラスタ（メッシュレット）単位の GPU カリング + 間接描画**を採る。本フェーズは間接描画基盤（§6）が前提。

### 5.1 前処理（ロード時）

- メッシュを ~64〜128 三角形のクラスタに分割（meshoptimizer 等のアルゴリズム、または単純な連続分割）。
- 各クラスタに **境界（AABB/球）** と **法線錐（cone: 軸 + 角度）** を計算・保持。

### 5.2 ランタイム（compute）

各クラスタに対し:
1. フラスタムカリング（クラスタ境界 × 視錐台）
2. バックフェースカリング（法線錐 × 視線方向）
3. Hi-Z オクリュージョン（§4 の HZB を流用）

通過したクラスタのインデックス範囲を compact し、間接描画引数バッファ（draw count / index 範囲）を構築。

### 5.3 描画

- 構築した間接引数で `DrawIndexedInstancedIndirect`（DX11）/ `ExecuteIndirect`（DX12）。
- 将来 DX12 は Mesh Shader 化も可能だが、本設計の範囲外。

---

## 6. 間接描画基盤（Phase 3・API 差をここに閉じ込める）

オクリュージョンの「遅延なし GPU 駆動化」とクラスタカリングの両方が、これを前提とする。

`RenderContext` / `IRenderContextImpl` に間接描画 API を追加:

| 抽象 API（新規） | DX11 実装 | DX12 実装 |
|---|---|---|
| `DrawIndexedIndirect(argBuffer, offset)` | `DrawIndexedInstancedIndirect` | `ExecuteIndirect`（1 引数の command signature） |
| 間接引数バッファ生成 | UAV 付き Buffer | UAV 付き Buffer + command signature |

これにより、オクリュージョン結果反映を §4.4（CPU リードバック）から **GPU 駆動 2-phase occlusion**（前フレーム可視物 → HZB → 今フレーム再テスト、遅延なし）へ置き換えられる。

## 7. フェーズ計画

| Phase | 内容 | API 差 | 抽象レイヤ変更 |
|---|---|---|---|
| **0** | バウンディング基盤: `MeshResource` AABB 計算、`RenderItem` 拡張、`Math::AABB`/`Frustum` 追加 | なし | なし |
| **1** | フラスタムカリング（CPU・共通）＋ シャドウのライト視錐台カリング | なし | なし |
| **2** | Hi-Z オクリュージョン（HZB 生成 + テスト compute、CPU リードバック反映） | リードバックのみ薄く追加 | 最小限（readback） |
| **3** | 間接描画 API（`DrawIndexedIndirect`）を抽象に追加 → オクリュージョンを GPU 駆動 2-phase 化 | ここに集約 | あり（間接描画） |
| **4** | クラスタ（メッシュレット）カリング = トライアングルカリング | Phase 3 を流用 | なし（Phase 3 で完了） |

各フェーズは独立して効果が出る。Phase 0→1 だけでも実用上の描画負荷は大きく下がる。

| プロファイラ（スレッド別タイムライン） | ✅ | — | `Util/Profiler.*`, `Util/ProfilerDebugPanel.*` |

DX11 は `ReadbackOffscreenR32` / GPU 駆動クラスタが既定 false/未対応（オクリュージョンは保守的に全可視、クラスタは CPU 方式 fallback）。フラスタム / Hi-Z 生成 / メッシュレットは DX11/DX12 共通。

**クラスタカリングの性能特性（重要・実機確認済み）**:
- **CPU 方式**: 毎フレーム「128クラスタ判定 + compact + 動的IBアップロード」で、小メッシュ（~8千三角形のキャラ）では CPU/転送コスト > GPU 節約 → 差し引きマイナス。
- **GPU 駆動方式**: CPU compact/転送は消えるが、**メッシュごとの固定コスト（reset+cull dispatch・バリア・ExecuteIndirect・コマンドのアイテムコピー）が残り**、小メッシュでは依然この固定コスト > 削減効果。
- 結論: **トライアングル/クラスタカリングは「巨大メッシュ・多数オブジェクト・GPU 三角形律速」でのみ実効**。小メッシュは三角形律速でないため、どの方式でも体感改善しない（バグではなく本質）。
- 対策として `clusterCount < 256`（`SetClusterCullMinClusters`、パネル調整可）のメッシュは GPU カリング機構を通さず通常描画し、ON にしても小シーンで損しないようにした。

## 11. トライアングル（クラスタ）カリングの GPU 駆動化（§11.1〜11.3 = 実装済み / 11.4〜 = 今後）

> §11.1〜11.3 は実装済み（§10 の GPU 駆動行を参照）。Step 1（インフラ）+ Step 2（フラスタムのみ）+ **Step 3（バックフェース錐 + Hi-Z オクリュージョン）**+ **Step 4（CPU 方式の整理）** まで完了。Step 2 までは実機で表示正常を確認済み。**Step 3 は実機検証待ち**（コンパイルのみ確認: msbuild + fxc cs_5_0 成功）。
>
> **Step 4（CPU 方式の整理, 2026-06）の決定**:
> - CPU 方式（`ClusterCull.cpp` `BindCulledIndices` / `cullIndexBuffer_`）は**撤去せず DX11 フォールバック + 閾値未満スキップ経路として残置**。full removal は DX11 のクラスタカリングを壊し、OFF 既定のニッチ機能のため残置が安全。
> - **min-clusters 閾値を GPU 経路（Renderer.cpp）と CPU 経路（BindCulledIndices）で統一**。従来 CPU 側は閾値非対応で、DX12 の閾値未満メッシュが GPU 機構をスキップして CPU 落ちすると設計意図（小メッシュは cull しない）に反して CPU カリングしていた不整合を解消。
> - CPU 経路が走るのは: ①DX11（GPU 駆動未対応で `gpuOutIndices/gpuArgs` が無い）②閾値未満メッシュ（現在は通常描画に倒れる）。CPU 経路は frustum + backface のみ（Hi-Z 非対応）。
>
> **Step 3 の設計判断（2026-06 追記・非自明）**:
> - **単一 CBV (b0) に集約**: compute ルートシグネチャは CBV が b0 のみ（[D3D12RootSignature.cpp](../aqEngine/Graphics/D3D12/D3D12RootSignature.cpp) `CreateCompute`）。b1 を増やさず、`ClusterCullCBData`(192B) に world / **viewProj** / camPos / clusterCount / Hi-Z 寸法 / near / far / hiZValid を全て収めた。
> - **フラスタム平面は viewProj からシェーダ内導出**（`ClusterCull.fx`）。CPU から 6 平面を渡さない。`clip = mul(g_ViewProj, p4)` の内側条件 `-w≤x≤w, -w≤y≤w, 0≤z≤w` から `left=row3+row0` 等を構成（規約非依存・非正規化でも AABB 符号テストは不変）。
> - **t2 = Hi-Z SRV**: compute SRV テーブルを t0..t1 → **t0..t2** へ拡張（`CS_SRV_TABLE_SIZE` / `CS_SRV_COUNT` を 2→3）。
> - **前フレームの Hi-Z を使う 1 フレーム遅延**: Pass 1.5（クラスタカリング）は Pass 2a.5（Hi-Z 構築）より前に走るため、ピラミッドには前フレーム内容が残る。`HiZRenderer::GetReadbackHandle/GetLevelSize` の粗いレベルを SRV 供給（[Application.cpp](../aqEngine/Core/Application.cpp) で `GpuClusterCuller::SetHiZSource`）。投影/サンプル式は CPU `HiZRenderer::IsOccluded` と一致。矩形が `kMaxSpan`(16) 超のクラスタは保守的に可視。

目的: CPU 方式の「毎フレーム compact + IB アップロード + ゲーム/レンダー二重計算」を排し、**GPU 上でクラスタを判定 → 可視クラスタだけを `ExecuteIndirect` で描画**する。CPU は判定にもインデックス転送にも関与しない。

### 11.1 必要な新規インフラ（抽象レイヤ）

1. **構造化バッファ / 生バッファ UAV**（現状 `IStructuredBuffer` は空スタブ）
   - クラスタ記述子 SRV（入力: center/extent/coneAxis/coneCutoff/triOffset/triCount）
   - 可視クラスタ index 出力 UAV（append 風 / カウンタ付き）
   - 間接引数バッファ UAV（`D3D12_DRAW_INDEXED_ARGUMENTS` 列）
2. **間接描画 API**: `RenderContext::DrawIndexedIndirect(argBuffer, offset)`
   - DX12: command signature（`D3D12_INDIRECT_ARGUMENT_TYPE_DRAW_INDEXED`）+ `ExecuteIndirect`
   - DX11: `DrawIndexedInstancedIndirect`
3. **UAV カウンタのクリア**（`ClearUnorderedAccessViewUint` 相当）

### 11.2 ランタイム フロー

```
[ロード時] メッシュ → クラスタ記述子バッファ (SRV) + 並べ替え済みインデックスバッファ (IB)
                       ※ Meshlet.cpp の出力をそのまま GPU へ常駐

[毎フレーム・compute]
  ClusterCull.cs:
    入力 SRV: clusters, viewProj/camPos CB, (任意) Hi-Z
    各クラスタ並列:
      - フラスタム（クラスタ AABB × 視錐台）
      - バックフェース（法線錐 × 視線）
      - (任意) Hi-Z オクリュージョン（§4 を流用）
      可視なら:
        appendIdx = InterlockedAdd(visibleCounter, 1)
        visibleClusterList[appendIdx] = clusterIndex
    その後 1 スレッドで:
        indirectArgs.IndexCountPerInstance = Σ可視クラスタ.triCount*3
        ... または「クラスタ単位の ExecuteIndirect 多重ドロー」にする

[描画]
  方式A: 可視クラスタの三角形を別 compute で compactedIB へ書き出し → 単一 DrawIndexedIndirect
  方式B: クラスタごとに 1 ドロー（多重 ExecuteIndirect, MaxCommandCount=クラスタ数）
         → compaction 不要だがドローコール増。最近の GPU では方式 B も実用的。
```

推奨は **方式A（compute で compactedIB を作り単一間接描画）**。Hi-Z は既存の `HiZRenderer` をクラスタ判定にも供給すれば、オブジェクト単位とクラスタ単位の遮蔽を統合できる。

### 11.3 既存資産の流用

- クラスタ記述子は `graphics::MeshCluster`（`Meshlet.h`）をそのまま GPU レイアウト化（16B 境界に整列して `float4` 詰め）。
- 並べ替え済みインデックスは `GetReorderedIndices()` を GPU 常駐 IB にする（CPU 方式の `cullIndexBuffer_` は不要化）。
- 判定式（フラスタム/バックフェース錐）は `IsClusterVisible`（`Meshlet.h`）を HLSL へ移植。`coneCutoff` の意味（`dot(viewDir, coneAxis) >= coneCutoff` で背面）も同じ。
- Hi-Z は `HiZRenderer` の R32 ピラミッドを SRV で供給。

### 11.4 実装フェーズ（段階導入・各段ビルド可能）

1. ✅ 抽象に `IStructuredBuffer`（SRV/UAV/カウンタ）+ `DrawIndexedIndirect` を追加（D3D12 実装）。クリア画面で UAV 書き込み→間接描画の最小往復を検証。
2. ✅ クラスタ記述子 + 並べ替え IB を GPU 常駐化。`ClusterCull.cs`（フラスタムのみ）で compactedIB 生成 → 単一間接描画。CPU 方式と同じ「画面端で削減」を GPU で再現。
3. ✅ バックフェース錐 + Hi-Z をクラスタ判定に追加（実機検証待ち）。
4. ✅ CPU 方式を整理: DX11 フォールバックとして残置し、min-clusters 閾値を GPU/CPU で統一（上記決定参照）。

### 11.5 リスク / 注意

- D3D12 の `ExecuteIndirect` + command signature + UAV カウンタ + バリアは新規実装で**実機検証必須**（CPU では追えない）。Step 2 のリードバック同様、診断カウンタを仕込みながら段階確認する。
- DX11 と DX12 で間接引数バッファ/シグネチャの作法が異なる。差は `IRenderContextImpl` 実装に閉じ込める。
- 小メッシュでは GPU 駆動でも「ドロー準備の固定コスト」が効果を上回ることがある。巨大メッシュ / 高ポリシーンで初めて実効。

## 12. テライン / 海をクラスタカリング対象に含める（メモ）

現状クラスタを持つのは `MeshResource`（StaticMesh）/ `SkeletalMeshResource`（SkeletalMesh）経由のメッシュのみ。**テライン・海は未対応**（集計にも実カリングにも入らない）。

### 12.1 テライン（`Terrain/HeightmapChunk`）

- 頂点は `vertCache_`（CPU 常駐）にある。`MeshResource` を介さず `InitializeDynamic` で動的VB生成しているためクラスタ未生成。
- 対応案:
  1. `HeightmapChunk` に `std::vector<graphics::MeshCluster> clusters_` + `reorderedIndices_` を追加し、`BuildMesh` / `RebuildFromHeights` 後に `graphics::GenerateClusters(vertCache の position 列, indices, 64, ...)` で生成（AABB と同様にキャッシュ・dirty 管理）。
  2. `FillRenderItem` で `item.clusters / reorderedIndices / cullIndexBuffer` を設定（StaticMesh と同じ要領）。動的IBは別途用意。
- 効果: テラインは**広く平らで上向き**のため、バックフェースはほぼ効かない。効くのは**フラスタム（チャンクが画面外/部分外）**。地形を複数チャンク化すると更にフラスタムが効く。**地形は「チャンク AABB のオブジェクト単位フラスタム」で先に切る方が安く効く**ので、クラスタ化は優先度低め。

### 12.2 海（`Ocean/OceanMesh`）

> **実装済み（2026-06）**: 海の**オブジェクト単位フラスタムカリング**を `BuildRenderFrame` の海収集ループに追加。
> 海は `mesh_.Initialize(生バッファ)` 初期化で `meshResource_==nullptr` → `hasBounds=false` のため `isVisible` を使えない。
> よってローカルグリッド `[0,size]×{0}×[0,size]` を **波の最大振幅（Σ|waves[i].amplitude|）で Y を、Gerstner 水平変位の保険で XZ を膨らませた保守 AABB** で `frustum.Intersects` 判定し、視錐台外なら `oceanItems` に push しない（`cullEnabled = frustumCullingEnabled_ && Main` のときのみ）。クラスタ化は引き続き未対応。

- `OceanMesh` は StaticMesh/SkeletalMesh ではなく独自。Gerstner 波で**毎フレーム頂点が動く**ため、クラスタの AABB / 法線錐が毎フレーム変わる → ロード時固定クラスタは不正確。
- 対応案:
  - 海は通常**カメラ中心の巨大グリッド**で全面可視のことが多く、クラスタカリングの効果は小さい。優先度低。
  - やるなら「波の最大振幅でクラスタ AABB を膨らませた保守的クラスタ」をロード時生成し、フラスタムのみ適用（バックフェースは波で不安定なため無効化）。

### 12.3 まとめ（優先度）

| 対象 | クラスタ化の価値 | 推奨 / 状況 |
|---|---|---|
| テライン | フラスタムのみ（チャンク単位で十分なことが多い） | チャンク AABB のオブジェクト単位フラスタムは**既に有効**（`isVisible`）。クラスタ化は未対応・優先度低 |
| 海 | 低（全面可視・頂点が動く） | ✅ **オブジェクト単位フラスタム（保守 AABB）実装済み**（§12.2）。クラスタ化は当面見送り |

いずれも GPU 駆動（§11）が入れば、頂点が動く海も compute 側で動的にクラスタ境界を作れるため相性が良くなる。

## 13. 明示バウンディング（MeshResource 非経由メッシュのフラスタムカリング）

> 設計 2026-09-07。動的生成プリミティブ（`BoxStaticMeshComponent` の共有箱など）を
> オブジェクト単位フラスタムカリングへ載せるための最小拡張。

### 13.1 問題

`RenderItem` のバウンディング供給元が `meshResource_` のみ
（`StaticMesh::FillRenderItem` の `if (meshResource_)` ガード）。
`InitializeShared` / `Initialize(生バッファ)` / `InitializeDynamic` 経路は
`meshResource_ == nullptr` のため `hasBounds = false` のままとなり、
`isVisible`（`BodyComponentSystem.cpp` の `!item.hasBounds → 常に可視`）を素通りする。
AquaDash では路面タイル箱 約 360 枚が全数描画され 180fps→60-95fps に低下した。

これまでの回避策は 2 系統に分裂している:
- テライン: `HeightmapChunk::FillRenderItem` が自前で `item.localBounds / hasBounds` を上書き
- 海: 収集ループ側で保守 AABB を組んで `frustum.Intersects` を直接呼ぶ（§12.2）

### 13.2 方式（確定）

`StaticMesh` に**明示ローカル AABB** を持たせ、`FillRenderItem` のフォールバックにする。

```cpp
// StaticMesh.h
void SetLocalBounds(const math::AABB& aabb);   // 生バッファ初期化メッシュ用の明示バウンディング
```

- `FillRenderItem`: `meshResource_` があれば従来どおり `GetLocalAABB()`、
  無ければ明示 AABB が設定済みのときのみ `localBounds / hasBounds = true` を設定。
- AABB の空間は「`worldMatrix` を掛ける前のメッシュローカル空間」
  （`meshResource_->GetLocalAABB()` と同一の契約）。
- 呼び出し側の第一号は `BoxStaticMeshComponent::Update()`:
  共有箱は ±0.5 の単位キューブなので `AABB{ center=(0,0,0), extent=(0.5,0.5,0.5) }` を
  `InitializeShared` 直後に一度設定するだけ（`AABBBuilder` 不要・dirty 管理不要）。

### 13.3 責務表

| クラス / ファイル | 責務 |
|---|---|
| `Graphics/StaticMesh.h/.cpp` | `SetLocalBounds` の保持と `FillRenderItem` でのフォールバック設定 |
| `Component/BodyComponentSystem.cpp` | 箱初期化時の単位キューブ AABB 設定（カリング判定側は変更なし） |

### 13.4 注意

- `castShadow == true` のアイテムはフラスタムを素通りする既存仕様（§3.3）。
  箱は `castShadow_ = false` 既定のため影響なし。影を落とす明示バウンディングメッシュを
  作る場合はライト視錐台側の考慮が別途必要。
- インスタンシング経路（`InstancedRenderItem`）にはバウンディングフィールド自体が無く
  カリング対象外のまま。per-instance カリングは gather（`Update()`）と
  `BuildRenderFrame`（フラスタム確定）のタイミング分離が論点になるため本書では扱わない（将来課題）。
- `HeightmapChunk` / 海の既存回避策は動作しているため本方式への統合は行わない
  （統合するなら `SetLocalBounds` へ寄せられるが、海は毎フレーム AABB が変わるため対象外）。

### 13.5 チェックポイント

- [x] `SetLocalBounds` 設定済みメッシュが視錐台外で `frame.forwardItems` に積まれない
  （2026-09-07 実機: コース背面を向くリザルト画面 224fps・走行中 99〜118fps と、
   全数描画時代の 60-95fps から可視タイル数連動で改善していることを確認）
- [x] `meshResource_` 経由メッシュの挙動が従来と同一（else-if フォールバックで従来経路は無変更。
   キャラ/地形/ゲーム一巡を実機確認）
- [x] AquaDash 路面タイル（約 360 枚）でフレームレートが改善する
  （中盤以降 99〜118fps。ただし開始地点はコースの大半が視錐台内に入るため 66fps —
   オブジェクト単位フラスタムでは削れない領域で、インスタンシング化 or Hi-Z が次の一手 → §14）

## 14. インスタンス描画の per-instance フラスタムカリング + 色

> 設計 2026-09-07。AquaDash P9（路面タイルのインスタンシング化）のエンジン側設計。
> 個別ドロー約 360 → 1 ドローへの削減と、インスタンス経路の 2 つの既知の穴
> （§4 調査時判明: カリング皆無 / 色ハードコード）の解消を同時に行う。

### 14.1 現状の問題

- `InstancedRenderItem` / `InstancedStaticMesh` にはバウンディングが無く、
  `CollectRenderItems` は `isVisible` を通らない → **インスタンス経路は完全にカリング対象外**。
- gather（`AddInstance` ループ）と `FlushInstances`（動的VB書き込み）は
  `RenderSystem::Update()` = **ワーカースレッド**上で走る。カメラ更新
  （`CameraManager::UpdateAll`）はその後のため、Update 時点の視錐台は 1 フレーム古い。
  また D3D12 動的VBのフレームリングは直列実行（`AQ_RENDER_PIPELINED` OFF）前提で
  たまたま安全という状態。
- `InstancedSimple.fx` は赤ハードコード。`InstancedRenderItem` に materialCB も無い。
- `InstancedPointListComponent` は位置 + 全点共通の一様スケールのみで、
  姿勢・非一様スケールを持てない（路面タイルには不足）。

### 14.2 方式（確定）

**gather を `BuildRenderFrame` へ移設**し、そこで確定済みの `frustum` で
`AddInstance` 前に per-instance 判定する。

1. **InstanceData 拡張**: `math::Vector4 color` を追加（64B → 80B、転置 world + 色）。
   `AddInstance(world, color)`（既定=白）。`InstancedSimple.fx` は VSInput に
   `float4 iColor : I_COLOR` を足して PS で `input.color` を返す（赤ハードコード廃止）。
   D3D12 の入力レイアウトはシェーダリフレクションが `I_` 前方一致で
   slot1 / PER_INSTANCE に自動振り分けするため C++ 変更不要。
   （D3D11 のリフレクションは `I_` 判定が無くインスタンシング自体が元々未成立 —
   既知の穴として現状維持）
2. **明示バウンディング**: `InstancedStaticMesh` に `SetLocalBounds / GetLocalBounds /
   HasLocalBounds` を追加（§13 の `StaticMesh` と同一契約。共有ジオメトリのローカル AABB）。
3. **gather 移設**: `RenderSystem::Update()` 内の gather ループ + `FlushAllRegistered()` を
   `BuildRenderFrame` の frustum 構築後・`CollectRenderItems` 直前へ移動。
   `AddInstance` 前に `HasLocalBounds()` なら `localBounds.Transformed(world)` を
   `frustum.Intersects` で判定（`cullEnabled` 条件は `isVisible` と同じ）。
   バウンディング未設定のインスタンスは従来どおり常に積む。
4. **Flush は 1 フレーム 1 回の維持**: `BuildRenderFrame` に gather 実行フラグ
   （`updateStats` と同型）を追加し、分割画面時は**先頭ビューのみ gather + Flush**、
   他ビューは Collect のみ（= ビュー0 の視錐台で切った結果を全ビューで共有）。
   パーティクル（先頭ビューのみ描画）と同じ既知の制限とする。
5. **点リスト拡張**: `InstancedPointListComponent` に
   `InstancePoint { position, rotation(Quaternion), scale(Vector3), color(Vector4) }` の
   配列を追加。非空ならこちらを gather（world = S·R·T を点毎に合成 × エンティティ行列）、
   空なら既存の `points_` + 一様スケール（色=白）で互換維持。シリアライズは
   従来どおり未対応のまま（コード生成専用。既存実装も serialize 空）。
6. **共有箱の名前付き登録**: 箱ジオメトリ（`BOX_VERTEX_BUFFER` 等）は
   `BodyComponentSystem.cpp` の無名 namespace 内でゲームから見えないため、
   `BoxStaticMeshComponent::RegisterInstancedMesh(const char* name)`（static）を追加。
   `RegisterFromData(..., InstancedSimple)` + 単位キューブ AABB 設定まで行う。

### 14.3 責務表

| クラス / ファイル | 責務 |
|---|---|
| `Graphics/InstancedStaticMesh.h/.cpp` | InstanceData 色 / AddInstance(world,color) / 明示 AABB 保持 |
| `Component/BodyComponentSystem.cpp` | gather 移設 + per-instance フラスタム判定 + 箱の名前付き登録ヘルパ |
| `Component/InstancedPointListComponentSystem.h` | InstancePoint 配列（姿勢・非一様スケール・色） |
| `Rendering/…` | 変更なし（`InstancedRenderItem` / 描画コマンドは現状のまま） |
| `Game/Assets/Shader/InstancedSimple.fx` | I_COLOR 追加・赤ハードコード廃止 |

### 14.4 注意 / 制限

- gather がメインスレッド化することで、動的VB書き込みも直列実行前提から
  「メインスレッド + 描画前」に前進する（`AQ_RENDER_PIPELINED` 有効化時の危険は残るが
  パーティクルと同一条件に揃う）。
- インスタンス経路はシャドウパスに積まれない（従来から）。路面タイルは影を落とさないので影響なし。
- Hi-Z オクリュージョンは per-instance には適用しない（オブジェクト単位テスターは
  RenderItem 前提。将来 GPU 駆動化(§11)の対象）。
- 1 ドロー化により §13 のオブジェクト単位フラスタム（タイル 360 個の個別判定）は不要になるが、
  `BoxStaticMeshComponent` 側の機構はコイン等で引き続き使用する。

### 14.5 チェックポイント

- [x] 視錐台外のインスタンスが instance buffer に積まれない（画面内タイル数と instanceCount が連動）
  （2026-09-07 実機・間接確認: コース背面のリザルト画面 3.60ms は個別ドロー時代の
   4.45ms よりさらに短く、背面タイルの頂点処理がほぼゼロ化している）
- [x] gather 移設後も Flush が 1 フレーム 1 回で、既存デモ・レベルの描画が壊れない
  （フル走行一巡 + RETRY を実機確認。gather はビュー0 のみのフラグで保護）
- [x] InstancedSimple の色が I_COLOR で指定でき、AquaDash 路面タイルの見た目が P8 と同一
- [x] AquaDash 開始地点のフレームレートが改善する
  （66.0fps/15.16ms → 97.4fps/10.27ms。180fps 未達 — 残りは視錐台内のコイン個別ドロー等の
   ベースコストで、コインのインスタンス化が次の一手）




## 15. 静的インスタンスのベイク + セル単位カリング（草 10 万本規模）

§14 で per-instance フラスタムカリングは入ったが、**判定コストがインスタンス数に比例する**。
10 万本規模（草）では毎フレームの CPU 負荷とアップロード量が破綻するため、
「配置後に動かないインスタンス」向けのベイク済み経路を追加する。

### 15.1 現状の問題（10 万本を想定した見積り）

`Component/BodyComponentSystem.cpp` の gather は毎フレーム、全インスタンスについて次を行う。

1. `InstancePoint` から S / R / T の 3 行列を構築する
2. 4 回の 4x4 乗算でローカル行列を作りエンティティ行列と合成する
3. メッシュのローカル AABB をワールドへ変換し、視錐台 6 面と判定する
4. 生存分を転置して 80B の `InstanceData` として `push_back` する

10 万本ではこれが単一スレッドで毎フレーム走り、加えて `InstancedStaticMesh::FlushInstances` が
**8 MB（10 万 × 80B）の memcpy** を毎フレーム行う。現行の実使用（路面タイル 360・コイン 186）
では顕在化しないが、桁が 2 つ上がると 16.6ms に収まらない。

### 15.2 方式（確定）

**「静止インスタンスは行列を事前計算し、カリングをセル単位に粗くする」**。

1. **ベイク**: 配置確定時に一度だけ `InstancePoint` 列を `InstanceData`
   （転置済みワールド行列 + 色）列へ変換する。以後フレーム中の行列演算はゼロになる。
2. **セル分割**: XZ 平面の均一グリッド（既定 32m 角）で分類し、同一セルのインスタンスを
   **連続領域**へ並べ替える。セルは `{ ワールド AABB, offset, count }` を持ち、空セルは保持しない。
3. **毎フレーム**: セル AABB を視錐台と判定し、さらにカメラからの距離が `maxDrawDistance` を
   超えるセルを捨てる。生存セルは `AddInstances(baked + offset, count)` で
   **ブロック一括コピー**する。
4. 判定回数が「インスタンス数」から「セル数」（草の帯で数十〜数百）へ落ち、
   アップロード量は**可視分のみ**になる。

ベイクはエンティティのワールド変換を織り込んだ状態で行うため、
**ベイク後にエンティティを動かしてはいけない**（静的配置専用）。動かす用途は従来の
`InstancePoint` 経路をそのまま使う（コインが該当）。

### 15.3 ベイクのスレッド境界

`BuildBakedData()` は**純 CPU 計算**（GPU リソースにも ECS にも触れない）とし、
ワーカースレッドから呼べるようにする。`Terrain/HeightmapChunk::PrepareCpuData` と同じ構図で、
ワーカーが作った不変データをメインスレッドがコンポーネントへ move する。
10 万本のベイクは Debug で無視できないコストになるため、ロード中のワーカーで済ませる。

### 15.5 注意 / 制限

- セル単位カリングのため、可視セル内の画面外インスタンスも積まれる（粗い分だけ過剰描画になる）。
  セルサイズは「判定回数」と「過剰描画」のトレードオフで決める。
- §14 の制限をそのまま引き継ぐ（シャドウパス非参加・Hi-Z 非適用・実効は D3D12 のみ）。
- 距離カリングはセル AABB とカメラ位置の最短距離で行う。`maxDrawDistance = 0` で無制限。
- ベイク済みデータは 80B/本 = 10 万本で 8MB。元の `InstancePoint`（44B）はベイク後に解放してよい。
- GPU 駆動カリング（§11 の方式を per-instance へ拡張）は本節の**次段**。本節はその前段として
  CPU 側のスケールを稼ぐ「ブロック単位カリング」に相当する。
