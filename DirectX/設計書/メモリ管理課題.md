# メモリ管理 課題メモ

最終更新: 2026-09-09。調査のみでコード変更は入れていない。後から順に対応するための一覧。

アロケータ実装は [Memory/](../aqEngine/Memory/)、予算値の定義は [PlatformBudget.h](../aqEngine/Platform/PlatformBudget.h)、
予算の位置づけは [07 リソース管理設計](07_リソース管理設計.md) の「プラットフォーム予算との関係」を参照。

## 0. 前提の整理

メモリの出どころは三系統あり、自作アロケータが管理しているのは三つ目だけ。

| 領域 | 確保する主体 | 解放 | MemoryTracker |
| --- | --- | --- | --- |
| コールスタック(ローカル変数) | OS。スレッド生成時に予約し、ページ単位で後追いコミット | 関数を抜けたら自動 | 映らない |
| StackAllocator | 起動時に `_aligned_malloc` で一括確保。以降はオフセット加算のみ | `Reset()` / `ScopedMarker` | 映らない |
| ヒープ(グローバル new / HeapAllocator) | `_aligned_malloc` | `delete` / `Deallocate` | 映る |

ローカル変数の確保はスタックポインタの加減算だけで、確保イベントそのものが存在しない。
このため `operator new` を差し替えている [GlobalNew.cpp](../aqEngine/Memory/GlobalNew.cpp) では原理的にフックできない。
`static` / `thread_local` は関数内にあってもスタックではなく、静的領域 / TLS に置かれる
(例: [D3D11Shader.cpp](../aqEngine/Graphics/D3D11/D3D11Shader.cpp) の 5MB シェーダバッファは `static` なのでスタックを使わない)。

コールスタックのサイズは実行ファイルのヘッダで決まる。`.vcxproj` に `StackReserveSize` の指定がないため
Win32 / UWP とも既定の 1MB。`RenderThread` と `ThreadPool` が作る `std::thread` も同じ予約値を継承する。
`MemoryConfig::stackSizeBytes`(Win32 4MB / UWP 8MB)は StackAllocator のバッファサイズであって
コールスタックとは無関係。ここを増やしてもスタックオーバーフローには一切効かない。

## 1. 課題一覧(優先度順)

### 1-1. メモリ予算が GPU リソースを計上していない

`GetTrackedBytes()` に乗るのは [HeapAllocator](../aqEngine/Memory/HeapAllocator.h) を通った確保だけ。
D3D の `CreateBuffer` / `CreateTexture2D` が確保する頂点バッファ・テクスチャ・レンダーターゲットは
`operator new` を通らないので、トラッカーにも `IsOverMemoryBudget()` にも一切現れない。
`IDXGIAdapter3::QueryVideoMemoryInfo` の類も未使用で、計上する手段自体がない。

レンダラーでは通常ここが最大の消費者。Xbox はメモリが統合されているため 5GB 枠を直接消費する。
現状の数値は「CPU ヒープだけの部分値」であり、これを基準に予算判断すると GPU 側で先に落ちる。

- 対処案: `QueryVideoMemoryInfo`(D3D12 / DXGI 1.4)でローカル / 非ローカル使用量を取得し、
  Profiler パネルの予算バーを CPU と GPU の二本立てにする。UWP は `AppMemoryUsage` が統合値を返すので併記する。

### 1-2. 予算値がコンパイル時定数。UWP は実数を取得済みなのに捨てている

[PlatformBudget.h](../aqEngine/Platform/PlatformBudget.h) の `memoryBudgetBytes` は 5GB の `constexpr` 決め打ち。
一方 [PlatformUWP.cpp](../aqEngine/Platform/PlatformUWP.cpp) の `LogSystemInfo()` は起動時に
`Windows::System::MemoryManager::AppMemoryUsageLimit()` で実機の本当の上限を取得しているが、
用途はログ出力のみで `MemoryConfig` には流れていない。

上限は本体世代やアプリ種別で変わり、バックグラウンド遷移時には縮む。定数で持つ意味がない。

- 対処案: プラットフォーム層に上限取得関数を足し、`aq::Initialize()` で `MemoryConfig` を実測値で上書きする。
  Win32 側は `GlobalMemoryStatusEx` が該当。ただし空き物理メモリは他プロセス次第で変動するので、
  起動時の空きではなく総量からの割合で決めるほうが安定する。
- あわせて UWP の `AppMemoryUsageLimitChanging` / `AppMemoryUsageIncreased` を購読すると、
  バックグラウンド制限(Game 分類で 128MB)に入る前に解放処理へ入れる。

### 1-3. Release ビルドで確保失敗が nullptr のまま伝播する

失敗経路が三種類あり、そのうち一つが原因追跡不能になる。

| 経路 | Debug | Release |
| --- | --- | --- |
| グローバル `new` | HeapAllocator の `assert` が確保地点で停止 | [GlobalNew.cpp](../aqEngine/Memory/GlobalNew.cpp) が `bad_alloc` を送出 |
| `StdAllocatorAdapter::allocate` | 同上 | **nullptr をそのまま返す。例外なし** |
| `AllocatedArray::Create` | 同上 | **nullptr のまま構築へ進む** |

後ろ二つは、確保とは無関係な場所のアクセス違反として後から落ちる。コールスタックが原因を指さない。

- 対処案: [StdAllocatorAdapter.h](../aqEngine/Memory/StdAllocatorAdapter.h) の `allocate` は
  STL の契約どおり失敗時に `std::bad_alloc` を投げる。`AllocatedArray::Create` は bool を返すか同様に投げる。

### 1-4. 再帰に深度ガードのない経路が残っている

スタックオーバーフローは容量不足ではなく、ほぼ必ず暴走再帰が原因。
1MB はローカル変数としては十分広く、正常な処理が自然に到達する量ではない。
スタックを広げる対応は無意味で、深度上限で止めるのが正しい。

ガード済みの経路(対処不要):

- [PrefabSerializer.cpp](../aqEngine/ECS/PrefabSerializer.cpp) のネスト参照展開(循環検出 + 最大深度)
- [LevelManager.cpp](../aqEngine/Level/LevelManager.cpp) のサブ Level 再帰(`MAX_DEPTH` 32)
- [SceneHierarchySystem.cpp](../aqEngine/ECS/SceneHierarchySystem.cpp) の階層描画(64)
- [HierarchicalTransformComponent.cpp](../aqEngine/Component/HierarchicalTransformComponent.cpp) の親たどり(64)

ガードのない経路:

- **[SimpleJson.cpp](../aqEngine/Util/SimpleJson.cpp) の `ParseVal` / `ParseArr` / `ParseObj`**。
  深度カウンタなしの相互再帰で、ファイルのネスト段数がそのままスタックの深さになる。
  書き出し側の `StringifyImpl` も同様。`ParseFile` の呼び出しは 15 箇所あり、
  Prefab / Level / UI / Particle / AudioBank / StageData が全部ここを通る。**ここを直すのが最も費用対効果が高い**。
- [UIBatchRenderer.cpp](../aqEngine/UI/Rendering/UIBatchRenderer.cpp) のツリー走査、
  [UIDocumentLoader.cpp](../aqEngine/UI/Resource/UIDocumentLoader.cpp) の子生成、
  [UIContext.cpp](../aqEngine/UI/UIContext.cpp) の再帰破棄
- [AudioBank.cpp](../aqEngine/Sound/Authoring/AudioBank.cpp) の SoundObject 再帰パース

- 対処案: `ParseCtx` に深度フィールドを足し、`ParseVal` 冒頭で上限判定して打ち切る。
  一箇所の修正で 15 箇所の呼び出し元をまとめて守れる。

スタックオーバーフローは `assert` も捕捉可能な例外も出さず、トラッカーにも予算判定にも現れない。
ハンドラを書いても実行するスタックが残っていないため動かない。検知手段がないことを前提にする。

### 1-5. StackAllocator のバッファ自体が予算に計上されない

[StackAllocator](../aqEngine/Memory/StackAllocator.h) のコンストラクタは `_aligned_malloc` を直接呼び、
HeapAllocator を経由しないため `TrackHeader` が付かない。Win32 4MB / UWP 8MB が丸ごと集計から漏れている。
そこからの `Allocate` も同様に非計上。

- 対処案: 実プロセス使用量との差分要因(このバッファ + スレッドごとのスタック)を
  Profiler パネルに固定費として表示し、数値の食い違いで悩まないようにする。

### 1-6. Win32 エントリに `bad_alloc` の受け皿がない

[UWPMain.cpp](../Game/Application/UWPMain.cpp) は `std::exception` を捕捉してログを残してから再送出するが、
[Main.cpp](../Game/Application/Main.cpp) の `WinMain` にはハンドラがなく、無言で終了する。

- 対処案: `WinMain` を `try` で包み、`bad_alloc` を含む例外を `StartupLog` に残してから落とす。

### 1-7. StackAllocator の実利用がゼロ

初期化と `aq::Update()` 末尾の `ResetStackAllocator()` の配線だけが入っていて、
`stackVector` / `ScopedMarker` / `engineNewWith` の利用箇所が一つもない。

フレーム内の一時バッファ(可視判定の中間結果、パーティクルの一時配列、JSON 解析の作業領域など)を
移す候補を洗い出せば、Debug の確保コストがそのまま減る。

- 注意: `stackVector` はフレームをまたげない。`ResetStackAllocator()` の後に生きているとダングリングになる。
- 注意: `ScopedMarker` と他スレッドの `Allocate` は同時に使えない。
  オフセット更新は CAS だが巻き戻しは単純な store のため、間に他スレッドが確保していると踏み潰す。

## 2. 将来対応: 仮想アドレス予約 + 遅延コミットのプール化

`MemoryConfig::heapSizeBytes` が「将来のプール化に備えた予約フィールド」として空けてある。ここに入る話。

要点は予約と確定を分けること。

- 仮想アドレスの予約(`VirtualAlloc` の `MEM_RESERVE`)はアドレス空間を使うだけで、
  実メモリもコミットチャージも消費しない。64 ビットでは大きく取っても実質無コスト。
- 実際に上限を消費するのは確定(`MEM_COMMIT`)したぶんだけ。
- 現在の `_aligned_malloc` は呼んだ時点で全量が確定する。ここで数 GB を先取りすると、
  一バイトも使っていなくても予算を丸ごと消費する。UWP のバックグラウンド制限では即死する。

したがって正しい形は「大きく予約し、実際に使うぶんだけ塊単位で確定させる」二段構え。

留意点:

- 先取りは枯渇そのものを防がない。「実行中の予測できない失敗」を「起動時の決定的な失敗」に変換するだけ。
  枯渇時に何をするか(レベルのロードを失敗させるのか、プロセスを落とすのか)は別途決める必要がある。
- 一本の大きなプールに汎用アロケータを載せると断片化が効き、
  空きバイトは足りているのに連続領域が取れず失敗する落ち方が出る。
  コンソール向け実装がサブシステムごとのアリーナを切るのはこれが理由。
- 着手は 1-1 と 1-2 の後。計上できていない消費者(GPU)がある状態で上限近くまで先取りすると、
  帳簿は健全なのに GPU 側の確保が通らず落ちる。

## 3. 対応順序の目安

1. **1-4 の SimpleJson 深度ガード**。修正一箇所で全ローダを守れる。単独で完結する。
2. **1-2 の予算実測化**。UWP は取得済みの値を流すだけ。Win32 は `GlobalMemoryStatusEx` を足す。
3. **1-3 の nullptr 伝播**。Release のクラッシュ解析コストに直結する。
4. **1-1 の GPU 計上**。予算という仕組みを意味のあるものにする本丸。
5. **1-5 / 1-6** は表示と保険。ついでの時でよい。
6. **1-7 の StackAllocator 活用**、その後に **2 のプール化**。

## 4. 調査で確認した事実

再調査を省くためのメモ。

- コールスタックは Win32 / UWP とも既定 1MB。`.vcxproj` に `StackReserveSize` の指定なし。
- 単体で巨大なローカル変数は存在しない。最大は
  [VulkanGraphicsDeviceImpl.cpp](../aqEngine/Graphics/Vulkan/VulkanGraphicsDeviceImpl.cpp) の 2KB ログバッファ。
- コルーチン(`co_await` 等)は未使用。中断をまたぐローカルがヒープへ移る問題は現時点で無関係。
- ヒープとスタックの枯渇は独立ではない。スタックは後追いコミットのため、
  ヒープがシステムのコミット量を食い尽くしているとページ追加に失敗し、
  論理的には余裕があってもスタックオーバーフローとして落ちる。UWP の 5GB 枠では起こり得る。
