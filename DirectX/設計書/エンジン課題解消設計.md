### 2.2 設計

**バックエンド側**(P1-A)。`IGraphicsDeviceImpl` に no-op 既定のフックを足す。

```cpp
struct ImDrawData;   // 前方宣言のみ。imgui.h を引き込まない

virtual bool ImGuiInit()                  { return true; }   // 失敗時 false
virtual void ImGuiShutdown()              {}
virtual void ImGuiNewFrame()              {}
virtual void ImGuiRender(ImDrawData*)     {}   // レンダースレッドで呼ばれる
// VSync(現状 D3D12 のみ)
virtual bool CanToggleVSync() const       { return false; }
virtual bool GetVSync() const             { return true; }
virtual void SetVSync(bool)               {}
```

- `GraphicsDevice` が同名の薄い転送を持つ(既存の `RecreateSurface` / `WaitIdle` と同じ流儀)。
- 各バックエンドの `ImGuiInit` 等は、いま AppHost / ImGuiRenderCommand が直接呼んでいる処理をそのまま内側へ移す。
  - D3D11: `ImGui_ImplDX11_*` を `D3D11GraphicsDeviceImpl` 内で呼ぶ(device/context は自分が持つので `dynamic_cast` が消える)。
  - D3D12: `BeginFrameIfNeeded()` + `D3D12ImGui::Render(drawData, GetCommandList())` を `ImGuiRender` 内へ。
  - Vulkan / Metal: `ImGuiRender` が従来の `SetImGuiDrawData` を呼ぶ(drawData は CopyToBackBuffer 後に描く従来の挙動を維持)。
- `ImGuiRenderCommand::Execute` は `GraphicsDevice::Get().ImGuiRender(drawData_)` の 1 行になり、`#include` の `#if` も消える。
- **スレッド境界は変えない**: `ImGuiInit` / `ImGuiNewFrame` / `ImGuiShutdown` はメインスレッド、
  `ImGuiRender` は `ImGuiRenderCommand::Execute` の実行スレッド(= コマンドを実行するレンダースレッド。
  `AQ_RENDER_PIPELINED` が変えるのは待機の位置で、実行スレッドではない)。
- **終了順序は現状の契約を保つ**: CPU 描画完了 → レンダースレッド join → GPU `WaitIdle` →
  バックエンドの `ImGuiShutdown` → Platform の `ImGuiShutdown` → `ImGui::DestroyContext`
  ([AppHost.cpp](../aqEngine/Core/AppHost.cpp) の終了処理と同順)。フックへ移しても順序を入れ替えない。
- AppHost のバックエンド名表示は `GraphicsDevice` に `GetBackendName()`(既定 `"?"`)を足して `#if` を消す。
  **TODO**: 既に同等の API が在るか確認してから足す。

**Platform 側**(P1-B)。`IPlatform` に no-op 既定のフックを足す。

```cpp
virtual bool ImGuiInit()      { return true; }
virtual void ImGuiShutdown()  {}
virtual void ImGuiNewFrame()  {}
```

- Win32 → `ImGui_ImplWin32_*`(HWND は自分が持つ)。Mac → `MacImGui::*`。Android / iOS → `ImGuiPointerInput::*`。
- **フックの形(P1-B で確定)**: `ImGuiInit()` は `bool`(既定 true)、`ImGuiShutdown()` は `void`、
  `ImGuiNewFrame()` は **`bool`(既定 false)**。`true` は「Platform のバックエンドが `ImGuiIO` を更新した」、
  `false` は「持たない」で、このとき **AppHost が最低限の `DisplaySize` / `DeltaTime` を自分で入れる**
  (UWP が該当。値は Engine のものなので、Platform 層に Engine の参照を持たせないための形)。
- **決定(P1-B)**: 初期化中のフォント読込(Win32/Mac のシステムフォント)、モバイルの UI スケール、iOS の ini パスは
  **プラットフォーム固有の設定だが AppHost に残す**(別フックへは出さない)。Win32 と Mac でフォント探索の
  ロジックを共用していて、5 つの Platform へ散らすと重複が増えるため。この領域は `AQ_PLATFORM_*` の `#if` が残る。
  P1 の合格線は「**バックエンド側の `ENGINE_GRAPHICS_*` の `#if` が 0 件**」と「**Platform の入力バックエンド
  (init / shutdown / newFrame)の `#if` が 0 件**」とする。
- Platform の取り出しに `Engine::GetPlatform()`(`IPlatform*`、無ければ nullptr)を `Engine.h` へ足した(従来は公開の経路が無かった)。

## 3. P2: 無言の失敗を潰す + README の記述更新

### 3.1 現状(実コード確認済み)

1. [AppHost.cpp](../aqEngine/Core/AppHost.cpp) `SetupStandardRenderers`(L151〜): `PipelineBuilder::Build` 失敗時に
   `EngineAssertMsg(false, ...)` の後 `return` する。`EngineAssertMsg` は **Release では no-op**
   ([Utility.h](../aqEngine/Utility.h):23)なので、`renderer_` にパイプラインが設定されないまま起動が続き、
   `Renderer.cpp` の `if (!pipeline_) return;` で**全描画が黙って消える**。`Build()` 自身は `[pipeline]` ログを出すが、
   起動は失敗扱いにならない。戻り値が `void` なので呼び出し側が失敗を知れない。
2. `ShadowPass::Build`(`if (!renderer_) return;`)、`SkyPass`(`if (!sky_) return;`)、
   `FullscreenComputeCommand`(RT 取得失敗 / `computeShader_` が null で return)は**ログ無し**。
   影・空・ポストが消えても原因が分からない。

### 3.2 設計

- **README の更新**: `dynamic_cast` / `PostProcessChain` の 2 項目を「解消済み」へ。ImGui の項目は P1 完了時に更新。
  `-mode=edit` の「未実装ログ」の場所は AppHost ではなく [Engine.cpp](../aqEngine/Engine.cpp):91〜93 と訂正する。
  01 レンダリング設計 §7 の「既知の課題④の寸法契約」は、README に該当項目が見当たらない宙に浮いた参照
  (grep で 01 の 1 箇所のみ)。P4 の設計書化で解消するので、そこへのリンクに置き換える。
- **Build 失敗を初期化失敗として伝える**: 実際のゲーム経路は `SetupStandardRenderers` ではなく
  `GameModule::OnInitialize` の `host.BuildStandardPipeline(preset)` → `builder.Build(...)` →
  `host.SetRenderPipeline(...)`(Game/Application/GameModule.cpp)で、`Build` が null を返しても
  そのまま `SetRenderPipeline(nullptr)` へ渡され、`OnInitialize` は最後に `true` を返す。よって:
  - `AppHost::SetRenderPipeline` を `bool` 戻りにし、null を受けたら Release でもログを出して `false` を返す。
  - `GameModule::OnInitialize` は `false` なら `false` を返す(初期化失敗として `AppHost::Initialize` へ伝わる)。
  - `SetupStandardRenderers` も同様に `bool` 戻りにし、呼び出し側が初期化失敗として返す。
  - [System登録契約設計](System登録契約設計.md) の「登録失敗を初期化失敗として伝える経路」と同じ作法に揃える。
- **無ログ return の解消**: 毎フレームのログは禁物なので、**生成時に 1 回だけ** `StartupMarkf` で理由を出す。
  - 影・空: 標準プリセット([PipelinePresets.cpp](../aqEngine/Rendering/Pipeline/PipelinePresets.cpp))は
    生成に失敗すると **`ShadowPass` / `SkyPass` を列へ追加しない**ので、パスの `Setup` にログを足しても実行されない。
    ログは**プリセット側の生成失敗の分岐**(`shadow->Create` / `sky->Create` が false の else)に足す。
    機能自体は従来どおり無効のまま続行する(影なしで続行する既存作法を維持)。
  - `FullscreenComputeCommand`: RT 取得失敗 / `computeShader_` が null での return は、初回のみフラグで 1 回ログ。

## 4. P3: ドローの計測 → ソート

### 4.1 現状(実コード確認済み)

- 収集: [BodyComponentSystem.cpp](../aqEngine/Component/BodyComponentSystem.cpp) が ECS 走査順に `frame.items`(deferred)と
  `frame.forwardItems` へ `push_back`。**ソートは無い**(Rendering 配下の `std::sort` はパーティクルのみ)。
- 発行: GBuffer → `DeferredRenderer`(items 順)。Shadow → ライトごとに items + forwardItems。
  Forward → 不透明 → 半透明(`AlphaBlend` に切替えて同じ forwardItems を**もう 1 回走査**)→ instancedItems。
  **半透明は奥→手前のソートが無く、収集順のまま。** 重なると描画が崩れ得る。
- `RenderItem`([RenderFrame.h](../aqEngine/Rendering/RenderFrame.h):57〜104)は shared_ptr の `vs`/`ps`/`gbufferPS`/`vertexBuffer`/
  `indexBuffer`/`samplerState`、`textures[4]`、`worldMatrix`、`materialCB`(値)、`translucent` 等を持つ。
  `layer` は**常に 0 で誰も使っていない**(`MeshRenderHelper.h` の代入のみ)。PSO やマテリアル ID は無い。
- 1 ドローごとに b0(per-draw)・b1(lighting)・b2(material)・b3(shadow)・テクスチャ t0〜t3・サンプラー・VB・シェーダを
  毎回設定する(`DrawItemCommand.cpp`)。b1 / b3 は**フレーム共通なのに毎ドロー再バインド**。
  D3D11 の `D3D11RenderContextImpl` は状態キャッシュ無しで直接 `Set`。**TODO**: D3D12 / Vulkan / Metal のキャッシュの有無。
- 既存のインスタンシング([InstancedStaticMesh](../aqEngine/Graphics/InstancedStaticMesh.h))は forward 専用で、
  メッシュとマテリアルを手で登録する前提。シャドウ・GBuffer・法線/PBR・`materialCB` には未対応。
- 計測: [Profiler](../aqEngine/Util/Profiler.h)(CPU スコープ、`AQ_DEBUG_IMGUI` のみ)と ProfilerDebugPanel はある。
  **ドロー数・状態変更数のカウンタも GPU タイムスタンプも無い。**
  AquaDash の通常メッシュのドロー数は**静的には分からない**(実行時に数える必要がある)。

### 4.2 設計: 3 段階。ソートの採否は計測結果で決める

**P3-A 計測(挙動を変えない)**。ソートやバッチングの効果を言うには、まず数える。

- レンダースレッドが `DrawItemCommand` / `GBufferItemCommand` / `ShadowCastCommand` / `InstancedDrawItemCommand` の

## 5. P4: リサイズ対応

### 5.1 着手前の状態(要約)

P4-A 着手前(2026-11-09)は、描画解像度が起動時に固定で、`WM_SIZE` の通知経路も無かった。画面寸法に依存する RT は
メイン RT / 深度、`GBufferPass`(G0〜G3)、`HiZPass`、`BloomPass`、`MotionBlurPass`、`TonemapPass`、`OutlinePass` で、
`PassViewInfo.fullWidth/Height` は RT の実寸でなく呼び出し側の viewport 値だった(面だけ拡大すると食い違い、MoltenVK で VUID-06079/06080 が出得る)。
シャドウは画面非依存、ミニマップ(512²)は固定寸法が正しい。Sky / UI / ClusterCull に画面依存 RT が無いことは P4-A の実装で確認した(全 `Independent`)。
**現行の姿(恒久仕様)は [01 §2.11](01_レンダリング設計.md) と [06 §1.2](06_ゲームアプリケーションコア設計.md) に移した**(2026-11-10)。

### 5.2 設計の判断(恒久仕様は 01 §2.11 / 06 §1.2 が一次資料)

手順・契約・クラスの責務は 01 / 06 へ移した(同じ内容を 2 か所に書かない)。ここには**採らなかった案と理由**だけ残す。

- **固定内部解像度 + アップスケールは採らない**: 描画解像度 = 提示面(倍率 1.0)。必要になったら別設計。
- **未対応バックエンドは挙動を変えない**: `SupportsRenderResize()` の宣言制にし、フェーズごとに独立コミットできるようにした。
- **デバイス層の強い保証は採らない**: Vulkan は `oldSwapchain` 指定後に旧が退役し、DXGI の `ResizeBuffers` は旧参照を先に解放する必要があり、
  旧へ戻せない。保証はパス層(準備 → 確定 / 取り消し)に置き、デバイス層は「保留 + 再試行」で扱う。
- **寸法の読み取りは Platform から**: Vulkan の `swapchainExtent_` はレンダースレッドが書き換えるため、メインスレッドから読むと競合し得る。
- **パイプライン全体の再 `Build` は採らない**: `GameModule` が `OutlinePass` を `UIPass` の前へ挿すなど、ゲームが列を加工しており、プリセットからの再構築では失われる。
- **`IRenderPass` の既定は「未対応」**: ゲームが独自パスを足せる公開の拡張点で、既定を「何もしない」にすると旧寸法のまま静かに壊れる。
- **保留中に一部だけ `Update` する案は採らない**: `AppHost::Update` は末尾で描画するため。代わりに `UpdateSoundOnly()` を切り出した。
- **Win32 は `WM_SIZE` を通知に使わず、ポーリングで値を返す**(P4-C)。
  **TODO(P4-C)**: `WS_THICKFRAME` の有無と全画面切替との関係を確認する。

**検出は、パス側の実装(6 パス)が揃ったバックエンドでだけ有効にする**(寸法の混在を防ぐ)。

### 5.4 評価チェックリスト

**P4-A の実装記録と結果(2026-11-09、Mac Metal Debug)**。Vulkan は `SupportsRenderResize` が false のままで P4-B で扱う。

実装で決めた点・設計からの差:
- **致命終了は `std::abort()`**。Engine に終了要求の API が無いため、失敗が累計 5 回(最初の試行を含む。200 ms 間隔)に達したら `[engine] FATAL` を残して止める
  (設計書の「終了を要求する」からの逸脱。終了要求の API を足すかは P4-B 以降で判断する)。
- **`DecalPass` は Independent ではなく Resizable(する作業は無い)**。`DeclareResources` が `GBuffer0` を Writes しており
  Independent の規則に当たるが、掲示板へは登録しない。G-Buffer の RT は GBufferPass が持ち、同じ `DeferredRenderer` の中身が入れ替わる。
- `MotionBlurEffect::CommitResize` は `prevValid_ = false`(旧寸法の前フレーム viewProj を使わず、速度ゼロから再開)。
  `HiZRenderer::CommitResize` は CPU リードバックを mutex 下でクリア(次の読み戻しまで遮蔽判定は「可視」扱い)。
- 追加した小物: `GameTimer::ResetDelta()`(再作成の時間をデルタ時間に載せない)、`Renderer::SetMainViewport()`、
  確定時にメインカメラの `SetViewportSize` を更新、`Engine::UpdateSoundOnly()`(保留中のサウンド供給。実経過時間を測る)。
- 検出は `IPlatform::GetClientPixelSize`(Mac はビューの bounds)。起動直後は要求済み寸法 = 描画解像度(1280×720)で、起動時にリサイズは発生しない。

確認できたこと:
- Metal / Vulkan(Game と Sample)が Debug でエラー 0 でビルドできる。
- **Metal・Debug・Validation 有効**で、タイトル画面(1000×608 / 1375×800 / 400×268)とゲームプレイ中(1100×668 / 1375×800 / 800×468)を
  拡大・縮小し、毎回 1.4〜8.5 ms で完了。撮影で、画面が引き伸ばされず黒帯も無く、GBuffer / ブルーム / アウトライン / Hi-Z / UI / ミニマップが新寸法で描かれた。
  Validation エラー・`FATAL` は無し。ドラッグ中を模した 40 ms 刻みの連続変更(8 回)も、1 回ごとに完了した。
- **GPU リーク無し**: 1000×640 と 1200×740 を交互に 100 回リサイズ。デバイス確保量(`currentAllocatedSize`)は、
  1200×708 が 175.70 MB のまま不変、1000×608 は初回 189.39 MB のあと 186.41 MB で安定(増え続けない)。
- **デバイス層の失敗**: 一時的に 1 回失敗させ、約 200 ms 後の再試行で完了した(`kMax` までの間隔は 197〜200 ms)。
- **パス層の失敗**: 準備に成功した後に意図的に失敗(`AbortResize` を通す)させ、再試行で完了。直後のリサイズの確保量も 175.70 MB のまま(Abort でリークしない)。
  常時失敗させると、200 ms 間隔で失敗が累計 5 回(最初の試行を含む)に達して `FATAL` で止まった。

**追加確認(2026-11-10、Mac。Metal・Vulkan とも Debug。Xcode 27.2)**。一時フック(環境変数で列を切り替える・デバイス層を N 回失敗させる・デルタ時間を記録する)で確認した。**フックはコミットしておらず、再現手段はリポジトリに残っていない**(再検証するときは同様の一時フックを入れ直す。常設のテストフックにするかは未判断)。
ウィンドウ操作は Accessibility API(寸法変更・最小化・復帰)で行った。

- **Tonemap なしの列**(`enablePostProcess=false`。Outline が `Output` を読む構成): Metal でタイトル(1280×720 → 1000×608 → 1300×728)と
  ゲームプレイ中(→ 900×528 → 1350×768 → 1100×668)を、毎回 2〜6 ms で完了。撮影で、引き伸ばし・黒帯無し、Outline が旧 RT を読んだ痕跡も無い。
  Vulkan でも 1100×668 を 0.5 ms で完了し、描画は正常。Metal の Validation エラー無し。
- **`Unsupported` のパス**(Frame scope のダミーパスを UI の手前へ追加): Metal・Vulkan とも、`[pipeline] リサイズ無効: <パス名> が未対応` と
  `[engine] リサイズ無効` が **1 回だけ**出て、2 回目のウィンドウ変更ではログも出ない。`リサイズ開始` が一度も出ない
  (= 入口で止まり `ResizeMainTargets` は呼ばれない)。固定寸法のまま描かれ続けた。
- **最小化と復帰**: Metal・Vulkan とも、最小化 → 復帰 → 寸法変更でプロセスは生存し、描画も復帰した。ただし AX の最小化では

## 9. P5: 終了要求 API

設計レビュー(Codex、2026-11-10。プラットフォーム側と Engine 側に分けて依頼): プラットフォーム側 中 1・軽 1、Engine 側 重大 1・中 2 → 全件反映 →
両方とも 2 回目「指摘なし」。反映したもの: Android には `RequestExit()` が無いので本体ごと新設 / iOS の `PumpEvents` のコメント更新 /
対象を「失敗が戻り値で返る故障」に限定し、GPU が応答しなくなる故障は対象外と明記(`WaitForRenderIdle` で止まり致命判定に届かないのは `abort` 版と同じ)/
`Finalize` の契約と 3 つの注入点・5 秒の制限時間 / 終了要求を一時的に無効にして `fatalStopped_` の分岐を通す評価。不採用は無し。

### 9.1 着手前の状態(実コード確認済み、2026-11-10。`6177747`)

- **Engine には終了を要求する手段が無い**。ループは `IPlatform::RunFrameLoop` の既定実装が `PumpEvents()` の false で抜けるだけで、
  false を返す理由は各プラットフォームの「閉じる」操作(Win32 の `WM_DESTROY` → `PostQuitMessage`、Mac の `windowShouldClose:`、
  UWP の `Closed`、Android の `APP_CMD_DESTROY`)に限られる。ゲームコードからは終われない。
- `RequestExit()` は Mac / iOS / Android / UWP の各実装に**個別の非 virtual 関数**としてあるが、`IPlatform` には無い。Win32 には無い。
- **リサイズの致命失敗は `std::abort()`**(`Engine::AttemptRenderResize`)。`Finalize` を通らないのでサウンドの停止・GPU の解放・リーク報告が走らず、
  終了コードも異常終了になる(README「既知の課題」。§5.4 の P4-A の記録で「終了要求の API を足すかは後で判断」としたもの)。
- プロセスの終了コードは `Main.cpp` / `MacMain.mm` が「初期化失敗なら 1、それ以外は 0」で返す(`6d9864e`)。実行中の理由は伝わらない。
- Mac はメニューを作っていない(`NSMenu` 無し)ので、Cmd+Q の経路は無い。MacMain.mm の TODO(`applicationShouldTerminate:`)は今は該当しない。

### 9.2 設計

**`IPlatform::RequestExit()`**(新設。純粋仮想 `virtual void RequestExit() = 0`。既定実装は持たない。全実装が持つべきもので、付け忘れをコンパイルで検出するため)。
意味は「次の `PumpEvents()` が false を返すようにする」。メインスレッドから呼ぶ。

| 実装 | 中身 |
| --- | --- |
| Win32 | `exitRequested_` を足し、`PumpEvents()` の先頭で true なら false を返す(`PostQuitMessage` は使わない。埋め込み時の親ウィンドウへ影響させないため) |
| Mac / UWP | 既存の `RequestExit()` に `override` を付けるだけ(中身は今のまま) |
| Android | `RequestExit()` は**無い**(`exitRequested_` だけある)。`exitRequested_ = true` にする本体ごと新設する。Activity の終了(`ANativeActivity_finish`)までは行わない(ループを抜けて `Finalize` まで進むのは既存の破棄経路と同じ) |
| iOS | **終了しない**。ログを 1 回出して無視する(`exitRequested_` も立てない)。iOS アプリはプログラムから終了しない決まりで、CADisplayLink のループも `PumpEvents` を見ていない。`PumpEvents()` のコメント(「終了要求で false の契約を保つ」)も「iOS は終了要求を受け付けない」に書き換える |

**`Engine::RequestExit(int exitCode = 0)`**(新設、public)。ゲームコードと Engine 内部の両方から呼ぶ。

- `exitCode_` に記録し(**最初に要求されたコードを保つ**。後から 0 で上書きしない)、`platform_->RequestExit()` を呼ぶ
- `int Engine::GetExitCode() const` を足し、`Main.cpp` / `MacMain.mm`(Game / Sample)は初期化成功時にこれを返す(初期化失敗は従来どおり 1)
- 要求したフレームは最後まで回る(Update・描画とも)。止まるのは次の `PumpEvents()`。iOS では止まらない(上の表)

**リサイズの致命失敗**(`AttemptRenderResize` の再試行上限):

- `std::abort()` をやめ、`[engine] FATAL` のログはそのままに `fatalStopped_ = true` と `RequestExit(2)` にする
- `FrameStep()` は先頭(`SyncSoundActivity` の後)で `fatalStopped_` なら何もせず 16 ms 待って戻る(Update・描画・リサイズ処理をしない)。
  デバイスが壊れている可能性があるので、以後は GPU を触らない。iOS では終了しないので、この状態のまま止まった画面になる
- その後の `Finalize()` は従来の順で走る(`appHost_->Finalize()` = レンダースレッドの停止・合流と GPU の完了待ち → デバイスの破棄)。

**対象にする故障の範囲**。P5 が扱うのは「**失敗が戻り値で返ってくる故障**」に限る: `ResizeMainTargets` が false を返す(スワップチェーンや
メイン RT の再作成に失敗。Vulkan は `oldSwapchain` 退役後の生成失敗で「スワップチェーン無し」に落ちる。§5.4 P4-B)、または全パスの
`PrepareResize` が失敗し続ける。このとき GPU は応答しており、`WaitForRenderIdle` は戻る。
**GPU が応答しなくなる故障**(完了待ちが戻らないデバイスロスト)は対象外: 再試行の手順 1 の `WaitForRenderIdle` で止まり、致命判定にも届かない。
これは今の `abort` 版でも同じで、P5 で悪化はしない(§9.5)。

**`Finalize` の契約**: 上の範囲の失敗の後に残る状態(Vulkan のスワップチェーン無し、新寸法のメイン RT と旧寸法のパス RT の混在、
パスの一時 RT は `AbortResize` 済み)で、`Finalize` が落ちず、レンダースレッドが合流し、プロセスが終わること。評価で 3 つの注入点を確かめる(§9.4)。
落ちる箇所が見つかった場合は、その箇所と原因を記録し、`fatalStopped_` のときだけ飛ばす処理を足す(設計変更として再承認)

**終了コードの割り当て**: 0 = 正常 / 1 = 初期化失敗(既存)/ 2 = 実行中の致命失敗(リサイズ)。ゲームが `RequestExit(n)` で任意の値を使うのは自由。
