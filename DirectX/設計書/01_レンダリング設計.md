## 0. 設計の全体像

レンダリングは **2 つのレイヤー**に分かれる。

| レイヤー | 名前空間 | フォルダ | 役割 |
|---|---|---|---|
| **グラフィックス抽象 (低レベル)** | `aq::graphics` | `Graphics/` | GPU API(D3D11/D3D12/Vulkan)を **Bridge パターン**で抽象化。リソース生成・ステート設定・ドローの発行だけを担う。API 固有型を上位に漏らさない。 |
| **レンダリング (高レベル)** | `aq::rendering` | `Rendering/` | 「1 フレームに何を描くか」を組み立てる。`RenderFrame`(スナップショット)→ `RenderCommandList`(記録)→ 専用スレッドで再生。ディファード/シャドウ/ポストプロセス/オクリュージョンの各パスを持つ。 |

ハイブリッド(DX11/DX12/Xbox/UWP)の要は **この 2 層の境界**にある。上位の `aq::rendering` は API を一切知らず、切り替えは `Graphics/` 内の実装差し替えだけで済む。

```
[ゲームスレッド]
  ECS(RenderSystem::BuildRenderFrame) → RenderFrame（描画スナップショット）
        │  フラスタムカリング済み
        ▼
  Renderer::BuildCommandList()  → RenderCommandList（API 非依存コマンド列）
        │  Submit()
        ▼
[レンダースレッド]  RenderThread
  RenderCommandList::Execute(RenderContext&)
        └─ RenderContext → impl_ : IRenderContextImpl
              ├─ D3D11RenderContextImpl
              ├─ D3D12RenderContextImpl
              └─ VulkanRenderContextImpl
```

## 1. グラフィックス抽象レイヤー(`aqEngine/Graphics/`)

### 1.1 Bridge パターンの中核

| ファイル | 責務 |
|---|---|
| `GraphicsDevice.h/.cpp` | **抽象デバイス(シングルトン)**。`Create<TImpl>()` テンプレートでバックエンド実装を注入する。`Initialize`/`Finalize`/`Present`、リソースファクトリ(`CreateVertexBuffer` 等)、オフスクリーン RT 生成、`OnSuspend/OnResume`(UWP PLM)を公開。内部に `IGraphicsDeviceImpl` を 1 つ持ち、全呼び出しを委譲する。上位コードはこのクラスしか触らない。 |
| `IGraphicsDeviceImpl.h` | **デバイス実装インターフェース**(Bridge の Implementor)。D3D11/D3D12/Vulkan の各実装が継承。デバイス/スワップチェーン初期化、リソースファクトリ、`ReadbackOffscreenR32`(GPU→CPU リードバック)、GPU 駆動バッファ生成(`CreateStructuredBuffer`/`CreateRawBuffer`)を宣言。未対応バックエンド用に安全な既定実装(no-op/nullptr)を持つ。 |
| `RenderContext.h` | **抽象コンテキスト**(コマンド発行の窓口)。`OMSet*`/`RSSet*`/`IASet*`/`VS/PS/CSSet*`/`Draw`/`Dispatch`/`DrawIndexedIndirect` 等の描画コマンドを、すべて**抽象インターフェース型引数**で受ける。`IRenderContextImpl` に委譲するだけの薄いラッパ。 |
| `IRenderContextImpl.h` | **コンテキスト実装インターフェース**。`DepthMode`/`BlendMode` 列挙もここで定義。GPU 駆動間接描画(`IASetIndexBufferGpu`/`DrawIndexedIndirect`/`UavBarrier`)とスライス指定シャドウは既定 no-op で、対応バックエンドのみ override する。 |
| `RenderContext.cpp` | `Execute` 系ヘルパ・`RenderContext` の非インライン実装。 |

**レビュー観点**: `RenderContext` は全メソッドがインラインで `impl_->` に流すだけ。API 追加時は「抽象 IF(no-op 既定)→ 各実装 override」の順で足す規約になっているか(間接描画がこの流儀)。

### 1.3 バックエンド実装(D3D11 / D3D12 / Vulkan)

3 API が **同じファイル構成で 1:1 に並ぶ**。ビルド構成 `ENGINE_GRAPHICS_D3D11 / _D3D12 / _VULKAN` で 1 つだけコンパイルされる。

| `D3D11Buffers` | `D3D12Buffers` | `VulkanBuffers` | 頂点/インデックス/定数バッファ具象。 |
| `D3D11Shader` | `D3D12Shader` | `VulkanShader` | シェーダコンパイル/ロード。 |
| `D3D11Resources` / `D3D11RenderResources.h` | `D3D12Resources` / `D3D12RenderTarget` | `VulkanResources` / `VulkanRenderTarget` | SRV/サンプラー/UAV/RT の具象。 |
| `D3D11DepthMap` | `D3D12DepthMap` | `VulkanDepthMap` | シャドウ深度マップ具象。 |

| — | `D3D12GpuBuffer` | — | GPU 駆動クラスタカリング用バッファ(構造化/RAW/間接引数)。 |
| `imgui_impl_dx11`(ThirdParty) | `D3D12ImGui` | `VulkanImGui` | ImGui バックエンド接続。 |
| — | `D3D12Common.h` | `VulkanCommon.h` / `VulkanVMAImpl.cpp` | 共通ヘルパ(DX12=ヘルパ、Vulkan=VMA アロケータ)。 |

**ハイブリッドの肝**:
- **DX11** … immediate context・動的ステート中心で最も単純。Xbox One UWP(FL11_0 未満 = App 分類の FL10_0 経路)フォールバックの主経路。compute/UAV/間接描画は FL によって非対応 → `SetComputeSupported(false)` で機能を落とす。具体的な FL 値の根拠は [Xbox移植設計](Xbox移植設計.md) に一元化。
- **DX12** … 明示的な PSO/ルートシグネチャ/フェンス/リードバックヒープ。GPU 駆動カリング・Hi-Z リードバックが完全動作する主戦力。実機 Xbox のフル描画経路。
- **Vulkan** … 同一構造の先行事例(抽象 IF 追加 0 本で移植した実績)。SDK 未導入時は `#ifdef` ガードで実コンパイル対象外。

## 3. フレームの流れ(`Application::Render` 実体)

`Core/Application.cpp` が毎フレーム行う手順(ハイブリッド分岐込み):

1. メインカメラ位置を `LightManager` に反映。
2. **ImGui**: `ImGui_ImplWin32_NewFrame` + バックエンド別 `NewFrame`(DX11/DX12/Vulkan を `#ifdef` 分岐)。FPS/バックエンド名/VSync(DX12)のオーバーレイ。
3. `OnPreRender()`(ゲーム固有のオフスクリーンパス Submit)。
4. メイン `RenderCommandList` を確保し、SetRenderTarget/Clear/SetViewport を Enqueue。
5. `RenderSystem::BuildRenderFrame(mainFrame)` … ECS 走査+**フラスタムカリング**で `RenderFrame` を構築。
6. `Renderer::BuildCommandList(...)` … シャドウ→G-Buffer→Hi-Z→ライティング→ポストプロセス→UI→ImGui の順にコマンド記録。
7. `RenderThread::Submit(...)` … レンダースレッドへ。表示 RT はポストプロセス最終出力(`GetDisplayRTHandle`)。

初期化時(`Application::Initialize`)の**機能ゲート**が重要:
- `IsComputeSupported()==false`(FL11_0 未満 = Xbox One UWP App 分類の FL10_0 経路 等)→ クラスタカリング無効・Hi-Z 未初期化。
- ディファードが有効なときだけ Hi-Z を初期化しオクリュージョンテスターに登録。

## 5. 分割画面ビュー(マルチビュー)設計

> 追加: 2026-09-06(AquaDash P5)。ゲーム側要件は
> [AquaDash 04_描画_分割画面_UI設計](../Game/Design/AquaDash/04_描画_分割画面_UI設計.md) が一次資料。

1 フレームに最大 4 ビュー(カメラ + ビューポート矩形)を同一バックバッファへ直接描く。
**ビュー数 1 のときは従来経路をそのまま通し、コスト増ゼロを保証する。**

### 方式(調査で確定した前提)

- カメラ定数 (b0) は **per-draw**(各コマンドが CameraData を値持ち)→ 1 リスト内でビュー毎にカメラを差し替え可能。
- ディファードライティングは SV_POSITION 基準の GBuffer Load → **サブビューポート設定だけで正しく領域制限**される。
- lighting(b1)/shadow(b3) は per-frame かつカメラ非依存 → 全ビュー共有。シャドウパスは先頭 1 回。
- Clear 系コマンドはビューポートを無視して全面クリア → **クリアはフレーム先頭/最初のビューのみ**。
- Bloom/トーンマップは compute 全画面 → ビューループ外で 1 回(ビュー境界のにじみは仕様上の妥協)。
- UI は NDC 固定頂点 → 全画面 1 回(ビュー毎 HUD は将来、ビューポート切替+バッチ分割で対応)。

### 実装(コマンド列)

```
Clear(メインRT+depth) … 1回
Shadow パス            … 1回 (view0 の frame)
for view in views:
    SetViewport(view.rect)
    GBuffer (クリアは view0 のみ) → デカール → ディファードライティング → フォワード → 海
    パーティクル … view0 のみ (エミッタ共有動的VBへの多重書込み回避。既知の制限)
SetViewport(全画面)
Bloom+トーンマップ … 1回
UI … 1回 / ImGui / CopyToBackBuffer+Present (Submit は 1 フレーム 1 回のまま)
```

### ファイル別変更

| ファイル | 変更 |
|---|---|
| `Rendering/Renderer.h/.cpp` | `ViewRect` と `BuildCommandListViews(frames, rects, count, ...)` を追加。既存 `BuildCommandList` は不変 |
| `Rendering/Deferred/IDeferredRenderer.h` / `Deferred/DeferredRenderer.*` | `BuildGBufferCommandList` に `clearTargets`(既定 true)を追加 |
| `Component/BodyComponentSystem.*` | `BuildRenderFrame(frame, camera, フラスタム有効, オクリュージョン有効, 統計更新)` のカメラ直指定版を追加し、既存関数は委譲に変更(`cameraType==Main` ゲートを引数化) |
| `Core/Application.h/.cpp` | `SetSplitViews(camera*, rect)[]` を追加。`Render()` はビュー数 >= 2 のときだけマルチビュー経路へ分岐(1 ビューは既存コードのまま) |
| `HID/Input.h` | `KeyBoardType::Num1..Num4` 追加(分割の擬似人数切替テスト用) |

### 制限(分割時のみ。1 ビュー時は無関係)

- Hi-Z オクリュージョン / GPU クラスタカリングは複数カメラ前提が崩れるため**分割時は無効**(フラスタムカリングはビュー毎に有効)。
- パーティクルは view0 にのみ描画(共有動的 VB の多重書込み対策。必要になれば VB 連結+offset 描画で解消)。
- シャドウは全ビュー共有 1 枚(注視点は player0)。
- HUD は全画面 1 枚(player0 の値)。ビュー毎 HUD は AquaDash P7 以降で検討。

## 6. インスタンス草の描画(手続きメッシュ + 風揺れ)

大量の草をインスタンス描画するための、メッシュ生成と専用シェーダ。
カリング側(静的インスタンスのベイク + セル単位カリング)は
[カリング設計.md §15](カリング設計.md) が一次資料。本節は**描画**のみを書く。

### 6.1 メッシュ(`Graphics/MeshPrimitives.{h,cpp}`・新規)

手続き生成の再利用可能なプリミティブを置く新ファイル。第一弾が草の房。

- 中心で交差する 3 枚のクアッド(房)。12 頂点。
- ラスタライザは `CULL_MODE_BACK` 固定のため、**巻き順を反転したインデックスも足して両面化**する
  (頂点は共有するので 12 頂点 / 12 三角形)。
- 法線は面法線ではなく**上向き寄り**にする。両面から見て明暗が反転せず、陰影が柔らかくなる。
- `uv.y` を「根元 0 / 先端 1」として持たせる。風の振幅と色グラデーションの両方がこれを使う。
- アルファテストは既存シェーダに無いため、抜きテクスチャではなく**実体形状**で表現する。

### 6.2 シェーダ(`Game/Assets/Shader/InstancedGrass.fx`・新規)

入力レイアウトは `InstancedSimple.fx` と同じ(slot0 = 位置/法線/UV、slot1 = `I_WORLD0..3` + `I_COLOR`)。
違いは 2 点。

- **VS で風の変位**: `uv.y` を重みに、根元を動かさず先端ほど大きく揺らす。
  位相はインスタンスのワールド位置(`I_WORLD` の平行移動成分)から作るため、
  **per-instance データを増やさずに**株ごとに揺れがずれる。
- **PS で縦グラデーション**: `uv.y` で根元を暗く、先端を明るくする。ライティングは
  `InstancedSimple.fx` と同じランバート。

### 6.3 風の定数バッファ(b2 `WindCB`)

- 中身: 時刻・強さ・周波数・風向。192 バイトに揃え、`perDrawCBPool` を借りる
  (`ClusterCullCBData` が同じ理由で 192B に揃えている前例に倣う)。
- **b2 は本来 `MaterialCB` / `PBRMaterialCB` だが、インスタンス描画経路はマテリアル CB を
  bind しない**ため衝突しない。将来インスタンス経路にマテリアルを持たせるときは要再配置。
- **時刻はゲームスレッドで `Engine::GetTotalTime()` を読み、`InstancedRenderItem` に載せて運ぶ**。
  レンダースレッドからエンジンのシングルトンを読まない(スレッド境界規約)。

### 6.4 責務表

| クラス / ファイル | 責務 |
|---|---|
| `Graphics/MeshPrimitives.h/.cpp`(新規) | 草の房メッシュの手続き生成(両面・uv.y=高さ) |

## 7. ポストプロセスチェーン(P15)

> 設計 2026-09-09。見た目を一切変えない純リファクタ(旧 BloomRenderer の分割)。
> ファイル構成は §2.6。ここではチェーンの契約と互換性の要点だけを書く。

### 7.1 チェーンの契約

- **入力**: `PostProcessContext { sceneRT(HDR), width, height, hasCamera, worldPosRT }`。
  値は毎フレーム `Renderer` 側から渡す(RT 寸法は初期化時固定。リサイズ対応は将来課題)。
- **パスの直列実行**: `MotionBlur → Bloom → Tonemap` の順。各パスは
  「1 入力 RT → 1 出力 RT + 自前の中間 RT」に閉じる。Tonemap だけは合成のため
  元の sceneRT(または MotionBlur 出力)と Bloom 結果の 2 入力を取る。
- **有効判定**: 各パスの `IsEnabled(context)` で毎フレーム判定し、無効なら積まず
  入力をそのまま次段へ流す。**Tonemap は常時 ON**(HDR→LDR 変換が無いと表示できないため)。
  モーションブラーの有効条件(強度 > 0 かつ当該フレームのカメラあり)は
  旧実装の mutable フラグ副作用をやめ、`context.hasCamera` で明示する
  (分割画面経路は hasCamera=false を渡してブラー無効: §5 の暗黙仕様の明文化)。
- **最終 RT と RTV 復元**: `GetFinalRT()` は Tonemap の出力(LDR)を返す。
  **チェーンの最後に最終 RT を RTV としてバインドして終える**(後続の UI / ImGui が
  そこへ描く契約)。この復元はパス任せにせずチェーン側が 1 箇所で行う。
- **RT の所有**: 各パスが自分の中間 RT を `Initialize(w, h)` で生成・所有する。
  プール化・リサイズは本フェーズではやらない(既知の課題④の寸法契約と合わせて将来)。

### 7.2 互換性の要点(変えないもの)

- `IPostProcessRenderer` の公開 API(`SetFrameCamera` / `SetMotionBlurStrength` /
  `SetWorldPosRT` / `GetFinalRT` / `CreateDebugPanel`)は維持し、チェーンが該当パスへ
  ルーティングする。呼び出し元(`Renderer.cpp` / ゲームの `Application.cpp`)は原則無改修。
- CB レイアウト(`BloomCBData`)は 4 シェーダ共有のまま(分割はシェーダ側 cbuffer と
  同時でないと壊れるため本フェーズでは触らない)。シェーダ(.fx)も無変更。
- `IsComputeSupported()==false` 経路(ポストプロセス全スキップ + sceneRT 直表示)は不変。
- 削除: 参照ゼロの `Game/Assets/Shader/BloomBlur.fx`(Dual Blur 移行の残骸)。

## 8. オフスクリーンシーンパス(P17)

> 設計 2026-09-09。既知の課題「オフスクリーンパス(512²)がディファード経路でシーンを
> 描けない」(README 2026-09-06 発見)の解消。発端はゲーム(AquaDash)の俯瞰 RT ミニマップ
> ([AquaDash 04 §4](../Game/Design/AquaDash/04_描画_分割画面_UI設計.md))。

### 8.1 問題と方針

- 症状: ライティング/フォワードが `OMSetRenderTargetWithDepth(オフスクリーンRT, GBuffer0)` で
  512² RTV と 1920×1080 DSV を同時バインドし、D3D の制約違反で静かに失敗する。
  原因は「GBuffer(=深度の持ち主)が `Renderer` のメンバ 1 組しか無く、メイン解像度固定」なこと。
- 方針: **縮小 GBuffer 一式を自前で所有する独立パス `OffscreenScenePass` を新設**する。
  `DeferredRenderer` は寸法をコンストラクト引数で取り static 依存も無いため、2 個目を
  512² で作れる(追加 VRAM は RGBA8×1 + RGBA16F×3 ≒ 3.1MB)。
- `Renderer` を流用しない理由: shadow / UI / Hi-Z / ポストのコールバックと所有物が 1 組しか
  無く、2 パス目に流用すると「UI のオフスクリーン焼き込み」「シャドウマップ二重描画」
  「1080p Hi-Z の再構築」を全部踏む。抑制フラグを増やすより、必要な最小パス列だけを
  持つ別クラスの方が短く安全。

### 8.2 責務表

| ファイル | 責務 |
|---|---|
| `Rendering/Offscreen/OffscreenScenePass.h/.cpp`(新規) | 独立オフスクリーンシーンパス。カラー RT(`hasDepth=false`)+自前 `DeferredRenderer`(縮小 GBuffer。深度は GBuffer0 内蔵)を所有し、GBuffer → ディファードライティング → フォワード/インスタンスの**最小パス列**だけを記録する。シャドウ / Hi-Z / ポストプロセス / UI / パーティクル / デカール / 海は積まない |
| `Graphics/Camera.h/.cpp` | **正射影モード追加**(`SetOrthographic(width, height)`。設定時は viewAngle/aspect 経路の代わりに `Matrix4x4::MakeOrthographic` で射影を作る。既存カメラは無影響) |
| `Component/BodyComponentSystem.h/.cpp` | **同一フレーム 2 回目の gather 要求を再利用するガード**。「登録インスタンスの Flush は毎フレーム必ず 1 回」の不変条件を保ったまま、オフスクリーン側の gather を先行実行できるようにする(後述 8.3) |
| `Graphics/GraphicsDevice.h/.cpp` | `GetRenderTargetSRVShared(handle)` 追加(RT の SRV を**非所有 deleter の shared_ptr** で返す。`UIImageComponent::texture` が `shared_ptr<IShaderResourceView>` のため) |

### 8.3 契約

- **Submit**: `displayRT = RenderTargetHandle{}(INVALID)` で Submit し、Present しない。
  `RenderThread` はリング 4 スロットで 2 Submit/フレームを想定済み(マルチスレッド設計 §2)。
  リングは FIFO なので `OnPreRender` の Submit はメインパスより先に実行される。
- **RenderFrame 構築**: カメラ直指定版 `BuildRenderFrame(frame, camera, false, false, false, gather)`
  で呼ぶ。フラスタムカリング無効(俯瞰は全景が入る)、オクリュージョン無効(Hi-Z は 1080p
  メインカメラ由来で誤判定する)、統計更新無効。
- **gather の順序**: インスタンスの gather(セルカリング+Flush)はフレームに 1 回の制約が
  ある。描画するフレームだけオフスクリーン側が `gather=true` で**先行して**行い(フラスタム
  無効なので全セルが積まれる)、同フレームのメインパスはガードにより再利用する
  (そのフレームだけ全インスタンス描画になるが、用途がロード時 1 回のベイクなので許容)。
  草など `maxDrawDistance` 持ちのセルは俯瞰カメラとの距離で自然に落ちる。
- **ライティング**: メインと同じ `LightManager` の `LightingData` を Submit に渡す。
  シャドウ CB は無効値(オフスクリーンは影なしの素朴なライティング)。
- **頻度は呼び出し側が決める**: 毎フレーム呼べばシーン約 1 回分のコストが素直に増える。
  AquaDash はロード完了時に 1 回だけベイクする(dirty フラグ)。旧実装の停止理由だった
  「未使用なのに毎フレーム二重描画」はこの契約で解消。
