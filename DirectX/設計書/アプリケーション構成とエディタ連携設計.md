# アプリケーション構成とエディタ連携 設計ドキュメント

> 対象コミット: 7f7e1b6 / 最終更新: 2026-10-01(P3 完了)

## 0. 目的と位置づけ

将来、WPF で作る外部エディタから TCP(ローカル)で操作される **ランタイム** として
エンジンを動かせるようにする。そのための土台として次の 3 つを入れる。

| フェーズ | 内容 | 挙動の変化 |
|---|---|---|
| P1 | `aq::Application`(継承の基底)を **`AppHost`(土台・常駐)と `IAppModule`(差し替え単位)** に分ける | なし(リファクタのみ) |
| P2 | **起動引数** `LaunchOptions` とモジュールのレジストリ。WPF の `HwndHost` へ埋め込むための **子ウィンドウ起動** | 引数を付けたときだけ変わる |
| P3 | **LinkService**: TCP + JSON(改行区切り)の命令受付。ランタイムの問い合わせと Level 操作の最小命令セット | `-editor-port` を付けたときだけ有効 |

P4 以降(Edit/Play の実行時切り替えなど)は「8. 今後の課題」に残す。本書は P1〜P3 の一次資料。
[06_ゲームアプリケーションコア設計.md](06_ゲームアプリケーションコア設計.md) の「2. アプリケーション基底」は、
P1 完了時に本書へのリンクに置き換える(同じ内容を 2 か所に書かない)。

### 全体像(P3 完了時)

```
┌─ 外部エディタ(将来 WPF)───┐  TCP 127.0.0.1:<port>   ┌─ Runtime (Game.exe) ───────────────────────┐
│  HwndHost ← 子ウィンドウ ───┼──── 改行区切り JSON ────▶│ Engine                                    │
│  (P2 の -parent-hwnd)       │                         │  └ AppHost(常駐。Engine が直接所有)     │
└─────────────────────────────┘                         │      ├ LinkService(P3。通信スレッド+     │
                                                        │      │   メインスレッドでの命令実行)       │
                                                        │      ├ 描画 / ECS / Resource / Input / ImGui│
                                                        │      └ IAppModule(AquaDash 等。P1)       │
                                                        └───────────────────────────────────────────┘
```

## 1. 現状(対象コミット時点)

- `aq::Application`([Core/Application.h](../aqEngine/Core/Application.h))は、エンジンの土台と
  ゲームのフックを兼ねている。土台とは、RenderThread / ResourceManager / ECS / Input / UIContext /
  ImGui / DebugUI パネルの初期化と終了のこと。ゲームは継承して `OnInitialize` などを override する。
- ゲーム側([Game/Application/Application.h](../Game/Application/Application.h))が基底から使っているもの:
  `renderer_` / `renderThread_`(protected メンバ)、`BuildStandardPipeline` / `SetRenderPipeline`、
  `WaitForRenderIdle`(`AquaDashStates.cpp` から `app::Application::Get()` 経由)。
  Sample は `SetupStandardRenderers()` だけを使う。
- アプリの生成は、エントリ 7 か所で `Engine::CreateApplication<T>()` を呼んでいる
  (Game: Win32/UWP/Android/Mac/iOS、Sample: Win32/Mac)。
- 起動引数は、どのエントリでも読んでいない(`lpCmdLine` / `argv` は捨てている)。
- `PlatformWin32` はトップレベルウィンドウ固定で、`WM_SIZE` を扱っていない(リサイズ非対応)。
- DirectInput は `SetCooperativeLevel(hwnd, DISCL_FOREGROUND)` を使う。子ウィンドウの HWND は
  受け付けないので、埋め込み時は別の手当てが要る(P2)。
- ソケット関連のコードはリポジトリに存在しない。PCH(`aq.h`)は `WIN32_LEAN_AND_MEAN` なしで
  `windows.h` を読むので、`winsock.h`(v1)が先に入る。

## 2. P1: AppHost / IAppModule 分割

### 2.1 方針

- **継承から所有へ。** 土台は `aq::AppHost`(`final`)1 つに固定し、ゲームは `aq::IAppModule` を実装して
  AppHost に所有させる。
- **フックの名前・順序・回数は今と同じにする。** P1 は純粋なリファクタで、絵も起動ログの順序も変わらない。
  実行時の差し替え(Enter/Exit)は P4 の課題として、P1 では入れない。
- `aq::Application` という名前は廃止する(ゲーム側の `app::Application` と紛らわしいため)。
  ゲーム側のクラス名は `app::Application` のまま残す。フォルダを丸ごと差し替える方針なので、
  1 ゲームにつき 1 モジュールという意味で自然な名前であり、呼び出し側の変更量も最小になる。

### 2.2 ファイル別責務

| `aqEngine/Core/IAppModule.h` | 新規 | 差し替え単位のインターフェース(2.3) |
| `aqEngine/Core/AppHost.h/.cpp` | 改名(`git mv` Application.h/.cpp) | 旧 `aq::Application` の土台部分すべて。フックの呼び出し先を `module_->` に替える。`IApplication` を実装 |

### 2.3 インターフェース

```cpp
namespace aq
{
	class AppHost;

	/**
	 * AppHost に載せて動かす差し替え単位(ゲーム本体・将来のエディタ用モードなど)。
	 * フックの呼ばれる位置は旧 aq::Application の On* と同じ。
	 */
	class IAppModule
	{
	public:
		virtual ~IAppModule() = default;

		/** ログやレジストリで使う名前(起動引数 -app= と照合する) */
		virtual const char* GetName() const = 0;

		/** エンジンサブシステム初期化後に 1 回 */
		virtual bool OnInitialize(AppHost& host) { return true; }
		/** エンジンサブシステム終了前に 1 回 */
		virtual void OnFinalize() {}
		/** エンジン標準 System の登録後、FinalizeRegistration 前に 1 回 */
		virtual void OnRegister() {}
		/** Input/ECS/Level/Resource 更新後、UI 更新前に毎フレーム */
		virtual void OnUpdate() {}
		/** メインパス Submit 前に毎フレーム */
		virtual void OnPreRender() {}
#ifdef AQ_IMGUI
		virtual void OnImGuiRender() {}
#endif
#ifdef AQ_DEBUG_IMGUI
		virtual void OnDebugRenderMenu() {}
		virtual void OnDebugRender() {}
#endif
	};
}
```

`AppHost` がモジュールへ公開する操作(旧 protected を public にする):

| メンバ | 備考 |
|---|---|
| `static AppHost& Get()` / `static bool IsAvailable()` | 旧 `app::Application::Get()` 経由の土台アクセスを置き換える |
| `rendering::Renderer& GetRenderer()` | 旧 `renderer_` |
| `rendering::RenderThread& GetRenderThread()` | 旧 `renderThread_`(オフスクリーン Submit 用) |
| `SetupStandardRenderers` / `BuildStandardPipeline` / `SetRenderPipeline` | 中身は変えない |
| `SetSplitViews` / `ClearSplitViews` / `WaitForRenderIdle` | 同上 |
| `IAppModule& GetModule()` | 現在のモジュール |

`RendererPreset` の `using` は `AppHost.h` へ移す(ゲームは `aq::RendererPreset` と書いたまま通る)。

## 3. P2: 起動引数・モジュールレジストリ・子ウィンドウ起動

### 3.1 起動引数

| 引数 | 既定 | 意味 |
|---|---|---|
| `-app=<名前>` | 登録順の先頭 | 起動するモジュールを `IAppModule::GetName()` で指定する。**見つからなければ初期化失敗**(エディタからの起動ミスを黙って別アプリで動かさないため) |
| `-mode=play\|edit` | `play` | P2 では値を受け取って保持するだけ。`edit` は「未実装のため play で起動」とログを出す(P4) |
| `-editor-port=<1-65535>` | 0(無効) | 0 以外なら P3 の LinkService をこのポートで待ち受ける |
| `-parent-hwnd=<10進 or 0x16進>` | 0(無効) | Win32 のみ。指定したウィンドウの子として作り、エディタに埋め込む |

- 形式は `-key=value` とする(`--key=value` も同じ扱い)。値の中の空白は `"` で囲む。
- 知らないキーや値の誤りはログに出して無視する(`-app` の不一致だけは失敗扱い)。
- 引数を渡せるのは Win32(`lpCmdLine`)と Mac(`argv`)。UWP / Android / iOS は既定値で動く。

### 3.3 埋め込み時の入力

**協調用の HWND と座標用の HWND を分ける。**

- DirectInput は子ウィンドウを協調ウィンドウとして受け付けず、`InputManager::Setup()` が失敗する。
  このままだと初期化全体が落ちる。そこで埋め込み時は `PlatformWin32` が **非表示のトップレベルウィンドウ**
  (入力の協調用。1x1、`WS_POPUP`、表示しない)を別に作り、DirectInput には `DISCL_BACKGROUND` で渡す。
- ただし、今の `DirectInputMouseBackend` は初期化で受け取った HWND をカーソル座標の `ScreenToClient` にも
  使っている。協調用の HWND を渡すだけだと、ゲーム内 UI の当たり判定が描画位置からずれる。そこで
  バックエンドへは次の 2 つを別々に渡す。

```cpp
struct InputWindowDesc
{
	aq::graphics::NativeWindowHandle clientWindow;       // 描画先。座標変換の基準
	aq::graphics::NativeWindowHandle cooperativeWindow;  // DirectInput の協調レベル設定先
	bool                             background = false; // true なら DISCL_BACKGROUND
};
```

  埋め込みでないときは、両方ともメインウィンドウで `background = false`(従来と同じ動作)。

**フォーカスの判定は、ゲームの子ウィンドウがキーボードフォーカスを持っているかで行う。**

- 前面ウィンドウ(`GetForegroundWindow`)とキーボードフォーカスは別物。ルートが前面かどうかで判定すると、
  エディタのテキスト欄で名前や数値を打っている間もゲームが動いてしまう。
- 判定: 前面ウィンドウのスレッドについて `GetGUIThreadInfo` を取り、`hwndFocus` がゲームの HWND かその子孫
  (`IsChild`)なら「フォーカスあり」とする。プロセスを跨ぐ親子ウィンドウは入力キューが結合されるので、
  WPF 側のスレッドの情報としてゲームの子ウィンドウが見える。
- 子ウィンドウはクリックしても自動ではフォーカスを取らない。埋め込み時は `WM_LBUTTONDOWN` / `WM_RBUTTONDOWN` /
  `WM_MBUTTONDOWN` で `SetFocus(hWnd_)` を呼ぶ。

**フォーカスが無いときの入力停止は、ImGui から独立させ、パッドも対象にする。**

- 既存の `SuppressKeyboard/Mouse` は `AQ_IMGUI` と `imguiReady_` の内側で呼ばれているうえ、パッドには効かない。
  そこに条件を足すだけでは、ImGui が無効な構成で止まらず、パッドでもゲームが動いてしまう。
- そこで `InputManager::SetFocusBlocked(bool)` を新しく設ける。これが立っているフレームの
  `InputManager::Update()` は、キーボード・マウス・全パッドについて、バックエンドの取得結果を
  **中立値(全ボタン離し・軸 0・マウス移動 0)に置き換えてから** 各デバイスの Update に流す。
  - 押しっぱなしのままフォーカスを失ったボタンにも、Released の立ち下がりが 1 回出る(押されたまま固まらない)。
  - ActionMap も含め、デバイスを読む経路はすべてこれで止まる。
  - **パッドの接続状態(`connected`)は、バックエンドから取った実際の値を保持する。** 中立化で書き換えるのは
    ボタンと軸だけにする。今の `Pad::Update()` は `connected == false` のとき前フレームの状態(`old_`)まで消すので、
    状態の構造体を丸ごとゼロにすると「未接続」扱いになり、約束した Released の立ち下がりが出ない。
  - 置き換えの具体的な挿入点(Pad / KeyBoard / Mouse の Update の中か、バックエンドの Poll の直後か)は、
    実装時にクラス構造を読んで決める(TODO)。
- **ブロック中は、パッドの出力を常にゼロにする。** 開始時に 1 回止めるだけでは足りない。フォーカスが外れても
  ゲーム処理は続くので、コインの取得などで `Pad::Rumble()` が呼ばれ、次の `Pad::Update()` の `ApplyOutput` から
  新しい振動が出てしまう。
  - ブロック中の `ApplyOutput` は、振動の左右とトリガーエフェクトの強度を 0 として送る。送った値は既存の
    `applied*` にも記録する。
  - **振動(`Rumble`。一過性の要求)は、ブロック中に要求されたものを一切再生しない。** フォーカスが戻った瞬間に
    古い振動が鳴り出すのを防ぐため。
    - **破棄とは、保留中の振動状態 3 つ(左右の強度 `rumbleLeft_` / `rumbleRight_` と残り時間 `rumbleRemainSec_`)を
      すべて 0 にすることを指す。** 今の `ApplyOutput()` は、残り時間が 0 でも保持している左右の強度を出力する
      (`durationSec = 0` は「止めるまで鳴り続ける」扱い)。残り時間だけを 0 にしても振動は止まらない。
    - **受付時に捨てる。** InputManager がブロック状態を `std::atomic<bool>` で持ち、`Pad::Rumble()` は呼ばれた時点で
      ブロック中なら何もしない。`Rumble` はワーカースレッドから呼ばれるので atomic で読む。
      旧 API の `Pad::Vibrate()` / `InputManager::Vibrate()` はバックエンドを直接叩くので、同じくブロック中は何もしない。
    - **ブロックに入るときと、ブロックが明けるときの両方で、保留中の振動を破棄する。**
      フレームの順序は「AppHost が `SetFocusBlocked` → `InputManager::Update()`(`Pad::Update` → `ApplyOutput`)→
      ゲーム処理(ここで `Rumble` が呼ばれる)」。ブロック最後のフレームのゲーム処理で出た要求は、受付時の判定で
      捨てられる。明ける時点での破棄は、判定と状態変更がすれ違った要求を拾うための保険である。
      `SetFocusBlocked` はメインスレッドがフレームの境目(ワーカーが動いていない時点)で呼ぶので、明ける時点で破棄しても、
      ブロック解除後の正規の要求を消すことはない。
  - **トリガーエフェクト(継続する設定)**: ブロック中もゲームが設定した値は保持し、出力だけを 0 にする。
    復帰したフレームに、保持していた値との差分として既存の差分送信で自然に送り直される。
- ImGui の `SuppressKeyboard/Mouse` はこれまでどおり残す(「ImGui が使用中」と「フォーカスなし」は別の理由)。
- `SetFocusBlocked` を立てるのは埋め込み時だけ。通常起動の挙動(パッドはフォーカス外でも読める等)は変えない。
- ImGui はウィンドウメッセージで入力を受けるため、子ウィンドウでもそのまま動く想定。
- **リサイズ追従は P2 の範囲外**。現状の Win32 に `WM_SIZE` 処理が無いため、埋め込み時の寸法は起動時の
  親の大きさで固定する(エディタ側で固定サイズにしておく)。

## 4. P3: LinkService(TCP + JSON)

### 4.1 プロトコル(バージョン 1)

- **トランスポート**: TCP。`127.0.0.1` にだけ bind する(外部ネットワークには公開しない)。同時に接続できるクライアントは 1 つ。
  2 つ目の接続は `error` イベントを 1 行送ってから切断する。
- **フレーミング**: **改行区切り JSON**(UTF-8。1 メッセージ = 1 行、終端 `\n`)。
  JSON の文字列中の改行はエスケープされるので、行を区切っても衝突しない。
  C# 側は `StreamReader.ReadLine()` だけで読める。1 行の上限は 16 MiB で、超えたら切断する。
- **メッセージ種別**:

```jsonc
// エディタ → ランタイム(要求)
{"type":"request","id":12,"cmd":"level.load","params":{"path":"Assets/Levels/Stage1.level.json"}}
// ランタイム → エディタ(応答。id は要求と同じ)
{"type":"response","id":12,"ok":true,"result":{"levelId":3}}
{"type":"response","id":12,"ok":false,"error":{"code":"not_found","message":"..."}}
// ランタイム → エディタ(通知。id なし)
{"type":"event","event":"hello","data":{"protocol":1,"app":"AquaDash","pid":1234,"connectionId":7}}
```

- **エラーコード**: `bad_request`(JSON として壊れている、必須キーが無い)、`unknown_command`、
  `invalid_params`、`not_found`、`failed`(ハンドラ内の失敗)。
  壊れた行を受けても接続は切らない(`id` が読めなければ `id: null` で返す)。

### 4.2 P3 の命令セット

| cmd | params | result | 備考 |
|---|---|---|---|
| `ping` | なし | `{"time": 総経過秒}` | 疎通と往復遅延の確認 |
| `runtime.info` | なし | `{"protocol","app","mode","graphicsApi","renderWidth","renderHeight","fps","pid"}` | |
| `runtime.commands` | なし | `{"commands":["ping",...]}` | 登録済みの命令一覧(エディタ側のデバッグ用) |
| `level.load` | `{"path"}` | `{"levelId"}` | `LevelManager::Load`(同期)。失敗時は `not_found` / `failed` |
| `level.reloadAll` | なし | `{}` | `LevelManager::ReloadAll` |

- 接続直後に、ランタイムから `hello` イベントを送る。
- モジュールは `OnInitialize` で `LinkService::Get().RegisterCommand(...)` を呼べば、ゲーム固有の命令を追加できる
  (`OnFinalize` で Unregister する)。P3 の AquaDash は何も追加しない。

### 4.3 スレッド構成

```
通信スレッド(std::thread。1 本)                    メインスレッド(AppHost::Update 内)
  select(listen/client, 50ms) ループ                  LinkService::Tick()
   ├ accept → 接続世代 ID を採番 → inbox に Connected   ├ 処理予算の範囲で inbox から取り出す(mutex)
   ├ recv → 行に分割 → inbox に Line(世代 ID 付き)     ├ Connected → hello を outbox へ(Connected の世代 ID 宛て)
   │   (inbox が上限なら受信を止める)                 ├ Line → 実行直前に世代を確認 → 実行 → 応答を outbox へ
   ├ 送信バッファを非ブロッキングで送る                 └ Disconnected → ログ
   ├ 切断 → 現在の世代を 0 にしてから inbox に Disconnected
   └ stop フラグで終了
```

- **命令はメインスレッドでだけ実行する。** 実行位置は `AppHost::Update` の `ResourceManager::Update()` の後、
  `module_->OnUpdate()` の前。ECS の反復中ではなく、Level の即時生成も安全な「安全点」。
  ハンドラに ECS / Level / Resource を触らせても、スレッド境界規約を破らない。
- 通信スレッドは JSON を解釈しない(バイト列と行の分割だけ)。

#### キューの上限と処理予算

送信バッファにだけ上限を付けても、通信全体のメモリ増加は防げない。大量の要求を受けると、送信バッファへ移す前に
inbox と outbox が膨らむからである。また、1 フレームに処理する数に制限が無いと、大量の `ping` でフレームが止まる。
そこで、すべての段に上限を設ける。

| 段 | 上限 | 超えたとき |
|---|---|---|
| 1 行 | 16 MiB | 切断する(4.1) |
| inbox(受信済み・未処理) | 1024 件 **または** 合計 32 MiB | **受付停止**。通信スレッドは select の受信側から接続ソケットを外し、`recv` をやめる。TCP のフロー制御によって、クライアント側の送信が詰まる。inbox が上限の半分まで減ったら受信を再開する。Connected / Disconnected の制御要素は数バイトなので上限に数えず、必ず積む |
| outbox + 送信バッファ(接続ごと・未送信) | 合計 64 MiB | **切断**。応答を読まないクライアントとみなす。メインスレッドは積む操作で待たされない。超えた場合は、その要素を捨ててから切断を要求するフラグを立てる |
| Tick の処理予算(1 フレーム) | 256 行 **または** 4 ms の早い方 | 残りは inbox に置いたまま次のフレームへ回す。時間の確認は 1 命令ごとに行う。そのため、1 つのハンドラが重い場合(同期の `level.load` など)は 4 ms を超えうる。命令の中断はしない |

- 処理予算で inbox が捌ききれない間は、inbox の上限に達して受付が止まる。メモリにもフレームにも上限がある状態になる。

#### 接続世代 ID(前の接続の応答を次の接続へ届けない)

キューの中身が文字列だけだと、どの接続宛てかを区別できない。そのため、A の要求をメインスレッドが処理する前に
A が切断して B が接続すると、A 宛ての応答が B に届いてしまう。要求の `id` は接続ごとに振られるので、
A と B で重複しうる。これを防ぐため、次の契約にする。

- 通信スレッドは accept のたびに **接続世代 ID**(`uint64_t`、1 から単調増加、0 は「接続なし」)を採番する。
  現在の世代は `std::atomic<uint64_t>` で公開する。切断を検出したら、**まず現在の世代を 0 にしてから**
  inbox に Disconnected を積む。
- inbox の要素は `{ connectionId, kind(Connected / Line / Disconnected), text }`、outbox の要素は
  `{ connectionId, text }` とする。
- **outbox の要素は、必ずどの世代宛てかを明示して積む。** 「その時点の現在の世代」宛てには積まない。
  - 応答: 要求の Line に付いていた世代宛て。
  - `hello`: **それを生んだ Connected に記録された世代宛て。** A の Connected を処理する前に B が再接続していても、
    A 由来の `hello` は A 宛てになって捨てられ、B が `hello` を二重に受け取ることはない。
  - P3 には、特定の接続に由来しない一斉通知は無い。将来追加するときは、積む時点の現在の世代を読んで、その値を明示して積む。
- 通信スレッドは、現在の世代と一致しない outbox の要素を送らずに捨てる。
- **実行開始前に切断を検出済みの要求は、破棄する。実行を開始した要求は取り消さない。**
  - Tick は各 Line を実行する **直前** に、`Line の世代 == 現在の世代(atomic)` を確かめる。一致しなければ実行せずに捨てる
    (捨てた件数はログに出す)。応答を受け取れない相手の編集を反映しないため。
  - 確認の直後に切断が起きた場合や、切断の検出より実行が先になった場合は、その要求は実行される(応答は通信スレッドが捨てる)。
    これは仕様である。つまり「送った直後に切断すれば実行されない」ことは保証しない。エディタ側は、実行の有無を
    知りたい要求については、応答を待ってから切断する。
- 要求の `id` が一意なのは、同じ接続の中だけ。

#### 評価用の同期点(debug 命令)

固定時間の待機では、テストの順序を確定できない。送った直後に切断すると、待機命令そのものが実行前に破棄されうる。
また、待った時間が切断検出の完了を保証しない。そこで、**「ハンドラが実行を開始した」ことと「通信スレッドが切断・接続を
検出した」ことを、それぞれ観測できる同期点** を用意する。いずれも `debug.` の名前空間で、LinkService が有効なときだけ存在する。

- `hello` の data に、その接続の世代 ID `connectionId` を含める(クライアントが自分の世代と次の世代を知るため)。
- 通信スレッドは、現在の世代(atomic)に加えて **最後に採番した世代**(atomic、減らない)も公開する。

| cmd | params | 動作 | result |
|---|---|---|---|
| `debug.holdUntilDisconnected` | `{"timeoutMs"}`(最大 5000) | 開始時に **`debug.holdStarted` イベント**(要求の世代宛て)を積む。その後、メインスレッドを止めたまま、現在の世代が要求の世代と一致しなくなる(= 切断を検出した)まで 1 ms 間隔で待つ | `{"released": bool}` |
| `debug.holdUntilGeneration` | `{"generation", "timeoutMs"}` | 開始時に `debug.holdStarted` を積む。その後、最後に採番した世代が `generation` 以上になる(= その接続を accept 済み)まで待つ | `{"released": bool}` |
| `debug.counter` | `{"op":"inc"\|"get"}` | 実行されたかどうかを、別の接続から観測するためのカウンタ | `{"value"}` |
| `debug.stats` | なし | 通信の統計 | `{"executed","discardedBeforeExec","droppedStaleOutbox","holdTimeouts"}` |

- 待っている間もメインスレッドは止まっているが、通信スレッドは独立して動くので、`holdStarted` は送信され、切断や接続の検出も進む。
- タイムアウトした場合は `released: false` を返し、`holdTimeouts` を 1 増やす。テストは、hold が `released: true` で終わったことを
  `debug.stats` で確かめる。hold の応答自体は切断済みの世代宛てなので届かないため。**タイムアウトしたテストは失敗扱い**
  (狙った経路を通らずに成功することを防ぐ)。
- `executed` と `discardedBeforeExec` はメインスレッドが数える。`droppedStaleOutbox` は通信スレッドが atomic で数える。
- hold 系の命令は、処理予算(4 ms)を意図的に無視してメインスレッドを止める。評価専用なので、エディタから呼んではいけない。

#### 非ブロッキング I/O と終了

stop フラグを立てて join するだけでは、終了時のハングを防げない。クライアントが受信を止めていると、
ブロッキングの `send` が戻らず、通信スレッドが stop フラグを確認できないまま join が返らなくなる。
select の 50ms は待ち時間の上限にすぎず、`send` のブロックは防げない。そこで次のようにする。

- 待ち受けソケットと接続ソケットを、どちらも `ioctlsocket(FIONBIO)` で **非ブロッキング** にする。
  accept したソケットにも明示的に設定する。
- select には、受信側として待ち受けソケットと接続ソケットを入れる。送信側は、未送信データがあるときだけ接続ソケットを入れる。
- **部分送信**: `send` が要求より少なく書いた分、または `WSAEWOULDBLOCK` で書けなかった分は、接続ごとの
  送信バッファ(`std::string` + 送信済みオフセット)に残し、次に書き込み可能になったときに続きを送る。
- 送信と受信の上限は「キューの上限と処理予算」の表のとおり(outbox と送信バッファを合わせて 64 MiB を超えたら切断、inbox が上限に達したら受付停止)。
- 受信は `WSAEWOULDBLOCK` なら何もしない。0(相手の切断)や、それ以外のエラーなら切断として扱う。
- **終了手順**: stop フラグを立てる → 通信スレッドは遅くとも 50ms 後の select 復帰で気付く(ブロックする呼び出しが無いので必ず戻る)
  → **未送信データは破棄して** `closesocket` → スレッド終了 → join → `WSACleanup`。
  これを AppHost の `Finalize` 冒頭(モジュールの `OnFinalize` の後)で行う。
- メインスレッド側が行うのは mutex 付きのキュー操作だけで、ソケットに触れないので、フレームが止まることもない。

### 4.4 ソケット実装

- P3 は **Win32 のみ**(`AQ_PLATFORM_WIN32`)。それ以外では `LinkService` はスタブになり、`-editor-port` を

  3. A が接続し(世代 c+1。メインが止まっているので Connected は未処理のまま)、すぐ切断する。
  4. B が接続する(世代 c+2)。ここで hold が解ける。

  確認すること: B が受け取る `hello` は 1 回だけで、その `connectionId` が c+2。B には A や C 宛ての応答が届かない。
  `debug.stats` の `droppedStaleOutbox` が増えている(A 宛ての `hello` と、C 宛ての hold 応答が捨てられた)。`holdTimeouts` が増えていない。(`link_client.py hello` で PASS)
- [x] 評価用クライアント(`link_client.py`)に、上の 2 つの手順を再現するモードがある
- [x] 接続したまま終了してもハングせず、終了コード 0 で終わる(通信スレッドの join)
- [x] **受信しないクライアント**: 接続して `ping` を大量に送り、一切読まないクライアントがいても、フレームが止まらない。そのまま終了してもハングせず、1 秒以内に終了コード 0 で終わる(154 ms で終了・`LinkService finalized` のログあり。この試験では取得方法の都合で終了コードは取れていない)
- [x] outbox と送信バッファの合計が上限を超えると、そのクライアントが切断されてログが出る(上限を一時的に 64 KiB にして確認。`send buffer limit exceeded` で切断。確認後に 64 MiB へ戻した)
- [x] **大量の要求**: `ping` を 10 万件、応答を読みながら一気に送っても、フレーム時間の増加が処理予算(約 4 ms)程度に収まる。inbox が上限に達すると受付が止まり、その後に再開する(ログで確認する)。ランタイムのメモリ使用量が上限の範囲内で頭打ちになる(10 万件すべて応答、1 フレームの処理は最大 62 件、受付停止→再開のログあり。フレーム時間は FPS 180→147 を見ただけで、プロファイラでの計測とメモリの推移は未確認)
- [x] `ping` を 100 回連続で送り、往復時間(フレーム律速で数十 ms 以内の想定)を記録する(平均 50.5 ms / 最大 51.2 ms。通信スレッドが select の 50 ms 周期でしか送らないのが支配的)
- [x] ゲームの走行中に命令を送っても、フレーム落ちやクラッシュが起きない(20 秒間に 359 件 + reloadAll 3 回。FPS 171〜180、クラッシュなし。途中で ReloadAll の GPU ハングを発見し 7f7e1b6 で修正)
- [x] D3D11 / D3D12 / Vulkan の 3 構成ビルドが通る(Sample も成功。警告は既存の 52 件)

#### P3 実装で分かったこと・設計に足したこと

- SimpleJson の `Stringify` はオブジェクトを常に改行入りで整形するため、1 行 1 メッセージに使えない。LinkService に 1 行専用の書き出しを持たせた。数値は double で保持され `AsDouble` が無いので、int32 を超える整数は正確に往復しない(接続世代 ID などは小さいので実害なし)。
- `level.load` は存在しないパスでエンジンのアサートに当たるので、先にファイルの有無を確かめて `not_found` を返す。中身が壊れたファイルは Debug ではアサートで止まる。
- `level.load` は同じ Level でも追加で読み込む(置き換えない)。
- `ws2_32.lib` は `#pragma comment(lib)` でリンクする(aq.cpp の dbghelp と同じ例外。理由は LinkSocket.cpp に記載)。
- 往復時間が select の周期(50 ms)に張り付く。応答を積んだ時点で通信スレッドを起こす仕組みは今後の課題。
- 評価中に、Level の `ReloadAll` が GPU 使用中のバッファを破棄して D3D12 で GPU がハングする既存の不具合を発見した(Level エディタの Reload Refs・自動リロードでも起きる)。`Engine::WaitForRenderIdle` を足し、Unload 後に描画完了を待って破棄を確定させる形で修正した(7f7e1b6)。

## 6. 採用しなかった案

| 案 | 採用しなかった理由 |
|---|---|
| 長さプレフィクス(4 バイト)のフレーミング | 大きなバイナリを送らない間は、改行区切りのほうが C# 側も手動デバッグ(telnet など)も簡単 |
| `WIN32_LEAN_AND_MEAN` を全体に入れて winsock2 を使う | 影響範囲が全 TU に及ぶ。IPv4 ループバックだけなら v1 API で足りる |
| 通信スレッドで命令を直接実行する | ECS / Level をメインスレッド外から触ることになり、規約に反する |
| P2 で埋め込みを共有テクスチャ(D3DImage)にする | DX11 / 12 / Vulkan で分岐が重い。子ウィンドウならプロセス分離の利点もある |
| フォーカスを「ルートウィンドウが前面か」で判定する | エディタのテキスト欄で入力している間もゲームが動く。前面とキーボードフォーカスは別物 |
| フォーカス外の入力停止を既存の `SuppressKeyboard/Mouse` で行う | ImGui 無効時に効かず、パッドも止まらない |
| 切断を検出済みの未実行命令も実行する | 結果を受け取れない相手の編集を反映することになる。エディタ側で状態がずれる |

## 7. 公開インターフェースの影響

**P3 後の整理(2026-10-02)**: P1 では `AppHost` が `IApplication` を実装していたが、実装が `AppHost` 1 つだけになり、
差し替えの役目は `IAppModule` が担うので、`IApplication` を削除して Engine が `AppHost*` を直接持つ形にした。
あわせてモジュールの名前を実態に合わせ、ゲームは `app::Application`(`Game/Application/Application.*`)→
`app::GameModule`(`GameModule.*`)、サンプルは `sample::Application` → `sample::SampleModule`(`SampleModule.*`)に改名した。
本書の P1〜P3 の節に出てくる旧名(`IApplication` / `app::Application`)は、実装当時の記録としてそのまま残す。


- ゲーム・サンプルのコードで変わるのは、エントリの 1 行、`app::Application` の基底クラス、`renderer_` などの参照先。
- `aq::RendererPreset` はそのまま使える。
