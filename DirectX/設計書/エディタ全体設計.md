## 1. 目的とスコープ

aqEngine に、Unity に近い操作感のエディタを追加する。現状はランタイム上に ImGui を重ねており、ゲーム画面が狭く見づらい。これを「エディタ用ビルド」と「ランタイム用ビルド」に分けて解決する。

### 作るもの

- エディタ用 exe(Editor)とランタイム用 exe(Game)の 2 系統のビルド
- ゲームビュー、ヒエラルキー、インスペクター、コンテンツブラウザ、コンソールのパネル(Docking / Multi-Viewport)
- 既存リフレクションの拡張(フィールド属性、文字列、フィールド単位の編集イベント)
- Level の編集・保存・読み込み(既存の `.level.json`)
- Play モード(再生、一時停止、停止)と Undo/Redo
- ゲーム内デバッグ UI は、従来どおりゲーム画面の中に表示する

### 初版では作らないもの

- アセットの GUID・.meta・マニフェスト(パス参照のまま進める。14 章に将来案として残す)
- エディタスクリプト(Python)。12 章に構想を残し、着手時に別の設計書に起こす
- Prefab 参照ノードの override 編集 UI(既存 override の**無変更保存**だけは保証する)
- プレハブのバリアント、スクリプトのホットリロード
- WPF 外部エディタ([アプリケーション構成とエディタ連携設計](アプリケーション構成とエディタ連携設計.md))との統合
- Xbox/UWP、Android、iOS でのエディタ動作(ランタイムのみ対象)
- 複数人での同時編集

### 一次資料の分担

同じ内容を 2 つの設計書に書かないため、次のように分担する。本書は「エディタとしての全体接続」と「エディタのために足す差分」だけを書く。

## 3. プロジェクト構成とビルド構成

### 3.1 方針

- **既存構成への追加にとどめる。** 既存の Debug / Release / Profile / DebugXbox / ReleaseXbox の意味と出力は変えない。
- エディタ構成は **Windows デスクトップ(x64)の VS ソリューションだけ**に足す。CMake(Mac)への追加は E10 で行う。
- 静的ライブラリ内の `#if` は、そのライブラリをビルドした構成で決まる。exe だけにマクロを付けても切り替わらないので、エディタ構成では aqEngine と GameLogic も別にビルドする。

### 3.2 プロジェクト

| プロジェクト | 種類 | 現状 | 変更 |
|---|---|---|---|
| imgui | 静的ライブラリ | 既存 | E1 で docking 版 + 公式バックエンドへ更新 |
| aqEngine | 静的ライブラリ | 既存 | エディタ構成を追加。エディタ支援コードを `aqEngine/Editor/` に置く |
| Bullet(3 プロジェクト) | 静的ライブラリ | 既存 | エディタ構成は Debug / Release の成果物を使う(`AQ_EDITOR` に依存しないため別ビルドしない) |
| **GameLogic** | 静的ライブラリ | **新規** | `Game/Application/` のうちエントリ以外を収める。デスクトップ VS 構成のみ |
| Game | exe | 既存 | エントリ(`Main.cpp`)だけを持ち、GameLogic をリンクする |
| GameUWP | exe | 既存 | 従来どおりゲームのソースを直接コンパイルする(エントリを props から自分の vcxproj へ移すだけ) |
| **Editor** | exe | **新規** | エディタのエントリ、パネル、コマンド、`EditorContext` |

`GameSources.props` は「ゲームロジックのソース一覧」に限定し、エントリ(`Main.cpp`、`UWPMain.cpp`)は各 exe の vcxproj へ移す。GameLogic.vcxproj と GameUWP.vcxproj が同じ props を読むので、ソースの追加は今までどおり 1 か所で済む。CMake(Mac / iOS / Android)は E10 まで現状のまま(`Application` 以下の再帰収集)。

### 3.3 依存のルール

- aqEngine と GameLogic は、Editor プロジェクトのヘッダーをインクルードしない。
- エンジン内部に触れるエディタ支援コード(GraphicsDevice への ImGui テクスチャ登録、エディタ用フック)は `aqEngine/Editor/` に置き、ファイル全体を `#if AQ_EDITOR` で囲む。
- 編集モデル(`LevelEditModel`、7 章)は既存の Level エディタも使うので、`aqEngine/Level/` に置き `AQ_DEBUG_IMGUI` で囲む。
- パネル、コマンド、Undo/Redo など、エンジンの公開 API で書けるものは Editor プロジェクトに置く。
- 両 exe は既存の `app::RegisterAppModules()` を呼んで GameModule を登録する。これがリンクの入口になり、GameLogic.lib の .obj が落ちない。

### 3.4 ビルド構成とマクロ

| 構成 | AQ_EDITOR | AQ_IMGUI | AQ_DEBUG_IMGUI | 最適化 | ビルド対象の exe |
|---|---|---|---|---|---|
| Debug(既存) | 0 | 定義 | 定義 | なし | Game |
| Release(既存) | 0 | 定義 | 未定義 | あり | Game |
| Profile / DebugXbox / ReleaseXbox(既存) | 0 | 既存のまま | 既存のまま | 既存のまま | 既存のまま |

- **`AQ_EDITOR=1` のときは `AQ_DEBUG_IMGUI` も必ず定義する。** 既存のインスペクター、Prefab / Level エディタ、`EntityDebugTag` が `AQ_DEBUG_IMGUI` でコンパイルされるため。逆(`AQ_DEBUG_IMGUI` だけ)は従来のランタイムのデバッグ UI。

- `#if AQ_EDITOR` と書く(値は 0 か 1)。既存の `AQ_IMGUI` などは `#ifdef` のまま変えない。
- 中間ファイルと出力は構成ごとに分ける(`x64\Editor_Debug\` など)。混ざると、エディタ用の lib をランタイムの exe がリンクしてしまう。

### 3.5 ifdef の運用

| 書いてよい場所 | 例 | 書き方 |
|---|---|---|
| エディタ支援コード | ImGui テクスチャ登録、エディタ用フック | `aqEngine/Editor/` のファイル全体を囲む |
| エンジンの入口 | AppHost のフック呼び出し、エディタ支援の初期化と終了 | 呼び出し数か所のみ |

- 既存のコンポーネントやクラスのメンバ変数を ifdef で増減させない。構成間でレイアウトが変わり、保存データの互換も崩れる。
- 関数の途中に細かい ifdef を散らさない。関数ごと分けて、ランタイム側は空実装にする。
- グローバル変数のコンストラクタによる自動登録は使わない(静的ライブラリでは参照されない .obj が落ちる)。

### 4.1 方針

- 公式バックエンドが in-flight のフレーム数を扱えることを確認し、エンジンの `FRAMES_IN_FLIGHT` と合わせる(TODO)。
- ランタイム(`AQ_EDITOR=0`)の見た目と操作は E1 の前後で変えない。

### 4.4 E1a の詳細(2026-11-16 追記)

着手前の調査で分かったことと、それを受けた決定。

#### 現状(調査結果)

| 項目 | 現状 |
|---|---|
| 同梱の公式バックエンド | `imgui_impl_win32`(コアと同世代)と `imgui_impl_dx11` を使用。`imgui_impl_dx12.cpp` は同梱されているがコアより新しく、`imgui.vcxproj` で `ExcludedFromBuild`。vulkan / metal / osx / android は同梱なし。CMake の imgui ターゲットは Win32 のときだけ win32 / dx11 を足し、Mac / iOS / Android はコア 4 ファイルだけ |
| 自前バックエンド | D3D12(`D3D12ImGui.cpp`。専用の shader-visible ヒープ 64 個、HLSL を実行時コンパイル)、Vulkan(`VulkanImGui.cpp`。`ImGuiVK.fx`、dynamic rendering、エンジンのフレーム別 DescriptorPool を共用。**Android も同じコード**)、Metal(`MetalImGui.mm`。`ImGuiVK.fx` から作った MSL)。どれも `GetTexDataAsRGBA32` と `SetTexID` で固定アトラスを作る旧式 |
| 描画位置 | D3D11 / D3D12 は描画コマンド列の末尾で、そのときの RT(`displayRT`)に描き、その後 `CopyToBackBuffer`。Vulkan / Metal は描画データを保存し、`CopyToBackBuffer` の後でスワップチェーン / drawable に直接描く |
| テクスチャ ID | デバッグパネル 11 か所が `ImGui::Image((ImTextureID)xxx->GetNativeHandle(), ...)` でエンジンのハンドルを渡す。D3D11 は `ID3D11ShaderResourceView*`、D3D12 は `D3D12SRV*`(自前バックエンドが描画時に遷移とディスクリプタのコピーをする)、Vulkan は `VkImageView` として解釈しているが、実際に渡っているのは `VulkanSRV*` / `ColorSRV*` で食い違っている疑いがある |
| 新コア(1.93.0)の互換 | `GetTexDataAsRGBA32`、`SetTexID`、`ImDrawData::CmdLists`、6 引数の旧 `Image` は残っている。`RendererHasTextures` を立てない旧式バックエンドも動く。`io.FontGlobalScale` は `style.FontScaleMain` へ移った(旧名は互換で残る) |
| Vulkan の関数 | `vulkan-1.lib` を静的リンク(関数ポインタの読み込みは不要) |

#### 決定

- **版**: `v1.93.0-docking`(2026-11-16 時点の docking ブランチ最新タグ)。`ThirdParty/imgui/` のコアと、使うバックエンドを差し替える。
- **E1a で公式に置き換えるもの**: win32(版を上げる)、dx11(版を上げる)、dx12(自前を削除)、vulkan(自前を削除。Android も同じコードなので公式に切り替わる)。
- **E1a で置き換えないもの**: Metal と MacImGui、Android / iOS の入力。新コアでも旧式のまま動くので、E1b で公式に置き換える。`ImGuiVK.fx` と `shader_entries.txt` の登録は Metal が使うので E1b まで残す。
- **描画位置は E1a では変えない。** D3D11 / D3D12 は `displayRT` へ、Vulkan はスワップチェーンへ、今と同じタイミングで描く。2 つの描画先への分離は E2a で行う。
- **テクスチャ ID は描画時に変換する。** パネルの `ImGui::Image` の呼び方は変えない。各バックエンドの `ImGuiRender`(レンダースレッド)で、公式の `RenderDrawData` を呼ぶ前に描画データを走査し、`TexRef._TexData == nullptr`(= アプリが渡したテクスチャ。フォントアトラスは `_TexData` を持つ)の描画コマンドの `_TexID` を、エンジンのハンドルからバックエンドの ID に書き換える。

| API | エンジンのハンドル | 変換 |
|---|---|---|
| D3D11 | `ID3D11ShaderResourceView*` | 不要(公式と同じ) |
| D3D12 | `D3D12SRV*` | SRV を `TransitionToSRV` し、ImGui 用ヒープのフレーム別の区画へ `CopyDescriptorsSimple` して、その GPU ハンドルを入れる(自前バックエンドの処理と同じ) |
| Vulkan | `VulkanSRV*` / `ColorSRV*`(`VkImageView`、`VkImage`、追跡中のレイアウトを持つ) | 画像を `SHADER_READ_ONLY_OPTIMAL` へ遷移して追跡中のレイアウトも更新し、`ImGui_ImplVulkan_AddTexture(view, SHADER_READ_ONLY_OPTIMAL)` の DescriptorSet をビュー単位でキャッシュして入れる。`AddTexture` は遷移をしないので、遷移は ImGui の `vkCmdBeginRendering` より前に行う(`CopyToBackBuffer` の遷移の後の状態を基準にする)。例: Hi-Z の出力は `GENERAL` のまま残っている。ビューの破棄時(RT の作り直しなど)にキャッシュから外して `RemoveTexture` する。渡されたハンドルの型を E1a で確かめ、食い違いがあれば直す |

  E2a の `GetImGuiTextureId` はこの変換を前提に、エンジンのハンドルをそのまま返す形にできる(5.4 の表は E2a で見直す)。
- **呼び方の例外(配列テクスチャ)**: 公式のシェーダは 2D テクスチャしか読めない。シャドウの深度マップ(`DeferredDebugPanel` が配列全体の SRV を渡している。D3D12 / Vulkan とも `TEXTURE2DARRAY`。D3D12 の既存のスライス用 SRV も配列型)は、E1a では**画像の表示をやめ、「シャドウ深度マップの画像表示は未対応」と解像度だけを出す**(全 API)。今の自前バックエンドでも 2D として読んでおり、正しく出ている保証がない。スライスを 2D のプレビュー RT に写して表示する方法は 15 章に残す。配列の SRV が `ImGui::Image` に渡された場合は、変換時に検出して描かずに警告ログを 1 回出す(D3D12 / Vulkan)。
- **D3D12 のヒープ**: ImGui 用の shader-visible ヒープを 256 個に広げる。前半をフォントアトラスなどバックエンドが確保するテクスチャ(`SrvDescriptorAllocFn` / `FreeFn` で空きリスト管理)、後半をフレーム別のユーザーテクスチャ区画(`D3D12_FRAME_COUNT` × 64)にする。`NumFramesInFlight = D3D12_FRAME_COUNT`。
  - **公式の `RenderDrawData` はヒープを設定しない**(設定するのは Multi-Viewport の別経路だけ)。`ImGuiRender` で、`RenderDrawData` の前に ImGui 用ヒープを `SetDescriptorHeaps` する。ImGui の後にエンジンが自前のヒープを使う描画を積む場合は張り直す(現状は ImGui の後は `CopyResource` だけ)。
  - ユーザー区画へのコピーは、そのフレームの区画を前回使った GPU 処理の完了を `BeginFrameIfNeeded` のフェンス待ちで保証した後に行う。
  - `RTVFormat` は `displayRT` のフォーマットを渡す。
- **Vulkan の初期化**: `UseDynamicRendering = true`、`PipelineInfoMain.PipelineRenderingCreateInfo` にスワップチェーンのフォーマット、`DescriptorPoolSize` を指定してバックエンド内部のプールを使う(エンジンのフレーム別プールは使わない)。`ImageCount` / `MinImageCount` は初期化時のスワップチェーンに合わせる。
  - **スワップチェーンの作り直し**: 寸法だけが変わる場合はバックエンドに何もしない(dynamic rendering なので描画先はその都度渡す)。フォーマットか画像数が変わる場合(Android のサーフェス再生成を含む)は、`SetMinImageCount` が非対応(assert)なので、GPU の完了を待ってからバックエンドを `Shutdown` → `Init` し直し、ユーザーテクスチャの DescriptorSet のキャッシュも捨てる。
- **フォント**: 読み込み方(`AddFontFromFileTTF` と独自のグリフ範囲)は変えない。D3D11 / D3D12 / Vulkan は公式バックエンドが `RendererHasTextures` を立てるので動的フォントになる。日本語グリフを足すかは E1a では決めない(15 章)。
- **スレッドの契約**: 公式バックエンドは描画中に `draw_data->Textures`(コンテキストが所有するフォントアトラスなど)の状態を書き換える。`ImGuiRenderCommand` は `ImDrawData*` しか持たないので、**ImGui 有効時はレンダーの直列実行を前提とする**。`AQ_RENDER_PIPELINED` と `AQ_IMGUI` が同時に定義されたらコンパイルエラーにする(`static_assert` か `#error`)。現状 PIPELINED は既定で無効なので挙動は変わらない。PIPELINED と ImGui を両立させる方法は 15 章に残す。
- **ビルド**: `imgui.vcxproj` に `imgui_impl_dx12.cpp` と `imgui_impl_vulkan.cpp` を足す(Vulkan の SDK のインクルードが要る)。CMake の imgui ターゲットにも、Windows の D3D12 構成で `imgui_impl_dx12.cpp`、Vulkan を使う構成(Windows の Vulkan、Android)で `imgui_impl_vulkan.cpp` を足す。CMake の Windows ビルド(D3D12 / Vulkan の Sample)はこの PC で確認する。**Android・Mac・iOS のビルド確認は Mac 機で作業するときに行う**(2026-11-16 ユーザー決定)。

#### E1a の結果(2026-11-17)

- **この PC に Vulkan SDK が無い**(`VULKAN_SDK` 環境変数が空)。公式 `imgui_impl_vulkan.cpp` は `#include <vulkan/vulkan.h>` を無条件に行う第三者コードでガードできないため、素のまま `imgui.vcxproj` に追加すると D3D11/D3D12 構成まで壊れる。**ユーザー決定**: `imgui.vcxproj` の `imgui_impl_vulkan.cpp` に `<ExcludedFromBuild Condition="'$(AqGraphicsApi)'!='Vulkan'">true</ExcludedFromBuild>` を付け、Vulkan 以外のビルドを守る。Vulkan 自体はこの PC では**実コンパイル未確認**(論理レビューのみ)。CMake(`ThirdParty/CMakeLists.txt`)側も同じ考え方で `AQ_GRAPHICS_API` 条件に合わせて `imgui_impl_dx12.cpp` / `imgui_impl_vulkan.cpp` を足す形にした。
- **ImGui 本体の更新**: `v1.93.0-docking`(GitHub の同タグ)を取得し、コア一式と win32/dx11/dx12/vulkan のバックエンドを `ThirdParty/imgui/` へ配置(既存ファイルの CRLF・BOM なしを保持)。既存の `imconfig.h` に独自定義は無く、素の upstream に差し替えるだけで済んだ。
- **D3D12ImGui.cpp/.h**: 自前の RootSignature・PSO・HLSL・VB/IB・フォントテクスチャ生成を全廃し、`ImGui_ImplDX12_Init/Shutdown/NewFrame/RenderDrawData` を呼ぶ接続層に書き換えた(480 行 → 251 行)。SRV ヒープは 256 個(バックエンド用 128 + フレーム別ユーザー区画 64×2)。`Render()` の冒頭で `TexRef._TexData==nullptr` のコマンドを `D3D12SRV*` として解釈し、このフレームの区画へ `CopyDescriptorsSimple` してからバックエンドの `RenderDrawData` を呼ぶ。`pcmd->GetTexID()` / クリップ矩形を潰すことで不正ハンドルの描画を止める仕組みを、ダウンロードした公式ソース(`imgui_impl_dx12.cpp` 432〜444 行目)と突き合わせて確認済み。

## 5. フレームの流れと ImGui の 2 コンテキスト

### 5.1 コンテキスト

| コンテキスト | 所有者 | 描画先 | Docking / Multi-Viewport | 入力 |
|---|---|---|---|---|
| ゲーム用 | AppHost(既存のもの) | ランタイム: バックバッファ(現行どおり)<br>エディタ: `displayRT` | 無効 | ランタイム: 現行どおり<br>エディタ: エディタが毎フレーム転送する |
| エディタ用 | Editor(AQ_EDITOR=1 のみ) | バックバッファと、外に出した各ウィンドウ | 有効 | プラットフォームバックエンド(win32)から |

- **コンテキストは常に明示的に切り替える。** `ImGui::SetCurrentContext()` を挟まずに `ImGui::GetIO()` 等を呼ぶ既存箇所(AppHost の入力抑制など)は、ゲーム用コンテキストを明示して呼ぶように直す。
- フォントアトラスは 2 つのコンテキストで共有する(`ImGui::CreateContext(sharedAtlas)`)。アトラスは AppHost が所有し、両コンテキストの破棄後に解放する。
- プラットフォームバックエンド(win32)はエディタ用コンテキストにだけ接続する。ゲーム用コンテキストには、エディタが `io.AddMousePosEvent` などで入力を転送する。座標はゲームビュー上の位置を `displayRT` の座標へ換算したもの(縮小表示の倍率を含む)。`io.DisplaySize` は `displayRT` のサイズにする。
- ゲームビューにフォーカスがない間は、既存の `InputManager::SetFocusBlocked()` でゲーム入力(キーボード・マウス・パッド)を止める。

### 5.2 エディタ用フック

ループは従来どおり `IPlatform::RunFrameLoop` → `AppHost::Update` のままにする。AppHost は Editor のヘッダーを知らないので、エンジン側にインターフェースを置き、Editor が実装して起動時に登録する(`AppModuleRegistry` と同じ考え方)。

実行モードの型は ECS とランタイムも使うので、常にコンパイルされる共通ヘッダーに置く。`IEditorLayer` だけをエディタ限定にする。

```cpp
// aqEngine/Core/RunMode.h(常にコンパイル)
namespace aq
{
	/** 実行モード。ランタイムは常に Play */
	enum class RunMode : uint8_t
	{
		Edit,
		Play,
		Pause,
	};

	/** System がどのモードで動くかの宣言(Play は常に動く) */
	enum class RunModeMask : uint8_t
	{
		PlayOnly	= 0,
		Edit		= 1 << 0,
		Pause		= 1 << 1,
	};
}
```

```cpp
// aqEngine/Editor/IEditorLayer.h(#if AQ_EDITOR)
namespace aq
{
	/** AppHost がフレームの決まった位置で呼ぶエディタ側の処理 */
	class IEditorLayer
	{
	public:
		virtual ~IEditorLayer() = default;

		/** フレーム先頭。前フレームに要求されたモード遷移を確定し、入力の行き先を決める */
		virtual void OnBeginFrame() = 0;
		/** このフレームのモード。OnBeginFrame で確定し、フレームの途中では変えない */
		virtual RunMode GetMode() const = 0;
		/** エディタ用コンテキストでパネルを構築し、発行されたコマンドを適用する */
		virtual void OnBuildUI() = 0;
		/** エディタ用コンテキストの描画データを確定する(ImGui::Render と UpdatePlatformWindows) */
		virtual void OnEndFrame() = 0;
	};
}
```

### 5.3 エディタビルドの 1 フレーム

**既存の `AppHost::Update` の順序は変えない。** フックを挟む位置と、モードによって飛ばす処理だけを決める。担当は「メイン」= メインスレッド、「レンダー」= RenderThread。エディタ構成は直列(`AQ_RENDER_PIPELINED` 無効)に固定するので、レンダーの実行中はメインが `FlushRender()` で止まっている。

| 順 | 担当 | 処理(既存は太字なし、追加は **太字**) | Edit | Play | Pause |
|---|---|---|---|---|---|
| 1 | メイン | **`OnBeginFrame`**: 前フレームに要求されたモード遷移を確定する(8.1)。ゲームビューのホバーとフォーカスから入力の行き先を決め、`SetFocusBlocked` を設定する | ○ | ○ | ○ |
| 2 | メイン | ImGui の入力抑制(ゲーム用コンテキストを明示)と `InputManager::Update` | ○ | ○ | ○ |

| 4 | メイン | `LevelManager::Tick`(ロードの進行と生成) | ○ | ○ | ○ |
| 5 | メイン | `ResourceManager::Update` | ○ | ○ | ○ |
| 6 | メイン | `LinkService::Tick`(有効時) | ○ | ○ | ○ |

| 8 | メイン | `module_->OnUpdate()` | × | ○ | × |

| 10 | メイン | `CameraManager::UpdateAll` | ○ | ○ | ○ |
| 11 | メイン | `Render()`: ゲーム用コンテキストの NewFrame とデバッグ UI の構築、描画コマンドの構築 | ○ | ○ | ○ |

### 5.4 描画抽象に足すもの

Editor プロジェクトは DX12 や Vulkan の型を扱わない。API ごとの差は GraphicsDevice の Bridge(`IGraphicsDeviceImpl`)に閉じ込める。具象クラス `Renderer` には置かない。

| 追加する API | 内容 |
|---|---|
| `ImTextureID GraphicsDevice::GetImGuiTextureId(RenderTargetHandle rt)` | RT を `ImGui::Image` に渡せる ID に変換する。DX11 は SRV、DX12 は ImGui 用ヒープ区画の GPU ハンドル、Vulkan は `ImGui_ImplVulkan_AddTexture` の DescriptorSet、Metal は `id<MTLTexture>`。未対応のバックエンドは無効 ID を返す |
| ImGui 描画先の指定 | ゲーム用の描画データを任意の RT(`displayRT`)へ描く経路と、エディタ用の描画データをバックバッファへ描く経路を分ける。現行の Vulkan / Metal は「描画データを 1 つ保存し、`CopyToBackBuffer` の末尾でスワップチェーンに描く」契約なので、2 つの描画先を表せる形に変える |

テクスチャ ID の寿命:

- ID は**毎フレーム取得し直す**。パネルがフレームをまたいで保持しない。
- RT の作り直し(E3b のリサイズ)で ID は無効になる。作り直しは完了待ちの中で行うので、使用中の ID が消えることはない。
- 登録の解除(Vulkan の DescriptorSet など)は RT の破棄と同じ箇所で行う。

### 5.5 ゲームビューのサイズ

- **E2 ではレンダー解像度を変えない。** `displayRT` はウィンドウのクライアントサイズに追従する既存の挙動のまま(D3D12 は固定寸法)。ゲームビューにはアスペクト比を保って縮小表示し、余白は黒にする。入力の座標換算(5.1)もこの倍率を使う。
- **E3b でゲームビューにレンダー解像度を追従させる。** 既存の `HandleRenderResize` は提示面(スワップチェーン)と RT を一緒に作り直すので、エディタでは「提示面はウィンドウに追従」「RT とパイプラインはゲームビューに追従」と分ける。D3D12 の `SupportsRenderResize` / `ResizeMainTargets` / `ReleaseOffscreenRenderTarget` の実装を E3b の前提作業にする。
- E3b では、ゲームビューのサイズ変更はドラッグ中は要求を上書きするだけにし、サイズが 2 フレーム続けて変わらなかったときに確定する。完了待ちを伴うリサイズを毎フレーム走らせないため。

### 5.6 注意点

- **エディタ構成は直列に固定する。** `ImGuiRenderCommand` は `ImDrawData*` しか持たないので、PIPELINED ではメインの次の `NewFrame` とレンダーの読み取りが重なりうる(コード構造からの推測、未再現)。エディタで PIPELINED を許すには、描画データをフレーム所有のコピーにする必要がある。解除条件として 15 章に残す。
- ゲームのカメラのアスペクト比は `displayRT` のサイズから計算されていることを E2b で確認する(TODO)。

#### 決定(Codex レビュー 3 回で計 5 点の重大な見落としを指摘され、実コードで確認して直した版)

1 回目: (1) `D3D12ImGui`(E1a)は匿名名前空間の static グローバルでヒープ・フォント変換状態を 1 組しか持たず、2 コンテキストを同時に扱えない。(2) バックバッファは `CopyToBackBuffer` の複写先専用で RTV を持たない。ほかに「`FrameContext` ではなく `FrameSlot`/`Submit()` の引数で運ぶ」「`AppHost` のメンバを ifdef で増減させない」「`GetImGuiTextureId` は既存の `GetRenderTargetSRVShared` 経由で足りる」。
2 回目: (3) 公式バックエンドはレンダー時に「現在の ImGui コンテキスト」の `BackendRendererUserData` を読むため、レンダースレッドでの明示的な `SetCurrentContext` が要る。(4) `CreateBackBuffers()` の時点では `rtvHeap_` が未初期化(`CreateRtvDsvHeaps()` より前に呼ばれる)。
3 回目: (5) **2 コンテキストで別々のヒープ(インスタンス)を使う設計は、共有フォントアトラスと両立しない**。共有アトラスの `ImTextureData` は単一の `TexID`/`BackendUserData` しか持たないため、先に生成した側のインスタンスの GPU ディスクリプタをもう一方がそのまま使ってしまい、`ResolveUserTextures()` は `_TexData != nullptr`(フォント等)を変換対象外にしているので別ヒープのハンドルのまま描画される。

この (5) を受けて、**ヒープ/バックエンドのインスタンスを 2 つに増やす設計(`D3D12ImGuiInstance` の新設)は撤回し、E1a の `D3D12ImGui`(単一の匿名名前空間 static)をそのまま使う**。

4 回目のレビューで、「`io.BackendRendererUserData` のポインタだけをもう一方のコンテキストへ共有する」という当初の直し方は不十分と判明した。公式の `ImGui_ImplDX12_Init()`(`imgui_impl_dx12.cpp:991-1023`)は、current なコンテキストの `io.BackendFlags |= ImGuiBackendFlags_RendererHasTextures` と、そのコンテキストの `ImGui::GetMainViewport()->RendererUserData` も合わせて設定する。これらはコンテキストごとの状態(メイン viewport は各コンテキストが個別に持つ)なので、ポインタ共有だけでは埋まらず、共有アトラスの整合性チェック(`imgui.cpp:9780-9798` の `UpdateTexturesNewFrame`。`atlas->RendererHasTextures == has_textures` を assert する)に落ちる。

**正しい直し方は、ヒープそのものは 1 つのままで、`ImGui_ImplDX12_Init()` 自体をコンテキストごとに正式に呼ぶこと。** `ImGui_ImplDX12_Init()` は呼ばれた時点の current context 専用の `ImGui_ImplDX12_Data`(PSO・ルートシグネチャ等も含めて)を新規に 1 つ作り、`bd->InitInfo = *init_info`(ディープコピー)で `SrvDescriptorHeap`/`SrvDescriptorAllocFn`/`FreeFn` の**値だけ**を引き継ぐ(`imgui_impl_dx12.cpp:999`)。ヒープの実体そのものは共有したまま、コンテキストごとに独立した正しい内部状態(`BackendFlags`、メイン viewport の `RendererUserData`、将来 Multi-Viewport を有効にしたときの `PlatformIO` コールバック)を公式コードに作らせられる。`ImGui_ImplDX12_Shutdown()` が解放するのは PSO・ルートシグネチャ・アップロードバッファ等(`bd` が所有するもの。`imgui_impl_dx12.cpp:935-949`)だけで、共有ヒープ(`pd3dSrvDescHeap` は参照を保持するだけ)には触らないことも確認済み。

- **`D3D12ImGui::InitEditor()`(新設)**: 既存の `Init()`(ヒープ作成・空きリスト初期化・ゲーム用コンテキストでの `ImGui_ImplDX12_Init()` 呼び出し。**変更なし**)がすでに実行済みであることを前提に、**ヒープは作り直さず**、`g_device`/`g_srvHeap`/`SrvDescriptorAlloc`/`SrvDescriptorFree` を指す**新しい** `ImGui_ImplDX12_InitInfo info2`(`Device`/`CommandQueue`/`NumFramesInFlight`/`RTVFormat`/`DSVFormat`/`SrvDescriptorHeap`/両コールバックは `Init()` と同じ値)を作り、エディタ用コンテキストが current の状態で `ImGui_ImplDX12_Init(&info2)` を呼ぶ。`ShutdownEditor()` はエディタ用コンテキストを current にして `ImGui_ImplDX12_Shutdown()` を呼ぶだけ(共有ヒープの解放は既存の `Shutdown()` が最後に 1 回だけ行う。呼び出し順は「`ShutdownEditor()` → `Shutdown()`」)。
- これは `GraphicsDevice::ImGuiInitEditor(ImGuiContext* gameCtx, ImGuiContext* editorCtx)`(新設。D3D12 以外は no-op)が `D3D12ImGui::InitEditor()` を呼ぶ形で実装し、同時に両方の `ImGuiContext*` を `D3D12GraphicsDeviceImpl` のメンバ(`gameImGuiCtx_`/`editorImGuiCtx_`)に控える(後述のレンダースレッドでの `SetCurrentContext` に使う)。`ResolveUserTextures`・`SrvDescriptorAlloc`/`Free` など `D3D12ImGui.cpp` の既存ロジックは変更しない。
- **レンダースレッドでの `SetCurrentContext` は、呼び出し側(`D3D12GraphicsDeviceImpl`)が行う。** 公式バックエンドはレンダー時に現在のコンテキストの `BackendRendererUserData` を読むため(Codex 2 回目の指摘):
  - `D3D12GraphicsDeviceImpl::ImGuiRender(ImDrawData* drawData)`(既存。ゲーム用コンテキストの描画データ)の先頭で `if (gameImGuiCtx_) ImGui::SetCurrentContext(gameImGuiCtx_);` を足す(ランタイムビルドは `gameImGuiCtx_` が未設定のままなので no-op、動作は変わらない)。
  - 新設の `RenderEditorOverlay(ImDrawData* editorDrawData)` の中で `if (editorImGuiCtx_) ImGui::SetCurrentContext(editorImGuiCtx_);` してから `D3D12ImGui::Render(editorDrawData, cmdList)`(既存の関数をそのまま呼ぶ)。
  - **これが安全な理由**: エディタ構成は 5.6 の決定で直列固定(`AQ_RENDER_PIPELINED` 無効)であり、メインスレッドは `RenderThread::Submit()` の後に `Engine::FlushRender()`(`Engine.cpp:678` 付近)→`AppHost` 経由の `WaitForCompletion()`(`AppHost.cpp:714` 付近)でレンダースレッドの完了を待ってから次フレームの UI 構築(= 次の `ImGui::SetCurrentContext` 呼び出し)に進む(Codex で確認済み)。したがってレンダースレッドが `GImGui`(単一のグローバル変数)に触れる区間とメインスレッドが触れる区間は重ならない。
  - **ユーザーテクスチャ用スロットの取り合いに注意する。** `ResolveUserTextures()` のスロット書き込みカーソル(`nextSlot`、現在は呼び出しごとにローカルで `slotBegin` へ戻る)は、1 実フレームに `ImGuiRender`(ゲーム用)と `RenderEditorOverlay`(エディタ用)の **2 回** 呼ばれるようになる。`CopyDescriptorsSimple` は CPU 側で即座にヒープを書き換えるため、同じ `slotBegin` から 2 回書き始めると、後から呼ばれた側が先に呼ばれた側のディスクリプタを GPU 実行前に上書きしてしまう(ゲーム側のデバッグパネルが `ImGui::Image` でエンジンのテクスチャを表示している状態で、エディタ側の `displayRT` 表示と同一フレームに重なると誤描画になりうる)。**このカーソルを「`ResolveUserTextures` 呼び出しごと」ではなく「実フレームごと」にリセットする**: `nextSlot` の初期値を保持する変数(フレームインデックスごとの配列)を `D3D12ImGui` 側に持たせ、リセットは(2 回呼ばれても 1 回しか走らない)`D3D12GraphicsDeviceImpl::BeginFrameIfNeeded()` の中(`frameOpen_` を立てる処理と同じタイミング)で行う。E2a の時点ではゲーム用コンテキストに入力が届かずデバッグパネルを開けない(5.1/5.7 の既知の制約)ため実際には発生しないが、E2b 以降は発生しうるため今のうちに直しておく。
- **バックバッファに RTV を足す。** 現在の初期化順は `CreateBackBuffers()`(L85)→`CreateRtvDsvHeaps()`(L86)→`CreateMainRenderTargets()`(L88)で、`CreateBackBuffers()` の時点では `rtvHeap_` がまだ無い(Codex の指摘で判明)。**`CreateBackBuffers()` 自体は変えず**、`CreateRtvDsvHeaps()` の直後に新設の `CreateBackBufferRTVs()` を呼ぶ(`RENDER_TARGET_COUNT` 枚ぶん `rtvHeap_` から `rtvNext_` を進めてスロットを確保し `CreateRenderTargetView`)。D3D12 はレンダーリサイズ未対応 = バックバッファは起動時の 1 回しか作られないため、作り直しへの追従は不要(E3b でレンダーリサイズに対応するときに合わせて見直す)。
- **`RenderEditorOverlay(ImDrawData* editorDrawData)` の D3D12 実装**: `BeginFrameIfNeeded()` → バックバッファを `PRESENT → RENDER_TARGET` へ遷移し `backBufferStates_[currentBackBufferIndex_]` を更新(`CopyToBackBuffer` の `PRESENT → COPY_DEST` と同じ形。**`Present()`(`D3D12GraphicsDeviceImpl.cpp:722-733`)は `backBufferStates_` の値を見て汎用的に `PRESENT` へ戻すので、ここを変える必要はない**ことを確認済み)→ 新設のバックバッファ RTV で `OMSetRenderTargets`→`ClearRenderTargetView`→(`editorImGuiCtx_` へ `SetCurrentContext` してから)`D3D12ImGui::Render(editorDrawData, GetCommandList())`。
- `IGraphicsDeviceImpl`/`GraphicsDevice` に新規メソッド `bool ImGuiInitEditor(ImGuiContext* gameCtx, ImGuiContext* editorCtx); void ImGuiShutdownEditor(); void ImGuiNewFrameEditor(); void RenderEditorOverlay(ImDrawData* editorDrawData);`(既定実装はすべて no-op/false。D3D12 だけ上記の実装を書く)。
- **`GetImGuiTextureId` は新しい仮想関数にしない。** `GraphicsDevice` に非仮想の `void* GetImGuiTextureId(RenderTargetHandle rt)`(戻り値は `void*`。`ImTextureID` にすると `IGraphicsDeviceImpl.h` が ImGui ヘッダに依存してしまうため、呼び出し側の Editor コードで `(ImTextureID)` にキャストする)を 1 つ足すだけでよい。実装は既存の `GetBackendName()` で D3D12 以外なら `nullptr`、D3D12 なら `GetRenderTarget(rt)->GetRenderTargetSRV().GetNativeHandle()` を返す(Hi-Z/GBuffer パネルと同じ経路の再利用で、`TransitionToSRV` は E1a の自動変換機構がそのまま行うため二重実装にならない)。
- **`IEditorLayer` は E2a では最小の 2 フックにする**(`displayRT` は引数で渡し、`Engine`/`AppHost` に新しい取得 API を足さない):
  ```cpp

  {
      class IEditorLayer
      {
      public:
          virtual ~IEditorLayer() = default;
  ```

  5.2 で示した `OnBeginFrame` / `GetMode` は、モード切り替え(Edit/Play/Pause)が要る **E5 で追加する**(インターフェースの拡張。`RunMode.h` も E5 で新設)。E2a 時点では存在しない。
- **フックの呼び出し位置は「構築」の直後・提出の直前の 1 か所だけに置く(簡略化)。** 5.3 の最終形(手順 7、ECS の反復より前)は、エディタのコマンドが編集モデルへ反映される E4/E5/E7 になってから意味を持つ。E2a はゲームビューの表示だけなので、`AppHost::Render()` を割った直後(新設の `BuildRenderCommands()` の後、`SubmitRenderCommands()` の前)で呼ぶ。**手順の位置を 5.3 の形へ移すことは E5 の TODO として残す。**
- **`AppHost::Render()` を分割する**: `BuildRenderCommands()`(現 L772〜964、ImGui 構築から `ImGuiRenderCommand` の Enqueue まで)と `SubmitRenderCommands(ImDrawData* editorDrawData)`(現 L965-966 の `Submit`)に分ける。`editorDrawData` は **`RenderThread::Submit()` の引数列と `RenderThread::FrameSlot`(`RenderThread.h:93-114`)に足す**(`FrameContext` は `RenderThread::Run()` 内で `FrameSlot` から都度組み立てられる一時オブジェクトで、スレッド間の運搬には使えないため。`RenderThread.h` に `struct ImDrawData;` の前方宣言を 1 行足す)。`Run()`(`RenderThread.cpp:173-183` 付近)は、`slots_[slot]->editorDrawData` が非 null なら `GraphicsDevice::Get().RenderEditorOverlay(editorDrawData)` を呼んで **`CopyToBackBuffer` を呼ばない**。null なら既存どおり `CopyToBackBuffer`。`Present()` はどちらの場合も呼ぶ(既存のまま)。この分岐はデータ駆動(`editorDrawData` の有無)であり `RenderThread.cpp` に `#if AQ_EDITOR` を書く必要はない(Game.exe は `editorDrawData` を常に null のまま渡すので既存の `CopyToBackBuffer` 経路から変わらない)。
- **`AppHost` のメンバ変数は ifdef で増減させない(3.5 節の規約)。** `class IEditorLayer;` の前方宣言と、メンバ `IEditorLayer* editorLayer_ = nullptr;`、トリビアルな inline setter `void SetEditorLayer(IEditorLayer* layer) { editorLayer_ = layer; }` は **常にコンパイルする**(ポインタ 1 個なのでランタイムビルドでも無害。ポインタを保持するだけなら前方宣言で足り、完全な型は不要)。`#if AQ_EDITOR` で囲むのは、完全な `IEditorLayer` 型が要る箇所 ── `AppHost.cpp` 側の `#include "Editor/IEditorLayer.h"` と、`editorLayer_->OnBuildUI(...)`/`OnEndFrame()` を実際に呼ぶ数か所の呼び出しだけ(3.5 節の「エンジンの入口」に該当)。登録は `DebugUI::Register` と同じ非所有ポインタの考え方(`IAppModule` のような所有・コンストラクタ注入は使わない。Editor 側のオブジェクトのライフタイムは `EditorMain.cpp` が持つ)。
- **`Engine` に `AppHost* GetAppHost() const` を 1 つ足す。** `EditorMain.cpp` が `SetEditorLayer()` を呼ぶ公開経路が無いため(`appHost_` は private)。既存の `GetPlatform()`(`Engine.h:227`)と同じ形の inline アクセサを、同じ `public:` ブロック(`Engine.h:260` 付近)に足す。
- **2 つの ImGui コンテキストとフォントアトラスの共有、バックエンドの接続順序**: `AppHost::Initialize` の既存の `CreateContext()`(L256)の直後、`AQ_EDITOR` のときだけ `ImFontAtlas* sharedAtlas = ImGui::GetIO().Fonts;` を控えて `editorImGuiContext_ = ImGui::CreateContext(sharedAtlas);` を作り、**`ImGui::SetCurrentContext(gameImGuiContext_)` で明示的にゲーム用へ戻す**(`CreateContext` が暗黙に current を変えるかに依存しない)。既存のフォント読み込み・スタイル設定(L285〜376)はゲーム用コンテキストのまま今までどおり実行する(アトラス共有によりエディタ側にも反映される)。
  続く既存のバックエンド初期化(L377-384: `platform->ImGuiInit()` と `GraphicsDevice::Get().ImGuiInit()`)は、**ランタイムビルドでは現状のまま**(win32+DX12 を同じ唯一のコンテキストへ)。**`AQ_EDITOR` のときは win32 をゲーム用コンテキストへ接続しない**(5.1 の方針。`platform->ImGuiInit()` の呼び出しをここではスキップし、DX12 の `GraphicsDevice::Get().ImGuiInit()`(ゲーム用インスタンス)だけ呼ぶ)。その後 `ImGui::SetCurrentContext(editorImGuiContext_)` に切り替え、`io.ConfigFlags |= ImGuiConfigFlags_DockingEnable`、`io.IniFilename = "editor_layout.ini"`(ゲーム用の `imgui.ini` と分ける)、`ImGui::StyleColorsDark()` を設定してから `platform->ImGuiInit()`(win32 → editor ctx)と `GraphicsDevice::Get().ImGuiInitEditor()`(DX12 editor インスタンス)を呼び、最後に `ImGui::SetCurrentContext(gameImGuiContext_)` へ戻す。
  - **終了処理の順序(5 回目の Codex レビューで指摘)**: `ImGui_ImplDX12_Shutdown()`(`imgui_impl_dx12.cpp:963` 付近)は参照カウントが 1 になったテクスチャを破棄する。両コンテキストが生きている間はフォントアトラスの参照カウントが 2 のままなので、**`ShutdownEditor()` → エディタ用コンテキストを `ImGui::DestroyContext()` → ゲーム用コンテキストへ `SetCurrentContext` → 既存の `Shutdown()` → ゲーム用コンテキストを `DestroyContext()`** の順で呼ぶ(エディタ側を先に破棄して参照カウントを 1 に落としてから、ゲーム側の `Shutdown()` にフォントテクスチャとディスクリプタを解放させる)。逆順(先に `Shutdown()`、後で `ShutdownEditor()`)やコンテキストを先に `DestroyContext` してしまう順序は GPU リソースリークになるので避ける。
  - **既知の未確認点(実装時に grep して確認する。TODO)**: `IPlatform::ImGuiNewFrame()`(= `ImGui_ImplWin32_NewFrame()`)の既存の呼び出し箇所。ゲーム用コンテキストには win32 バックエンドを接続しなくなるため、**ゲーム用コンテキストが current のときにこの呼び出しが走ると未初期化の `BackendPlatformUserData` を踏んで assert する**。呼び出し位置を特定し、エディタ構成では「エディタ用コンテキストが current のときだけ呼ぶ」に変える(具体的には、新設する「エディタ用コンテキストへ切り替えて `OnBuildUI`/`OnEndFrame` を呼ぶ」ブロックの先頭で呼ぶのが自然)。
  - **この結果、E2a の時点ではゲーム用コンテキストのデバッグ UI はゲームビュー内に表示されるが操作できない(クリックが効かない)。既知の制約であり、E2b で解決するため 11.3 の E2a チェック対象には含めない。**
- **ゲームビューパネルは Editor プロジェクト側に実装する。** `IEditorLayer::OnBuildUI(gameViewRT)` で受け取った `RenderTargetHandle` を使い、`ImGui::DockSpaceOverViewport()` の中で `ImGui::Image((ImTextureID)GraphicsDevice::Get().GetImGuiTextureId(gameViewRT), size)` を、アスペクト比を保って表示する(5.5 の方針どおりレンダー解像度は変えない)。戻り値が `nullptr` のときは「未対応」の文字列を表示する。ファイルは `Editor/EditorLayer.h/.cpp`(E2a 時点では唯一のパネルなので分けない。`Editor/Panels/` への分割は E7 でパネルが増えてから行う)。

## 6. リフレクションの拡張

### 6.1 既存の仕組み(一次資料は [Prefab設計](Prefab設計.md) 5 章)

- コンポーネントは `IComponent` を継承し、`ecsComponent(型名)` で型情報を持つ。
- 永続フィールドは、メンバテンプレート `Reflect(V& visitor)` の中で `visitor.Field("キー", 値, "ラベル")` と列挙する。JSON 保存・読込(`JsonFieldVisitor`)と ImGui 編集(`ImGuiFieldVisitor`)が同じ列挙を共有する。
- `ComponentRegistry` が型ごとの `ComponentMeta`(`serialize` / `deserialize`、型消去版の `serializePtr` / `deserializePtr` / `drawInspectorPtr`、`requiredWith`、`add` / `remove`)を持つ。JSON のキーは `typeName`(名前)。
- 型の識別は `TYPE_INFO` の `size_t` ハッシュ。初版の `aqHash32` による型 ID は採らない。永続化はすべて名前(`typeName` とフィールドのキー)で行う。

### 6.2 足すもの

| 追加 | 内容 | 使う所 |
|---|---|---|
| フィールド属性 | `Field()` に省略可能な属性を足す(最小・最大、ツールチップ、読み取り専用、非公開、アセットの種類)。属性は小さな値型で、ランタイムでもコンパイルされる(ifdef で消さない) | インスペクター、将来のスクリプト |
| 文字列フィールド | `std::string` 用の `Field()` を各 Visitor に足す。パス参照(モデル、Prefab、テクスチャ)はこれで扱う | インスペクター、コンテンツブラウザのドロップ先 |
| 編集イベント Visitor | 編集用のコピーに対してウィジェットを描き、フィールドごとに「編集開始(変更前の値)」「変更中(現在の値)」「確定(変更後の値)」を、キーと JSON 値の組で返す。対象を直接書き換えない | インスペクター(7.4) |
| コンポーネントの公開情報 | `ComponentMeta` に「インスペクターから追加・削除してよいか」「カテゴリ」を足す | Add Component パレット |

```cpp
// 例: TransformComponent の Reflect(既存の形に属性を足すだけ)
template <typename V>
void Reflect(V& visitor)
{
	visitor.Field("position", position, "position (local)");
	visitor.Field("scale",    scale,    "scale    (local)", FieldAttr{}.Min(0.001f).Tooltip("0以下にしない"));
	visitor.Field("rotation", rotation, "rotation (local)");
}
```

属性の具体的な型名と、既存の Visitor の `Field()` オーバーロードへの足し方は E6 の冒頭で既存の Visitor を読んで決める(TODO)。既存の `drawInspectorPtr`(直接書き換え)は Prefab エディタのために残し、エディタのインスペクターは編集イベント Visitor を使う。

### 6.3 値の保存と復元

- **バイトコピーはしない。** Undo の値の控え、コピー&ペーストは、すべて JSON で行う。文字列・配列・リソース参照を持つ型も同じ経路で扱え、`deserialize` が持つ復元後処理(モデルの再読込など)もそのまま効く。
- フィールド単位の値は `{ "キー": 値 }` の疎な JSON として扱う。`deserialize` に疎な JSON を渡したとき、書かれていないキーを変えないことを E6 で確認する(TODO)。
- Reflect 化されていないコンポーネント(`serialize` が nullptr)は、インスペクターで読み取り専用表示にし、保存・Undo の対象にしない。対象外の型を E6 で一覧にする。

## 7. 編集モデルとエディタパネル

### 7.1 編集モデル

エディタが編集する正本は**ワールド(ECS)ではなく、Level の編集モデル**にする。既存の `LevelEditorPanel` と同じく、`PrefabEditNode`(名前 + 型消去コンポーネント + 子)のツリーで `.level.json` を表す。ワールドは編集モデルから作るプレビューである。

| 理由 | 内容 |
|---|---|
| 既存資産 | ノード編集の共有関数と Level の保存・読み込みを直して使える |
| ID の安定 | ECS の ID は再利用される。編集モデルのノードはエディタが ID を振るので、Undo の履歴が壊れない |
| 構造変更の安全 | ノードの追加・削除はただのツリー操作で、ECS の反復中かどうかを気にしなくてよい |
| Play の復元 | 停止時はワールドを破棄して編集モデルから作り直せばよい。ECS 全体のスナップショットが要らない |

`LevelEditorPanel` の private な編集状態を、`LevelEditModel`(新規、`aqEngine/Level/`)へ切り出す。`LevelEditorPanel` と Editor の両方がこれを使う。

| `LevelEditModel` が持つもの | 内容 |
|---|---|
| ノードのツリー | `PrefabEditNode` のフォレストとサブ Level |
| ノード ID | 各ノードに振る `uint32_t`(保存しない)。モデルの中で一意で、読み込みのたびに振り直す |
| 参照ノードの override | 参照ノード(`prefabRef` あり)は、読み込んだ `overrides` の**生 JSON をそのまま保持**する。`overrides.children` / `removedChildren` も含む。保存時は生 JSON を書き戻す。表示用には参照先を解決した値を別に作る |
| 保存先パス | 開いている `.level.json` |
| プレビューの状態 | 現在のプレビューの LevelId と in-memory 登録キー |

### 7.2 参照ノードの扱い(既存 override の保持)

- **未編集の参照ノードは、override の生 JSON を一字一句変えずに書き戻す。** 既存の `PrefabNodeToJson` がコンポーネント全体を書き出す挙動は、`LevelEditModel` の保存経路では使わない。
- 参照ノードのフィールドを編集したときは、生 JSON の `overrides.components.<typeName>` にそのキーだけを書き足す(既存の deep-merge の意味に合わせる)。
- 参照ノードへのコンポーネントの追加と削除、子の追加と削除は、初版ではできないようにする(override 編集 UI は E12)。
- **数値の精度**: 既存の SimpleJson は数値を `AsFloat()` で float に狭め、`%g`(6 桁)で書き出すので、7 桁以上の小数は保存し直すと変わる。E4 で次のように直す。
  - `JsonValue` に `AsDouble()` を足し(アプリ連携設計 8 章の持ち越し項目と同じ)、書き出しは double を往復できる最短表現(`std::to_chars`)にする。生 JSON の数値は double のまま往復する。
  - `JsonFieldVisitor` の float フィールドは、float の最短表現(`std::to_chars(float)`)を書き出す。`0.1f` が `0.10000000149011612` のような表記にならないようにするため。
  - `std::to_chars` の浮動小数点版が Mac / Android の標準ライブラリで使えるかを E4 で確認する(TODO)。使えなければ `%.9g`(float)/ `%.17g`(double)で代える。
- 既存の `LevelEditorPanel` の保存も同じ経路に寄せ、同じ不具合(往復で override が増える)を直す。直す前の挙動は README の「既知の課題」に記録する。

### 7.3 プレビューの置換

初版は**全再生成に固定**する。編集ノードと実エンティティの対応表は作らない(生成コールバックが解決済みのデータしか受け取らないため)。値の編集も、確定時にワールドを作り直す。ドラッグ中の途中経過はゲームビューに出ない(後で対応表を作るときの課題として 15 章に残す)。

置換は手順 7(5.3、System の反復外)で、次の順にその場で行う。既存の `LevelManager::ReloadAll` と同じく、**GPU の完了を待ってから破棄を確定する**。直列構成でも `FlushRender()` が待つのはレンダースレッドの完了だけで、D3D12 / Vulkan の GPU はまだ前フレームのバッファを使っていることがあるため。

1. **最初に** `Engine::WaitForRenderIdle()` で CPU と GPU の完了を待つ。次の Flush は生成だけでなく予約済みの破棄(同じフレームの `LevelManager::Tick` の自動リロードが予約したものなど)も実行するので、その前に GPU を止めておく。
2. `EntityContext::FlushPendingCommands()` で、予約済みのコマンドをすべて実行する。前回のプレビューの同期 `Load` の生成もここで実体化する。生成前にアンロードすると、まだ存在しないエンティティを拾えず、予約済みの生成が後から走ってしまうため。
3. 前回のプレビューの Level と、Play 中にゲームがロードした Level をアンロードする(`LevelManager::Unload`。破棄は予約される)。非同期ロード(`LoadAsync`)が進行中なら取り消す。**非同期ロードの取り消し API は既存にないので E4 で足す**(TODO)。
4. もう一度 `FlushPendingCommands()` で破棄を確定する。1 から描画を挟んでいないので、GPU の完了待ちは要らない。
5. 前回の in-memory 登録キーを `LevelRegistry` から外す。**キー単位の登録解除 API は既存にない(`Register` と全消去の `Clear` だけ)ので E4 で足す。**
6. 現在の編集モデルから `LevelData` を作り、新しいキーで in-memory 登録して `LevelManager::Load` する。生成は次フレームの手順 3(5.3)の Flush で行われる。
7. 新しい LevelId とキーを `LevelEditModel` に記録する。

生成の完了は `LevelManager::IsLoaded()` では判定できない(スロットを確保した時点で true になり、生成は遅延される)。**E4 で「予約した生成が実行された」ことを返す API(例: `IsSpawned(id)`)を LevelManager に足す。**

- 完了待ちを伴うので、同じフレームに置換を何回要求しても、実行は 1 回にまとめる(最後の要求だけを使う)。値の確定のたびに完了待ちが入るのは初版では許容する(ドラッグ中は置換しない)。

### 7.4 パネル

パネルは `EditorContext` を共有し、編集モデルへの変更はすべてコマンド経由で行う。パネル同士は直接呼び合わない。

| パネル | 役割 | 再利用する既存資産 |
|---|---|---|
| ツールバー | 再生、一時停止、停止。Level の新規・開く・保存 | `LevelEditModel` |
| ゲームビュー | `displayRT` の表示。ゲームへの入力の窓口 | `displayRT`、`SetFocusBlocked` |
| ヒエラルキー | Edit 中: 編集モデルのツリー。Play 中: 実行中ワールドのエンティティ(読み取り中心) | ツリー描画(操作要求を返す形に直す)、`SceneHierarchySystem` |
| インスペクター | Edit 中: ノードのコンポーネントを編集。Play 中: 実エンティティの値を表示・直接編集(履歴に残さない) | 編集イベント Visitor(6.2)、Play 中は `ImGuiFieldVisitor` |
| コンテンツブラウザ | アセットのフォルダ表示。パスのドラッグアンドドロップ | 新規(13 章) |
| コンソール | ログの表示 | 既存のログ出力(出力先を E8 で確認、TODO) |
| 既存のデバッグパネル | Prefab Editor、プロファイラなど、DebugUI のメニューに登録済みのもの | ゲーム用とエディタ用のどちらのコンテキストに置くかは E3a で決める(TODO) |

- ツリー描画の共有関数(`PrefabNodeDrawTree` など)は、子の追加・削除・並べ替えを直接行っている。E7 で「操作要求を返す」形に直し、適用はコマンドに任せる。既存の Prefab / Level エディタは、返った要求をその場で適用して挙動を保つ。

シーンビュー(編集用カメラ、ギズモ、クリック選択)は E11 で追加する。それまではゲームビューだけで進める。

### 7.5 EditorContext が持つもの

- 編集モデル(`LevelEditModel`)
- 選択中のノード(ノード ID の配列)
- コマンドスタック(Undo/Redo)
- 現在のモード(`RunMode`)と、次フレームで確定する遷移要求、再生の開始待ちの状態

### 7.6 インスペクターの動作

1. 選択中ノードのコンポーネントごとに、編集用のコピーを作って編集イベント Visitor で描く。参照ノードは解決済みの表示用の値を描く。
2. 「編集開始」で変更前の値(キーと JSON 値)を控え、「確定」で変更後の値と組にして 1 つのフィールド変更コマンドを発行する。ドラッグ中の途中経過は Undo 履歴に溜まらない。
3. 特定の型に専用の見た目が必要なら、型ごとにカスタム描画関数を登録できるようにする。カスタム描画関数も編集イベントを返す契約にする。

### 7.7 ファイルへの書き込み

編集の途中ではディスクに書かない。SSD の書き込み量を増やさないことと、保存していない変更を勝手にファイルへ反映しないことのため。

| 操作 | 書き込み先 | ディスクへの書き込み |
|---|---|---|
| 値の編集、ノードの作成と削除、Undo / Redo | 編集モデル(メモリ) | なし |
| プレビューの置換、Play / Stop | `LevelRegistry` の in-memory 登録 | なし |
| 保存(ツールバー / Ctrl+S) | `.level.json` | **ここだけ**。変更がなければ書かない |
| Prefab の作成(E9) | `.prefab.json` | 操作 1 回につき 1 回 |
| ドックの配置 | `imgui.ini` | ImGui の既定どおり、配置が変わったときだけ数秒おきにまとめて書く(`IniSavingRate`) |

- 保存は一時ファイルに書いてから置き換える(書き込み中に落ちても元のファイルが壊れないように)。
- 自動保存(13 章の候補)を入れるときは、変更があるときだけ、数分以上の間隔で書く。
- 目安: Level 1 本は数十 KB なので、1 日に 1,000 回保存しても数十 MB。一般的な SSD の書き込み耐性(数百 TBW)に対して無視できる量である。注意すべきは毎フレームの書き込みで、これは上の表のとおり行わない。

## 8. Play モード

アプリ連携設計 8 章の「P4 Edit/Play の実行時切り替え」の一次資料は本書とする。

### 8.1 モードの遷移

遷移は手順 7(5.3)で要求として記録し、次フレームの手順 1 で確定する。

| 操作 | 遷移 | 処理 |
|---|---|---|
| 再生 | Edit → (開始待ち) → Play | 要求を受けたフレームの手順 7 でプレビューを置換する(7.3)。次フレームから「開始待ち」になり、更新は Edit と同じに扱う。生成は開始待ちの最初のフレームの手順 3 の Flush で行われるが、そのフレームの System は生成前に走っている。そこで、手順 1 で `IsSpawned`(7.3)が true だったフレームはもう 1 フレーム開始待ちのまま進め、手順 3 で新しいエンティティの階層変換と描画データを更新する。その次のフレームの手順 1 で `IAppModule::OnPlayBegin()` を呼び、そのフレームから Play にする |
| 一時停止 | Play → Pause | 次フレームの手順 1 から Pause。ゲームの更新を止める。描画とインスペクターは動く |
| 再開 | Pause → Play | 次フレームの手順 1 から Play |
| 停止 | Play / Pause → Edit | 次フレームの手順 1 で `IAppModule::OnPlayEnd()` を呼んで Edit にし、同じフレームの手順 7 で 8.3 の表に従って状態を戻してプレビューを置換する(7.3) |

- 編集モデルは Play 中に変更しない(Play 中のインスペクターは実エンティティを直接書き、履歴に残さない)ので、停止で自然に再生前へ戻る。初版の「ワールドのバイナリスナップショット」は作らない。
- 再生中にゲームがロードした Level(ステージの切り替えなど)も、停止時のアンロードの対象にする(8.3)。

### 8.2 更新の制御

`SystemBase` に「どのモードで動かすか」の宣言(`RunModeMask`。Play は常に動く)を足す。`EntityContext::Update(RunMode mode = RunMode::Play)` は、宣言のない System を飛ばして wave を実行し、**System の後の `FlushCommands` はモードに関係なく必ず行う**。飛ばした System に依存する System は、順序の制約が消えるだけなので、wave の順序はそのまま使える。

| 対象 | Edit | Play | Pause | 理由 |
|---|---|---|---|---|
| 階層変換(`HierarcicalTransformSystem`) | ○ | ○ | ○ | 編集結果と描画の位置を合わせる |
| 描画データの収集(`RenderSystem`) | ○ | ○ | ○ | 描画を続ける |
| アニメーション | × | ○ | × | 時間で進む |
| パーティクル | ○(プレビュー) | ○ | × | Edit では見た目の確認のために流す。Pause では止める(実デルタ時間で進むため) |
| `SpawnSystem`、`LevelStreamSystem` | × | ○ | × | ゲームの進行 |
| ゲームの System | × | ○ | × | ゲームの進行 |
| `module_->OnUpdate()` | × | ○ | × | 5.3 の 8 |
| UI(Screen 更新) | × | ○ | 収集のみ | 5.3 の 9 |
| `LevelManager::Tick` | ○ | ○ | ○ | ロードの進行はゲームの時間ではない。Pause 中に始まったロードも進める |
| カメラ | エディタ用の既定カメラ(E11 まではゲームのカメラをそのまま使う) | ゲームのカメラ | ゲームのカメラ | E5 で決める(TODO) |

ランタイムは常に Play で動く。System の宣言の既定値は「Play のみ」なので、既存のゲームの System は変更しなくてよい。

### 8.3 停止時にワールドの外を戻す

| 対象 | 停止時の処理 | 担当 |
|---|---|---|
| GameFlow の状態機械と保持ハンドル | 破棄して初期状態に戻す | `GameModule::OnPlayEnd` |
| BGM などのサウンド | 再生中のものをすべて止める | `GameModule::OnPlayEnd` とエンジン |
| UI Screen | ゲームが開いた Screen をすべて閉じる | `GameModule::OnPlayEnd` |
| LevelManager のロード中のハンドルと生成待ち | ロードを取り消し、プレビュー以外にロードされた Level をすべてアンロードしてから、プレビューを置換する | エンジン |
| PrefabRegistry のキャッシュ | 残す(Prefab ファイルが変わっていなければ有効) | — |
| 静的変数・シングルトン | E5 の冒頭でゲーム側を洗い出し、この表に追記する(TODO) | — |

### 8.4 IAppModule に足すもの

```cpp
/** エディタの再生開始。ゲームの状態機械を開始状態にする(ランタイムでは OnInitialize の後に 1 回呼ぶ) */
virtual void OnPlayBegin() {}
/** エディタの再生停止。ワールドの外に持つ状態を初期状態へ戻す */
virtual void OnPlayEnd() {}
```

ランタイムでの呼び方(`OnInitialize` の中で今やっている開始処理をどこまで `OnPlayBegin` へ移すか)は E5 の冒頭で GameModule を読んで決める(TODO)。ランタイムの挙動は変えない。

## 9. Undo/Redo とコマンド

編集操作を Command パターンで記録する。コマンドは**編集モデル**に対して実行・取り消しをする。

```cpp
class IEditorCommand
{
public:
	virtual ~IEditorCommand() = default;
	virtual void Execute(EditorContext& context) = 0;
	virtual void Undo(EditorContext& context) = 0;
	/** 履歴に出す名前 */
	virtual const char* GetName() const = 0;
};
```

| コマンド | 保持するデータ | 適用後 |
|---|---|---|
| フィールドの変更 | ノード ID、`typeName`、フィールドのキー、変更前と変更後の JSON 値。参照ノードは「変更前にそのキーが override にあったか」も持つ(Undo でキーを消すため) | プレビューを置換 |
| コンポーネントの追加と削除 | ノード ID、`typeName`、コンポーネント JSON | プレビューを置換 |
| ノードの作成と削除 | 親のノード ID、兄弟内の位置、**取り外したサブツリーそのもの**(`std::unique_ptr<PrefabEditNode>`) | プレビューを置換 |
| 親の付け替え | ノード ID、変更前と変更後の親 ID と位置 | プレビューを置換 |
| 複合 | コマンドの列 | まとめて 1 回置換 |

- 削除コマンドは、ツリーから外したサブツリーをコマンドの中に所有して保持する。Undo ではそれをそのまま元の位置へ戻すので、**子孫のノード ID も含めて**元に戻る。削除前に子孫を対象にしていた履歴も有効なまま使える。作成コマンドの Undo も同様にサブツリーをコマンドへ移す。
- コマンドは手順 7(5.3)でまとめて適用する。プレビューの置換は 1 フレームに 1 回にまとめる(7.3)。
- Play 中の編集は履歴に記録しない。
- 実装の順序: E7 ではコマンドの形だけで編集し(Undo なし)、E8 で Undo/Redo を足す。E7 から変更の経路はコマンドに統一し、「直接書き換え」の段階を作らない。

## 10. クロスプラットフォーム

| プラットフォーム | ランタイム | エディタ |
|---|---|---|
| Windows(DX12) | 対象 | 対象(最初に実装) |
| Windows(DX11 / Vulkan) | 対象 | 対象(E3a の Multi-Viewport までで対応) |
| Mac(Metal) | 対象 | 対象(E10) |
| Xbox / UWP、Android、iOS | 対象 | 対象外 |

- Editor プロジェクトの新規コードに、Win32 や DX12 の型(`HWND`、`ID3D12...`)を書かない。既存の `Engine.h` の `GetHWND()` などは使わない。例外はプラットフォーム別のエントリ(`EditorMain.cpp`)で、Game の `Main.cpp` と同じく `PlatformWin32` を作るために `HINSTANCE` などを使う。
- ファイルパスは `std::filesystem::path` で扱い、区切り文字を直書きしない。Mac は大文字と小文字を区別する設定があるので、アセット名の表記をそろえる。
- ファイル選択ダイアログなど OS の機能は、プラットフォーム抽象化層の後ろに置く。
- Mac の Multi-Viewport は、E1a で固定する ImGui の版で imgui_impl_metal.mm と imgui_impl_osx.mm の対応機能を確認する。未対応なら Mac は Docking のみとし、1 ウィンドウ内で完結させる。

  - **ゲームビューはアルファを 1 に固定して表示する。** エンジンの `BlendMode::AlphaBlend` はアルファを src の値で上書きする(`SrcBlendAlpha=ONE` / `DestBlendAlpha=ZERO`)ため、ゲームの半透明 UI を描いた場所の `displayRT` のアルファが 1 未満になり、ImGui のアルファブレンドで黒く透けた(Game.exe はコピーでアルファを無視するので見えない)。ブレンド式は全バックエンドに効くので変えず、`IGraphicsDeviceImpl::GetImGuiTextureId(IRenderTarget*)`(既定 `nullptr` = 未対応)を足し、D3D12 は ImGui 用ヒープのスロットへ `Shader4ComponentMapping` のアルファを `FORCE_VALUE_1` にした SRV を描画時に作る(`D3D12ImGui::RegisterOpaqueTexture`)。`GraphicsDevice::GetImGuiTextureId` はバックエンド名の判定をやめてこれに委譲する。不透明エントリは RT の破棄経路が無い(D3D12 はレンダーリサイズ未対応)ので表から外していない。E3b で作り直しに対応するときに外す。デバッグパネルの `ImGui::Image` は従来の経路のまま(G-Buffer0 などが透ける既知の課題は、この口へ寄せれば直せる)。
  - 初回起動(`editor_layout.ini` が無いとき)は、`SetNextWindowDockID(dockspace, ImGuiCond_FirstUseEver)` でゲームビューをドックスペースいっぱいにドッキングする(指定が無いと 32 ピクセル四方の浮いたウィンドウで出た)。
  - フレームの合間(`AppHost::FlushRender` の最後)にエディタ用コンテキストを current にしておく。win32 のメッセージ処理は current のコンテキストへ入力を渡すため、ゲーム用が current のままだとエディタの UI を操作できない。`Update()` の先頭でゲーム用へ戻す。
  - レンダースレッドでコンテキストを切り替えた D3D12 の関数は、終わりに元の current へ戻す(メインスレッドの暗黙の前提を崩さないため)。
  - 「未対応」の表示文言は英語(`Game View: not supported on this graphics API`)。
- 既知の制約(E2b で扱う): ゲーム内のデバッグ UI は見えるが操作できない。エディタの UI のクリックがゲームの入力にも届く。

### 11.4 往復テストの比較規則

「読み込んで保存し直したファイル」と「元のファイル」を、文字列ではなく意味で比べる。

| 対象 | 比較の仕方 |
|---|---|
| 実体ノード(参照でないノード) | 両方のファイルからコンポーネントを既定値で構築して `deserialize` し、`serialize` した JSON どうしを比べる(キーの順序は無視、数値は double で完全一致)。元のファイルで省略されていたフィールドが既定値で書き足されるのは同値とみなす |
| 参照ノード | `prefab` のパスと、`overrides` の生 JSON を構造で比べる(キーの順序は無視、数値は double で完全一致)。**キーの有無も一致すること**(既定値の書き足しは不合格) |
| ノードの構造 | ノード名、子の順序と数、サブ Level(パス、`loadOnStart`、インライン定義)が一致する |

比較は Editor_Debug 構成で動くテスト用のコマンドライン(または Editor の隠しメニュー)で行い、結果をログに出す。実装方法は E4 で決める(TODO)。

## 12. エディタスクリプト(Python)の構想

エディタに Python を内包し、エディタ内コンソールから編集モデルの操作を自動化できるようにする。設計は E12 で別の設計書に起こす。ここには初版の構想の要点だけを残す。

- リフレクション(6 章)を使い、コンポーネントごとのバインディングは書かない。コンポーネントのクラスは `ComponentRegistry` から起動時に自動生成する。
- 変更はすべて `IEditorCommand`(9 章)を経由し、スクリプト 1 回の実行を 1 つの複合コマンドにする。例外が出たら全体を巻き戻す。
- スクリプトは編集モデルを操作する(ECS を直接触らない)。実行は Edit 中のみ、メインスレッドで手順 7(5.3)の中で行う。
- Windows は公式の embeddable package を同梱し、`PyConfig` で検索パスを同梱フォルダに固定する。Mac は自前ビルドか再配布用ビルドを同梱する。エディタ構成だけでリンクする。
- 補完は「`dir()` で実行中のオブジェクトを調べる方式」から始め、後で jedi と型スタブ(.pyi)へ進める。
- 未決: Python の版と Mac 向け配布物、以前のスクリプトエンジンの流用範囲、Debug 構成でリンクするライブラリ、jedi と ImGuiColorTextEdit のライセンス、無限ループの中断手段。

## 14. アセット GUID(将来案)

初版の 9 章の構想(.meta、アセットデータベース、マニフェスト、`AssetRef`)は E12 で別の設計書に起こす。そのとき扱うこと:

- 既存のモデル・Prefab・Spawner・`.particle` 内のテクスチャがパス文字列を永続化しているので、GUID を入れるだけでは改名に強くならない。パスから GUID への移行と、複合アセットの内部参照の扱いを決める。
- `PrefabRegistry` の `pathOrGuid` は、実装では文字列をそのままファイル読込へ渡している。GUID の解決経路とキャッシュの無効化を決める。

## 16. 採用しなかった案

| 初版の案 | 不採用の理由 | 代わり |
|---|---|---|
| 新しい `TypeInfo` / `FieldInfo` と `AQ_REFLECT_BEGIN` マクロ | 既存の `Reflect<V>` と `ComponentRegistry` が同じ責務を持ち、二重管理になる | 既存の拡張(6 章) |
| `aqHash32` による型 ID とフィールド ID | 既存 ECS の型 ID は `TYPE_INFO` の `size_t`。永続化は名前で足りる | 名前で永続化 |
| フィールド変更のバイトコピー、ワールドのバイナリスナップショット | 文字列・配列・`unique_ptr`・リソース参照を持つコンポーネントがあり、成立しない | JSON での保存と復元、編集モデルからの作り直し |
| 新しいシーンファイル形式 | Level と生成・保存・所属管理が二重になる | シーン = Level |
| `.prefab`、ファイル内 ID、フィールドハッシュの上書き | 既存の `.prefab.json` と名前ベースの override と互換がない | 既存形式を正本に |
| メインループを exe 側へ移す | iOS は OS がループを持つ。ループは IPlatform にある | AppHost にエディタ用フック(5.2) |
| `IRenderer::GetImGuiTextureId` | 既存の Bridge の接続先は GraphicsDevice / IGraphicsDeviceImpl で、IRenderer はない | `GraphicsDevice::GetImGuiTextureId` |
| ECS のワールドを直接編集し、ID 指定生成で Undo する | ECS の ID は再利用され、ID 指定生成もない。構造変更は反復中に行えない | 編集モデルを正本にする(7.1) |
| 既存インスペクター(`drawInspectorPtr`)をそのまま使う | 対象を直接書き換えるので、変更前の値の控えとコマンド化ができない | 編集イベント Visitor(6.2) |
| 既存の `PrefabNodeToJson` で参照ノードを保存する | override をコンポーネント全体で書き出し、往復で override が増える | override の生 JSON を保持(7.2) |
| 初版からゲームビューにレンダー解像度を追従させる | 既存のリサイズは提示面と RT を一緒に作り直し、D3D12 は未対応 | 縮小表示から始め、E3b で追従 |
| 初版からアセット GUID を入れる | 既存のアセットがパス文字列を永続化しており、GUID だけでは改名耐性が得られない。移行設計が大きい | パス参照のまま進め、E12 で別設計 |
| Mac の入力に SDL3 | 依存が増える。公式の osx バックエンドがある | imgui_impl_osx |
| GameUWP と CMake も GameLogic.lib に切り替える | 初期のエディタは Windows デスクトップのみで、他のビルドを巻き込む理由がない | デスクトップ VS だけ切り出す |
