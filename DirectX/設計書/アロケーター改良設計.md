## 0. 方針と P0 計測計画

### 0.1 方針

- **固定チャンク化は未承認。P0 の計測で採否を判断する。** 確かな利点は「容量拡張時の全件移動と、その間の一時ピーク(新旧バッファが共存)の解消」。
  欠点は、体数の少ないアーキタイプが多数ある場合のメモリ増・全件走査でのチャンク境界処理・実装の複雑化(「最後以外のチャンクは満杯」を削除・アーキタイプ移動・非 trivial 型の破棄・位置更新で保つ)。
  現状も SoA なので、固定化だけでキャッシュ効率が改善するとは言えない。
- **PlatformMemory / PageProvider / ChunkPool は、仮想メモリ管理が必要と分かるまで着手しない。** `mmap` 版も同様(`mprotect` は権限変更で commit と同じ資源保証ではなく、返却は `madvise` など別操作で OS ごとに違う)。
- **StackAllocator の載せ替えは条件付き。** 再開条件は「具体的な利用箇所」「所有スレッド」「巻き戻し前に待つ処理」の確定。フレームをまたぐ複数領域は別設計(領域を交互に切り替えるだけでは読み手の完了を保証できない)。
- 発端は**見通し**(ユーザー回答 2026-11-09。実害は観測されていない)。そのため P0 は「問題が実在するか」の確認から始める。GPU 計上(メモリ管理課題 §1-1)など別課題の優先順位は、本設計では確定しない。

### 0.2 現状の事実(P0 の前提)

- 容量 1 から始まり、満杯で倍々([Chunk.h](../aqEngine/ECS/Chunk.h) / `Chunk::ResetMemory`)。削除では縮めない(大量削除後は使用量の 2 倍以上を保持し得る)。
- `ResetMemory` は新バッファを確保 → 移動 → 旧バッファ解放の順。容量 C → 2C で **一時的に C + 2C = 3C 分のコンポーネント領域が共存**する。
- EntityID は別の `std::vector`(`entityIDs_`)。
- `EntityLocation` は既に `(chunkIndex, index)` の 2 要素。`FindFirstComponent` の契約(T を持つ最初のエンティティの T)は複数チャンクでも保てる。確認対象は検索順序・コスト・ポインタ寿命。
- `GetChunkIndex` は `chunkList_` の線形探索(アーキタイプあたりのチャンクが複数になると影響する)。

### 0.3 P0-1 現方式の計測

- 統計は**計測フラグ(CMake オプション / マクロ)で有効化**する。Debug 専用にしない(`HeapAllocator` は Debug と Release で追跡処理が違うため、時間比較が歪む)。
- **時間比較は最適化ビルド(Release)でも行う。** 計測区間内ではログを出さず、集計してから出力する。
- 取る値:

| 区分 | 項目 |
| --- | --- |
| 分布 | アーキタイプ数 / アーキタイプごとの体数・1 体のバイト数 / capacity と size |
| 使用量 | 初期生成後・大量追加後・大量削除後それぞれの、コンポーネント領域の確保量と使用量 / `entityIDs_` の確保容量 |
| 再確保 | 回数 / 拡張中の新旧バッファ合計量(一時ピーク)/ 再確保時間の最大値と、そのフレーム全体の時間 / 移動した要素数・バイト数(非 trivial 型は move / destructor 呼び出し回数も) |

- 移動バイト数は処理量の目安にすぎない。非 trivial 型は move / destructor を呼ぶので、バイト数だけでは負荷を判断できない。

### 0.4 P0-2 机上比較(16KiB / 64KiB)

- P0-1 と同じ分布で、**ヘッダ・EntityID 配列・各 SoA 配列のアラインメント余白・端数**を含めて必要量を計算する。
- 空チャンクの保持量は別項目にする。
- **1 体も収まらないアーキタイプは「対象外」と明示して一覧に出す。** 計算から黙って除外しない。
- 現方式の一時ピーク(3C)も同じ表に並べる。

### 0.5 P0-3 試作と比較(P0-1・P0-2 で問題が確認できた場合のみ)

- 通常の aligned `operator new` で固定チャンクを試作し、追加・削除・全件走査・アーキタイプ移動を現方式と比較する。
- 試作の対象は P0-1 で見つかった実際の問題に合わせて絞る。

### 0.6 採否基準

「追加が速くなった」だけでは採用しない。**次をすべて満たすときに採用する**:

1. 問題だったフレーム時間(拡張時の停止)が改善している。
2. 全件走査の時間が許容範囲に収まっている。
3. メモリ増加(体数の少ないアーキタイプ分・空チャンク保持分)が許容範囲に収まっている。

許容値は対象シーン・端末(Win / UWP / Mac / iOS / Android)・予算に合わせて、P0-1 の結果を見て設定する。採用しない結論もあり得る(その場合、問題に応じた局所対策を別途検討する)。

### 0.8 21ms の原因調査(2026-11-09・4 回実行)

**結果: 原因はアロケーターでも固定チャンク化の論点でもなく、コンポーネントの move が実際にはコピーになっていることだった。**

- 4 回とも同じ再確保で再現(21.2 / 25.4 / 29.8 / 29.8ms)。288 B/体のアーキタイプ(`InstancedPointListComponent` 112 B・`InstancedStaticMeshComponent` 48 B・`HierarchicalTransformComponent` 88 B・`TransformComponent` 40 B)の capacity 8 → 16。
- 内訳: 確保 0.0004ms・解放 0.0002ms に対し、移動 29.75ms。さらに型別では **`InstancedPointListComponent` だけで 29.75ms**、他の 3 型は 0.0002ms 以下。そのフレーム全体は約 30〜35ms(ステージ読み込みのフレーム)。
- 原因: `InstancedPointListComponent` は `~InstancedPointListComponent() {}` を宣言している。**ユーザー宣言のデストラクタがあると、暗黙の move コンストラクタが生成されない。** `TypeInfo::MoveImpl` は `new(dst) T(std::move(src))` なので、**コピーコンストラクタが選ばれ、`std::vector`(`points_` / `instancePoints_` / `baked_.instances` / `baked_.cells`)を深いコピーしている**。コインなどの配置データが大きいと、拡張のたびに数十 ms かかる。
- 同じパターン(ユーザー宣言のデストラクタで move が抑制される)が他に 3 つある: `InstancedStaticMeshComponent`(`std::string` 2 つ。今回は 0.0001ms で実害なし)/ `StateMachineComponent`(`StateMachine` を保持。コピーの意味が move と違う恐れがあり要確認)/ `CharacterSteeringComponent`(`virtual` デストラクタ、`EntityHandle` のみで無害)。
- 修正案(未実施・要承認): 各コンポーネントのデストラクタを `= default` にするか、move コンストラクタ / move 代入を `= default` で明示する。コンポーネント登録時に `static_assert(std::is_nothrow_move_constructible_v<T>)` を入れ、今後の再発を防ぐ案も有効。
- 設計への影響: 「拡張時の停止」は固定化では**なく**この修正で消える。**§0.6 の採用基準 1 は、固定化を採用する根拠にならない**(同じ停止は move の修正で解消し、固定化は不要)。→ 固定チャンク化は見送りで確定させる提案。

**修正と再計測(2026-11-09)**: `InstancedPointListComponent` の `~T() {}` を削除。再計測で再確保の最大が 29.8ms → **0.0036ms**、14 回の合計が 0.0116ms になり、原因の推論が実測で確認できた(ステージ読み込みのフレームの停止は解消)。

**訂正**: 先の説明で「`~T() = default;` にすれば move が復活する」としたのは**誤り**。`= default` で宣言したデストラクタも「ユーザー宣言」なので、暗黙の move は生成されない。直す方法は、(a) デストラクタの宣言そのものを削除する、(b) `T(T&&) noexcept = default;` と `T& operator=(T&&) noexcept = default;`(必要ならコピーも)を明示する、のどちらか。

**横展開の調査**: `TypeInfo::Create` に `static_assert(std::is_nothrow_move_constructible_v<T>)` を入れて Mac でビルドすると、次の 11 型が該当した。`AQ_ECS_STRICT_COMPONENT_MOVE` を定義したときだけ検査する形で入れてある(既定は無効。同マクロで再現できる)。

| 区分 | 型 | 状況 |
| --- | --- | --- |
| デストラクタを宣言している | `AnimationComponent`(`= default`)/ `DecalComponent`(`= default`)/ `StaticMeshComponent` / `BoxStaticMeshComponent` / `SkeletalMeshComponent` / `InstancedStaticMeshComponent` / `StateMachineComponent` | move が抑制されコピーになっている疑い。`std::string` / `std::map` / GPU リソース参照を持つ型が多く、コピーと move で参照カウントなどの意味が変わるため、1 つずつ確認してから直す |
| デストラクタ宣言なし(数学型のメンバ) | `TransformComponent` / `HierarchicalTransformComponent` / `CoinComponent` | 数学型(`Vector3` 等)のコピーが noexcept でないため判定が false になる。動作上は無害(小さい POD 相当)。**この検査の誤検出** |
| 不明 | `OceanComponent` / `TerrainComponent` | 未確認 |

結論: `static_assert` を既定で有効にするには、数学型の noexcept 化など範囲が広い。**既定は無効のまま、必要なときに列挙する道具として残す。** 実害(巨大な vector を持つ型)の洗い出しには、`InstancedPointListComponent` を見つけた計測(型別の移動時間)のほうが確実。

**横展開の修正(2026-11-09)**: 空のデストラクタ宣言を削除した型: `AnimationComponent` / `DecalComponent` / `InstancedStaticMeshComponent`(厳格検査を通るようになった)、`StaticMeshComponent` / `BoxStaticMeshComponent` / `SkeletalMeshComponent`(宣言と空の定義を削除。ただし厳格検査はまだ通らない)。

**残り(未修正)**:
- `StaticMeshComponent` / `BoxStaticMeshComponent` / `SkeletalMeshComponent` は、メンバの `graphics::StaticMesh` / `SkeletalMesh` が `~StaticMesh();` を宣言しているため、メンバ側がコピーに落ちる(`shared_ptr` の参照カウント加算程度で、巨大な深いコピーではない)。直すにはグラフィックスのクラスの変更が要るので、実害(計測で見えた停止)が出るまで保留。
- `OceanComponent` / `TerrainComponent` は原因未確認。
- **`StateMachineComponent` の潜在バグは修正済み**(2026-11-09): `StateMachine` が `IState*` を生ポインタで所有して `delete` し、各 `IState` が `StateMachine*` を保持していたため、Chunk の拡張でコピーされると二重 delete / dangling になる作りだった。ステートを `unique_ptr` 所有にし、`StateMachine` のコピー/move を禁止し、`StateMachineComponent` は `StateMachine` を `unique_ptr` 経由で持つ形に変更。厳格検査(`AQ_ECS_STRICT_COMPONENT_MOVE`)の一覧からも消えた。

## 1. 目的

ECS アーキタイプのチャンクと、フレーム単位の一時メモリ(StackAllocator)のメモリ管理を改良する。

- 容量拡張で既存コンポーネントのアドレスが変わらないようにする(**swap-and-pop とアーキタイプ変更では引き続き移動する**。構造変更後も生ポインタを保持できる保証ではない)。
- 断片化を抑える。
- 確保量(commit 量・ピーク)を測れるようにする。
- OS ごとの差は Bridge パターンの裏に閉じ込める。

略称: commit = 予約した範囲に使用枠(commit charge)を割り当てること。decommit = その取り消し(予約は残る)。
LIFO = 後入れ先出し。RAII = スコープで確保と解放を自動化する書き方。

## 2. 現状との差分(調査結果・2026-11-09)

メモは「現状のコードを見ずに書いた」ものなので、実コードを調べた結果を先に示す。**メモの前提と食い違う点が 4 つある。**

| 項目 | メモの前提 | 実コード |
| --- | --- | --- |
| StackAllocator | スレッドごとに 1 本(TLS)。Mark / Rewind | **プロセスに 1 本**([MemoryManager.h](../aqEngine/Memory/MemoryManager.h))。全スレッドが CAS(compare-and-swap)で同じオフセットを進める。API は `GetMarker` / `FreeToMarker` / `Reset` / `ScopedMarker`。バッファは `AlignedAlloc` で一括確保(Win32 4MB / UWP 8MB)。**利用箇所はゼロ**で、`Engine.cpp:483` の `ResetStackAllocator()` だけが配線済み |
| ECS のチャンク | 固定サイズ(16/64KiB)・ヘッダ付き・アーキタイプごとに複数 | **[Chunk](../aqEngine/ECS/Chunk.h) = 1 アーキタイプ 1 個の SoA バッファ**。容量は 2 倍ずつ増え(`ResetMemory`)、増えるたびに**全コンポーネントを新バッファへ移してアドレスが変わる**。コンポーネント i の配列は `offset_i * capacity_`。`EntityLocation` は `chunkIndex`(= `chunkList_` の添字)+ 行。`EntityIDs` は別に `std::vector` |
| 確保方法 | (調査対象) | `::operator new(bytes, align_val_t)`(`Chunk::AllocBuffer`)。`AlignedStorage`(Prefab エディタ用)も同方式 |
| 対象プラットフォーム | Windows と Xbox UWP | 上記に加え **Mac / iOS / Android** が移植済み([AlignedAlloc.h](../aqEngine/Platform/Common/AlignedAlloc.h) が既に `posix_memalign` へ分岐)。PlatformMemory は非 Windows でもビルドが通る必要がある |

その他:

- 既存のメモリ周りの Bridge 相当は `Platform/IPlatform.h` と `Platform/Common/AlignedAlloc.h`(ヘッダ内 `#if`)。
- MemoryTracker は `HeapAllocator` 経由の確保しか計上しない。StackAllocator のバッファも未計上([メモリ管理課題](メモリ管理課題.md) §1-5)。
- 単体テストの仕組みは**無い**(gtest / ctest の記述なし。`Tools/MixerTest` が手動確認ツールの先例)。
- `EngineAssertMsg` は **Release では何もしない**([Utility.h:23](../aqEngine/Utility.h#L23))。

## 3. 全体構成

```
[OS] VirtualAlloc など
  └─ PlatformMemory (Bridge。Windows / Xbox UWP の実装を切り替える)
       └─ PageProvider (予約領域を持ち、64KiB 単位でページを払い出す)
            ├─ StackAllocator × スレッド数  (フレーム一時メモリ。自分専用の予約領域)
            ├─ ChunkPool                    (ECS のチャンクの貸出・返却)
            └─ (後回し) SmallObjectAllocator / 中・大ブロック用
```

予約領域は用途ごとに別にする(ECS チャンク用・スタック用・後回しの小オブジェクト用・中大ブロック用)。
1 つが大きくなっても他の領域のアドレスにぶつからないようにするため。

## 4. 各コンポーネントの仕様(未承認の候補案)

> §0.6 の採用基準を満たすまで、§4 は着手しない。レビュー(§9)で出た修正は各節末の「承認時の補正」に残した。

### 4.1 PlatformMemory(Bridge)

- 4 操作: `Reserve` / `Release` / `Commit` / `Decommit`。
- Windows: `VirtualAlloc(MEM_RESERVE)` / `VirtualAlloc(MEM_COMMIT)` / `VirtualFree(MEM_DECOMMIT)` / `VirtualFree(MEM_RELEASE)`。
- Xbox UWP: まずスタブ。同じ API が使えるか、予約サイズの上限、decommit の挙動は**未確認**。実機で確認するまで動作を仮定せず、未確認であることをコードのコメントにも残す。
- API 固有の型・関数は PlatformMemory の外へ漏らさない。

### 4.2 PageProvider

- 起動時に領域ごとに大きなアドレス空間を予約する(サイズは設定可能な定数)。
- 64KiB 単位で commit / decommit してページを払い出す。連続 N ページの確保(ページ列)にも対応する。
- ページ情報(用途・使用状況)はページの**外**の配列に置く。ページ番号は `(ptr - base) >> 16`。
- 払い出しは低いアドレス優先(後ろのページが丸ごと空きやすくなり、decommit しやすい)。
- 統計: commit 量・使用ページ数・ピーク。
- 予約サイズ超過は `EngineAssertMsg` で検出。黙って別の場所へ移さない(ポインタが変わるため)。

### 4.3 StackAllocator の載せ替え

- 公開 API とマーカーの意味は変えない。裏のメモリを PageProvider の予約領域へ差し替える。
- スレッドごとに 1 本(TLS 等)。予約領域の先頭から積み、先頭が進んだ分だけ 64KiB ずつ commit する。
- ブロックをつなぐ方式ではなく、**固定の予約領域の中で伸びる**方式(ポインタが動かない。マーカーは単純なオフセット)。
- Rewind では即 decommit しない。ピーク使用量を数フレーム追跡し、余剰が N フレーム続いたときだけ余りを decommit する(ヒステリシス)。N は定数。
- デバッグ時: Rewind した範囲を特定パターンで埋める。現在位置より先を指すマーカーでの Rewind はアサート。スコープ用に RAII ガード。
- 使い方のルール(コメントに書く):
  - スコープの外へ渡すデータは、スコープに入る前に確保する。
  - 別ジョブが読むデータは、フレーム終了まで巻き戻されない位置に置く。
  - 次のフレームでも使うデータは別の領域(フレームごとに切り替える複数領域)に置く。
- フレーム終了時の Rewind は、ワーカーが止まっている場所で行う(各スタックを、止まった状態で直接戻す)。

### 4.4 ChunkPool(ECS のチャンク)

- チャンクサイズは定数 `ChunkSize`。候補は 16KiB / 64KiB で切り替え可能に作る。初期値は実測してから決める(§7)。
- チャンクの先頭は `ChunkSize` でアライン。`ptr & ~(ChunkSize - 1)` でヘッダに届く。
- チャンクヘッダは固定サイズ(仮に 64 バイト)。アーキタイプ情報・エンティティ数・容量などを持つ。
- 16KiB の場合は 64KiB ページを借りて 4 つに割る。
- 払い出しは低いアドレス優先。返却されたチャンクは即 decommit せずプールに持つ。ページ全体が空き、かつ余剰が N フレーム続いたときだけ decommit。
- エンティティ削除は swap-and-pop(アーキタイプの最後の 1 体を穴へ移す)。半端なチャンクがアーキタイプごとに最後の 1 つだけになることを守る。
- 既存のチャンク確保を ChunkPool 経由へ差し替える。チャンク内のデータ配置(SoA)は変えない。

### 4.5 後回しにするもの(必要性が確認できてから)

- SmallObjectAllocator(64KiB ページを 1 サイズクラス専用にし、空きリストでつなぐ。ECS 以外の小オブジェクト用)。
- 中・大ブロック(中 = 連続ページ列、大 = 専用予約領域。境界は実測で決める)。
- 伸びる配列(最大サイズ分を予約し、伸びた分だけ commit。上限超過は別領域への作り直しでポインタが変わる)。
- 型ごとに数が非常に多いものの専用プール。

## 9. レビュー履歴と、承認時に反映する補正(2026-11-09・3 回)

### 9.1 確定した方針の変更

- 固定チャンク化は、メモリ増・走査・複雑化の可能性があり、**P0 の計測で採否を判断する**(§0)。
- StackAllocator は利用箇所ゼロの現状で TLS 化・スレッド登録を先行しない(条件付き、§0.1)。
- 当初レビューの誤りを訂正した: 「最大 2 倍の余白の解消」は誤り(余白の出方が変わるだけで、分布次第で増減する)/ `ForEach` の公開 API 変更は必須ではない(現実装は既にチャンク単位走査で、1 体分のポインタを渡す)/ `FindFirstComponent` の意味は変わらない / `EntityLocation` の二階層化は**必須ではない**(2 要素を維持する案でも、チャンク削除時に他の ID をずらさない管理が要る)。

### 9.2 P1 以降を承認するときの補正(未反映の候補案への条件)

- **P1(固定チャンク化)**: 容量計算はヘッダ + EntityID 配列 + 各 SoA 配列のアラインメント余白を含める。1 体も収まらない場合の扱いは着手前に確定する。「アドレス不変」は §1 の限定に従う。
- **P2(PlatformMemory)**:
  - 全対象 OS(Win / UWP / Mac / iOS / Android)を維持するため、`AlignedAlloc` ベースのフォールバックを暫定採用する。全量を一括確保して動かさなければアドレスは安定する。失うのは段階的な commit / decommit による返却だけ。
  - フォールバックには専用の容量設定を設け、仮想予約向けの巨大なサイズをそのまま全量確保しない。論理使用量と確保済み量を分け、no-op の decommit で「メモリが返った」と表示しない。
  - UWP は `VirtualAllocFromApp` を採用候補にする(Xbox SDK・実機での成立は別途確認)。
  - OS ページサイズ・予約粒度・アロケータの管理単位を分離する(ページサイズは固定 4KiB と仮定せず取得する)。16KiB の直接 commit は、64KiB ページを 4 分割する案より単純で候補になる。
  - 失敗は PlatformMemory が値で返し、上位で診断して**明示終了**する(ECS 操作途中の例外回復は設計外)。対象は予約枯渇に加えて Reserve / Commit 失敗とサイズ計算のオーバーフロー。成功前に使用ページ数・オフセットを更新しない。ログは Release で消える `EnginePrintf`(`Utility.h`)を使わず、追加のヒープ確保に依存しない経路にする。エディタ連携中の終了前通知は別途検討する。
  - 検証基盤は独立した `Tools/MemoryTest`。Release の失敗経路・チャンク間 swap-and-pop 後の `EntityLocation`・非 trivial 型の移動と破棄を対象に含める。
- **P3(ChunkPool)**: 空き管理のデータ構造(ビットマップなど)、ptr → 領域の対応、スレッド安全性(EntityManager のライトロック内に限定するか内部ミューテックス)、ヒステリシスの `Tick()` の呼び出し位置(フレーム数で数える)を決める。
- **P4(統計)**: commit 量は `MemoryTracker` に映らない。Profiler パネルへ「予約 / commit / 使用」の 3 値で出す前提にする(メモリ管理課題 §1-1, §1-5)。
