# リソース管理 設計ドキュメント

> 対象コミット: `92b6c54` / 最終更新: 2026-11-09

対象: `aqEngine/Resource/`、各リソース型のローダ(`Sound/SoundClip`、`Graphics` メッシュ/テクスチャ経路 等)
関連: [マルチスレッド設計](05_マルチスレッド設計.md)(ThreadPool)、[サウンド設計](03_サウンド設計.md)、[レンダリング設計](01_レンダリング設計.md)、`Platform/PlatformBudget.h`

非同期ロード・共有キャッシュ・重複排除・ローダ登録を担うリソース基盤。
スレッド境界の契約(デコード=ワーカー / GPU 反映=メインの `Update()` 集約)は**本書が一次資料**。

> **実装メモ**: キャッシュ(`Resource.h` の `TResourceBank`)は **世代を持たない共有キャッシュ**。
> `Unload<T>()` / `UnloadUnused()`(`8f16111`)でキャッシュから解放できる。世代カウンタは
> shared_ptr 所有モデルのため不採用(dangling が原理的に起きない。§3)。本書は実装に合わせて記述する。

## 0. 設計の全体像

```
Game / ECS
   │  ResourceManager::Get().Load<T>(path)   // 即座に shared_ptr<T> を返す
   ▼
ResourceManager（シングルトン）
   ├─ TResourceBank<T>::Find(key)            // 正規化パスで照会 → 既存なら共有 = 重複排除
   ├─ 新規なら loader = CreateLoader<T>()（Reflection 登録の工場）
   │        loader->StartAsync()             // ThreadPool::Get().Submit(...)
   │            └─ [ワーカースレッド] Loading()：ファイル IO + デコード（CPU のみ）
   └─ Update()（毎フレーム・メインスレッド）
            └─ ClearFinishedLoaders() → loader->Finish()
                 └─ FinalizeLoading()：GPU リソース生成（Texture/Shader）
                      → SetState(Completed / Invalid)
```

実コード対応:
- 入口: `ResourceManager::Load<Resource>(const char* path)`(`Resource.h`)。
- 非同期起動: `ResourceLoaderBase::StartAsync()` が `util::ThreadPool::Get().Submit([this]{ Loading(); ... })`(`Resource.cpp`)。
- メイン反映: `ResourceManager::Update()` → `ClearFinishedLoaders()` → `ResourceLoaderBase::Finish()` → `FinalizeLoading()`。

## 2. ロード状態機械

`ResourceBase` は `atomic<ResourceState>` で 3 状態を持つ(`Resource.h`):

```cpp
enum class ResourceState : uint8_t { Invalid, Loading, Completed };
// ctor で Loading に初期化。IsLoading()/IsCompleted()/IsFailed() が atomic を読む。
```

状態遷移(**状態変数は `ResourceState` のみ。デコード完了は別途 loader の `future_` で判定**):

```
                Load<T>()               Update()→Finish()
[生成: Loading] ───────▶ [Loading のまま] ───────────────▶ [Completed]  (IsCompleted()==true)
   │  (ctor)      worker: Loading() 実行       succeeded==true で FinalizeLoading() 成功
   │              (状態は変えず                       │
   │               loadSucceeded_ のみ更新)           └─ false ──▶ [Invalid]  (IsFailed()==true)
   │
   └─ Loading() が false / 例外 ─(loadSucceeded_=false)─▶ Update()→Finish() で [Invalid]
```

重要な事実(実コード準拠):
- **ワーカースレッドは `ResourceState` を変えない。** `Loading()` は `loadSucceeded_`(loader 内の `atomic<bool>`)だけを更新する。よって「デコード中」も「デコード完了・GPU 未反映」も、`ResourceBase` から見ると**どちらも `Loading`**。両者の区別は `ResourceLoaderBase::IsFinished()`(= `future_.wait_for(0)==ready`)で行う。
- **状態を `Completed`/`Invalid` に確定させるのはメインスレッドの `Finish()` のみ**(`Update()` 経由)。`IsCompleted()` が true を返すのは、`FinalizeLoading()` まで完了した後。
- **失敗(ファイル欠落・デコードエラー・例外)** … `Loading()` が false を返す/例外送出 → `loadSucceeded_=false` → `Finish()` で `SetState(Invalid)`。`IsFailed()`(旧綴り `IsFaild()` も alias)で検出。無限「ロード中」にはならない(次フレームの `Update()` で必ず確定する)。

## 3. キャッシュ・重複排除(世代管理は無し)

`TResourceBank<T>`(`Resource.h`)= 型別の `unordered_map<std::string, shared_ptr<T>>` + `mutex`。

- **パス正規化(キャッシュキー)**: `ResourceManager::NormalizeResourcePath()` が `\` を `/` に置換し、先頭 `./` を除去する。**大文字小文字の畳み込みはしない**(大小異なるパスは別キー)。キーは `GetContentRoot` を含まない生の要求パスなので、プラットフォームが違っても同一要求パスなら同一キーになる(実ファイル解決は §7 の `AssetPath` がローダ内で別途行う)。ローダの `requestPath_` にもこの正規化済みキーが入る。
- **重複排除**: `Load<T>` はまず `bank->Find(key)`(mutex 下)で既存を返す。無ければリソースを生成し `bank->RegisterOrGet(key, ref)` で登録。競合で既に登録済みなら**生成した loader を破棄して既存を返す**(`registerResult.second==false`)。→ 同一パスの同時 `Load` は**単一デコード**に合流する。
- **失敗エントリの遅延排除**: `Find`/`RegisterOrGet` は `IsFailed()` のエントリを見つけると map から erase する。→ 一度失敗したパスは次の `Load` で**再試行**される。
- **解放(unload)**: `ResourceManager::Unload<T>(path)`(単体除去)と `UnloadUnused()`(全型で `use_count()==1` = bank のみ参照の未使用リソースを解放)を提供する(`8f16111`)。バンクは通常 `shared_ptr` を保持し続けるが、これらでキャッシュから外してメモリを解放できる(シーン切替時など)。**ロード中・利用中**(ローダの `resource_` や呼び出し側が shared_ptr を保持)は `use_count>=2` のため `UnloadUnused()` では**誤解放しない**。`Unload<T>()` は強制除去だが、既存保持者があっても寿命は shared_ptr が管理するためクラッシュしない(bank が参照を手放すだけ)。
  - **世代カウンタは不採用**: 呼び出し側が `shared_ptr` で所有するモデルでは、bank が参照を手放しても既存保持者の寿命は shared_ptr が管理するため dangling が原理的に起きない。よって世代/ハンドル方式は導入していない(導入すると全呼び出し側のハンドル化という大改修になり、かつ安全上の追加価値が無い)。将来 raw ポインタ主体のハンドルアクセスへ移行する場合が導入のトリガー。

## 4. リソース型とローダ登録

ローダは **リソース型ごとに 1 つ**(`Reflection<T, Loader>()` で `Resource::ID()`= 型名 CRC32 をキーに登録)。**拡張子分岐はローダ内部**で行う。

| リソース型 | ローダ | デコード内容(worker `Loading()`) | GPU 反映(`FinalizeLoading()`) |
|---|---|---|---|
| `GPUResource`(テクスチャ) | `TextureLoader` | DDS=`LoadFromDDSFile` / その他=`LoadFromWICFile`、mip 生成、PCM 相当画素を `TextureData` へ | あり: `GraphicsDevice::CreateTexture2D`(**メイン**) |
| `ShaderResource` | `ShaderLoader` | `ParseShaderResourceKey`(記述子解析のみ) | あり: `GraphicsDevice::CreateShader`(**メイン**) |
| `MeshResource` | `MeshLoader` | `.tkm` を `LoadTkmMeshFile`(頂点/インデックス/マテリアルパス)、法線再計算 / `.fbx` / `.obj`(`LoadObjMesh`) | なし(VB/IB は `StaticMesh::Initialize` で生成) |
| `SkeletalMeshResource` | `SkeletalMeshLoader` | `.tkm`(スキン頂点)+ 兄弟 `.tks`(ボーン) | なし(VB/IB は `SkeletalMesh` 側) |
| `AnimationResource` | `AnimationLoader` | `.tka` を `LoadTkaAnimationFile`(キーフレーム) | なし(CPU 常駐) |
| `SoundClip` | `SoundClipLoader` | 拡張子で WAV/MF 分岐 → PCM 全展開 | なし(CPU 常駐) |
| `PMDResource` | `PMDLoader` | `.pmd` ヘッダ読み(現状スタブ的)。`fopen(requestPath_)` で直接開き、`OpenBinaryReadWithFallback` を通らない(§7 の候補探索の対象外) | なし |
| `FontResource`(UI) | `FontLoader` | `FontAsset::LoadFromJson`(巨大 JSON のパース) | (UI 側) |
| `ParticleSystemData` | `ParticleLoader` | `.particle` v1 を SimpleJson でパース、カーブ/グラデーションの LUT 焼き込み | なし(CPU 常駐) |

- 拡張子→処理の解決は各ローダの `Loading()` 内(例: `MeshLoader` は `GetLowerExtension()` で `.tkm` / `.fbx` を判定)。新フォーマット追加は「新ローダを書く」か「既存ローダに拡張子分岐を足す」。
- 追加手順: ①リソース型 `T : res::ResourceBase`(`engineResource(名前)` マクロで `ID()` 付与) ②`Loader : res::ResourceLoaderBase` ③`RegisterBank<T,...>()` + `Reflection<T, Loader>()`。エンジン所有の型は `Core/AppHost.cpp` の `RegisterEngineResourceBanks()` に足す。ゲーム独自の型だけ `IAppModule::OnRegister()` で登録する。**エンジン所有の型をゲーム側で再登録すると `RegisterBank` が `EngineAssertMsg` で止まる**(二重登録検出)。バンクが無い型の `Load<T>` も `EngineAssertMsg` で止まり nullptr を返す。`Reflection` 側には重複検出が無い(`insert` が無視されるだけ)。
- **FBX(`.fbx`)は ufbx で取り込む**。`MeshLoader`=静的メッシュ / `SkeletalMeshLoader`=スキン / `AnimationLoader`=アニメ(`path.fbx#index` or `#clipName` でクリップ選択)がそれぞれ `Loading()` 内で `.fbx` を分岐する(`Resource.cpp` の `LoadFbxStaticMesh` / `LoadFbxSkeletalMesh` / `LoadFbxAnimation`)。座標系は `ufbx_axes_left_handed_y_up` で DirectX 左手 Y-up へ正規化。旧 `FbxLoader` スタブは削除済み。

## 5. スレッド境界の契約(一次資料)

- **デコード(CPU)** … ワーカースレッド(`ThreadPool`)。`Loading()` でファイル IO・展開・パースまで。
- **GPU リソース生成・アップロード** … メインスレッドに集約する。実装上は 2 経路あるが**どちらもメイン/ゲームスレッド**で、ワーカー/レンダースレッドでは行わない:
  - テクスチャ/シェーダ: `ResourceManager::Update()` → `Finish()` → `FinalizeLoading()`(`CreateTexture2D`/`CreateShader`)。
  - メッシュ: `StaticMesh` / `SkeletalMesh` の `Initialize()`(ゲームスレッド)で VB/IB 生成。ローダの `FinalizeLoading` は使わない。
- **レンダースレッド** … コンテキスト操作(描画コマンド実行)のみ。リソース生成はしない。
- DX11 のデバイスはフリースレッドだが**この規約で統一**する。DX12 移行時はこの集約点をコピーキュー化の候補とする。
- ワーカーで COM/MF を使うデコーダ(`MFDecoder`)は自前で COM/MF を初期化する([サウンド設計](03_サウンド設計.md) §1)。

> **A-2 契約と実装の一致確認(2026-07-03 / `144ae8a`)**: `Resource.cpp` を確認した結果、
> GPU 反映は上記のとおり**メインスレッドに集約されており、契約文と実装は一致**する。
> ワーカーは `Loading()` の CPU デコードまで、`ResourceState` 確定と GPU 生成はメインの `Update()`/`Initialize()` 側。
> 唯一の注意点は「メッシュの GPU 反映がローダの `FinalizeLoading` でなく `StaticMesh::Initialize` にある」点で、
> スレッド(メイン/ゲーム)としては契約を満たす。

`Platform/PlatformBudget.h` の `ResourceBudget`(コンパイル時定数)がリソース系に効く箇所:

## 7. パス解決(`Resource/AssetPath`)

ファイルを開く前の「パス → 実在パス」の解決は `aq::res` の `AssetPath` **1 箇所**が担う。以前は `FindProjectRoot` と候補組み立てが Resource.cpp / D3D11・D3D12・Vulkan のシェーダ / Metal の 2 ファイルに計 12 個のコピーとして散っていた(`AssetPath.h` 冒頭コメント。設計の経緯は [使いやすさ改善設計](使いやすさ改善設計.md) §1.2)。

### 7.1 API と利用側

| 関数 | 役割 | 主な呼び出し側(実コードで確認) |
|---|---|---|
| `FindContentRoot()` | コンテンツ基点(プロセスで 1 度だけ算出)。スレッドセーフな関数ローカル static | D3D12 のシェーダキャッシュ先(`<基点>/x64/ShaderCache`) |
| `BuildAssetPathCandidates(path, out)` | 探索候補を全部組む | `OpenBinaryReadWithFallback`、FBX 4 経路、D3D11 シェーダ |
| `ResolveExistingAssetPath(path)` | 実在する最初の候補。全滅なら**入力そのまま**を返しログ | `ResolveExistingResourcePath` 経由で `LoadImageFile` / `SimpleJson` / `WavDecoder` / `WavStreamDecoder` / `LinkCommands`、直接 `MFDecoder` / `ExtAudioFileDecoder.mm` |
| `ResolveShaderPath(path)` | 同規則。全滅時の戻り値だけ「区切りを `/` へ正規化した入力」 | D3D12 / Vulkan / Metal(`MetalShader.mm`・`MetalRenderContextImpl.mm`) |
| `LogUnresolvedAssetPath(path)` | 全滅時の診断ログ(`[asset] 見つかりません` + 候補を最大 8 件 + 残件数) | 上記のほか、候補を自前で回す側(`OpenBinaryReadWithFallback`、`LogFbxLoadFailure`、D3D11 シェーダ) |

- **静かに失敗させない**: 全候補で開けなかったとき必ず `StartupMarkf` でログを残す(以前は静かに false を返し、症状が「何も出ない」だけだった)。FBX は、ファイルが無ければ候補一覧、あるのにパースできなければ ufbx の理由を出す(`LogFbxLoadFailure`)。
- 静的 `.tkm` / `.obj` も `OpenBinaryReadWithFallback` を通る(スケルタルと同じ。`7908ed3`)。`maxSingleFileBytes` の予算照合(§6)はこの関数の中で行う。
- `AssetPath.h` は `aq.h` に依存せず `<string>` / `<vector>` だけを include する。Metal の `.mm` から include するため(非 Windows の DirectXTex スタブが `BOOL` を再定義し Cocoa と衝突する事故を構造的に避ける)。

### 7.2 候補の順序(`BuildAssetPathCandidates`)

1. 入力そのまま(`\` は `/` へ)。
2. 絶対パスならここで終了。ただし拡張子の大小バリアントだけは足す(tkm のマテリアルは解決済み絶対パスを基点にテクスチャ名を組むため)。
3. 相対パスは `<基点>/<入力>`。**入力が `Assets/` で始まるときだけ** `<基点>/<ゲームルート名>/Assets/...` へ組む(§7.4)。
4. 最後に、既存候補それぞれの拡張子だけを小文字化 / 大文字化した候補を追記(`PushExtensionCaseVariants`)。完全一致を必ず優先し、当たる環境では到達しない。大文字小文字を区別するファイルシステム(iOS・Android の内部ストレージ)対策で、tkm が参照する `.dds`(小文字)に対し実体が `.DDS` のとき用。

### 7.3 コンテンツ基点とその番兵

- **基点の決め方**(`FindContentRoot`): ①`Engine::GetContentRoot()` が返し、**かつ基点の下に番兵が実在するときだけ採用**。②それ以外はカレントディレクトリから親へ上方探索し、番兵を持つ最初のディレクトリ。③見つからなければカレントディレクトリ。
- **番兵は `aqEngine/Assets`**(`CONTENT_SENTINEL_PATH`)。ゲーム側の `Assets` ではなくエンジン側を見る。アセットを 1 つも持たない最小ゲームでも基点が見つかるため(エンジンアセットは必ず存在する)。
- **「番兵が実在するときだけ」の理由**: `PlatformMac::GetContentRoot()` は実行ファイルが `.app` 内にあるだけで `Contents/Resources` を返すが、`aqBundleApp` を通さない開発ビルドにはその中身が無い。存在確認なしで採ると基点が実在しないパスに固定され、エンジンアセットが 1 つも解決できず画面が真っ黒になる。外れたときは `[asset] コンテンツ基点に ... が無いので上方探索へ落ちます` を出して上方探索へ落ちる(iOS / Android の同梱漏れも同様に開発実行が生き延びる)。
- 算出はプロセスで 1 度(`ScopedPersistentAlloc` 内。終了時リーク報告の対象外、§8)。

### 7.4 ゲームルート名(`SetGameRootName`)

- `"Assets/foo.png"` は `<基点>/<ゲームルート名>/Assets/foo.png` へ解決される。ゲームルート名は既定 `"Game"` で可変。
- 通常は `Engine::InitializeParameter::gameRootName`(既定 `"Game"`)に入れ、`Engine::Initialize` が `MemoryManager::Initialize` の直後(アセット解決より前)に `SetGameRootName` を呼ぶ。nullptr / 空文字は既定 `"Game"` に戻す。
- **スレッド規約**: 解決はワーカーから並列に走るため、**ワーカーが動き出す前に 1 度だけ**呼ぶ。内部の `g_gameRootName` は排他なしの素の `std::string` で、後から変えるとデータ競合になる。
- Game プロジェクトのコード(`DirectX/Game`)から `gameRootName` を設定している箇所は見つからなかった(既定 `"Game"` のまま。2026-11-09 時点の grep)。

### 7.5 エンジンアセット(`aqEngine/Assets`)

- エンジン同梱のアセットはゲーム側 `Game/Assets` ではなく **`aqEngine/Assets/` に置き**、パスは基点相対の `aqEngine/Assets/...` と書く(`Assets/` 始まりではないので §7.2 の手順 3 のうち「`<基点>/<入力>`」側に当たり、ゲームルート名の影響を受けない)。
- 現在の中身: `aqEngine/Assets/Shader/`(`.fx` / `.h` / `FullscreenBlit.metal` など 50 ファイル。コンパイル済みの SPIR-V / MSL は CMake の `Tools/ShaderCompile` が `Shader/spv`・`Shader/msl`・`Shader/msl-ios` へ出力する。`DirectX/CMakeLists.txt` のコメントによる)と `aqEngine/Assets/Sky/DefaultSkyCube.dds`(既定スカイキューブ。`SkyRenderer::Create` / `PipelinePresets` が参照)。
- シェーダ(UI / パーティクル / アウトライン / ディファード / シャドウ / スカイ)は `aqEngine/Assets/Shader/*.fx` をこの形で参照している。
- 分離の経緯: `883ea1d`(シェーダ 50 本と既定キューブマップを移設)。基点の番兵がこのフォルダであることが §7.3 の根拠。

### 7.6 プラットフォーム別の基点(`IPlatform::GetContentRoot`)

| プラットフォーム | `GetContentRoot()` | 備考 |
|---|---|---|
| Win32 | `nullptr` | `FindContentRoot` が CWD から上方探索(ソースツリー基点) |
| UWP | パッケージ install フォルダ | サンドボックスで番兵を遡れないため。パッケージ内にソースツリー相対構造を再現する |
| Mac | ①環境変数 `AQ_CONTENT_ROOT` ②`.app` なら `Contents/Resources`(`mainBundle` のパス拡張子が `app` のときだけ)③それ以外は `nullptr` | `nullptr` なら Win32 と同じ上方探索。②は `aqBundleApp` 経由でない開発ビルドでは番兵が無く、§7.3 の判定で上方探索へ落ちる |
| iOS | `<Bundle>/Content` | アセットは `<Bundle>/Content/Game/Assets`。バンドル直下は実行ファイル `<Bundle>/Game` 等 OS の名前空間と衝突するため 1 段隔離している。投入側は `Tools/PackageApp/package_app.cmake`(**片方だけ変えない**。`PlatformiOS.mm` のコメント) |
| Android | `<internalDataPath>/content` | 初回呼び出しで APK の assets を展開する(`EnsureContentExtracted`)。APK 内の `asset_stamp.txt`(ファイル数と合計バイト数)と展開先の印が一致すれば再展開しない。不一致なら `content/` を消して `asset_index.txt` の一覧どおりに作り直し、印は最後に書く(途中失敗は次回やり直し)。展開に数秒かかるため、`AndroidMain` が Engine 初期化の前に一度呼んでおく |

- 大文字小文字を区別する環境(iOS / Android)では §7.2 手順 4 が効く。iOS 移植 P2 で「モデルだけ出て真っ白」として実際に踏んだ。
- D3D12 のシェーダキャッシュ(`ShaderCacheDir`)は `GetContentRoot()` が非 null(= パッケージ配置・読み取り専用)のとき無効化され、null のとき `<基点>/x64/ShaderCache/` を使う。
- TODO: Android の展開が実機で何ファイル / 何秒かかるか、Mac の非バンドル実行時に `mainBundle` が何を返すか(`PlatformMac.mm` に「要確認」の TODO が残る)は本書では未確認。

## 8. 終了処理とリーク報告

- **破棄順**(`AppHost::Finalize`): `UIContext` → `LightManager` → `EntityContext` → **`ResourceManager::Finalize()`** → `InputManager` → `CameraManager`。`UIContext::Finalize` が `FontAssetCache` を空にするのは、フォントアトラスの参照が `ResourceManager::Finalize` を越えて残り、GPU デバイス破棄後に解放されるのを避けるため(`UIContext.cpp` のコメント)。
- **`ResourceManager::Finalize()`**: シングルトンを `delete`(`~ResourceManager` が未完了ローダを `Wait()` + `Finish()` してから破棄。ThreadPool はまだ生きている)→ `ClearBank()`(各 bank を delete)→ `ClearReflection()`。`bankMap_` / `loaderHashMap_` は `clear()` ではバケット配列が残るため、**空マップと `swap` して手放す**(静的メンバでプロセス終了まで居座るのを避ける。`fc1f2b0`)。
- **終了時リーク報告**(Debug): `MemoryTracker::ReportLeaks` は `Engine::Finalize()` の最終行ではなく、エントリポイントが最後に呼ぶ `aq::ShutdownMemory()`(= `MemoryManager::Finalize()`)で走る。`Engine::Release()` とプラットフォームの破棄が済んだ後なので、「まだ生きているだけのもの」が漏れとして並ばない(`fc1f2b0`)。
- **プロセス寿命の確保**: 関数ローカル static やレジストリのように終了時に生きているのが正常なものは `aq::memory::ScopedPersistentAlloc`(Debug のみ有効)の範囲内で確保する。リーク報告は「数だけ出して並べない」。`GetTrackedBytes` の集計には含まれる。`AssetPath` の `FindContentRoot` もこれを使う。リソースの新しい static キャッシュを足すときは同じスコープで囲む。
- GPU リソースを抱える `*Data` の削除で `static_cast` が要る点(`ResourceBase::data_` が `void*`)は `Resource.h` の `data_` のコメントを参照(本書では再掲しない)。

## 9. レビュー時のチェックポイント

- [ ] **スレッド境界**: GPU リソース生成がワーカー/レンダースレッドに漏れていないか。テクスチャ/シェーダの `FinalizeLoading` がメインの `Update()` 経由か、メッシュ VB/IB がゲームスレッドの `Initialize` か。
- [ ] **解放・寿命**: `UnloadUnused()` / `Unload<T>()` が用意された。シーン切替時などに呼ぶ運用になっているか(呼ばないとキャッシュはアプリ寿命まで残る)。`use_count` ガードで利用中リソースを誤解放しないか。
- [ ] **重複排除**: 同一パスの同時 `Load` が単一 loader に合流するか(`RegisterOrGet` の二重防止)。二重デコードしていないか。
- [ ] **失敗経路**: ファイル欠落/デコード失敗が無限「ロード中」にならず、`Invalid` へ確定し次 `Load` で再試行されるか。
- [ ] **パス正規化**: Win32 / UWP(`GetContentRoot` 差)で同一アセットが同一キャッシュキーになるか。大小文字非畳み込みで別キー化していないか。
- [ ] **パス解決の一元化**: ローダ / シェーダ / デコーダが自前の `FindProjectRoot` 相当や CWD 相対でファイルを開かず、`AssetPath`(§7)を通っているか。`PMDLoader` のように素の `fopen` が残る箇所は意図的か。全滅時に `[asset] 見つかりません` が出るか。
- [ ] **基点と番兵**: `FindContentRoot` が番兵 `aqEngine/Assets` の実在を確認してからプラットフォーム基点を採用しているか。iOS の `Content/` 隔離と `package_app.cmake`、Android の展開(`asset_stamp.txt`)が噛み合っているか。
- [ ] **ゲームルート名**: `SetGameRootName` が `Engine::Initialize` 内で、ワーカー起動前に 1 度だけ呼ばれているか。新しいプロジェクトが `gameRootName` を自分のフォルダ名にしているか。
- [ ] **バンク登録**: 新しいエンジン所有のリソース型が `RegisterEngineResourceBanks()` に足されているか(ゲーム側で二重登録していないか)。
- [ ] **予算の実効性**: `maxSingleFileBytes` 超過ファイルが `res::CheckFileBudget()` で拒否されるか(UWP)。全ローダ経路(TKM/TKS/TKA/PMD/テクスチャ/SoundClip)に配線されているか。`memoryBudgetBytes` の観測(`IsOverMemoryBudget`)が `_DEBUG` で実数を返すか。`threadPoolWorkerCount` が実際に反映されているか。
- [ ] **Finalize 順序**: 終了時 `~ResourceManager` が in-flight loader を `Wait()`+`Finish()` してから破棄しているか。`ThreadPool::Finalize` との前後関係(ThreadPool がまだ生きているうちに待つ)。
- [ ] **終了時リーク**: 新しい static / シングルトンのキャッシュが `ScopedPersistentAlloc` で囲まれているか(§8)。リークが出たとき、`ShutdownMemory()` の位置が `Engine::Release()` の後か。
