## 0. 現状と方針

### 0.1 現状(実コードで確認。中継の契約そのものは [レンダーパイプライン設計](レンダーパイプライン設計.md) が正)

- **掲示板(`PassResources`)は毎フレーム消されない。** `RenderPipeline::BuildViews` は毎フレーム `Scene` を登録し直すだけで、
  `Clear()` はリサイズなどの組み直しのときだけ(`RenderPipeline.cpp`)。前フレームに登録した `PostInput` は残る。
  標準構成では `MotionBlurPass` が毎フレーム必ず `PostInput` を登録し直す(実行しなければ `Scene` を)ので表に出ていない。
- **Frame scope のパスには `viewCount = 1` が渡る。** `BuildViews` は後段(ポストプロセス・UI)に、分割画面でも
  `viewCount = 1` の `fullView` を渡す。したがって **Frame scope のパスで `IsSingleView()` を見ても分割画面を見分けられない**。
  `MotionBlurPass` はこれで「分割画面では無効」のつもりでいるが、実際には分割画面でもビュー 0 のカメラで画面全体に掛かっている
  (README「既知の課題」に記録する。本書では直さない)。
- **深度は worldPos(GBuffer2 = `PassResourceKeys::WorldPos`)からしか取れない**([SSR設計](SSR設計.md) §0.1)。
  G-Buffer は毎フレームクリアされ(背景 = 0)、ディファードの物が worldPos を書く。**フォワードで描いた物は worldPos を書かない**ので、
  その画素の worldPos は **その後ろにあるディファードの物の値**、後ろに何も無ければ **0(背景)** になる。
- **AquaDash の道路はフォワード描画**([SSR設計](SSR設計.md) P2)。キャラクター(SkeletalPBRLit)と地形(TerrainPBRLit)はディファード。
- compute のポストプロセスの作法は `MotionBlurEffect` / `MotionBlurPassCommand`: シェーダと CB は Effect が所有し、コマンドには生ポインタで渡す。
  CB の中身はコマンドが値で持ち、`Execute`(レンダースレッド)で `UpdateSubresource` する。出力 RT は `R16G16B16A16_Float`、
  リサイズは `PrepareResize` / `CommitResize` / `AbortResize`(ゲームスレッド、レンダースレッド停止中)。Effect とその資源は
  パイプラインと同じ寿命で、パイプラインの破棄は `WaitIdle` 後(`AppHost`)。
- **CPU への読み戻し(`ReadbackOffscreenR32`)は D3D12 にしか実装が無い**(Metal / Vulkan は既定の false)。
- Mac でもウィンドウのサイズ変更で描画解像度のリサイズが起きる([エンジン課題解消設計](エンジン課題解消設計.md) P4。Metal / Vulkan 対応)。

### 0.2 確定した方針

| 項目 | 決定 | 理由 |
|---|---|---|
| 置く位置 | **`MotionBlurPass` の直後、`BloomPass` の前**。入力は `PostInput`(無ければ `Scene`) | 他のパスを変えずに挟める。HDR のままぼかすので、明るい点が大きな玉ボケになり、その後の Bloom も自然に乗る。モーションブラーの後にぼかす順は一般的な順(DoF → MB)と逆だが、カメラ由来のブラーだけなので見た目の差は小さい |
| `PostInput` の寿命 | **パス列を実行する入口(`RenderPipeline::Build` / `BuildViews`)が、始めに `PostInput` を掲示板から消す**(`PassResources::Remove` を足す)。DoF は毎フレーム必ず登録する: 実行したら自分の出力 RT、しなかったら読んだ入力(`PostInput` があればそれ、無ければ `Scene`) | 掲示板は毎フレーム消えない(§0.1)。消さないと、MotionBlur が無い構成で DoF が翌フレームに**自分の前回の出力**を入力として拾う(有効なら同じ RT を SRV と UAV で同時に使い、無効なら古い画を流し続ける)。中継のキーはそのフレームのうちに書いたものだけが有効、という契約にする |
| scope と分割画面 | **Frame scope**。`PassViewInfo` に **`frameViewCount`(そのフレームの全ビュー数)**を足し、`BuildViews` が全パス(Frame / View とも)に入れる。DoF は `frameViewCount == 1` のときだけ動く | Frame scope の `viewCount` は常に 1(§0.1)。ビューごとにピントが違う分割画面では、ビュー 0 のカメラで全画面をぼかすのは誤り。View scope 化は §5 課題 3 |
| 深度 | worldPos からビュー空間の z(`view` 行列で変換した z。ユークリッド距離ではない)を作る。**worldPos が 0 の画素は無限遠** | 深度 SRV が無い。空は無限遠で正しい。フォワードの物は §0.3 |
| ぼけ量(CoC) | 画素ごとの**符号付き CoC**(-1 = 手前に最大、0 = ピント内、+1 = 奥に最大)。`z < focus − range` なら `-saturate((focus − range − z) / nearTransition)`、`z > focus + range` なら `saturate((z − focus − range) / farTransition)`、間は 0。半径(画素)= `|CoC| × maxRadius` | 物理的な薄レンズ式より、ゲームで調整しやすいパラメータを優先する(焦点距離・F 値で決めるとシーンの単位に強く依存する) |
| ぼかし方 | **1 パスの集め方式(scatter-as-gather)**。全解像度の compute。**中心画素は必ず重み 1 で入れる**。周りに最大半径 `maxRadius` の円盤で 48 点(黄金角の螺旋)を置き、各サンプルは**自分のぼけ半径が中心までの距離以上のときだけ**重み 1 で加える。結果は重みの総和で割る(総和は中心の 1 以上なので 0 にならない)。`maxRadius ≤ 0` なら入力をそのまま書く | ピント内の画素(CoC 0)は自分の円が 0 なので周りに広がらず、周りにぼけた画素が無ければ中心だけが残ってくっきりする |
| 前後の漏れ対策 | **奥側のサンプル(CoC > 0)が中心より奥にある(サンプルの z > 中心の z + 許容差)ときは、そのサンプルが届く半径を中心自身のぼけ半径までに抑える**(手前か同じくらいなら抑えない)。手前側のサンプル(CoC < 0)は深度に関係なく使う。許容差は `0.05 × 中心の z`(背景 = 無限遠どうしは同じ深度とみなす) | ピントの合った前景(中心の半径 0)の後ろにある、ぼけた背景は前景に被さってはいけない。一方、中心もぼけているなら、その半径の範囲で奥の物を取り込まないと、ぼけた物どうしの輪郭が片側だけ硬く残る。手前のぼけは背景に被さってよい(実際のレンズでも前ボケは手前に広がる)。**P2 で変えた**(下の「P2 で分かったこと」) |
| 有効化 | `RendererPreset::enableDoF`(**既定 false**)。パラメータは `DoFPass` の setter(ゲームは `Find<DoFPass>()`) | 「既定値なら従来と同じ絵」を守る([IBL設計](IBL設計.md) と同じ扱い)。ピント位置はゲームが場面ごとに変えるもので、preset に固定値を置く意味が薄い |
| オートフォーカス | **P3 で入れる**。§1 の `DoFFocus.fx` が、画面中央 5×5 画素の z から目標ピント位置を求め、1×1 の `R32_Float` RT を `lerp(前, 目標, speed)` で更新する。`DoF.fx` はその RT を SRV で読む。**CPU へは読み戻さない**(Metal / Vulkan に実装が無い。§0.1)。値の確認は CoC の表示で行う | ゲームが毎フレームピント位置を計算しなくても使える。補間はピントが急に飛ぶのを防ぐ |
| 値と資源の寿命 | `MotionBlurEffect` と同じ(§0.1)。パラメータはメインスレッドで読み書きし、**コマンド生成時に CB の値として写す**。シェーダ・CB・出力 RT・フォーカス RT は Effect が所有し、コマンドは生ポインタとハンドルで参照する(パイプラインの破棄は `WaitIdle` 後) | 既存のポストプロセスと揃える。デバッグ UI からの変更が実行中のコマンドと競合しない |

### 0.3 フォワードの物の深度(制約)

フォワードの物の画素は、**後ろのディファードの物の深度**(後ろに何も無ければ無限遠)で扱われる(§0.1)。

- 後ろに近い深度のディファードの物があれば、ほぼ正しくぼける(例: 地形の上に乗った道路なら、地形の深度になる)。
- 後ろが空(背景)なら無限遠扱いになり、ピントを近くに合わせると距離に関係なく最大までぼける(例: 空を背にした半透明・パーティクル)。

本書の範囲では直さない。直すには深度バッファを SRV として読めるようにするか、フォワードのパスも深度を書く必要がある(§5 課題 1)。
**AquaDash で使うかは P3 で、実際の画を撮って判断する。**

### 0.4 落とし穴(実装前に読むこと)

1. **入力と出力を同じ RT にしない。** 入力が `Scene` のこともある。出力は必ず自分の RT。
2. **`PostInput` は毎フレーム必ず登録する**。`BuildViews` がフレームの始めに消すので、登録しないと後段が `Scene` を読む(§0.2)。
3. **行列の規約は `MotionBlur.fx` に合わせる**(`mul(M, v)`。C++ 側は `Mull(view, projection)` をそのまま渡している)。
4. `.fx` を足したら `shader_entries.txt` にも足す。compute の出力 `RWTexture2D<float4>` は Vulkan で Rgba32f の警告が出る既知の課題
   ([Mac移植設計.md](Mac移植設計.md))があるが、既存のポストプロセスと揃える。
5. **フォーカス RT は SRV と UAV を同時に使わない。** 更新(`DoFFocus.fx`、UAV)と読み取り(`DoF.fx`、SRV)は別の dispatch・別のコマンドにする。
   更新は**1 スレッド**(`[numthreads(1,1,1)]` を 1 グループ)が中央 25 画素を読み、1 回だけ書く。初回(RT を作った直後・リサイズ後)は
   CB の `reset` フラグで目標値をそのまま書く。
6. Metal の `CreateShader` は失敗しても null を返さない(README「既知の課題」)。生成失敗で外れる経路の確認は Vulkan で行う。

### 0.5 輪郭線のぼかし(P2 のユーザー確認で追加。2026-11-11)

**現状(実コードで確認)**: `OutlinePass`(エンジンの任意パス。AquaDash は `GameModule.cpp` で `UIPass` の手前に挿す)は、
トーンマップ後の LDR(`Output`)を入力に、G-Buffer の法線(`GBuffer1`)の差から線を見つけて線色を重ねる
(`Outline.fx`。十字 4 近傍で、片方だけ背景ならシルエット、法線が大きく曲がれば折り目)。DoF より後ろにあるので、
**ぼけたキャラクターにくっきりした線が重なる**。

**方針**:
- **DoF が画素ごとの符号付きぼけ半径(画素。`CoC × maxRadius`)を `R32_Float` の RT に書き、掲示板の新しいキー
  `PassResourceKeys::DoFCoC` に載せる。** DoF が動かないフレーム(無効・単一ビューでない・生成失敗)は `DoFCoC` を掲示板から消す
  (前フレームの値が残らないように。§0.2 の `PostInput` と同じ理由)。
- **`OutlinePass` は `DoFCoC` があれば、画素 p の半径 r の円盤に 48 点(黄金角の螺旋)を置き、各点の「線の濃さ」
  (今の `edge` の計算)を平均した値を線の濃さにする**(中心も 1 点として含める)。r < 0.5 なら今と同じ計算(中心だけ)。
  **r(線のぼけ半径)は p と、`edge` が比べる十字 4 近傍(太さの距離)の |半径| の最小値**とする。輪郭線はシルエットの物体側と背景側の両方の画素に
  描かれるので、背景側の画素の半径(背景 = 最大)をそのまま使うと、ピントの合った物の線までぼける。最小にすれば、ピント内の物に
  接する線はくっきり残り、ぼけた物どうしの線だけがぼける。
  **円盤の各点 q は、q の線のぼけ半径が p までの距離(画素に丸めた後の q との距離)以上のときだけ取り込み、届かない点は濃さ 0 として数える**
  (平均の分母には入れる。DoF の集め方式と同じ考え方)。
  コストはぼける画素だけで、1 画素あたり最大 CoC 245 回 + 法線 245 回の Load(中心 + 48 点、各点で十字 4 近傍込み 5 回ずつ)。
  ピント内(r < 0.5)と DoF なしは今と同じ 5 回。
  線の色・濃さ・しきい値・太さのパラメータは今のまま。
- **P3 の実装で変えた 2 点(2026-11-12)**: 当初の案(16 点、届くかを見ずに平均)は評価で次の 2 つが出た。
  1. **ピント内の線がぼけた背景に輪のように滲む。** 線から数画素離れた空の画素は、自分も十字 4 近傍も空(半径 = 最大)なので r が大きく、
     円盤の中にあるピント内の箱の線をそのまま拾っていた(箱の周り 12 画素ほどに薄い輪。線そのものはくっきりのまま)。
     「q の線が p まで届くときだけ取り込む」条件で消えた(箱の輪郭の帯の差 11,128 画素 → 26 画素・最大 2/255)。
  2. **16 点では、細い線が 16 本の薄い写しに分かれて見える**(点の置き方が全画素で同じなので、写しが縞になる)。48 点(DoF と同じ)で
     なめらかになった。Sample で画面のほぼ全体をぼかしても 60 FPS。
- `DoFCoC` が無ければ、今とまったく同じ計算(DoF を使わない列・使わないフレームの見た目は変わらない)。
- 輪郭線を DoF の前(HDR)へ移す案は採らない。輪郭線をトーンマップ後に描くのは「露出やブルームの影響を受けない」ための意図で
  (`GameModule.cpp` のコメント)、移すと DoF を使わないときの見た目も変わる。

**限界**: 線をぼけ半径の円で平均するだけなので、線の後ろにある背景の色との関係(前ボケが線の上に被さるなど)は再現しない。
線は「その画素のぼけ半径で薄く広がる」近似。

## 5. オープン課題

1. **フォワードの物の深度**(§0.3)。深度 SRV か、フォワードの深度書き込みが要る。SSAO・SSR の改善とも共通の土台。
2. **玉ボケの形**: 円盤の一様な重みなので、明るい点は円にぼけるが、絞りの形(多角形)や縁の明るさは出ない。
3. **分割画面**: Frame scope なので単一ビューだけ。ビューごとに使うなら View scope 化とビューごとのピント位置が要る。
4. **手前のぼけの縁**: 手前の物が背景に被さるとき、その裏の背景の情報は画面に無い。手前のぼけの縁が薄く透けるのは集め方式の一般的な限界。
5. **時間方向の安定化は無い**: カメラが動くとき、サンプルの粒々がちらつくなら TAA と一緒に扱う。
6. **DoF が止まっている間はフォーカスも更新されない**(P3 で確認)。DoF を無効にした・分割画面になったフレームはフォーカス RT が古い値のまま残り、
   再開時は古い値から補間で寄る。カメラのカットでもリセットしない。気になるなら、再開時やカメラのカットでリセット要求を立てる入口を足す。
