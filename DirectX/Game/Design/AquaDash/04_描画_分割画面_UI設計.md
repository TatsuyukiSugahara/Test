# 04. 描画・分割画面・UI 設計

> 対象コミット: ccfce22 / 最終更新: 2026-09-06
> 対応要求: R-02, R-07, R-10, R-14([00_企画概要.md](00_企画概要.md))

本書の分割画面とモーションブラーは**エンジン側作業**を含む。エンジン内部の詳細設計は
実装フェーズで `DirectX/設計書/01_レンダリング設計.md` 側に追記し、本書はゲーム要件のみ持つ。

## 1. 分割画面(R-07)— エンジン側作業

> **(変更 2026-09-06)** R-07 改訂によりゲームは一人プレイ専用。本節の方式は P5 で
> エンジン機能(設計書01 §5 マルチビュー)として実装・検証済みだが、ゲームからは使用しない。

- 参加人数によるレイアウト: 1 人 = 全画面 / 2 人 = 上下 / 3〜4 人 = 田の字(3 人時の余りは
  ロゴ or 全体マップ表示)。
- 方式: **1 フレームに N ビューを描く**。`RenderFrame` に「ビュー(カメラ + ビューポート矩形)」の
  配列を持たせ、レンダースレッドがビュー毎にシーンパスを回して同一バックバッファの
  ビューポートへ出力する。オフスクリーン合成方式より実装が薄く、既存 HDR/Bloom パスの
  流用がしやすい。
- カリング・シャドウの注視点はビュー毎に計算(既存 `GetFocusPosition` の複数化)。
- HUD はビュー毎にビューポート内へ描く(§3)。リザルト等の全画面 UI はビュー外の最前面レイヤー。
- 負荷は素朴に N 倍になる。まず素朴実装で計測し、問題が出たら分割時の解像度・影品質を
  落とす(`PlatformBudget` と同様のプロファイル値で制御)。

## 2. モーションブラー(R-10)— エンジン側作業

> **(実装済 2026-09-06)** 本節の方式で実装済み(MotionBlur.fx + MotionBlurPassCommand。
> 深度バッファではなく GBuffer2 の worldPos から速度を再構成)。
> 強度 0 のフレームはパス自体を積まないため、タイトル/リザルト/低速時のコストはゼロ。
> P15 で `PostProcessChain` の `MotionBlurPass` へ移設(エンジン設計書 01 §2.6/§7)。

- 方式: **カメラモーションブラー(ポストエフェクト)**。前フレームのビュー射影行列との差から
  ピクセル毎の速度ベクトルを再構成し、速度方向にサンプルをぼかす。深度バッファのみで済み、
  オブジェクト毎の速度バッファが不要なため導入が薄い。高速走行 = カメラも高速移動なので
  本ゲームの要件には十分。
- 挿入位置: HDR シーン描画 → **モーションブラー** → Bloom 合成 → トーンマップ(既存 HDR パスに追加)。
- 分割画面ではビュー毎に前フレーム行列を保持して適用。
- ブラー強度は速度に比例させ、`.stage.json` ではなくゲーム側定数で調整
  (低速時はほぼ無効化してタイトル/リザルトに影響させない)。
- 補助演出(エンジン変更不要): 速度比例 FOV(02 参照)、スピードライン用パーティクル、
  路面テクスチャの流し。

## 3. HUD(R-14)

既存 UI システム(`UIScreen` + `*.screen.json` レイアウト)で構成する。
分割画面時は各ビューの矩形を基準にアンカー配置(ビュー相対座標対応が必要なら UI 側に追加)。

| 位置 | 要素 | 内容 |
|---|---|---|
| 左上 | ミニマップ | コース全体の俯瞰線 + プレイヤー位置マーカー(§4) |
| 右上 | 経過時間 | `MM:SS.ss`。InGame 突入からの計時 |
| 左下 | コイン枚数 | アイコン + 枚数。取得時にスケールポップ |
| 右下 | 速度 | km/h 表示(内部 m/s × 3.6)。数字は大きく、スピード感の演出を兼ねる |

## 4. ミニマップ

> **(変更 2026-09-09 P17)** P7 時点ではエンジンの既知の課題(512² RTV × 1080p 深度の
> 寸法不一致)で RT 方式を断念し UI 点列方式で実装していたが、P17 でエンジンの
> オフスクリーンシーンパス(設計書 01 §8)により**実シーンの俯瞰レンダリング**へ置換。

- ステージロード完了時に、真上からの正射影カメラ(構図 = `minimapCenterXZ` ±
  `minimapHalfExtent`)でシーンを 512² RT へ **1 回だけ**ベイクし、`Minimap` ノードの
  テクスチャとして表示する(毎フレーム描かない)。
- 毎フレームはその上にプレイヤーマーカー(プレイヤー色の点)だけを UI 描画で重ねる。
  マーカー位置は distance からスプライン評価 → 同じ正規化パラメータで UV 化(従来と同式)。
- ベイクは 1 回のため、コイン取得などの動的変化は映らない(進行度把握の目的には支障なし)。
- ループは真上からだと潰れるが、ミニマップの目的(進行度の把握)には支障なしと割り切る。

## 5. タイトル画面ビジュアル(R-02)

- 既存 `TitleScreen`(墨/和風)は残刃用のため流用せず、`AquaDashTitleScreen` を新設。
- 構成: 背景(空 + 海の色面 or インゲームのカメラ回しをそのまま背景に)、ロゴ、
  ステージ選択リスト(サムネイル + 名前)、参加プレイヤー表示(パッドを押した人が点灯)。
- 素材はすべて `Assets/UI/AquaDash/` に分離し、レイアウトは `Title.screen.json`
  (登録名 "AquaDashTitle"。当初案のファイル名 AquaDashTitle.screen.json から変更)。
  **画像差し替えのみでソニック風に更新できる**状態をゴールとする(本番アートはスコープ外)。
- **(追記 2026-09-09 P18)ステージサムネイル**: ステージパネル(y=150 の帯)を縦に拡大し、
  左にサムネイル画像 `StageThumb`(16:9)、右にステージ名 `StageLabel` を置く。
  画像は `StageList.json` の `thumbnail`(03 §2)から実行時に差し替える
  (`TitleScreen::SetStageThumbnail`。ミニマップの SetMinimapTexture と同型)。
  画像自体は `Game/Tools/generate_stage_thumbnail.py` で .stage.json から生成する仮アセット。
