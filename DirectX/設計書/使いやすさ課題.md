# 使いやすさ 課題メモ

最終更新: 2026-09-16。対応は [使いやすさ改善設計.md](使いやすさ改善設計.md) が一次資料で、
P1〜P4 完了(P1-C2 の Android / UWP 同梱と、いくつかの持ち越しを除く。改善設計 §6 の持ち越し一覧)。
本書は課題側の記述に徹する。

「**学生でも使いやすいエンジン**」を目標に、現状 aqEngine で新しくゲームを作り始めた人が
どこで詰まるかを棚卸しした一覧。後から順に対応するために残す。

現状の唯一の作例は AquaDash([Game/Application/](../Game/Application/))で、
エンジンの利用例としても事実上これしかない。以下の指摘はすべてそこを読んだ結果。

## 0. 前提 — 何が「使いやすさ」の障害になるか

三層に分けて考える。下の層が崩れていると、上の層をいくら整備しても効かない。

| 層 | 内容 | 現状 |
| --- | --- | --- |
| 成立性 | 新規プロジェクトがそもそも起動するか | **崩れている**(§1) |
| 記述量 | 起動までにゲーム側が何行書くか | 321 行(§2 / §3 / §4) |
| 復帰性 | 詰まったとき自力で原因に辿り着けるか | 静かに失敗する経路が残る(§6) |

## 1. 課題一覧(優先度順)

### 1-1. エンジンが単体で完結していない — アセットがゲーム側にある — 対応済(P1-A / P1-B / P1-C。Android/UWP 同梱のみ未)

エンジン内部に `"Assets/..."` のパス直書きが **39 ファイル・87 箇所**ある(2026-09-14 実測)。
内訳は 3 種類で、性質が違う:

| 種別 | ファイル数 | 箇所 | 内容 |
| --- | --- | --- | --- |
| 実ロード | 16 | 48 | エンジンが実行時に必ず開くアセット。**ここが本体** |
| パス解決規則 | 13 | 23 | `Assets/` → `<root>/Game/Assets/` と組む規則の重複実装(§1-6) |
| エディタ既定値・コメント | 10 | 16 | ImGui のヒント文字列や Doxygen。実行を止めない |

実ロードしている主なモジュール:

| ファイル | 箇所 | 依存しているもの |
| --- | --- | --- |
| [StaticMesh.cpp](../aqEngine/Graphics/StaticMesh.cpp) | 9 | モデル描画シェーダ 8 種 |
| [ParticleComponentSystem.cpp](../aqEngine/Component/ParticleComponentSystem.cpp) | 5 | `Particle.fx` |
| [DeferredRenderer.cpp](../aqEngine/Rendering/Deferred/DeferredRenderer.cpp) | 4 | PBRLighting / Decal |
| [BloomPass.cpp](../aqEngine/Rendering/PostProcess/Passes/BloomPass.cpp) | 4 | ブラー CS x4 |
| [UIRenderPipeline.cpp](../aqEngine/UI/Rendering/UIRenderPipeline.cpp) | 4 | UI シェーダ x3 |
| [SkyRenderer.cpp](../aqEngine/Rendering/Sky/SkyRenderer.cpp) | 2 | `Skybox.fx` + **`Assets/Sky/SkyCube.dds`** |

**エンジンが実行時に必ず要求する実体は 44 個で、そのうち 43 個がシェーダ**
(エントリ持ち 31 本 + `#include` 専用ヘッダ 11 本 + 注入型の `ShadowDepth.fx` 1 本)。
残る 1 個が `SkyCube.dds`。つまり**依存の実質はシェーダ 1 種類**に絞れる。

つまり**新しいゲームを作るには、まず AquaDash の Assets を丸ごとコピーする**ところから始まる。
(P1-B で解消)

- 対処案: [使いやすさ改善設計.md](使いやすさ改善設計.md) を一次資料とする。
  実測の結果、**`Game/Assets/Shader/` には AquaDash 固有シェーダが 1 本も無い**(全 41 本の `.fx` が
  エンジン資産か旧世代の残置)ため、フォルダごとエンジン側へ移せる。当初想定より安い。

#### 1-1a. 逆依存が 1 本ある — 対応済(P1-B。`MaterialDef.h` の転送先を直した)

[aqEngine/Assets/Shader/MaterialDef.h](../aqEngine/Assets/Shader/MaterialDef.h)(移設前は `Game/Assets/Shader/`)は中身 1 行で、
`../../../aqEngine/Graphics/MaterialDef.h` をソースツリー相対で引いていた(移設後は 1 段浅くなり
`../../Graphics/MaterialDef.h`)。C++ と HLSL で材質定義を共有するための転送ヘッダで、**アセットを移すと即壊れる**。
[GameUWP.vcxproj:155-159](../Game/GameUWP.vcxproj#L155-L159) は既にこれを
`install/aqEngine/Graphics/MaterialDef.h` として同梱しており、
**コンテンツルート配下に `aqEngine/` を置く前例が UWP に既にある**。

#### 1-1b. UI が既定アセットを持っていない — 未対応(P3 で「最小サンプルは UI を出さない」として持ち越し)

エンジンの UI は単色塗りに `Assets/UI/Textures/white.png`、テキストに
ゲーム側のフォントアトラスを要求するが、**エンジン側に既定が無い**
([GameFlow.cpp:466-481](../Game/Application/GameFlow.cpp#L466-L481) が先読みしている)。
最小サンプル(§1-2)が UI を出すなら、既定の白テクスチャとフォントもエンジン側に要る。

### 1-2. 新規プロジェクトの出発点が無い — 対応済(P3-B)

テンプレートも最小サンプルも無い。[Application.cpp](../Game/Application/Application.cpp) は 321 行あるが、
その大半は「どのゲームでも同じ」処理で、AquaDash 固有の部分と混在している。
新規に始める人は、この 321 行から何を消していいか判断できない。

- 対処案: 箱が 1 個出て動くだけの最小サンプルを用意する。§1-3 / §1-4 を終えた後なら
  50 行程度に収まるはずで、それ自体が「エンジンの使い方」の説明になる。

### 1-3. 全ゲーム共通の定型文がゲーム側にある — 対応済(P2-A)

[Application.cpp:212-230](../Game/Application/Application.cpp#L212-L230) の
`RegisterBank` x 9 + `Reflection` x 9 = 18 行は、**登録している型がすべて `aq::` 名前空間**、
つまりエンジン所有の型。ゲーム側が書く理由が無い。

`GPUResource` / `MeshResource` / `PMDResource` / `ShaderResource` / `SkeletalMeshResource` /
`AnimationResource` / `FontResource` / `SoundClip` / `ParticleSystemData`。

- 対処案: エンジン側の既定登録にし、ゲーム固有リソースを足したいときだけ `OnRegister` を書く形にする。

### 1-4. 描画セットアップが手組みで、しかも順序に罠がある — 対応済(P2-B。+ P2-A で順序の罠を解消)

Shadow / Deferred / PostProcess / Sky を毎回ゲーム側で `make_unique` し、
シェーダパスと設定値を直に埋めている([Application.cpp:65-118](../Game/Application/Application.cpp#L65-L118))。

さらに悪いことに、**生成する場所を間違えると落ちる**。
[Application.cpp:232-250](../Game/Application/Application.cpp#L232-L250) に、

> SkyRenderer はキューブマップを ResourceManager 経由で非同期ロードするが、
> リソースバンクの登録は `OnRegister` が済むまで行われない。
> `OnInitialize` で Load するとバンクが無く EngineAssert で落ちる。

という注意書きがある。**コメントで回避している時点で、API 側で防ぐべき設計**。
初見の人はこのコメントを読む前に踏む。

- 対処案: Deferred + Shadow + Bloom + Sky を 1 行で組める既定プリセットを用意する。
  併せて、バンク登録前の Load を検出して「まだ登録されていない」と名指しで言うか、
  そもそも順序に依存しない初期化にする。

### 1-5. System の依存配線が手動 — P2-C は見送り(既存の `AddSystem<T, Deps...>` と循環検出で足りると判断)

[Application.cpp:252-284](../Game/Application/Application.cpp#L252-L284) で
`AddSystem` / `AddDependency` が 20 行以上並ぶ。順序を間違えても**ビルドは通り、
実行時に 1 フレーム遅れなどの分かりにくい挙動**として出る。
「カメラは走行更新の後」「サウンドはワールド変換確定後」といった制約は、
今はコメントとしてしか表現されていない。

- 対処案: まずは依存を宣言する側(System)に寄せられないか検討する。
  最低限、循環や明らかな順序矛盾を登録時に検出して落とす。

### 1-6. 失敗が静か — 表 3 行とも解決済

詰まったときに原因へ辿り着けない経路がいくつか残っている。いずれも既知。

| 症状 | 原因 | 影響 | 状態 |
| --- | --- | --- | --- |
| テクスチャが出ない | Metal に GPU 機能クエリが無く、非対応フォーマットで生成が nil になる | Apple 系(→ [iOS移植設計.md](iOS移植設計.md) §4.3) | 解決済(iOS 移植で解決) |
| アセットが見つからない | `.tkm` が要求する小文字 `.dds` に対し実体が `.DDS` | iOS / Android のみ | 解決済(P1-A で候補提示。`PushExtensionCaseVariants`) |
| 実行場所で挙動が変わる | `FindProjectRoot` が 6 ファイルに重複実装され、Metal 経路の 2 本は `GetContentRoot()` を見ていない | 全般 | 解決済(P1-A で `AssetPath` へ一元化) |

- 対処案: §1-1 と併せてパス解決を一元化する。大文字小文字の不一致は読み込み失敗時に候補を出して知らせる。
  GPU 機能クエリは Metal バックエンドに追加し、非対応は黙って nil ではなく明示的に失敗させる。
- ただし FBX の 4 経路(`LoadFbxStaticMesh` / `LoadFbxSkeletalMesh` / `LoadFbxAnimation` /
  `GetFbxAnimationClipNames`。いずれも `Resource.cpp`)は候補全滅時に `LogUnresolvedAssetPath` を
  呼ばず、候補一覧を出さない(改善設計 §5 / §6)。

### 1-7. 入門ドキュメントが無い — 対応済(P3-C。`DirectX/Sample/README.md`)

[設計書/](.) は**設計意図をレビューするための資料**であって、使い方の説明ではない。
「最初のゲームを作る」「Prefab を追加する」「Level を差し替える」といった手順書が無い。

- 対処案: §1-2 の最小サンプルとセットで、そこから 1 機能ずつ足す形のガイドを書く。
  先に API を整理しないと書き直しになるので、§1-1 〜 §1-4 の後。

## 2. 着手順の方針

1. **エンジン自立化**(§1-1 + §1-6 のパス解決) — 新規プロジェクトが成立する前提条件
2. **ブートストラップ短縮**(§1-3 / §1-4) — 321 行 → 50 行程度へ
3. **テンプレート + 入門ドキュメント**(§1-2 / §1-7)
4. **失敗をうるさくする**(§1-6 の残り)

1 を飛ばして 2 をやると、用意した既定プリセットがゲーム側のシェーダを参照し続けることになる。
順序は入れ替えられない。

## 3. 決定事項(2026-09-14 ユーザー判断)

§1 以降の作業量を左右する前提を確定させた。

- **想定する利用者** — **他の学生が実際にこのエンジンでゲームを作る**。
  自分の保守性向上だけで止めず、§1-2 のテンプレートと §1-7 の入門ドキュメントまで対象に含める。
- **対象プラットフォーム** — **Windows / Mac / iOS / Android / Xbox(UWP)の全部**。
  §1-1 のアセット分離は、各プラットフォームのバンドル構成
  ([iOS移植設計.md](iOS移植設計.md) §7.3、[Android移植設計.md](Android移植設計.md) §7.1、
  [Xbox移植設計.md](Xbox移植設計.md) §3.5、[Mac移植設計.md](Mac移植設計.md) §6)すべてと整合させる。
- **着手順** — §2 のとおり 1 → 2 → 3 → 4。

### 3-1. 全プラットフォーム対象にしたことの帰結

現在のパス解決規則は、全プラットフォームで **`"Assets/..."` を `<コンテンツルート>/Game/Assets/...`**
へ組む形に統一されている(Android 移植で寄せた。[Android移植設計.md](Android移植設計.md) §7.1)。
パッケージング側もその形を再現している:

| プラットフォーム | アセットの置き場所 |
| --- | --- |
| Windows | ソースツリーの `Game/Assets/` を上方探索 |
| macOS | `Game.app/Contents/Resources/Game/Assets/` |
| iOS | `Game.app/Content/Game/Assets/` |
| Android | `<internalDataPath>/content/Game/Assets/`(APK から初回展開) |
| Xbox / UWP | `<install>/Game/Assets/` |

つまり `aqEngine/Assets/` を第 2 のルートとして足すなら、**この 5 系統すべてに
第 2 ルートの同梱とパス解決を通す**必要がある。§1-1 の実作業はこの一致作業が本体になる。
