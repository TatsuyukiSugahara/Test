### P8(設計 2026-09-07)

実装内容(設計の一次資料: バウンディング方式は `DirectX/設計書/カリング設計.md` §13):

1. **明示バウンディング(エンジン)**: `StaticMesh::SetLocalBounds(math::AABB)` を追加し、
   `FillRenderItem` で `meshResource_` 無しでも `hasBounds` を立てられるようにする。
   `BoxStaticMeshComponent::Update()` の `InitializeShared` 直後に単位キューブ
   AABB(center 0, extent 0.5)を設定 → 路面タイル約 360 枚がフラスタムカリング対象になる。
2. **色指定 API(エンジン+シェーダ)**: `SimpleBox.fx` のハードコード赤
   (`PSMain` の `float4(1,0,0,1)`)を `MaterialCB.h`(b2) の `params[0]` 参照へ変更。
   b2 は `DrawItemCommand` が全 forward アイテムへ既にアップロードしているため
   C++ パイプライン変更は不要。`BoxStaticMeshComponent` に `SetColor(Vector4)` +
   保持メンバ(既定は現状互換の赤)を追加し、
   初期化完了時に `staticMesh_.SetParameter(0, color_)` を適用する
   (`SetColor` が初期化前に呼ばれても保持値が後から適用される)。
   ※ `Reflect` への `color_` 登録は見送り: 反射 Visitor(ImGui/Json)に `Vector4` の
   `Field` オーバーロードが無くコンパイル不可のため。箱色はコード設定専用とし、
   Prefab JSON への永続化が必要になったら Visitor の `Vector4` 対応とセットで行う。
3. **ゲーム側の色設定**: `AquaDashStates.cpp` の路面タイルを青みグレー系、
   コインをゴールド系に変更(具体値は実機の見た目で微調整)。
   `InstancedSimple.fx` の赤ハードコードは未使用経路のため本フェーズでは触らない。

### P10(設計 2026-09-07)

実装内容(**ゲーム側のみ**。エンジンは P9 の per-instance カリング+I_COLOR をそのまま利用):

1. **コインの描画をインスタンス化**: コインエンティティから `BoxStaticMeshComponent` を外し
   (`Transform` + `CoinComponent` は論理用に維持: 位置=取得判定とエフェクト、
   spinPhase/baseRotation=回転)、`RegisterInstancedMesh("CoinBox")` + Coins 1 エンティティ
   (`InstancedStaticMeshComponent` + `InstancedPointListComponent`)を追加。
   `GameContext` に `coinInstancesHandle` を追加(collectFxHandle と同パターン。
   退場時のクリアも同箇所)。
2. **CoinSystem が毎フレーム InstancePoints を再構築**: Update の最後に
   Clear → 非取得コインのみ Add(position / spin×baseRotation / scale(0.8, 0.8, 0.15) /
   ゴールド)。スピンは `tc->rotation` への書き込みをやめ InstancePoint 側だけに反映。
   取得時の `SetVisible(false)` と `ReactivateAll` の `SetVisible(true)` は削除し、
   取得=再構築で消える/復活=`ReactivateAll` 内で即時再構築(ポーズ中でも見た目が戻る)。
3. スレッド境界: CoinSystem(ワーカー)が書く InstancePoints を読むのは
   後段の BuildRenderFrame(メイン)の gather のみで、実行フェーズが分かれているため競合しない。

**P12-3: 散布と 10 万本へのスケール**(ゲーム)
- **散布規則**: コーススプラインに沿った帯(片側 40m 目安)にジッタ付きグリッドで配置する。
  - 路面上(|lateral| < `width`/2 + マージン)は除外する

  - 傾斜が急な場所は除外する
  - 回転(Y 軸)・スケール・色は位置シードの決定的ハッシュ乱数で散らす(再ロードで揺れない)
- **実行スレッド**: 散布とベイクは、地形の CPU 前計算と同じ `LoadingState` のワーカータスクで行う。
  メインスレッドは GPU 生成とコンポーネントへの move のみ。
- 本数を 10 万本へ上げ、セルサイズと描画距離を実測しながら詰める。

### P19(設計・実装 2026-09-11)

**ループ足元の地形埋まり修正**(ユーザー報告「一回転の坂のところで地面に埋まっている」)。
変更は `Game/Tools/bake_stage_terrain.py` と再生成した 2 枚の PNG のみ。エンジン・ゲーム側の
コード変更なし。一次資料は [03_ステージデータ仕様.md](03_ステージデータ仕様.md) の terrain 節。

**原因**: P11 追補で入れた「回廊の地形 = 最寄り路面 y − 0.70m」の追従は、路面が**接地して
いること**を暗黙の前提にしていた。ループ区間では路面が真上へ立ち上がるため、その足元の画素
だけが数 m〜十数 m 隆起し、**同じ XZ を通る往復の平坦な路面が地面に埋まる**。
Stage01 のループ 2(x=1265〜1315 / z≈1060)で実測:

| | 修正前 | 修正後 |
|---|---|---|
| 路面 y − 地形 y の最小値(全長 7218m を 2m 刻み) | **−1.85m**(d=2268m) | **+0.40m** |
| ループ足元の地形(z=1063 断面の最大) | **+5.13m**(x=1270) | −0.36m |

ループ 1(z=450〜490)は XZ footprint が往復とも同じ画素列に載るため最小 y が正しく拾われて
おり、症状が出ていなかった。ループ 2 は z が 1060→1066 へわずかに流れるぶん、往路と復路が
別の画素行になり隆起した。

**方式**: 距離場の種にするサンプルを「接地している路面サンプル」だけに絞る(`is_grounded`)。

- 判定は `up.y >= GROUND_UP_Y_MIN`(0.90 ≒ バンク 26 度)かつ
  `|dy/ds| <= GROUND_SLOPE_MAX`(0.40 ≒ 22 度)。どちらも満たす区間だけを種にする。
- ループ区間は種を置かないので、入口/出口の接地高さがチャンファー距離場で足元まで伝播し、
  **ループの真下は平ら**になる。丘(点17/34/43)は勾配 0.12〜0.23 なので従来どおり追従する。
- Stage01 での除外は 2 区間・計 239m(全長 7218m)= 2 つのループのみ。
- 代替案として検討した「最小 y を半径 25m の円板で伝播」は、丘の勾配ぶん地形が路面から
  離れて**路面が浮く**ため不採用。

      修正前は路面の先が緑の丘へ吸い込まれ、ループの根本が隠れていた。修正後は地面が
      平らで、路面がループへそのまま入る)
- [x] 路面 y − 地形 y が全長で正(最小 +0.40m)

**P20-1 メッシュ**(エンジン: `aqEngine/Graphics/MeshPrimitives.{h,cpp}`)

- `BuildGrassTuftMesh` を「放射状対称のスター」から「**非対称な葉の集まり**」へ作り直す。

    傾き 25 度は「葉の軸の平均傾き」の上限として実装しており、水平変位を `t²` で配分するため
    先端の接線は鉛直から約 43 度になる。
  - 各葉を縦 3 セグメントへ分割し、傾き方向へ 2 次曲線で湾曲させ、幅を根元 1.0 → 先端 0.15 に絞る。
  - 三角形数は 3 葉 × 3 セグメント(クアッド)× 2(三角形)× 2(表裏)= **36**(現行 12)。
  - `uv.y` は根元 0 / 先端 1 を維持(風の重みと縦グラデがそのまま効く)。
- `BuildFlowerMesh` を新設。**茎を持たず花冠だけ**にして per-instance 色 1 色で塗れる形にし、

  増やさないための設計判断。`shader_entries.txt` と spv/msl 生成に手を入れない)。
  - 花弁 5 枚を放射状・水平から 35 度上向き + 中心の花芯。三角形数 24。
  - `uv.y` を 0.80〜1.00 に焼き、縦グラデでほとんど暗くならないようにする。

**P20-2 散布**(ゲーム: `Game/Application/Flow/AquaDashStates.cpp`)

- 本数 `GRASS_TARGET_COUNT` 100,000 → **1,800,000**(初回実装は 400,000。実機で
  「まだ地肌が見える」と判断して 2 段階で引き上げた。詳細は下の「密度の詰め方」)。
- **クラスタ散布**へ変更(疎密を作るのが主目的):
  - 1 ステップにつきクラスタ中心を 7 個。
  - 各クラスタへ 5〜16 本を半径 0.6〜1.5m の中心寄り分布(`r = R * u^1.5`)で置く。
  - クラスタごとの密度倍率(0.55〜1.45)をハッシュで持ち、まばらな所と密な所を混在させる。
- **横位置の分布**: `lateral = roadHalf + u^3 × (bandHalf - roadHalf)`、`bandHalf = 45m`、

  当初は「帯を 26m に狭めて手前へ集める」方式にしたが、**端で草がぱったり途切れて
  境界線が見えた**ため、帯は広いまま指数で寄せる方式へ改めた。
- **姿勢**: Y 回転に加えてランダム方位へ 0〜20 度の傾き。スケールを非一様化
  (Y = 0.55〜1.60 / XZ = 0.80〜1.20)。同じメッシュの繰り返しに見せないため。

  黄緑 ↔ 深緑のまとまった色むらを作り、その上に per-instance ±4% だけ乗せる。
  基準色も彩度を上げて地形テクスチャへ寄せる。
- **背丈**: 路面に近いほど低く、離れるほど高い(踏まれた路肩 → 伸びた野原)。
- **花**: クラスタ単位で **11%** を「花クラスタ」に選び、そこにだけ草 1 本あたり 0.25 本の
  割合で置く(1,800,000 × 0.11 × 0.25 = 合計 **約 50,000 本**)。
  ※ 当初は「約 12,000 本」としていたが、7.2km に散ると視界内に数本しか入らず
  **実質見えなかった**ため 50,000 本へ増やした(2026-09-12 実機確認)。

**P20-3 風**(エンジン: `Game/Assets/Shader/InstancedGrass.fx`)

- 一定振幅の揺れに**低周波の突風**を掛け、野原を波が渡るようにする:
  `gust = 0.55 + 0.45 * sin(t*0.23 + worldPos.x*0.008 + worldPos.z*0.006)`。
- 縦グラデの根元を 0.45 → 0.32 へ下げ、接地の影を強める。
- VS / PS 各 1〜2 行。Mac の `.metal` は `aqCompileMsl` がビルド時に再生成する。

**密度の詰め方(2026-09-12 の実機反復)**

ユーザー確認で「まだ草が少ない / 禿げている」となり、3 回の反復で詰めた。

| 段階 | 本数 | 帯 | 見え方 |
|---|---|---|---|
| 初回 | 400,000 | 8〜40m (u²) | 株が点在し、株間の地肌が目立つ |
| 2 回目 | 900,000 | 6.6〜26m (u²) | 路肩は埋まったが **26m で草が切れる境界線**が出た |
| 3 回目 | **1,800,000** | **6.6〜45m (u³)** | 路肩が埋まり、外側は裾を引いて境界線なし |

- あわせて 1 株の被覆を上げた(葉 3→4 枚、房幅 0.12→0.14m、縦スケール下限 0.55→0.70)。
- 株の色は地面テクスチャの緑へ寄せた。暗い株を明るい地面に置くと、株間の地肌が
  かえって目立つため。
- **地面テクスチャ自体は問題なし**。`grass.DDS` は 1024² の芝生写真で `layerTiling =

**性能の見積りと確認方法**

- **支配的なのは三角形数ではなく本数**。描画距離 120m で切っているので、視界内は
  10 万本で 3000〜5000 本(P12-3 実測)→ 40 万本で 12000〜20000 本。三角形数は
  20000 × 36 = **約 72 万**で、地形やキャラに比べれば小さい。
  コストは per-instance のカリング判定とインスタンスデータの転送が主。
  Win/RTX4060 の実測(P12-3)で 10 万本の追加コストが約 0.1ms だったので、
  本数 4 倍 + 三角形 3 倍で **+0.6ms 程度**を見込む。花は +0.05ms 程度。
- ベイク済みインスタンスは 40 万 × 80B ≒ **32MB**(VRAM)。ベイク中はワーカー上に
  変換元 (56B/本) と行列 (64B/本) も同時に載るので、一時的に **+48MB** 程度の CPU メモリを使う。
- 散布時間はワーカーで 61ms → **約 250ms** の見込み。ローディングの最低表示 0.6 秒に
  収まるかを計測し、超えるならステップを ThreadPool へ分割する。
- Mac は VSync 60fps 上限のため、**VSync オフの ms 実測**で判定する。

**スコープ外**: 草の LOD / 距離フェード、影、GPU 駆動カリング、テクスチャ(アルファ抜き)。

### P21(設計 2026-09-12 / 未実装)

**ブーストパッド + コインコンボ**。ユーザー選択によるゲーム性の追加(企画概要の R-10
「300km/h のスピード感」と R-11「コイン取得がランクに影響」の強化)。

**なぜこれを先にやるか**: 現状は走り出しから終わりまで速度が一定で、**体感の山が無い**。
最高速 83m/s がずっと続くと「普通の速さ」になってしまう。要素を増やすより
**緩急をつける**ほうが、最重要要求である R-10 に効く。コインも「拾うだけ」で
取り方に意味が無く、ランクも枚数の線形なのでリプレイ動機が薄い。
コース配置を一切変えずに両方を解決できるのがこの組み合わせ。

#### P21-1 ブーストパッド

**データ**(`.stage.json`。仕様の一次資料は [03_ステージデータ仕様.md](03_ステージデータ仕様.md))

```json
"boosts": [
	{ "distance": 350.0, "lateral": 0.0, "width": 6.0 }
]
```

| フィールド | 意味 |
|---|---|
| `distance` | スプライン距離。この位置を**跨いだ**フレームで判定する |
| `lateral` | パッド中心の横位置 |
| `width` | パッドの幅。`|プレイヤーの lateral − pad.lateral| <= width/2` で踏んだ判定 |

- 省略可。無ければブーストパッドの無いステージになる(既存 Stage01 も壊れない)。

**走行**(`SpeedCharacterComponent` / `SpeedCharacterSystem`)

- コンポーネントに `boostTimer`(残り秒)を追加する。
- 踏んだ瞬間に `speed = max(speed, BOOST_SPEED)` へ**跳ね上げ**、`boostTimer = BOOST_SEC`。
  じわじわ加速させると「踏んだ」感触が出ないので、**即時に上げてから減衰させる**。
- `boostTimer > 0` の間は速度上限を `BOOST_SPEED`(= `MAX_SPEED × 1.50` ≒ 125m/s ≒ 448km/h)、
  切れたら `BOOST_DECEL` で `MAX_SPEED` まで落とす(通常の `DRAG_DECEL` とは別定数。
  「ブーストが切れて伸びが止まる」感触を作るため)。
- 判定は「前フレームの distance < pad.distance <= 今フレームの distance」。
  1 フレームで 2.1m(125m/s × 16.6ms)進むので、距離の単純比較では取りこぼす。
- ループ中(`fallen`)は判定しない。

**演出**

- FOV: `AutoCameraComponentSystem` の `FOV_SPEED_MAX` を `BOOST_SPEED` へ広げる
  (現状 83 でクランプされるため、ブースト中に画角が変わらない)。
- モーションブラー: `Application.cpp` の `BLUR_SPEED_MAX` も同様に広げる。
- SE: `Game/Tools/generate_boost_se.py`(新規・純 Python)で生成した WAV。
  既存の `generate_coin_se.py` と同じ作り方に倣う。
- **見た目**: 路面上に山形(シェブロン)の矢印メッシュを手続き生成し、コインリングと同じ
  インスタンス描画で出す。断面はスプラインの frame に追従させ、路面上面から
  `ROAD_MARKING_LIFT` だけ浮かせる(P18 のライン装飾と同じ z-fight 回避)。
  色は per-instance のシアン。**アニメーションはしない**(ベイク経路に載せるため)。

#### P21-2 コインコンボ

**スコア**(`PlayerScoreComponent`)

- `comboCount` / `comboTimer` / `bestCombo` / `score` を追加する。
- コイン取得時: `comboTimer > 0` なら `comboCount++`、そうでなければ `comboCount = 1`。
  取得のたびに `comboTimer = COMBO_WINDOW_SEC`(2.0 秒)へ戻す。
- 倍率 `multiplier = clamp(1 + (comboCount - 1) / 3, 1, 8)`(3 枚ごとに 1 段、上限 8)。
- `score += COIN_BASE_SCORE(100) × multiplier`。
- `comboTimer` は `CoinSystem::Update` で減算する。0 になったら `comboCount = 0`。

**HUD**(`InGame.screen.json` / `HUDScreen`)

- `CoinText` の下に `ComboText`(`x3` のような倍率)と `ComboGauge`(残り時間のバー)を足す。
- 倍率 1(= コンボ無し)のときは両方とも非表示にする。
- `SetHUD` に `comboMultiplier` と `comboRate`(0-1)を追加する。

**ランク**(`StageData::CalcRank`)

- 現行 `score = 0.6 × コイン取得率 + 0.4 × タイム率` の**コイン取得率をスコア率へ差し替える**:
  `scoreRate = min(1, playerScore / (コイン総数 × COIN_BASE_SCORE × TARGET_MULTIPLIER))`、
  `TARGET_MULTIPLIER = 3.0`(平均 3 倍で取り切れば満点)。
- シグネチャを `CalcRank(score, timeSec)` へ変更する。呼び出しは `ResultState` の 1 箇所。
- リザルトに SCORE と BEST COMBO の行を足す(`SetResult` に引数追加)。

### P22(設計 2026-09-12 / 未実装)

**ジャンプ台 + エアトリック**。P21 でブーストが入り「速度の緩急」はできたが、
**A ボタン(ジャンプ)には依然として何の意味も無い**。跳んでも滞空 0.87 秒・高さ 2.8m で、
避けるものも稼ぐものも無いためプレイヤーは押す理由が無い。
ジャンプ台で滞空を作り、その滞空を稼ぎに変えることで A ボタンに役割を与える。
ブースト → ジャンプ台 → トリック → ブースト、という循環を作るのが狙い。

#### 操作方針(重要)

R-08「操作は左スティック移動 + A ジャンプのみ」を守る。**入力は増やさない**。

- **空中で A を押すとトリック(1 回転)が始まる。** 回転中にもう一度 A を押すと追加回転が
  積まれる(チェーン)。
- スティックは空中でも**レーン移動のまま**にする。トリックにスティックを使うと着地位置を
  調整できなくなり、ジャンプ台の先に穴やカーブがある構成が作れなくなるため。

#### P22-1 ジャンプ台

**データ**(`.stage.json`。一次資料は [03_ステージデータ仕様.md](03_ステージデータ仕様.md))

```json
"ramps": [
	{ "distance": 1200.0, "lateral": 0.0, "width": 6.0, "power": 26.0 }
]
```

| フィールド | 意味 |
|---|---|
| `distance` / `lateral` / `width` | ブーストパッドと同じ。跨ぎ判定 + 横位置の一致で発動 |
| `power` | 打ち上げの初速 [m/s]。省略時 26.0(頂点 11.3m・滞空 1.73 秒) |

- 省略可。パースと昇順ソートはブーストパッドと同じ経路にする。
- 発動時は `verticalVelocity = power`、`grounded = false`。**速度(前進)は変えない**。

**見た目**: ブーストパッドと同じ「平らな板 + 矢印」方式にする。**物理的な楔(くさび)形の
台は作らない** — プレイヤーの `height` は路面相対で、台の上を登る処理が無いため、
楔を置くとメッシュを突き抜けてしまう。板はオレンジ、矢印は**上向き(台形)** にして
ブーストパッド(シアン・前向き三角)と区別する。

#### P22-2 エアトリック

`SpeedCharacterComponent` に追加:

| フィールド | 意味 |
|---|---|
| `trickSpinTimer` | 回転中の残り時間 [s]。0 なら回転していない |
| `trickPendingCount` | 積まれた回転数(チェーン) |
| `trickCompletedCount` | この滞空で完了した回転数 |
| `trickRoll` | 見た目の回転角 [rad]。進行方向軸まわり |

- **開始**: `!grounded` かつ `height >= TRICK_MIN_HEIGHT`(1.5m)で A を押すと
  `trickPendingCount++`。回転していなければ `trickSpinTimer = TRICK_SPIN_SEC`(0.45 秒)。
- **進行**: `trickSpinTimer` を減らし、`trickRoll` を `2π / TRICK_SPIN_SEC × dt` で回す。
  1 回転し切ったら `trickCompletedCount++`。`trickPendingCount` が残っていれば次の回転へ、
  無ければ `trickRoll` を 0 へ戻して回転終了。
- **着地**:
  - 回転が**完了している**(`trickSpinTimer <= 0`)かつ `trickCompletedCount > 0` → **成功**。
    `score += TRICK_SCORE(300) × trickCompletedCount`、`boostTimer = TRICK_BOOST_SEC`(1.2 秒)、
    速度をブースト速度へ引き上げる(P21 のパッドと同じ扱い)。
  - 回転の**途中で着地**した(`trickSpinTimer > 0`)→ **失敗**。
    `speed *= TRICK_FAIL_SPEED_RATE`(0.6)。スコアは入らない。
  - どちらでもトリック状態はリセットする。
- **見た目**: `tc->rotation` に、進行方向(`frame.tangent`)まわりの `trickRoll` 回転を
  合成する。既存の `frame.ToRotation()` の後ろに掛ける。
